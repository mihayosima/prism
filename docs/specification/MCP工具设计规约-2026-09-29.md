## 1. 设计原则

「不要把完整内容放进上下文」——这句话有**两面**，本规约管的是**源头**那一面（另一面——窗口内的折叠/收窗——归治理器，见 S3 设计文档）：

> 模型是「只看大纲和摘要的编辑」，不是「需要通读全文的校对员」。
> 工具返回什么、参数怎么报错，决定了每一轮窗口里有多少 token 是**被迫重发**的废料。

## 2. 硬性约束

### 2.1 write 类工具：返回短确认，禁止回显

- **必须返回**：目标（路径/资源标识）+ 影响量（字节数/行数/条数）+ 状态（ok/部分成功）。
- **禁止返回**：写入内容的全文回显、完整的响应 JSON 原文。
- 模板：`{"ok": true, "path": "...", "bytes": 3200}`（或等价短文本一行）。
- 依据：写入内容的作者本来就在模型窗口里（是它自己生成的）——回显等于双倍计入。

### 2.2 read 类工具：可分页、可限量，大产物走引用

- **必须支持其一**：`maxTokenBudget`（服务端先截再返）、`limit/offset` 或游标分页；
- **大产物**（预计 > 2k token）：返回**摘要 + 引用**（引用 = 文件路径 / 资源 URI / 存档键），
  模型需要全文时用独立读取操作按需拉取——本仓对应物即工作记忆 checkpoint 键；
- **禁止**：无条件返回完整文件 / 完整列表（护栏 `guard_source` 只兜底，不替代设计）。

### 2.3 错误返回：可自纠

- 缺参报错**必须**附「必填清单 + 可省清单」（一期 B 已在 `validate_kwargs` 统一实现）；
- 截断类错误**必须**附分片自纠指引（一期 E 已在 Actor 统一实现）；
- 工具自身错误同理：说什么错了，还要说**怎么改对**。

## 3. 存量工具合规对照表

| 工具 | 类别 | 现状 | 合规 | 备注 |
|------|------|------|------|------|
| `agent.ping`（内置） | read | 返回短确认 | ✅ | — |
| `test.echo`（测试） | read | 回显入参 | ✅ | 体积由测试控制 |
| `react.tool_search` / `tool_load`（L1 元工具） | read | 返回目录卡 | ✅ | 目录卡本身就是摘要 |
| `mcp.windows.*`（动态桥，如 FileSystem） | write/read 混合 | **透传 MCP 服务器返回** | ⚠️ | 桥不改协议，依赖：① `guard_source` 源头护栏兜底；② 对端服务器按 §2 演进；③ `mode=write` 类返回由 MCP 服务器保证短确认 |
| `mcp.windows.FileSystem(mode=write)` | write | 写入返回通常为短确认 | ✅ | 事故当晚的验证项：正常路径返回不回显全文 |
| `mcp.windows.FileSystem(mode=read)` | read | 全量返回，靠 `guard_source` 8K 截断 | ⚠️ 欠账 | 建议：对端支持 `maxTokenBudget` / 分页后再收敛；现阶段护栏兜底 |
| approval `ask_user` / 审批弹窗 | 交互 | 返回用户选择（短） | ✅ | — |

> 动态桥（`mcp.windows.*` / `mcp.playwright.*`）的工具清单在装配期由对端服务器决定，
> 本表按运行时目录审计；新增对端工具时按 §2 评估后再接入。

## 4. 演进项（登记，不进本计划）

1. `guard_source` 增「write 类返回体积」软告警（超阈值记 `agent/context/governed` 事件）；
2. 对端 MCP 服务器（windows-mcp）升级时携带 §2 约束需求清单；
3. 工具注册时增加 `returns: "confirm" | "content"` 元数据标注，供 L1 目录卡展示。

---

## 5. 守护与执行

- 本规约是**文档约束**，不新增运行时强制（避免与护栏/治理器口径打架）；
- 代码评审对照 §2 三条硬性约束；新工具 PR 必须在描述中声明类别与返回形态；
- 违规的最终兜底是既有机制：`guard_source`（源头截断）→ `clip_head_tail`（观察折叠）→ 治理器收窗。
