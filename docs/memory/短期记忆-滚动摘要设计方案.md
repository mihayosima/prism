# 短期记忆（第 4 层）· 滚动摘要压缩设计方案

> 状态：待审（v5，已采纳失败退避修正：递增退避 + 失败粒度 + 作用域 + 恢复探测 + 降级路径 + 分批补偿）。
> 系统记忆（第 1 层）、工作记忆（第 3 层）已落地；长期记忆（第 2 层）待改造。
> **架构定调（已与用户确认）**：短期记忆 = **独立插件 `plugins/short_term/`**（内容层），与长期记忆 `plugins/memory` 平级；
> `ContextGovernor`（G0 已建，位于 `plugins/context`）**仅做调度**，不拥有内容。
> 本方案聚焦第 4 层「短期记忆」的**压缩**——即会话历史超窗口后的滚动摘要。

---

## 1. 职责划分（重点：上下文管理 ≠ 短期记忆）

> 参考方案原写"管理归属 上下文管理模块"，**此处已纠正**：那是把调度层与内容层混为一谈。
> 正确边界——**上下文管理管调度，短期记忆管对话历史这份内容**。

| 职责 | 归属 | 说明 |
|---|---|---|
| 窗口总预算计算（`context_window − fixed_blocks − compact_buffer`） | **上下文管理**（`plugins/context`） | 调度层决定"对话历史能占多少 token" |
| `pick_history(raw, budget)` 收窗 | **上下文管理** | 决定窗口里**放多少**历史（调度决策），不拥有内容 |
| 各记忆层内容装配进窗口（system/长期/工作/短期） | **上下文管理** | 统管 4 层如何拼装 |
| 对话历史存储（`agent_messages`） | **短期记忆**（`plugins/short_term`） | 内容层独占 |
| 历史检索（`get_history`） | **短期记忆** | 内容层 |
| 对自己内容的压缩（`compactor`：本地截短 + LLM 摘要） | **短期记忆** | 内容太大了，短期记忆**自己**凝练，不是调度 |
| 摘要存储 / 回溯（`agent_session_summaries`） | **短期记忆** | 内容层 |
| 摘要注入 prior 的角色 / 前缀 | **短期记忆产出 + 调用方组装** | 摘要是短期记忆产物，按约定用 `user` 角色 |

**三条对外边界**（沿用参考方案、措辞纠正）：
1. **不存提炼知识**——那是长期记忆（`remember`）的事；
2. **不存任务进度**——那是工作记忆的事；
3. **只提供内容、不决定"该不该记"**——"窗口放多少"的调度归上下文管理（`pick_history`），"是否晋升长期记忆"归 `remember`；短期记忆只管好自己的对话历史内容与压缩。

**依赖方向（单向）**：`plugins/short_term` 经 `ctx.get(Services.CONTEXT).pick_history` **咨询**调度层的收窗结果来计算"要摘要哪些"，再压缩；`plugins/context` **从不** import 或依赖 `short_term`。降级互不裸崩。

## 2. 存储设计

### 2.1 消息表 `agent_messages`（扩字段）

```sql
CREATE TABLE IF NOT EXISTS agent_messages (
    id              TEXT PRIMARY KEY,
    session_id      TEXT NOT NULL,
    seq             INTEGER NOT NULL,        -- 会话内递增序号（不依赖时间戳）
    role            TEXT NOT NULL,           -- user | assistant | tool
    content         TEXT NOT NULL,
    tool_calls      JSON,                    -- 工具调用结构化信息
    tool_call_id    TEXT,                    -- 关联工具返回
    token_count     INTEGER,                 -- 写入时预估，供预算计算
    is_summary      BOOLEAN DEFAULT FALSE,   -- 可选：是否作为内联摘要记录
    compressed_into INTEGER,                 -- 被哪个摘要版本覆盖（回溯用）
    created_at      DATETIME DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_msg_session_seq ON agent_messages(session_id, seq);
CREATE INDEX idx_msg_session_created ON agent_messages(session_id, created_at);
```
- `seq`：会话内递增，顺序稳定；`token_count`：写入即预估，避免回算；`compressed_into`：指向覆盖它的摘要版本，便于审计与按需调取原文。
- **原文策略**：`agent_messages` 始终保留**完整原文**，截短与摘要都不改写它（见 §4.1.4 / §7.1）。

### 2.2 摘要表 `agent_session_summaries`

```sql
CREATE TABLE IF NOT EXISTS agent_session_summaries (
    session_id      TEXT PRIMARY KEY,
    summary         TEXT,
    version         INTEGER DEFAULT 1,       -- 每次更新 +1
    covers_up_to_seq INTEGER,               -- 摘要覆盖到哪个 seq
    tokens          INTEGER,                 -- 摘要自身 token 数（供预算）
    updated_at      DATETIME
);
```
- `covers_up_to_seq`：构造 prior / 压缩时据此判断哪些消息已被摘要覆盖；`version` 便于调追溯。

### 2.3 迁移

```
agent_011_session_summaries   -- 摘要表
agent_012_message_seq         -- 消息表加 seq / token_count / compressed_into 等字段
```
由 `plugins/short_term` 插件自带（D1 拆包同款：新名 `agent_01x_*`，幂等应用）。

## 3. 触发策略

### 3.1 触发公式（绝对 buffer，非比例）

```python
window          = config.context_window                 # 如 300000
fixed_blocks    = estimate_fixed_blocks()               # system/工具/工作/长期召回/输入，如 80000
effective_window = window - fixed_blocks               # 如 220000
COMPACT_BUFFER  = 13000                                # 为摘要生成留输出空间（参考 Claude Code 13K）
threshold       = effective_window - COMPACT_BUFFER    # 如 207000
```
> 为何用绝对 buffer 而非比例：摘要输出大小不随窗口等比缩放（无论 30w 还是 100w，摘要都是几 K）。绝对量更安全。

### 3.2 未摘要历史口径

```python
unsummarized_tokens = total_history_tokens - summary.tokens - kept_tokens
```
触发条件：
```python
if unsummarized_tokens >= threshold and len(unsummarized_msgs) >= 4:
    trigger_summary()
```
`len >= 4`（约 2 轮）最小条数防抖，避免单条超长消息误触发。

### 3.3 触发时机
`chat.send` 末尾（回复已落库后）异步评估，不阻塞主回复：`asyncio.create_task(short_term.maybe_compress(session_id))`，协程内整体 `try/except`，异常仅告警。

## 4. 压缩流水线（两层：先便宜后昂贵）

参考分层策略，本地截短优先，LLM 摘要兜底。

### 4.1 第一层：本地截短（不调 LLM，窗口内可逆）

目标：不调 LLM，直接截短大块内容，把未摘要 token 压下来。截短是对"喂给模型的视图"的裁剪，**不改写 `agent_messages` 原文**（可逆，见 4.1.4）。

#### 4.1.1 阈值（提高，避免频繁触发）
- 老工具结果 > **6000** token → 截短；
- 大文件内容 > **12000** token → 截短。
> 原 2000 / 3000 偏低，正常对话极易触发；提高到 6000 / 12000 后仅真正大块才截。

#### 4.1.2 时间维度（老内容才截短）
- 仅对距当前 **≥ 3 轮**的"老"消息做截短；
- **最近 3 轮（含当前）一律不截短**，保证正在进行的推理有完整上下文，避免误伤在用信息。

#### 4.1.3 截短策略（明确保留什么）
| 对象 | 截短后保留 |
|---|---|
| 老工具结果 | **首尾**：首部（工具名 + 参数摘要）+ 尾部（最终状态/错误码/结论）；中间大块省略为 `[...已省略 N token...]` |
| 大文件内容 | **结构 + 关键行**：文件头（imports/签名/定义等结构）+ 命中关键行；其余正文省略 |
| 重复 `tool_call`/`tool_result` 对 | **合并**：保留最后一次结果 + 标记"此前 N 次同类调用已合并" |

通用原则：**首尾保留 + 结构保留 + 关键行保留**，中间冗余省略并标注省略量，不丢"结论 / 状态 / 结构"。

#### 4.1.4 可逆性（原文是否保留）
- 截短**只发生在窗口内**（构建 prior / `pick_history` 时），是对"模型可见视图"的裁剪；
- `agent_messages` 原文**始终保留**（截短不写库；`compressed_into` 仅由 LLM 摘要流程标记）；
- 故截短**完全可逆**：同一原始消息在另一窗口或按需调取（`get_original_messages`）时仍是完整原文。

### 4.2 第二层：LLM 摘要（兜底）
仅当本地截短仍超阈值才调 LLM。

```
系统指令：你是会话压缩器。把以下对话压缩成要点式摘要，按下述五类分节：
  1. 用户反馈/纠正（最高优先级，不可牺牲）
  2. 未决问题（高优先级，不可牺牲）
  3. 用户目标与意图
  4. 已确认的事实与决策
  5. 关键实体（人名、项目名、文件名）
不要保留：寒暄、试错过程、重复内容。
预算：总软上限 ≤600 token；五类各有独立预算，单类超限先内部要点化；
总超 600 时从最低优先级（实体→事实→目标）开始压缩，反馈与未决受保护绝不裁掉。
输入：[旧摘要(if any)] + [本轮被裁历史格式化]
```
**增量合并**（`new_summary = LLM(旧摘要 + 被裁历史)`，而非全量重算）——增量成本恒定、摘要稳定。

### 4.3 摘要预算模型（软上限 + 优先级）与三约束

**五类优先级（高→低）**：反馈 > 未决 > 目标 > 事实 > 实体。

**每类独立预算**（软，合计 = 600 软上限，防单类膨胀）：

| 类 | 预算(token) | 性质 |
|---|---|---|
| 反馈/纠正 | 150 | 受保护，不可牺牲 |
| 未决问题 | 120 | 受保护，不可牺牲 |
| 目标/意图 | 120 | 可压缩 |
| 事实/决策 | 130 | 可压缩 |
| 实体 | 80 | 可压缩（最先压） |

**超限处理**（明确"超限时怎么办"）：
1. **单类超自身独立预算** → 该类先**内部压缩**（要点化、去重、合并），不影响其他类；
2. **总 token 仍超 600 软上限** → **从最低优先级开始压缩**：实体 → 事实 → 目标；
3. **反馈与未决为受保护区，不可牺牲**——即便总预算被逼，也优先保反馈/未决，宁可不压它们；
4. **极端情形**（压到仅剩受保护区仍超） → 受保护区内再**缩短表述**，但**绝不丢弃反馈/未决的条目**，仅精简措辞。

> 五类默认够用；时间线 / 条件类信息未单列，若后续发现遗漏可扩展类别，不影响"优先级 + 每类独立预算"框架。

**三约束防退化**（沿用）：

| 约束 | 说明 |
|---|---|
| 软上限 + 优先级 | 600 为软上限；受保护区（反馈/未决）不可牺牲，超限从低优先级压起 |
| 最近 K 条不摘要 | `pick_history` 刚性保留最新若干条 + `keep_first` 首问（调度层保障） |
| 合并而非纯重写 | LLM 同时看旧摘要与被裁历史，输出连贯滚动摘要 |

## 5. 摘要覆盖范围对齐 + 原子性

**核心原则**：摘要覆盖"**所有不在当前 kept 里的历史**"，不是"本轮 dropped"——否则窗口滑动时会出现"被裁掉但没被摘要"的消息，永久丢失。

```
compactor.maybe_compress(session_id):
  1. raw          = short_term.get_history(session_id)   # 内容层提供
  2. kept         = governor.pick_history(raw, budget)   # 调度层决策（单向依赖）
  3. to_summarize = raw 中不在 kept 里、且未被旧摘要覆盖的部分
  4. 若 to_summarize 达到阈值：
       new_summary = LLM(旧摘要 + to_summarize)          # 软上限+优先级预算（§4.3）
       事务：写摘要 + 标记 compressed_into
```
> 注：本地截短（§4.1）属窗口内视图裁剪，不参与 `to_summarize` 的持久化；compactor 评估"截短后仍超阈值"时，对 `to_summarize` 套用同样的窗口内截短视图估算 token。

**原子性**（先写摘要再标记，保证不出现"标记了但没摘要"）：
```sql
BEGIN;
  UPSERT agent_session_summaries (session_id, summary, version, covers_up_to_seq, tokens);
  UPDATE agent_messages SET compressed_into = ? WHERE seq <= ?;
COMMIT;
```

## 6. 注入策略

### 6.1 prior 构造
```python
def _build_prior(ctx, session_id):
    raw     = short_term.get_history(session_id)      # 内容层提供，seq ASC
    summary = short_term.latest_summary(session_id)   # 可能为 None
    kept, _ = governor.pick_history(raw, budget)      # 调度层收窗（窗口内截短在此生效，§4.1）
    prior   = []
    if summary:
        # ⚠️ 用 user 角色，不用 system
        prior.append({
            "role": "user",
            "content": "[会话前情 · 以下为历史摘要，仅供参考]\n" + summary
        })
    prior.extend(kept)   # pick_history 返回的 kept 不含本轮 user 消息
    return prior
# 调用方单独 append 当前轮 user 消息
```

### 6.2 角色选择（采用参考方案，纠正原方案）
**不用 `system` 角色注入摘要**：
- system 消息被模型当权威指令，摘要里的"用户要求 X"可能被当硬性规则；
- 与真正的 system prompt（身份、边界）冲突。
→ 推荐 `user` 角色 + 明确前缀区分"背景"。

### 6.3 `kept` 返回契约
`pick_history` 返回的 `kept` **不含**本轮 user 消息，由调用方单独追加——`_build_prior` 内不再做 `[:-1]`，避免丢内容 bug。

## 7. 回溯与审计

### 7.1 原文保留
- 摘要生成后原文**不删**（`agent_messages` 始终完整保留）；
- 本地截短**不写库**，仅窗口内视图裁剪（§4.1.4）；
- `compressed_into` 仅标记"被哪版摘要覆盖"，供审计与按需调取。

### 7.2 按需调取原文
```python
def get_original_messages(session_id, seq_start, seq_end):
    return query("SELECT * FROM agent_messages "
                 "WHERE session_id=? AND seq BETWEEN ? AND ? ORDER BY seq",
                 session_id, seq_start, seq_end)
```

### 7.3 审计日志
每次压缩记录：`session_id` / 压缩前 `unsummarized_tokens` / 压缩后 / 摘要版本 / `covers_up_to_seq` / 耗时 / 是否失败。

## 8. 异常处理、退避与降级

### 8.0 失败粒度定义（先界定什么是"失败"）
- **算失败（执行异常）**：压缩流水线**真出异常**——LLM 调用抛错/超时、DB 写入或标记失败、本地截短/解析异常、异步任务裸奔异常。
- **不算失败**：
  - "无内容可摘要"（阈值未达、历史过短、已全被摘要覆盖）；
  - "本轮未触发压缩"（评估后决定不压）；
  - 流程正常完成但摘要为空（视为跳过）。
- 含义：**正常的"没东西可压"不触发退避计数**，退避只在真出异常时累加，避免空转惩罚。

### 8.1 作用域（per plugin + 按失败原因分类）
- 退避状态**作用域隔离**到短期记忆插件实例（`short_term` 内一个 `CompressionBackoff` 状态机），**不**跨 plugin 共享（per plugin）。
- 按**失败原因分类**分别计数与退避，避免"本地截短偶发失败"累死"LLM 摘要"通道：
  - 原因分类：`llm_error`（LLM 摘要执行异常）、`db_error`（摘要写库/标记失败）、`truncate_error`（第一层本地截短异常）、`unknown`（其余）。
  - 每类独立维护"连续失败次数 + 当前退避档 + 暂停截止时间"。
  - 注：`truncate_error` 通常不计入严重退避——本地截短本就是可逆窗口内视图裁剪，异常时降级为"不截短直接用原文视图"即可。

### 8.2 递增退避（替换固定 10 分钟）
- 档位：**1m → 10m → 1h → 24h**（对应连续失败次数 1 / 2 / 3 / ≥4）。
- 规则：某原因连续失败达当前档 → 进入该档暂停（期间不对该原因重试压缩）；**该原因成功一次 → 清零计数、退回 1m 档**（不再惩罚）。

| 连续失败次数 | 退避时长 |
|---|---|
| 1 | 1 分钟 |
| 2 | 10 分钟 |
| 3 | 1 小时 |
| ≥4 | 24 小时 |

- 暂停期间：告警（不崩、不阻塞主回复），异步评估跳过该原因的压缩。

### 8.3 恢复探测（暂停后用轻量方式探测）
- 退避暂停期间**不立即全量恢复**，而是用**轻量探测**判断该原因是否已恢复：
  - 探测负载：**极小**——仅对最近一次失败 session 的最少消息（或一条合成健康检查）跑一次该原因的压缩路径，不波及全量历史；
  - 探测**成功** → 清零退避、恢复该原因正常压缩；
  - 探测**失败** → **续期**当前暂停（不升级档位、不累加计数），避免暂停期内的探测失败被误算成"又连续失败"导致档位飙升。
- 探测频率：取当前档时长的 `recovery_probe_ratio`（默认 0.5，如 10m 档每 5m 探一次），最小 1m。

### 8.4 降级路径（层级递降，不裸崩）
失败/不可用时的**逐级降级**（与 §8.1 原因分类配合：某一层失败不影响更低层已生效的裁剪）：

| 层级 | 触发 | 降级到 | 说明 |
|---|---|---|---|
| L1 | LLM 摘要失败（`llm_error`） | **本地截短**（第一层仍生效，窗口内截短照常） | 不摘要但能压大块 |
| L2 | 本地截短也失败（`truncate_error`） | **硬裁**（窗口内直接喂原文视图，按 `pick_history` 条数） | 接受窗口紧张，但对话不崩 |
| L3 | 短期记忆插件 / 治理器整体停用 | `HISTORY_LIMIT` 条数硬裁 | 无摘要、无截短，纯兜底 |

- 每一级**独立可降级**：例如 LLM 不可用但本地截短可用，则"本地截短 + 不摘要"组合仍生效。对话不崩、不阻塞。

### 8.5 恢复后分批补偿（避免一次性全失败）
- 退避清零/恢复后，**不一次性**对所有"积压未摘要" session 全量补偿——否则若根因未真正解除，会瞬间再次连续失败、重新进入长退避。
- 策略：**分批补偿**——
  - 每轮异步评估只处理**一个** session 的补偿压缩（节流，见 `recovery_batch_size`）；
  - 连续成功达 `recovery_warmup_success`（默认 3）次后才逐步放宽到正常并发；
  - 若补偿中再次失败 → 重新进入该原因的退避（计数从 1 起，不沿用旧计数）。
- 把"恢复"当渐暖过程，平滑验证根因已解。

### 8.6 可见性（沿用并扩展）
`stats` 暴露：各原因连续失败次数 / 当前退避档 / 最近一次失败原因与时间 / 最近成功摘要时间 / 摘要滞后轮数 / 探测命中率。

## 9. 完整流程图

```
chat.send(session_id, user_msg):
  1. 落库 user_msg
  2. 构造 prior:
       raw     = short_term.get_history(session_id)   # 内容层
       summary = short_term.latest_summary(session_id)
       kept    = governor.pick_history(raw, budget)   # 调度层（窗口内截短生效，§4.1）
       prior   = [summary] + kept
  3. 调 LLM 生成回复
  4. 落库 assistant 回复
  5. 异步压缩评估: asyncio.create_task(short_term.maybe_compress(session_id))

short_term.maybe_compress(session_id):                # 内容层自管压缩
  1. raw          = short_term.get_history(session_id)
  2. kept         = governor.pick_history(raw, budget) # 咨询调度层
  3. to_summarize = raw - kept - 旧摘要已覆盖
  4. unsummarized_tokens = sum(tokens of to_summarize)（套用窗口内截短视图）
  5. if unsummarized_tokens < threshold or len < 4: return
  6. 本地截短（第一层，仅老内容、窗口内可逆）
  7. 若仍超阈值 → LLM 摘要（第二层，软上限+优先级预算 §4.3）
  8. 事务：写摘要 + 标记 compressed_into
  9. 审计日志
  注：步骤 6–8 任一「执行异常」按 §8 退避（仅 execution 异常计入，无内容可摘要/未触发不算）；该原因暂停期间跳过压缩。
```

## 10. 配置项（`agent.short_term` 节）

```yaml
short_term_memory:
  context_window: 300000          # 窗口（可配）
  fixed_blocks: 80000             # 固定块估算（system/工具/工作/长期召回/输入）
  compact_buffer: 13000           # 压缩预留 buffer（绝对量）
  summary_max_tokens: 600         # 摘要总软上限
  summary_budget_feedback: 150    # 反馈/纠正（受保护，不可牺牲）
  summary_budget_unresolved: 120  # 未决问题（受保护，不可牺牲）
  summary_budget_goal: 120        # 目标/意图（可压缩）
  summary_budget_facts: 130       # 事实/决策（可压缩）
  summary_budget_entity: 80       # 实体（可压缩，最先压）
  min_messages_to_summarize: 4    # 最小条数防抖
  keep_recent: 6                  # 最近保留条数
  keep_first: 1                   # 首问保留条数
  tool_result_max_tokens: 6000    # 本地截短：老工具结果阈值（>此值才截）
  file_content_max_tokens: 12000  # 本地截短：大文件内容阈值（>此值才截）
  truncate_recent_rounds: 3       # 最近 N 轮不截短（仅老内容截短）
  # —— 失败退避（递增；per plugin + 按失败原因分类）——
  backoff_schedule: [1, 10, 60, 1440]   # 连续失败 1/2/3/≥4 次 → 退避分钟数（1m/10m/1h/24h）
  backoff_reset_on_success: true        # 成功一次即清零计数、退回 1m 档
  failure_granularity: "execution_only" # 仅执行异常算失败；无内容可摘要/未触发不算
  recovery_probe_ratio: 0.5             # 探测频率 = 当前档时长 × 此比例（最小 1m）
  recovery_batch_size: 1                # 恢复后每轮补偿的 session 数（分批，防一次性全败）
  recovery_warmup_success: 3            # 连续成功达此值才放宽并发
```
> 触发阈值 `threshold = (context_window − fixed_blocks) − compact_buffer`，由上面三项算出，不直接配置。
> 摘要五类预算合计 = `summary_max_tokens`（软上限）；受保护区（反馈/未决=270）为不可牺牲下限。
