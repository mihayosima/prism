# 上下文装配链路：现状与完善方案

> 文档目的：把「一次对话请求 → 拼装成喂给 LLM 的 messages」的**完整链路**讲清楚（现状），并给出上下文治理器的**分阶段完善方案**（G1–G5）供评审。
> 范围：上下文调度层（`plugins.context`）+ 各记忆层（system / long-term / work / short-term）+ 对话驱动（`sys.chat`）。
> 立场：所有断言均来自当前代码实证（含 `file:line`），非设计臆测。
> 当前状态（已确认）：长期记忆 `plugins.memory` 经插件页停用，处于 `desired:false / actual:false / 未装配`，故下文"长期记忆块"现状为**不注入**。

---

## 1. 现状

### 1.1 组件与职责边界

| 组件 | 层 / 类型 | 是否启用 | 职责 | 关键文件 |
|---|---|---|---|---|
| `plugins.system_memory` | ① 系统记忆 | ✅ | 静态声明底座（身份/规则），**前置注入**到 plan/narrate 的 system | `plugins/system_memory/` |
| `plugins.context` (`ContextGovernor`) | 调度（system 层目录插件） | ✅ | **只做调度决策**：token 预算分块 + 历史收窗（`pick_history`）；**不持有任何记忆内容** | `plugins/context/governor.py` |
| `plugins.short_term` | ④ 短期记忆（内容层） | ✅ | 会话转写（`agent_messages`）+ 滚动摘要（`agent_session_summaries`）+ 本地截短 | `plugins/short_term/` |
| `plugins.work_memory` | ③ 工作记忆 | ✅（本机无 Redis→内存降级） | 任务/会话态（run 级），非对话历史 | `plugins/work_memory/` |
| `plugins.memory`（长期记忆） | ② 长期记忆 | ⛔ **已停用** | 实体/关系/打分召回；停用后 `ctx.memory` 缺失，`_memory_block` 返回 `""` | `plugins/memory/` |
| `sys.chat`（`ChatDriver`） | 业务驱动 | ✅ | 把上述内容**装配**成 LLM messages；协调 plan→execute→narrate | `sys/chat.py` |

**单向依赖纪律**（沿用用户纠正的红线：上下文管理管调度，短期记忆管内容）：
- `sys.chat` 经 `ctx.get(Services.CONTEXT)` 调用治理器，消费面一律软依赖（停用即退回降级，不裸崩）。
- `short_term.compactor` 在压缩前**咨询** `ctx.get(Services.CONTEXT).pick_history`，但不拥有收窗决策。
- 短期记忆表归属（`agent_messages` / `agent_session_summaries`）已收口到 `store.py`，chat 零 SQL。

### 1.2 一次对话的完整装配链路

入口：`ChatDriver.send()`（`sys/chat.py:94`）→ 单步分支 `plan/execute/narrate`，或多步分支 `_send_via_react`。

```
send(message, session_id)
├─[1] 写 durable 事件 CHAT_IN                           (chat.py:99)
├─[2] _append(user)  → short_term.append               (chat.py:101,196)
├─[3] prior = _build_prior(session_id, message)        (chat.py:103)  ← 核心装配
├─[4] if ctx.has(REACT):  _send_via_react(prior)       (chat.py:106)
│       └─ react.run(prior=prior)  # 复用同一 prior；循环内窗口治理=G2 缺口
│   else:
│     ├─ plan      = _plan(message, prior)             (chat.py:109)
│     ├─ evidence  = _execute(plan)                    (chat.py:110)
│     └─ text,...  = _narrate(plan, evidence, prior)  (chat.py:111)
├─[5] _append(assistant)  → short_term.append          (chat.py:121,169)
├─[6] if ctx.has(MEMORY):  ctx.memory.remember(...)    (chat.py:127,170)  ← 当前恒 false
├─[7] 写 durable 事件 CHAT_DONE                        (chat.py:134,178)
└─[8] asyncio.create_task(_safe_compress)  后台触发滚动摘要 (chat.py:139,184)
```

#### 链路核心：`_build_prior`（chat.py:217–246）

```
raw      = short.get_history(session_id)        # 全量历史 seq ASC，含原文 (store.py:41)
raw_excl = raw[:-1]                            # 排除本轮 user（调用方单独追加）
summary  = short.latest_summary(session_id)    # 滚动摘要（可能为 None）
governor = ctx.get(Services.CONTEXT)           # 调度层
budget   = governor.history_budget()           # = input_budget × 0.60
kept,_   = governor.pick_history(raw_excl, budget, keep_first=True)  # 从新到旧贪心收窗
kept_view= short.truncate_view(kept)           # 内容层窗口内本地截短（老内容可逆）
prior = ([summary 头部] if summary else []) + kept_view
```

- `pick_history`（`governor.py:77`）：token 口径，从最新往回贪心；**刚性保留**最新一条 + 首条 user（`keep_first`，多步"首问"语义）。只裁喂给模型的窗口，不改 `get_history` 持有的全集。
- `truncate_view`（`compactor.py:183`）：仅对 `kept` 里**老内容**做窗口内截短（保留最近 3 轮、工具结果≤6000 tok、文件≤12000 tok），**可逆**——原文留在 `agent_messages`，窗口内视图凝练。

#### 装配出的最终 messages 结构

**plan 段**（chat.py:289–290）：
```
[ system = MARK_CHAT_PLAN
          + 系统记忆(system_memory)            ← 前置注入 (chat.py:277-280)
          + PLAN_SYSTEM
          + 长期记忆块(_memory_block)          ← 当前停用→空 (chat.py:282)
          + 工具目录(_tools_block)             (chat.py:285)
          + 环境事实(_env_facts)               (chat.py:288)
] + prior + [ user = message ]
```

**narrate 段**（chat.py:363–364）：
```
[ system = MARK_CHAT_ANSWER
          + 系统记忆(system_memory)            (chat.py:355-358)
          + ANSWER_SYSTEM
          + 证据 JSON(plan+evidence)
          + 长期记忆块(_memory_block)          ← 当前停用→空 (chat.py:360)
] + prior + [ user = message ]
```

> 两段（plan / narrate）**各自独立重拼** prior，且 system 组成不同（规划器 vs 解说员），因此同一轮对话 LLM 被调两次、各带一份上下文。

### 1.3 降级与解耦纪律

- **软依赖守卫**：`sys/chat.py` 对四记忆层一律 `ctx.has(...)` 判断 + `ctx.get(...) or 默认`，绝不写进 `inject`（否则未启用即 `MissingDependencyError`）。
- **治理器缺失降级**：`_build_prior` 无 `CONTEXT` 时退回旧 `HISTORY_LIMIT=12` 条数硬裁（chat.py:244–246）。
- **压缩失败不拖累主链路**：`_safe_compress` 外层 try/except；`maybe_compress` 仅"执行异常"计失败+递增退避（compactor.py:70–77）。
- **reset 级联清摘要**：`delete_session` 同事务删历史 + 摘要，避免"已删历史的前情"残留注入（store.py:128–141）。

### 1.4 现状已知短板（即"待完善"清单）

| # | 缺口 | 现状事实 | 影响 |
|---|---|---|---|
| S1 | **G1 分块装配未做** | 四块（summary/历史/system/工具）各自独立塞，无统一"块预算→互斥"编排；摘要与窗口边界未保证互斥 | 长会话下可能"摘要+原文"重复注入 |
| S2 | **G1 会话压缩摘要已部分运行但未接管收窗衔接** | `maybe_compress` 跑通（LLM 摘要 + 优先级预算），但 `pick_history` 不感知 `covers_up_to_seq` | 被压缩但未超预算的历史可能与摘要并存 |
| S3 | **G2 react 窗口未治理** | `_send_via_react` 直接复用 `_build_prior` 的 prior，循环内部 Think/Act/Observe 多轮无独立窗口约束 | 多步长任务可能撑爆上下文 |
| S4 | **G3 MCP 源头护栏未接线** | `source_clip_tokens=8192` 已在 `ContextGovernor` 固化口径，但**无任何消费方调用** `source_clip_budget()` | MCP/工具巨量输出直进模型（注入入口未净化） |
| S5 | **G4 记忆配额反推未接** | `memory_budget()` 已固化，但 `_memory_block` 用硬编码 `limit=5`（chat.py:270），未用治理器反推实参 | 记忆块与历史块预算各自为政 |
| S6 | **G5 工具块降载未做** | `_tools_block` 描述截断 60 字（chat.py:322），无动态按预算裁剪 | 工具多时描述仍可能占大量 token |
| S7 | **长期记忆块缺失** | 用户已停用 `plugins.memory` | 当前对话无跨会话长期知识注入（设计上可接受，属暂缓） |

## 2. 完善方案（分阶段落地 G1–G5）

### 2.1 设计原则（沿用既定纪律）

1. **调度/内容分离**：`context` 只做预算与收窗决策，记忆内容（含摘要）仍归各记忆层 owner。
2. **软依赖 + 降级**：任一新能力缺失须退回现状，不裸崩。
3. **零特权**：预算/裁剪只走 `core.tokens` 公共原语；表归属收口到 owner 插件。
4. **可逆优先**：窗口内凝练不改原文（`agent_messages` 始终完整），摘要为独立表。

### 2.2 分阶段路线图

#### G0（已完成）
预算模型 + token 历史收窗（`pick_history`）+ 接缝可注入。✅ 已上线。

#### G1 — 分块装配 + 摘要/窗口互斥衔接（建议优先级：**最高**）
- **目标**：把"四块如何拼、各占多少"收敛到治理器统一编排；消除 S1/S2 的摘要/原文重复。
- **改动面**：
  - `ContextGovernor` 新增 `assemble_window(ctx, blocks)` 或各块 `budget_*` 查询已齐（`memory_budget`/`history_budget`/`source_clip_budget`），由 `chat._build_prior` 改为"先查各块预算→构造互斥边界"。
  - `pick_history` 接收 `covers_up_to_seq` 参数：`seq <= covers` 的历史直接交给摘要头部，**不再进 kept**（消除 S2）。
  - 摘要头部与 kept 视窗做互斥校验（单测守卫：同一 seq 不重复出现于两者）。
- **接口**：`pick_history(messages, budget, *, keep_first, exclude_upto=None)`。
- **验收**：长会话（>50 轮）下 prior token 数逼近 `history_budget`、无"摘要+原文"重复 seq。

#### G2 — react 多步窗口治理
- **目标**：多步循环内 Think/Act/Observe 也受上下文预算约束（S3）。
- **改动面**：`plugins.react` 的 `run(ctx, message, prior)` 内部在每轮 Act/Observe 后调用治理器收窗（复用 `pick_history`），而非仅依赖入口 prior。
- **验收**：10+ 步工具链不溢出 `max_context_tokens`。

#### G3 — MCP/工具源头护栏接线
- **目标**：巨量工具/MCP 输出在进模型前被裁到 `source_clip_budget()`（S4）。
- **改动面**：`chat._execute` 拿到 `evidence.result` 后，对超长结果经治理器 `source_clip_budget()` 截断（或交由 `short_term.truncate_view` 统一处理）。
- **验收**：单工具返回 50k tok 时，进模型的仅 ≤8192 tok，且关键行保留。

#### G4 — 记忆注入配额反推
- **目标**：`_memory_block` 用 `governor.memory_budget()` 反推 `limit`/`max_tokens`（S5）。
- **改动面**：`chat._memory_block` 改为 `ctx.memory.context(query, max_tokens=governor.memory_budget())`；长期记忆停用时不调用。
- **验收**：记忆块 token 不超过 `memory_budget()`，与历史块预算可加总校验。

#### G5 — 工具块动态降载
- **目标**：工具目录描述按剩余预算动态裁剪（S6）。
- **改动面**：`_tools_block` 接收治理器剩余预算，超阈值时压缩描述 / 折叠低频工具。
- **验收**：工具数从 5→50 时，工具块 token 增长受控。

### 2.3 优先级与节奏建议

| 优先级 | 阶段 | 理由 |
|---|---|---|
| P0 | **G1** | 当前唯一"会出错"的短板（长会话重复注入），且是其余阶段的基础编排 |
| P1 | **G3 → G4** | 安全（源头净化）+ 配额闭环，风险收益比高 |
| P2 | **G2** | 仅多步场景受影响，依赖 react 插件启用 |
| P3 | **G5** | 体验优化，非阻塞 |

建议顺序：**G1 → G3 → G4 → G2 → G5**，每阶段独立 PR + 守卫测试（沿用 `test_plugin_decoupling.py` 的"分层方向/inject 耦合/表归属"三向守卫）。

### 2.4 风险与守卫

- **回归风险**：G1 改 `pick_history` 签名，须同步更新 `short_term.compactor` 调用点与单测；建议先在 facade 层做兼容包装。
- **解耦纪律**：所有新调用必须经 `ctx.get(Services.CONTEXT)` 软依赖；不得让 `sys/chat.py` 或 `react` 反向 import 治理器实现。
- **守卫复用**：表归属守卫（`agent_messages`/`agent_session_summaries` 仅 owner 读写）已在解耦复核中固化，G1 摘要衔接不得破坏该归属。
