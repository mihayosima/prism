# 记忆插件物理拆包 — 设计方案（M1–M4）

> 前置：D2 已完成运行时解耦（目录插件形态、`ctx.has` 软依赖消费、三组件接缝、零特权）。
> 本方案解决**物理拆包**的最后一公里：让 `agent/plugins/memory` 不再依赖系统层的任何专属定义，
> 达到"整个目录拷走即独立"的程度。标号 M1–M4，全部实施并测试通过后统一提交。

## 0. 现状盘点（拆包前依赖清单）

| 依赖项 | 位置 | 性质 | 处置 |
|---|---|---|---|
| 三张表 DDL | `agent/tables.py` L29-45（`agent_007/008/009` 三组迁移） | **真实残留** | M1 随插件迁移 |
| `MARK_MEMORY_EXTRACT` | `agent/api.py` L35 | 插件专属标记混入宿主门面 | M2 随插件迁移 |
| `Services.MEMORY` | `core/services_catalog.py` | 宿主登记项 | M3 保留（登记语义） |
| `Events.MEMORY_REMEMBERED/RECALL` | `core/events_catalog.py` | 宿主登记项 | M3 保留 |
| `config_schema "memory": "_any"` | `core/config_schema.py` | 宿主登记项 | M3 保留 |
| `agent.api` 公共门面 | `plugin/Services/Events/durable/now_iso/CapabilityNotImplemented` | 健康（公共 API） | 不动 |

消费面零静态依赖已达成：`sys/chat.py` 全部经 `ctx.has(Services.MEMORY)` + `ctx.memory`，
`run/chat.py` 的 `/api/memory` 有友好降级，无任何 `import agent.plugins.memory`。

## M1 — DDL 随插件迁移（核心）

**难点**：`MigrationRegistry` 有防脏武校验（已应用 ∖ 当前定义 ≠ ∅ → 拒绝启动）。
若直接从 `agent.tables.MIGRATIONS` 摘除 `agent_007/008/009`，存量库启动即 stray 报错；
若插件沿用同名迁移，新库上 storage 先以空语句登记名字 → 插件再 apply 同名会被跳过，表永远建不出来。

**方案**：旧名转"空登记"（沿用 `_DEPRECATED` 既有模式），插件用**新迁移名**自带 DDL：

1. `agent/tables.py`
   - `_MEMORIES/_ENTITIES/_EDGES` 三组 DDL 语句摘除；
   - `agent_007_memories / agent_008_entities / agent_009_edges` 三个名字保留在 `MIGRATIONS`，
     语句集置空（与 `_DEPRECATED` 同构：幂等 no-op），注释注明"DDL 已随 plugins.memory 迁走"。
2. `agent/plugins/memory/__init__.py`
   - 新增模块级 `MEMORY_MIGRATIONS`：`agent_mem_001_memories / agent_mem_002_entities / agent_mem_003_edges`，
     DDL 原文从 tables.py 平移（`_per` 辅助函数内联或复制，三行而已）；
   - `apply()` 开头：`await ctx.migrations.apply(ctx, MEMORY_MIGRATIONS, "sqlite", namespace="agent")`；
   - `inject` 增补 `"migrations"`（storage 提供；DB 依赖已保证次序，显式声明更稳）。

**正确性推演**：
- 存量库：旧名已应用 → 空语句 no-op；新名未应用 → `CREATE TABLE IF NOT EXISTS` 幂等 no-op（表已在）。✓
- 新库：旧名空登记；新名由插件建表。✓
- 防脏武：storage 的 apply 调用 defined 集含旧名（空语句）→ 存量库不 stray；
  memory 自己的 apply 同理。两处调用互不越界。✓
- **零内核改动**：storage / container / registry 均不动，纯复用既有原语。

**语义变化（接受）**：停用/卸载 memory 后三张表不再创建（原全局 DDL 时代即使停用也建）。
消费面仅 `ctx.memory`（已全部守卫降级），无实际影响，语义上更干净。

## M2 — 提取标记随插件

`MARK_MEMORY_EXTRACT` 是 memory 专属的 LLM 路由标记，不应住在宿主门面：

1. `agent/plugins/memory/__init__.py`：定义 `MARK_MEMORY_EXTRACT = "<!--memory:extract-->"`，
   `EXTRACT_SYSTEM` 改用本地常量，并加入 `__all__`；
2. `agent/api.py`：删除 `MARK_MEMORY_EXTRACT`（含 `__all__`）；
3. `agent/fixtures/llm.py`：改从 `agent.plugins.memory` import（离线 Fixture 本就是测试侧，
   引具体插件路径合理）。

> 范围声明：`MARK_CHAT_*` / `MARK_REACT_*` 同为目录插件标记，本次**不动**；
> react 若日后同等拆包，照此模式办理（列为后续可选项，不属于本方案）。

## M3 — 宿主登记项界定（不改代码）

- `Services.MEMORY`、`Events.MEMORY_REMEMBERED/RECALL`、`config_schema "memory": "_any"`
  属宿主登记表（目录/枚举性质），**保留在宿主**。这是插件体系的正常形态：插件注册键，宿主持目录。
- 新增守卫测试一条：`sys/*` 层不得静态 `import agent.plugins.memory`（固化消费面零依赖，
  挂入 `tests/test_decouple_guards.py` 风格）。

## M4 — 测试与验证

新增测试（`tests/test_memory_extraction.py` 或并入 `test_memory.py`）：

1. **冷库由插件建表**：全新 tmp 库 → 启动 → `agent_migrations` 含 `agent_mem_001/002/003`
   三个新名、旧名空登记；`agent_memories` 表存在且 remember/recall 可用。
2. **存量库幂等**：先按旧 DDL 建库（模拟升级前）→ 换新代码启动 → 不 stray、
   旧数据完整保留、新迁移名补登记、表结构未破坏。
3. **停用 memory**：`set_enabled("plugins.memory", False)` → chat 照常
   （既有测试覆盖），补充断言：新迁移名未出现（表未建，语义变化固化）。
4. **守卫**：sys 层无 `agent.plugins.memory` 静态引用（M3）。

最后跑全量 pytest（现 144 项 + 新增），全绿后统一提交。

## 风险与边界

- 防脏武跨调用：已推演两处 apply 调用互不越界（见 M1）。
- 旧库手工残留 `agent_mem_*` 名 + 卸载 memory → 无调用即无校验，无影响。
- 拆成独立 pip 包/仓库的剩余工作（超出本次）：`agent.api` 门面的包化、宿主登记项的
  注册机制化——本方案落地后，插件本体已零系统层专属依赖，届时只动宿主侧装配代码。
