> 前置文档：《B5B6-流式与取消-设计方案.md》（B5.1 + B6 已落地，`bf711cc`）。

## 1. 目标与范围

| | B5.1（已完成） | **B5.2（本文）** |
|---|---|---|

## 2. 现状与代码事实（已逐处核对）

| 位置 | 事实 |
|---|---|
| `sys/llm.py:219-250` | `DeepSeekLlm.complete`：构造 payload → `httpx.AsyncClient(timeout=90.0)` → **`await client.post(...)`（无 stream）** → `resp.json()["choices"][0]["message"]` → 返回 dict |
| `sys/llm.py:229-234` | `tools` 走 native function-calling；`schema` 时加 `response_format: json_object` |
| `sys/llm.py:71-90` | `LlmService.complete`：waterfall `LLM_PRE_CALL`（guard/budget 裁决）→ `provider.complete(...)` → emit `LLM_POST_CALL` |

| `plugins/react/components.py:95-102` | `DefaultReasoner.reason`：`complete(..., tools=tools)`，**无 schema** → 最终答复来自这里 |
| `plugins/react/components.py:148-160` | `DefaultFinalizer.finalize`：`complete(probe)`，**无 tools 无 schema** → 纯散文 |
| `sys/chat.py:267-285` | `_narrate`：`complete(..., caller="agent.chat")`，无 schema → 散文 |
| `sys/chat.py:207` | `_plan`：`complete(..., schema=PLAN_SCHEMA)` → **结构化 JSON，属内部** |

**两条决定性推论**：
1. 三条用户可见路径（reason / finalize / _narrate）**都没有 schema**；唯一带 schema 的是 `_plan`（内部规划）。
   ⇒ 可以据此区分"该不该把文字吐给用户"。
2. 它们都经 `ctx.llm.complete` 单点进入 ⇒ **改造点集中在 provider 一处**，不必逐条改调用方。

## 3. 核心设计决策：用**事件法**，不用回调透传

| 方案 | 代价 |
|---|---|
| 回调透传 `on_token` | 需改 `LlmProvider` 契约 + `LlmService` + `Reasoner` + `Finalizer` + fixture，且要把回调从 `run/` 一路传到 `llm.complete`（**破坏"B5.1 签名不变"的成果**） |
| **事件法（选用）** | provider 每片 `ctx.events.emit(Events.LLM_TOKEN, {"text": 片})`，**仍返回原 dict** |

事件法的好处：
- **`core/contract.py` 一行不改**——契约仍是 `-> dict`。
- `ChatDriver.send` / `ReactLoop.run` / `complete()` **签名全部不变**，与 B5.1 一致的解耦形态。
- 桥接层（`sys/progress.py`）照样只订阅事件，**不知道 HTTP**；换 CLI/WebSocket 无需改动。
- `durable()` 才写库，`emit` 不写库 ⇒ 高频 token **不会污染 `agent_events` 表**。

代价：每片一次事件分发（同步监听器内联执行，`put_nowait`），数百片开销可忽略。

## 4. 详细设计

### 4.1 事件常量（`core/events_catalog.py`）

```python
LLM_TOKEN = "agent/llm/token"     # payload: {"text": "片段"}
```
`EVENT_MODE[LLM_TOKEN] = "emit"`（遥测性质，不进 required seam）。
> 这是**唯一**触碰 `core/` 的改动（加一个常量），且不含业务词，`test_agent_purity` 不受影响。

### 4.2 配置项 + schema 同步

- 新增 `config["agent"]["llm"]["stream"]: bool`。
- **必须同步** `core/config_schema.py` 的 `_SCHEMA["agent"]["llm"]` 加 `"stream": bool`，
  否则 P2 校验会把新键判为未知键而启动报错（这正是 P2 的价值）。
- 默认值建议 **false**（见 §7-D5 待确认）。

### 4.3 `DeepSeekLlm.complete` 流式改造（`sys/llm.py:219-250`）

开启 `stream` 时走分支：

```python
payload["stream"] = True
async with httpx.AsyncClient(timeout=90.0) as client:
    async with client.stream("POST", self.BASE_URL, json=payload, headers=headers) as resp:
        if resp.status_code != 200:
            await resp.aread()                       # 流式下不能 resp.json()
            raise AgentError(f"deepseek api 异常 {resp.status_code}: {text[:200]}")
        async for line in resp.aiter_lines():
            if not line.startswith("data:"): continue
            data = line[5:].strip()
            if data == "[DONE]": break
            ...                                      # 见下方重组
```

**Delta 重组**（含 content 与 tool_calls）：

```
choices[0].delta.content        → 累加到 content；若本次要发帧则 emit LLM_TOKEN
choices[0].delta.tool_calls[]   → 按 index 归并：
    id / type 直接取；function.name 取首个非空；function.arguments **字符串累加**
finish_reason                   → "stop" / "tool_calls"
```

重组出的 `raw_calls` 形状与 OpenAI 一致 ⇒ **可直接复用现有 `_wire_call(c, name_map)`**，
净化名→内部原名的回程映射逻辑完全不用改（B5.1 之前那个 DeepSeek 400 修复继续有效）。

### 4.4 何时发 token 帧（规则）

| 条件 | 是否发帧 | 理由 |
|---|---|---|
| `stream` 未开启 | 否 | 行为与今天完全一致 |
| `schema is not None` | **否** | 结构化 JSON 是内部规划（`_plan`），吐出来是噪音 |
| `schema is None` | **是** | 用户可见的散文（_narrate / reason / finalize） |
| 工具调用片段 | 否（只重组，不发） | 工具参数不是给用户看的文本 |

### 4.5 fixture 支持（**离线可测**的关键）

`FixtureLlm.complete`（`fixtures/llm.py:112-128`）在 `stream` 开启且 `schema is None` 时，
把返回的文本**切成若干片依次 emit `LLM_TOKEN`**（片数可固定，如 4 片），再返回原 dict。
⇒ B5.2 可**完全离线**验证，不依赖真实 API（沿用现有 fixture 测试纪律）。

### 4.6 桥接层帧映射（`sys/progress.py`）

`tap_progress` 增加帧类型映射：

```python
FRAME_TYPES = {Events.LLM_TOKEN: "token"}      # 其余仍为 "progress"
```
并把 `Events.LLM_TOKEN` 加入默认订阅集 `PROGRESS_EVENTS`。

### 4.7 前端打字机渲染（`run/chat.py`）

- 收到 `token` 帧 → 往当前气泡**追加转义文本**（不逐片跑 markdown，避免半成品标签闪烁）；
- 收到 `final` 帧 → 若本轮收到过 token 帧，则**只对累积文本跑一次 `md()`** 并补 evidence；
  未收到过 token（非流式/降级）则照旧用 `final.text`。
  ⇒ **去重**：文字不会出现两遍。
- 取消（`cancelled` 帧）时停止追加，保留已打出部分并标注"（已取消）"。

### 4.8 与取消的交互

token 帧与取消共用同一 run 生命周期：`task.cancel()` 会中止流式读取循环，
`httpx` 连接随即断开 ⇒ 打字机立即停住。**无需额外改动**。

## 6. 验收

**离线（无网络）**
1. fixture 开启 `stream` → 断言收到多片 `token` 帧，且拼接等于最终文本；
2. `schema` 非空的调用 → 断言**不产生** token 帧；
3. 关闭 `stream` → 断言行为与今天完全一致（零 token 帧）；
4. 全量 pytest 通过（103 → 新增若干）。

**真实 API（人工）**
5. 页面上答案逐段打出（打字机）；
6. 多步任务：步骤卡片照常出现，最后答复打字机；
7. 打字过程中点"停止" → 立即停住且标注已取消；
8. `agent_events` 表**不因 token 而膨胀**（emit 不落库）。

## 7. 风险与**待你拍板**的决策

| # | 决策点 | 选项 | 我的建议 |
|---|---|---|---|
| **D3** | **工具调用的 delta 重组** | ① 完整重组（能流 ReAct 最终答复，但要多写 ~20 行且有边界情况）② `tools` 非空时不流（简单，但**ReAct 最终答复就流不出来了**） | **①**。否则打字机只在单步路径才有，主路径没有 |
| **D4** | ReAct 中间步的"思考文本" | 模型在带 tool_calls 的轮次也可能输出 `content`，会被流出来 → 用户看到思考过程 | 建议**照单全流**（多数 UI 这么做，也算可见性）。若嫌吵可加开关 |
| **D5** | `stream` 默认值 | false（保守，需显式开启）/ true（默认即打字机） | **先 false**，真实 API 验证通过后再考虑改默认 |
| **D6** | 流式超时 | 现 `timeout=90.0`（httpx 对流式按读超时计） | 保持 90s；若长答复被截断再调 |

**已知边界（如实说明）**
- 打字机是"几字符一片"，非逐字。
- `response_format: json_object` + stream 的兼容性以实测为准（若有问题，`schema` 调用本就不流，影响可控）。
- token 事件频率高（数百次/轮），但**不落库**、同步监听器内联执行，开销可忽略。

## 8. 不做（范围外）

- 工具**执行结果**的流式（工具是一次性返回，语义上不是流）。
- 思考链（reasoning_content）单独通道。
- B5.2 之外的 B7 调度器 / B8 会话管理 / A4 审批。
