## 0. 结论先行

1. **形态**：目录插件 `plugins.approval`，`layer="system"`、`provides=["approval"]`、`inject=["events","db"]`，**默认启用且默认配置下行为与现状完全一致**（不改任何东西，便于灰度）。
2. **职责三分，互不混同**：
   - **模式（mode）** —— 会话级档位：`default` / `plan` / `auto` / `bypass`；
   - **判定（policy）** —— 三态 `allow / deny / ask` + 通配符；
   - **通道（provider）** —— 怎么把人叫过来（可换接缝）。
3. **挂点**：`agent/tasks/pre-execute`（waterfall，**默认 append ⇒ 排在 guard 之后**）。**不改 guard**。
   - v1.2 复核确认此挂点成立（2026-09-27 调研曾误判为死路，系把 guard 的 `risk.*="ask"` 短路误当成 approval 的接缝）：guard 默认配置全放行时会调 `next()`，排其后的 approval 对每个 guard 放行的任务都会被调用；ask 的**来源是 approval 自身名单**（`approval.ask` 工具名 fnmatch）+ 模式，**不是** guard 的 risk 配置。
   - guard 的 `permissions.risk.*="ask"`（现为短路拒绝并被 `test_guard_risk.py` 锁定）语义 = **无 approval 时的 fail-safe 兜底**；与 `approval.ask` 名单**不应同时使用**（guard 会先短路，问人无从发生），文档对外需写明。
4. **优先级恒定**：`guard 硬规则（一票否决）> approval 的 deny > ask > allow`。**任何模式下 guard 都生效。**
5. **`plan` 不是一个判定分支**，而是三段机制：**工具可见集裁剪 + 终态工具 `submit_plan` + 批准后切模式**；且**软约束（看不到）必须配硬约束（拒绝）**。
6. **分期落地**：机制（第 1 期，用非交互 provider 即可完整可测）→ `plan`（第 2 期）→ 真实通道（第 3 期，与 SSE/取消同批）。**第 1 期不依赖任何新基础设施。**

## 2. 三个正交概念（先把术语钉死）

| 概念 | 作用域 | 取值 | 谁读它 |
|---|---|---|---|
| **mode** | 会话（`ctx.state`） | `default` / `plan` / `auto` / `bypass` | approval、`react`/`chat`（取工具可见集） |
| **policy** | 配置（`config["agent"]["approval"]`） | 三张名单：`allow` / `deny` / `ask`（支持 `*`） | approval |
| **provider** | 装配（按配置选实现） | CLI / 网页 / auto-allow / auto-deny | approval（只在 `ask` 时调用） |

> 关键：**mode 决定"打扰还是不打扰"，policy 决定"哪些要问"，provider 决定"怎么问"。** 三者任一可换而不动其余。

---

## 3. 模式定义（两个正交开关的组合）

| | 工具可见集 | approval 打扰策略 | guard |
|---|---|---|---|
| `default` | 全量 | 按 `ask` 名单问 | 生效 |
| `auto` | 全量 | 只对 `risk != "read"` 的工具问 | 生效 |
| `bypass` | 全量 | **不打扰**（恒放行） | **仍生效** |
| `plan` | **只读子集** | 不打扰（压根没有写工具） | 生效 |

- `auto` 的"危险"判据来自 **`Tool.risk` 元数据**（§6.1），**不用模型自评**（不可靠、可被提示注入绕过）。
- `plan` 落入"只读 × 不打扰"格；`只读 × 要问` 等组合无意义。

---

## 4. 判定链与优先级

```
工具调用
  → agent/tasks/pre-execute（waterfall）
      ① guard（prepend=第一）：硬规则 → allow / deny        ← 一票否决
      ② approval（append=第二）：
           若 mode==bypass            → next()（放行，记审计）
           若 mode==plan 且工具是写类  → 拒绝（硬约束兜底）
           若 命中 deny（fnmatch）     → 拒绝
           若 命中 ask（或 mode==auto 且非只读）→ 调 provider.ask() → 允/拒
           否则                        → next()（放行）
  → 执行工具
```

- **顺序不可颠倒**：若让"用户点头"能推翻 guard，权限系统就退化成橡皮图章。
- approval 用**默认注册序**（append）即可排在 guard 之后 —— **无需改 guard 一行**。

## 5. 挂起与通道（provider 接缝）

### 5.1 可行性依据（已核实）

`EventBus.waterfall` 会 `await` 监听器（`core/events.py` 的 `_invoke_one` 对可等待对象直接 await）⇒ **监听器可以合法"挂起等人类回答"**，无需改内核。这是整个插件成立的基石。

### 5.2 接缝定义

```python
class ApprovalProvider(Protocol):
    interface_version = (1, 0)
    label: str
    async def ask(self, req: ApprovalRequest) -> ApprovalAnswer: ...

@dataclass
class ApprovalRequest:
    call_id: str            # 去重键
    tool: str
    args: dict
    reason: str             # 为什么被拦（来自 policy/mode）
    timeout_s: float

@dataclass
class ApprovalAnswer:
    approved: bool
    by: str                 # 谁答的（provider 自报：cli / web / auto）
    note: str = ""          # 可附"改参数后放行"的说明（本期只记录，不生效）
```

### 5.3 内置 provider（第 1 期先做前两个）

| label | 行为 | 用途 |
|---|---|---|
| `auto-deny` | 恒拒绝 | **CI / 无人值守的默认**（fail-safe） |
| `auto-allow` | 恒放行（照记审计） | 本地开发、已有外部管控 |
| `cli` | `input()` 提示 y/n | 终端交互（`--once` 不适用） |
| `web` | 经通道推给浏览器、等回填 | **第 3 期**，依赖 SSE/轮询 |

### 5.4 三条纪律

1. **超时即拒绝**（`timeout_s` 默认 60）—— 挂起会占住一次调用链，不能无限等；
2. **去重**：同一 `call_id` 只问一次；同一轮内同工具重复调用按 `(tool, args)` 归一；
3. **审计必落**：`asked` / `answered` / `timeout` 三事件都写 `agent_events`。

## 6. `plan` 模式的三段机制

### 6.1 ① 工具可见集裁剪（软约束）

- 落点：`ctx.tasks.catalog(include=...)` —— **该参数已存在**（`agent/sys/tasks.py`）。
- `_visible_tools(ctx)`：`mode==plan` 时只保留 `risk == "read"` 的任务。
- `Tool.risk` 由 `tasks.register(..., risk="read"|"write"|"danger")` 声明，**默认 `"write"`（保守）**。

### 6.2 ② 终态工具 `submit_plan`（输出契约）

- 注册一个 `submit_plan(plan: str)` 任务，仅在 `plan` 模式下出现在可见集；
- 模型调它即表示"计划在此"，`react` 循环据此**收敛**（= LoongFlow 的 final-answer-as-tool 范式的直接应用）；
- 产出 `Message.result` 交给用户批准。

### 6.3 ③ 批准后切模式

```
plan 模式 → 模型调 submit_plan → 循环收敛 → provider.ask("批准此计划？")
  ├─ 同意 → ctx.state["permission_mode"] = "auto"（或 default）→ 带"已批准计划"重跑
  └─ 拒绝 → 留在 plan，把拒绝意见回灌给模型再规划
```

### 6.4 ④ 必须配的硬约束兜底

工具可见集只是"模型看不到"（**软约束，防误导**）；模型仍可能幻觉出写工具名。因此 **`mode==plan` 时 approval 必须直接拒绝写类工具**（**硬约束，防越权**）。**软硬两层缺一不可。**

## 7. 状态与存储

| 状态 | 位置 | 是否持久化 |
|---|---|---|
| `permission_mode` | `ctx.state`（容器作用域） | ❌ **不持久化** —— 重启回 `default` |
| 待答审批（未决请求） | `ctx.state`（内存表 + Future） | ❌ 不持久化（进程死即视为拒绝） |

> **安全设计**：`bypass` 绝不能被持久化。恰好 `ctx.state` 不落盘（此前被列为缺陷，此处反成优点）。若将来要做"记住上次模式"，**也必须排除 `bypass`**。

## 8. 事件与审计

| 事件 | 域 | payload |
|---|---|---|
| `agent/approval/asked` | durable | `{call_id, tool, args_digest, mode, reason, at}` |
| `agent/approval/answered` | durable | `{call_id, approved, by, waited_ms, at}` |
| `agent/approval/timeout` | durable | `{call_id, tool, timeout_s, at}` |
| `agent/approval/mode_changed` | durable | `{from, to, by, at}` |
| `agent/approval/pending` | live（emit） | `{call_id, tool}` —— 供前端弹窗 |

- `args_digest` 存**摘要**而非原文（避免把凭据写进审计）；原文只在 provider 的交互面出现。
- 审计对齐现有纪律：**不另建表**，一律落 `agent_events`。

## 10. 配置项

```toml
[agent.approval]                 # config["agent"]["approval"]
provider = "auto-deny"           # auto-deny | auto-allow | cli | web
timeout_s = 60
allow = ["*"]                    # fnmatch 名单
deny  = []                       # 一票否决（优先于 ask）
ask   = ["Write", "Bash", "mcp.windows.*"]   # 需要人工确认的（支持通配）
mode_default = "default"         # 启动时的模式
```

判定顺序：`deny` → `ask` → `allow` → **默认拒绝**。

## 16. 解耦契约与可管理性（v1.1 补充，开工前确认）

### 16.1 依赖方向：本插件对 `react` **零依赖**

```
approval ──✗──▶ react          （本插件不认识任何循环/驱动）
react ──软(读 permission_mode)──▶ approval
```

- **本插件只挂 `agent/tasks/pre-execute`**，不关心上层是单步 `chat` 还是多步 `react` ⇒ 两者都自动获得审批能力。
- 本插件 **不 import / 不检测 `react`**；`plan` 模式的"计划待批准"**复用普通 `ask` 路径**（`plan` 模式下 `submit_plan` 命中 ask），不需要知道 `submit_plan` 是谁注册的。
- 对外只提供两个稳定接口：`ctx.approval`（判定）与 `permission_mode`（状态，经 `ctx.get("permission_mode", "default")` 读取，缺省即 `default`）。

> 这修正了初版设计的隐患：`plan` 曾要求 approval ↔ react 互相知道。现在 approval **零依赖**，`plan` 由「mode + `Tool.risk` + ask」三个通用概念拼出。

## 18. 第 4 期：澄清问询的"选择规格"（v1.5 新增，2026-09-28）

### 18.1 问题

`ask_user` 首版把候选压成 `options: str`（逗号分隔），前端只能把全部候选项**平铺进同一条选择栏**。三处症状：

| 位置 | 事实 | 后果 |
|---|---|---|
| 工具 schema | `options` 声明 `{"type": "str"}`，描述"逗号分隔" | 模型**只能**交出一个扁平字符串，"哪些是一组""能否多选""每项理由"都无从表达 |
| 归一 | `options.replace("，", ",").split(",")` | 选项文本含逗号（或模型按直觉传 JSON 数组）即被**硬切成碎片** |
| 渲染 | 全部候选项 `map` 成 `.hitops` 里的一排 chip | 所有候选挤在**同一条选择栏**，无层级、无分组、无多选 |

**审计实证**：`agent/approval/answered` 曾出现 `"choice": "\"电影主题曲\""`——值自带引号，正是 JSON 数组字符串被逗号切开后留下的碎片。即模型已在尝试传结构化数组，而后端只会按逗号切。

### 18.2 修法（内核与 guard 零改动）

1. **新增 `plugins/approval/options.py`**（纯函数 `normalize_options`）：把候选归一为**选择规格** `[{label, value, desc, group}]`。
   - 顺序：**JSON 优先**（`'["A","B"]'` 或对象数组；选项含逗号亦安全）→ 换行/逗号/顿号/分号**兜底**（旧提示词零破坏）→ 逐项**清洗**引号与首尾括号残渣（可多层）；
   - 键名同义归并：`label/title/text/name/option`、`desc/description/detail/hint/note/why`、`value/id/key`、`group/category/section/dimension`；
   - 防御：映射写法 `{方案: 说明}` 视作带说明的候选；上限 24 项 × 200 字；label 去重保序。
2. **参数**：`ask_user` 增 `multi`（默认 `false`）；`options` 的 description 改为"推荐传 JSON 数组字符串"并给出对象示例。无候选时 `multi` 自动退回单选语义（多选无意义）。
3. **应答统一**：插件侧 `_picked()` 把单选 `choice` / 多选 `choices` 归一为列表；返回体给 `choices`（列表），仅一项时额外给 `choice`，多选时给 `multi`；多选 hint 提示"一并满足，冲突以先列出者为主"。`POST /api/approval/answer` 增 `choices` 透传（≤24 项 × 200 字）。
4. **前端形态由规格决定**（`run/chat.py`）：仅有候选名 → 紧凑 chip 行（保持原观感）；出现 `desc` / `group` / `multi` 任一 → **卡片行**（`label` 主 + `desc` 次），并按 `group` 分区；`multi` 时方形勾选 + 底部"提交选择"（未选中即禁用）。单选点选即提交；答复后追加"你"气泡留痕（显示**选项名**，提交的是 `value`）。
5. **审计补记**：`agent/approval/asked` 增 `options`（label 列表）与 `multi`；`agent/approval/answered` 增 `choices`——旧版只记 `question`，事后无法复盘卡片形态。
6. **顺带修复**：卡片选项行是 `<div>`，原 `done()` 只禁用 `button/input` ⇒ 了结后选项**仍可点**。改为卡片加 `done` 类 + `pointer-events:none`（`showAskUser` 与 `dismissAskUser` 两处）。

### 18.3 边界（未越界声明）

- **内核零改动**：`sys/tasks.py` 的轻量 schema 校验器未动，`options` 仍声明 `type="str"`（贴合模型既有习惯，避免"传数组即报错"的回归）；本期的兼容由 `normalize_options` 承担。
- **既有语义原样保留**：`risk="read"`、plan 模式可见性（常驻注册）、非交互通道降级、超时 fail-safe 默认拒绝，均未变更。
- **未做（保留在方案内可选）**：多问题卡片（一张卡承载多个决策点、各自独立选择栏、底部统一提交）——本期选了复杂度更低的"单问题 + 富形态选项"。
