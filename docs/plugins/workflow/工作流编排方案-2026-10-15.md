## 1. 背景与定位

### 1.1 用户诉求
> "不仅仅是对于单个工作流，我需要的是所有工作流的编排方案。现在有 MCP、Skill，再加上工作流编排才能实现业务。"

即：**工作流编排是与 MCP、Skill 并列的、能编排"所有业务"的通用能力**，不是某个具体流程（如 ASR 转写）的一次性实现。

### 1.2 三层能力正交分工（设计目标）

| 支柱 | 角色 | 现状（代码实核） |
|---|---|---|
| **MCP** | 外部能力接入：把外部工具/服务包装成 agent 工具 | `plugins/skills_mcp` 等桥，经 `ctx.tasks.register` 注册成 `mcp.*` task |
| **Skill** | 领域知识/"怎么做"：说明式（content 注入 LLM）+ 可选 `run` 入口 | `agent/plugins/skills/model.py`：`Skill` 含 `content` + `run` |
| **Workflow（本方案）** | 业务流程编排：把上述能力串成**确定性、可复用、可配置**的有向流程 | **当前缺失**，仅有 react loop 的 `max_steps=8` 让 LLM 临场自主编排（隐式、非确定性） |

### 1.3 现有"隐式编排"的缺口
- react loop（`loop.py:733` `while steps < cfg.max_steps`）让 LLM 自主决定调哪些 tool、顺序、依赖——**步骤顺序不可固化、不可复用、不可审计为确定性流程**。
- Skill 是"说明式"（告诉 LLM 思路），不是"执行式"（引擎按图跑）。
- 没有"把多个 task 串成可复用流程"的载体，每次都要 LLM 临场发挥，业务一致性无法保证。

### 1.4 本方案解决的差距
引入 **Workflow 层**：把已注册 task（含 MCP 工具、asr、skill 的 `run`、原生 tool）编排成 **DAG**，由 **确定性引擎** 按图执行，可复用、可配置、可触发、可组合。

## 3. 工作流编排架构设计

### 3.1 定位与边界（正交）
- **Workflow ≠ 重新定义能力**：节点直接复用 `ctx.tasks` 已注册的 task，**不重复造能力层**。
- **Workflow ≠ Skill**：Skill 是"说明式"（content 给 LLM 看，LLM 临场决定步骤）；Workflow 是"执行式"（DAG 固化，引擎按图确定性执行，顺序/分支不靠 LLM 临场发挥）。
- **Workflow 可消费 MCP/Skill**：节点可直接引用 `mcp.skills.*`、`asr.transcribe_file`、某 skill 的 `run`。

### 3.2 核心抽象：Workflow = DAG of registered tasks
```yaml
# data/workflows/<name>.yaml
name: meeting_transcribe
title: 会议录音转写与纪要
input:                       # 工作流级入参 schema（复用 tasks 的 schema 语法）
  audio_path: { type: str, required: true }
steps:
  - id: transcribe
    task: asr.transcribe_file          # 直接引用已注册 task
    inputs: { path: "{{ input.audio_path }}" }
  - id: summarize
    task: llm.summarize                # 引用 LLM 节点（见 §7 待确认 Q4）
    inputs: { text: "{{ transcribe.segments }}" }
  - id: save
    task: fs.write
    inputs: { path: "{{ input.audio_path }}.md", content: "{{ summarize.text }}" }
```
- **节点 = 引用一个已注册 task 名 + 输入映射**。
- **数据流转**：`{{ node_id.field }}` 引用上游节点输出字段；`{{ input.x }}` 引用工作流入参。引擎做变量解析与传递。
- **DAG 天然支持并行叶子**（拓扑排序即可），分支/条件在阶段 2 引入。

### 3.3 执行引擎（WorkflowEngine）
- 输入：工作流名 + 入参。
- 调度：拓扑排序 → 逐节点 `ctx.tasks.invoke(node_task, **resolved_inputs)`。
- **关键复用**：因为走 `ctx.tasks.invoke`，**guard 裁决 / schema 校验 / owner 审计 / 预算记账全部自动继承**（components.py:10-11 已声明此纪律）。工作流不必重写护栏。
- 节点输出写入工作流上下文（变量作用域），供下游引用。
- 执行状态持久化：每节点结果、进度、失败点（落 `agent_events` 或专用表），支持断点续看（不强制断点续跑，阶段 2 再议）。

### 3.4 工作流自身注册成 task（可组合 · 关键设计）
- 每个工作流注册为 `workflow.<name>` 的 task（`owner="plugins.workflow"`，risk 取工作流内最高风险节点的并集或显式声明）。
- 效果：
  - **可 LLM 调用**：react loop 里 LLM 能像调工具一样调 `workflow.<name>`，把"隐式编排"升级为"LLM 选择预定义流程"。
  - **可组合/嵌套**：一个工作流节点可引用另一个 `workflow.<other>`，形成工作流复用层级。
  - **与 MCP/Skill/tool 同构**（都是 task），统一经 `ctx.tasks.catalog()` 暴露。

### 3.5 三层触发入口
| 入口 | 形态 | 适用 |
|---|---|---|
| **① 交互式（LLM 调）** | 工作流注册成 `workflow.<name>` task，LLM 在对话里调用 | 对话中按需触发，复用现有 tool-call 机制，零新增端点 |
| **② HTTP 端点** | `POST /api/workflows/<name>/run`（body=入参），返回 run_id + 状态流 | 前端按钮、外部系统、自动化脚本触发 |
| **③ 事件触发（阶段 3）** | 目录监听（data/inbox 新文件）、消息队列、cron 定时 | "放录音即自动跑""每日定时报表"等无人值守场景 |

### 3.6 持久化与配置归属
- **定义文件**：`data/workflows/<name>.yaml`（参照 `data/skills/` 文件型范式，简单、可版本化、可被 config_store 范式读写）。
- **运行态**：工作流实例（run）状态经 `durable` 落 `agent_events`（复用既有审计表，避免新表）。
- **权限/启用**：在 `agent_plugin_config.json` 增 `workflows` 节（enabled 清单、域裁剪）。

### 3.7 分层归属（严守铁律）
| 组件 | 层 | 路径 | 理由 |
|---|---|---|---|
| 引擎核心（DAG 调度、变量作用域、拓扑） | **system**（中性能力，与 tasks 同层） | `agent/sys/workflow.py` + `Services.WORKFLOW`（经 `agent.api` 导出） | 引擎是中性编排能力，不持业务词；插件层经 api 取用 |
| 文件加载 / HTTP 端点 / 前端 / 注册具体工作流为 task | **business/plugins** | `agent/plugins/workflow/__init__.py` + `run/chat.py` 端点 + `web/src/views/WorkflowsView.vue` | 业务装配、传输、UI |

> 注：凡要被插件/传输层构造的对象落中性层（本方案引擎落 `sys/`），业务配置与端点落 `plugins/`，与 tasks 既有的 `sys/tasks.py` + 各 `plugins/*` 注册范式完全一致。

## 4. ASR 接入工作流的端到端示例（呼应原始需求）

原始需求"ASR 整合进工作流"在本方案下变成：**定义一个消费 `asr.transcribe_file` 的工作流**。

```yaml
# data/workflows/meeting_transcribe.yaml
name: meeting_transcribe
title: 会议录音 → 转写 → 纪要 → 落盘
input:
  audio_path: { type: str, required: true }
steps:
  - id: transcribe
    task: asr.transcribe_file
    inputs: { path: "{{ input.audio_path }}", min_segment_sec: 0 }
  - id: summarize
    task: llm.summarize
    inputs: { text: "{{ transcribe.segments }}" }
  - id: save
    task: fs.write
    inputs:
      path: "{{ input.audio_path }}.md"
      content: "{{ summarize.text }}"
```
- 触发：对话里说"把 C:\测试\录音.mp3 转写并出纪要" → LLM 调 `workflow.meeting_transcribe`；或前端工作流页点"运行"；或目录监听自动触发。
- 全程复用 ASR 已注册工具 + 现有 guard/审计，**不重复造轮子**。

## 5. 分阶段实施计划

| 阶段 | 内容 | 交付 | 风险 |
|---|---|---|---|
| **阶段 0（引擎 + 注册）** | `agent/sys/workflow.py` 引擎核心（DAG 加载、拓扑、变量解析、`ctx.tasks.invoke` 调度）；`plugins/workflow` 加载 `data/workflows/*.yaml` 并注册成 `workflow.<name>` task；单测（拓扑/变量解析/嵌套） | LLM 可在对话里调 `workflow.<name>`；工作流可组合 | 低（复用 tasks 基座） |
| **阶段 1（HTTP + 前端）** | `POST /api/workflows` 列表 + `POST /api/workflows/<name>/run`；`WorkflowsView.vue`（列表/查看/触发/状态）；`agent_plugin_config.json` 增 `workflows` 节 | 前端可管理、可一键触发；外部可 API 触发 | 中（前端 + 端点） |
| **阶段 2（高级编排）** | 分支/条件节点、并行 fan-out、子工作流、运行态可视化（逐节点进度/结果） | 复杂业务流程可编排、可观测 | 中 |
| **阶段 3（事件触发 + 外部协同）** | 目录监听 / cron / 消息队列触发；与飞书 MCP 双向（飞书触发工作流 / 工作流调飞书） | 无人值守自动化；呼应飞书 MCP 方案阶段 4 | 中高 |

## 6. 契约 / 测试 / 风险

**契约影响**
- 新增 `Services.WORKFLOW`（core 中性接缝）。
- 新增 HTTP 端点（阶段 1），需在 SSE/API 契约文档补登记。
- `workflow.<name>` 进入 `ctx.tasks.catalog()`，自动受 `tool_domains` 白名单与 guard 管辖。

**测试方案**
- 引擎单测：DAG 拓扑排序、变量解析（`{{ node.field }}`）、嵌套工作流、失败节点隔离。
- 回归：现有 `test_services_contract`（新增 Service 键须进 `ALL` frozenset）、`test_plugin_decoupling`（分层守卫）。
- 可选 e2e：定义示例工作流 → 经 LLM 或 HTTP 触发 → 断言节点执行与产物。

**风险与回滚**
- 全部经 config 开关（`workflows.enabled` 默认 `false`，保持零影响），符合既有"新增能力 opt-in"纪律。
- 引擎落 `sys/` 中性层 + 注册落 `plugins/`，不破分层铁律。
- 工作流节点复用 `ctx.tasks.invoke` ⇒ 既有护栏/审计不丢失。

## 7. 待确认项（需用户拍板）

1. **工作流定义格式**：先 YAML 文本文件（`data/workflows/*.yaml`，简单、可 diff、可版本化），还是直接上可视化 DAG 编辑器？**建议先 YAML**。
2. **触发范围**：阶段 0/1 先做"LLM 调 + HTTP 端点"，事件触发（目录/cron）是否纳入阶段 1 还是留到阶段 3？
3. **引擎落点**：确认 `agent/sys/workflow.py`（system 层，与 tasks 同层）是否接受，还是你更希望纯 `plugins/` 内闭环？
4. **内嵌 LLM 节点**：确定性 DAG 里是否需要"LLM 自由生成"节点（如示例的 `llm.summarize`）？若需要，要新增一个 `llm.generate` 之类的 task 把 LLM 能力也纳入 task 体系；若不需要，工作流只能编排"已有 task"，纯 LLM 步骤仍靠 Skill 说明式。
5. **前端工作流页优先级**：是否需要和 ToolsView/SkillsView 同级的 `WorkflowsView.vue`（列表/编辑/触发/状态）？还是先只做后端 + HTTP，前端后补？
6. **权限粒度**：工作流是否受 `tool_domains` 白名单裁剪（每个 `workflow.<name>` 作为独立域），还是工作流整体一个开关？

## 8. 与飞书 MCP 的协同（呼应阶段 4）

飞书 MCP 方案（待审批）里"阶段 4 飞书工作流"在本方案下变为：**飞书既能作为工作流的一个节点（调飞书 API），也能作为工作流的触发源（飞书消息/审批触发 agent 工作流）**。两者正交——飞书桥负责"能力接入"，本工作流层负责"把这些能力（含飞书）编排成业务"。

## 9. 结论
- 工作流编排**不需要重建能力层**——`ctx.tasks` 已是统一基座，工作流 = "DAG of registered tasks"。
- 核心交付是**引擎（system 层）+ 文件型定义（data/workflows/）+ 注册/端点/前端（plugins/）** 三层。
- 工作流自身注册成 `workflow.<name>` task ⇒ 与 MCP/Skill/tool **同构、可组合、可 LLM 调用**，构成你想要的"三支柱"闭环。
- 建议从**阶段 0（引擎 + 注册）** 起步，零风险跑通"LLM 调工作流"，再逐步上 HTTP/前端/高级编排/事件触发。
