## 0. 一句话结论

沙箱在本项目的正确形态是**准入控制 + 审计**，落成一个**目录插件**（复用既有 waterfall

## 2. 定位（写清楚不做什么）

**是**：一个**准入网关**——回答"这个会话能不能调这个外部工具"，并逐次留痕。
**不是**：进程隔离/系统调用沙箱。理由：项目定位是"操作本机的助手"，真隔离会自废武功
（浏览器/窗口自动化本来就要求访问宿主），且跨平台成本高、平台相关。

> 纪律：本方案**不承诺**任何进程级隔离。若将来要多租户云服务形态，那是独立议题
> （路线图 #7 的另半 + 产品定位决策），届时应新建文档而不是扩写本文。

## 3. 已裁定的决定

1. **默认姿态 = 放行 + 审计**（用户裁定）：启用后 MCP 调用照常通过，但每次裁决落 durable
   账本（可按 `request_id` 串起来查，#5 已提供该能力）。先看清"谁在用什么"，再逐步收紧。
2. **作用面 = 工具级模式准入 + 审计**（用户裁定）：不做参数改写，不做子进程隔离。
   **不动 MCP 桥、不动两个 MCP 插件**（注册处一行不改）。
3. **接入设置页**（用户批复，**已实施**）：`targets` / `default` / `allow` / `deny` 四项
   容器级与会话级均可写，且受 schema 校验（顺次消除 §1 F11 的两个落差）。
4. **审计事件另立**（用户批复，**已实施**）：用 `agent/sandbox/decision`，
   **不复用** `agent/permission/decision`。理由：沙箱的判据是「名称模式 + 会话」，
   guard 的判据是「权限矩阵」——**两套判据混在一张事件里就分不清是谁拒的**。
   代价（已知并接受）：「权限」视图的"最近裁决"不再含沙箱行，改由「事件」视图的
   `agent/sandbox` 过滤项查看（已加该过滤项）。

## 4. 设计

### 4.1 挂点与顺序

挂 `agent/tasks/pre-execute`，`prepend=True` ⇒ **最先裁决**。两条理由：

1. 沙箱是"能不能进"的前置门，先于权限矩阵；
2. 若将来做参数改写，必须在 guard/approval **看到参数之前**完成（事实 4/5）。

已知代价：沙箱拒绝时 guard 的审计行不会产生（链被短路）。**沙箱自己落审计**，
不依赖 guard，故审计不丢。

### 4.2 裁决算法（纯函数，便于穷举单测）

```
deny 名单 → allow 名单 → risk 覆盖 → default
```

- 顺序固定：**显式黑名单是"硬"的，白名单不能穿透它**（与 guard 的"deny 名单优先"同向，
  避免两份配置互相打洞）。
- 返回 `(裁决, 命中理由)`；理由会写进审计与拒绝消息，便于排查"为什么被拦"。
- ⚠️ **risk 维度的实际效力受 F9 限制**：MCP 工具全是 `write` ⇒ `risk: {"write": …}`
  等于"对全部 MCP 工具一刀切"。要按工具细分只能靠**名称模式**（`deny`/`allow`）。
  是否加一张"按名称模式推断有效 risk"的覆盖表 → 见 §8 开放问题 4。

### 4.3 作用域（哪些工具归它管）

`targets`：工具名模式列表，**默认 `["mcp.*"]`** ⇒ 默认只管 MCP，不干扰其它工具。
不在作用域 ⇒ **完全不过问**（直接 `next()`），避免它变成"第二个 guard"去改变
非 MCP 工具的现有行为。

### 4.4 模式语法

只支持**尾部 `*`**：`mcp.*`（某个桥的全部工具）、`*`（全部），其余精确名。
**刻意不用正则**：这份配置是运维手写的，语义越简单越不会错配。

### 4.5 配置面（容器级 + 会话级）

容器级 `config["agent"]["sandbox"]`；会话级覆盖走既有 `plugins.sandbox` 节
（`SESSION_CFG_VIEW` + `section_of`，与 G2 的 ConfigStore v2 同构）⇒ **天然按会话隔离**，
不需新存储机制。

```yaml
agent:
  sandbox:
    targets: ["mcp.*"]        # 受管辖的工具名模式
    default: allow            # allow（默认，保持现状）/ ask / deny
    allow: []                 # 白名单模式
    deny:  []                 # 黑名单模式
    risk:  {}                 # 按风险级覆盖：{"write": "ask", "danger": "deny"}
```

生效值 = 插件默认 ← 容器级 ← 会话级（后者优先）。

**写入途径（接入设置页后已打通，v0.3）**：

| 途径 | 容器级 | 会话级 |
| --- | --- | --- |
| 设置页 / `POST /api/settings` | ✅（`scope=container`，触发容器重建） | ✅（`scope=session`，下个请求自然生效、**不重建**） |
| 手改 `data/agent_plugin_config.json` 的 `container` | ✅ | — |
| 手改同文件的 `sessions.<会话键>` | — | ✅（⚠️ 键名拼错**静默失效**：会话桶不经过 `validate_config`；走设置页/API 则受校验） |
| 程序化 `build_agent(config=…)` | ✅ | — |

### 4.6 审计落点

每次在作用域内的裁决落 **`agent/sandbox/decision`**（durable 直写，**另立事件**，见 §3.4），
字段：`who/level/target/risk/decision` + `by: "sandbox"` + `session` + `reason` + `at`。

**可见性**：① 「事件」视图新增 `agent/sandbox` 过滤项（`filterEvents` 用 `startsWith`
匹配，前缀即可）⇒ 沙箱轨迹按前缀筛出来；② `#5` 之后该账本带 `request_id`/`session`
⇒ 可按一次请求把外部工具轨迹串起来查（`/api/events?request_id=<rid>`）。
**代价**：「权限」视图的"最近裁决"只列 `agent/permission/decision`（SQL 里写死），
故**不再含沙箱行**——这是"另立"的必然结果，已在 §3.4 登记为已知代价。
另按 #5 的计数器惯例累加 `agent_sandbox_decisions_total / allowed / denied`。


### 4.7 `ask` 的诚实说明

waterfall 里"要问人"必须由**下游** approval 裁决，而 guard 的 prepend 已先短路 ⇒
本插件的 `ask` 与 guard 同款：**拒绝 + 在理由里点名**（"要放行请加入 allow 白名单，
或改由审批插件裁决"）。真 ask 需把该裁决权交给 approval，属后续项，本批不做。

## 7. 明确不做 / 风险

**不做**：

1. **参数改写 / 路径重定向**——机制现成（事实 4），但要动两个 MCP 插件的注册处
   （声明哪些参数是路径），且各桥参数语义不一致（playwright 的 selector 与 windows 的
   path 不可同构处理）。等 MCP 工具清单与参数语义稳定后再做。
2. **进程级隔离**——见 §2。
3. **真 ask 链路**——见 §4.7。
4. **启用到仓库的 `data/agent_plugin_state.json`**——不动运行态；启用方式由你决定。
5. **设置页 / API 写入通道**——见 §5 可选项与 §8 开放问题 1。

**风险**：

### 8.2 启用 vs 不启用（决策依据，保留备查）

即：要不要把 `plugins.sandbox` 写进 `data/agent_plugin_state.json` 的 `enabled` 列表
（目录插件默认关，这是唯一"打开"的动作）。**注意该文件被 gitignore ⇒ 不进仓库。**

**启用**的好处：

1. **出事能查**——这是最大的不对称收益。默认姿态是"放行 + 审计"，**行为风险为零**，
   但收益是"每一次外部工具调用都有 rid 可追"；事故往往只在**没记录**之后才查得到。
2. **为收紧策略提供数据**：先看真实的工具名与调用频次，再决定黑名单——而不是凭想象配。
3. 设置页会出现该分区 ⇒ 用户知道"这个旋钮存在"（未启用时页面显示明确提示，不会产生
   "以为受保护"的错觉）。

**不启用**的好处：

1. 账本不涨：每个 MCP 调用多 1 行 durable（`agent_events` 无归档，见 §11 结构债）。
2. 零额外开销：每次工具调用少一次 waterfall 遍历 + 一次落库写。
3. 保持"本机运行态与仓库默认一致"的整洁（不引入只有本机才有的行为差异）。

**代价与风险**：

- 启用后若有人把 `default` 误设为 `deny`，MCP 全挂——但拒绝消息带**命中理由**，
  且 `ask`/`deny` 都可被白名单覆盖；属可接受的配置错误。
- 若日后要按读写分层，会撞上 F9（MCP 全是 `write`）——与启不启用无关。

**裁定：启用**。理由是"零行为风险 ↔ 事故可追溯"这个不对称太划算，而成本只是账本多几行。
启用时**必须同时**把"启用 ≠ 已收紧"写进设置页与插件说明，避免安全错觉（**已写进页面提示**）。

### 8.3 risk_map 加 vs 不加（决策依据，保留备查）

`risk_map` 形如 `{"mcp.playwright.navigate": "read"}`——**纯插件内推断**，不改 MCP 插件，
让 `risk: {"read": "allow", "write": "deny"}` 这类意图真正可用（因为 F9：MCP 全是 `write`）。

**加**的好处：

1. 让 `risk` 维度从"一刀切"变成"按读写分层"，策略更贴近人的意图
   （"只读类放行、写类问人"比逐个工具名列 deny 更好读）。
2. 不只修 MCP：任何**注册时未声明 risk** 的插件都会落到 `write` 档，
   于是 guard 的 `risk: {write: deny}` 会**一刀切误伤**它们。`risk_map` 是插件侧的补救。
3. 零侵入：推断留在本插件内，MCP 插件注册处不动。

**不加**的好处：

1. **风险方向不对**：`risk_map` 的值是"**猜**"的——本插件并没有读 MCP 协议去判断哪个工具
   真的只读。猜错的后果分两种，但**方向不对称**："把只读当写"只是多拒一次（可接受），
   "把写当只读"是**放行本该拦的操作**（不可接受）。所以这张表的**出错方向必须被约束**。
2. **会过期**：MCP 工具清单随桥升级变化，`risk_map` 需人工维护；过期条目静默失效
   （与 F11 的"会话级拼错静默失效"同型——都是"看起来配了、其实没生效"）。
3. **多一层间接**：现在是 `名称模式 → 裁决`（一步）；加表后是 `名称模式 → risk → 裁决`（两步），
   排查"为什么被拦"要多想一层，配置面也多处一栏。
4. **收益有限**：多数场景 `deny: ["mcp.windows.*"]` / `allow: ["mcp.playwright.*"]` 已经够用；
   真要按读写分层，直接列工具名**更准确**（没有推断误差）。

**裁定：不加**。理由见上（风险方向 + 过期 + 间接层 + 收益有限），启用条件见 §8.1 第 4 行。
