## 0. 一句话结论

两方案的差别**不在"隔离谁"**，而在**"会话键（选择器）能否抵达读取方"**。

代码事实决定了：**请求级 child 到不了三个关键读取方**——它们拿到的都是**装配期捕获的容器 ctx**，
child 从未进入它们的视野。而事件总线的纯度契约（`strict_payload`）**禁止**把 ctx 塞进 payload 送进去。

⇒ **ContextVar 胜，且不是"便宜一点的次优选择"，而是"在不改事件总线契约的前提下唯一能到位的做法"。**

另需更正一处提法：严格说 R1 的第二候选**不是** child（child 的装配作用已被 G2 的 `GovernorRouter` 吃掉），
而是「把 identity 显式传进旁路」。详见 §6。

## 1. 问题的准确形状

`SESSION_KEY` 是纯粹的**选择器**（"此刻是谁"），它有三读两写（生产代码全量）：

| 类型 | 位置 | 读取方如何拿到 ctx |
| --- | --- | --- |
| 写 | `agent/sys/chat.py:198` | 入参 `ctx` |
| 写 | `agent/plugins/react/loop.py:431` | 入参 `ctx` |
| 读 | `agent/sys/budget.py:53`（经 `:193/:229/:274`） | **闭包变量 `ctx`**（apply 期捕获） |
| 读 | `agent/plugins/context/router.py:53` | **`self._ctx`**（apply 期捕获） |
| 读 | `agent/plugins/approval/__init__.py:209` | **`self._ctx`**（apply 期捕获） |

关键事实：

- **插件永远拿到 root ctx**：`agent/core/container.py:282` `await p.apply(self._root)`
  ⇒ `approval/__init__.py:75 self._ctx = ctx`、`budget.py` 的 `_pre/_post/_call_failed` 闭包、
  `router.py:39 self._ctx = ctx` 三者捕获的**都是容器根 ctx**，与"请求"无关。

**这就是全部争点。** 谁能让这三个捕获值感知到当前请求的会话，谁就赢。

## 2. 请求级 child 方案的可行性核实

### 2.1 方案原意（引自方案 §4.2 / §8）

child 仅承载 **config / 服务覆盖**；参数快照型插件在 `apply` 内声明
`ctx.provide(f"session_scope:{SVC}", factory)`，适配层 `run/chat.py` 机械执行遮蔽，**消费方零改动**。

### 2.2 三条硬阻塞（按致命程度排序）

**① 事件总线不接受 ctx 参数——这是硬阻塞，不是难度问题。**

- 分发约定：handler 收 `(*args, next)`：`agent/core/events.py:147` `payload = (*args, next_)`。
  调用点 `agent/sys/tasks.py:163-166` 传的是纯 dict `{"task","kwargs","caller","risk"}`。
- 纯度守卫**默认开启**：`events.py:69 strict_payload: bool = True`；
  `events.py:47-50`：`raise TypeError("event payload must be pure data; got ... 禁止传出内核内部对象（防跨作用域泄漏）")`。
  ⇒ 把 child ctx 放进 payload 会**当场抛错**，且这个守卫的设计意图正是"防跨作用域泄漏"。

后果：`approval._pre_task(payload, next)`（`approval/__init__.py:119`）与
`guard._pre_task(payload, next)`（`agent/sys/guard.py:71`）**在设计上就不可能拿到请求 ctx**。
approval 的会话判定（`:141 session = self._skey()`）只能读 `self._ctx` = 容器。

**② 对读方在"装配期捕获"的场景，child 根本不参与。**

- `budget.py:193/229/274` 用的是 `_pre/_post/_call_failed` 的**闭包 ctx**；
- `router.py:53` 用的是 `self._ctx`；
- `approval/__init__.py:209` 用的是 `self._ctx`。

即使适配层为每个请求造了 child 并沿线传下去，这三处**依然读容器槽**。
child 方案要覆盖它们，只能：改 `self._ctx`（需每请求重建插件实例 → 重新 `apply` → `provide` 冲突、effect 累积），
或改总线契约（同 ①）。两条都不是"插件一行声明"能解决的。

**③ `State` 无父链 ⇒ child 反而**制造**新的语义断裂。**

`agent/core/context.py:106` `self._state = State()`；`child()`（`:231-233`）**不复制 state**。
于是当 `ctx` 是 child 时：

| 键 | 写方 | 读方 | 后果 |
| --- | --- | --- | --- |
| `PERMISSION_MODE` | `approval/__init__.py:87`（root setdefault）、`:222`（root 写） | `loop.py:235`（**经 child 读**） | **plan 模式的工具软裁剪失效**（写工具重新可见） |
| `REACT_RUN_ID` | `loop.py:429`（**写 child**） | `budget.py` pre-call | 账单归组键读不到 |

方案 §2.5 已承认第一列（"每个新会话丢掉 plan/auto 模式"），并给出 §7.3 三选项；
但该表**低估了普遍性**——不是"丢一个模式"，而是**所有"写方在 root、读方在 child"的键全部失联**。

### 2.3 child 方案的**真实价值已被 G2 吃掉**

child 原本要解决的问题是"会话级服务装配"（governor / 窗口参数 / 预算额度）。
G2 已用 `GovernorRouter` 达成，且实现更省：

- `router.py:96-101 __getattr__` 转发 ⇒ 消费方**零改动**、新增方法自动跟随（协议漂移为零）；
- `router.py:79-80`：无会话覆盖时恒返回容器实例 ⇒ **逐值等价**，低风险；
- 预算额度早已是 `dict[会话键,…]` 分桶（`budget.py:101/125/137/270`）⇒ child 对预算**零增益**。

⇒ 若现在采用 child，要么**替换** router（回退到"每会话一实例"，多一层生命周期与缓存面），
要么**并存**（两套选择器，职责重叠）。两者都增加复杂度而收益≈0。

### 2.4 被低估的成本

- 每请求建 child + `teardown()`：新增一条生命周期路径（teardown 失败语义、effect 归属）；
- `session_scope:` 约定的注册键会进入 `Container.keys()` ⇒ 与服务键命名空间混用；
- `State` 三选项（方案 §7.3）每一选项都要额外改动：S1 要求插件显式读写 `ctx.root.state`
  （即**每个**会话级值都要改），S2 引入 seed 白名单配置面，S3 与 2.2 隔离目标相悖。

## 3. ContextVar 方案的可行性核实

### 3.1 隔离粒度天然对齐"一个 HTTP 请求"

| 环节 | 事实 | 是否复制上下文 |
| --- | --- | --- |
| `/api/chat` | `run/chat.py:715` 直接 `await`（uvicorn 每请求一 task） | 天然隔离 |
| `/api/chat/stream` | `run/chat.py:764 asyncio.create_task(_worker())` | **复制**（创建时刻） |
| `emit` 的 async 监听 | `events.py:115 asyncio.create_task(...)` | **复制** |
| `waterfall` 链 | `events.py:147-155` **inline await** | 同 task，直接可见 |
| 后台压缩任务 | `sys/chat.py:246 asyncio.create_task(self._safe_compress(ctx, session_id))` | **复制** |

⇒ 五个读写点**全部落在"发起写的那条请求链"**内部，ContextVar 全覆盖；无一处跨 task 逃逸。

### 3.2 同类问题的既有先例（同一文件、同一理由）

`agent/core/context.py:32-37`：

> 当前插件 id：容器在装配/启动窗口内注入…**用 ContextVar 而非 ctx 上的普通属性——并发安全（多轮可并行互不串扰）**

即：本项目**已经**为"共享槽被并发覆盖"这一模一样的病因开过同一味药，并把理由写进了注释。
`CURRENT_PLUGIN` 与 `SESSION_KEY` 属同一类需求（"此刻在谁的处理链里"）。

### 3.3 兼容性：现有测试**零改动**

`grep "\.state\[" agent/tests/*.py` = **20 处 / 6 文件**（如 `test_budget_reset.py:31` 写 `SESSION_KEY`、
`test_react.py:256` 写 `permission_mode`、`test_followup_topics.py:78` 写 `LLM_COST_RATIO`）。
读时采「**ContextVar 优先、缺失回退 `ctx.state`**」⇒ 这些写法**全部继续有效**。

### 3.4 已核实的残余风险（三条，均可处置）

| # | 风险 | 代码事实 | 处置 |
| --- | --- | --- | --- |
| 1 | 线程池不继承 ContextVar | `approval/providers.py:96 await asyncio.to_thread(...)` | 该线程只做阻塞 stdin 读，不读会话键；**约定**"读会话键的代码不得入线程池"，并在文档写明 |
| 2 | 入口漏设 | **`/api/approval/mode`（`run/chat.py:874`）没有调用 `_identity()`** | 改为从 header/body 解析身份（顺带修掉下述越权）；其余 12 处 `_identity` 调用（`:713/736/791/827/866/895/932/940/953/1120/1147`）构成单一漏斗，在其中一处设即可全覆盖 |
| 3 | 隐式通道难以察觉 | 无 | 加守卫测试（如断言"经 `/api/chat` 后 `current_session_key()` 非空"）；写入 `agent/plugins`/`sys` 的契约注释 |

### 3.5 顺带发现（与 R1 同源，且**安全相关**）

`PERMISSION_MODE` 是**会话级的值，却存在容器级槽**：

- 写：`approval/__init__.py:222 ctx.state[PERMISSION_MODE] = mode`，调用方 `run/chat.py:888 svc.set_mode(c.root, mode)`
- 读：`approval/__init__.py:215`（审批判定 `:121 mode = self.mode()`）、`loop.py:235`（工具软裁剪）、`react/__init__.py:93`（状态上报）

⇒ **A 会话把档位切到 `bypass`，会同时打开 B 会话在跑 run 的审批闸**（`decide()` 首行 `mode == "bypass"` 直接放行，
`approval/__init__.py:122-123`）。这比"预算记错桶"更严重，因为它**放行本应被问的写操作**。

**结论：ContextVar 只解决"谁在问"（选择器），不解决"值存哪"（存储）。**
`PERMISSION_MODE` 必须**按会话分桶**（`dict[session_key, mode]`，与 budget 同款），
`REACT_RUN_ID` 同源同理。⇒ **建议 G2 范围从"S-CHANNEL 选择器"扩为 `SESSION_KEY + REACT_RUN_ID + PERMISSION_MODE(值需分桶)`。**

## 4. 逐维对照

| 维度 | 请求级 child | 会话键 ContextVar |
| --- | --- | --- |
| 新增内核面 | `session_scope:` 注册约定 + `_ctx_for()` + `State` 语义三选一 | 1 个 ContextVar + 2 个函数 + `api` 导出 |
| 插件改动 | 每个参数快照型服务 1 行声明；**但 budget/approval/router 仍须另改**（拿不到 child） | 3 处读包装（一行/处） |
| 适配层改动 | 每请求建 child + teardown 生命周期 | `_identity()` 内 1 行 |
| **能否覆盖 approval** | ❌（须改总线契约或每请求重建实例） | ✅ |
| **能否覆盖 budget** | ❌（闭包 ctx） | ✅ |
| 能否覆盖 router | 需替换/并存 G2 成果 | ✅（正交，router 继续负责选实例） |
| 状态语义风险 | **高**：`State` 无父链 ⇒ plan 软闸、账单归组键同时失联 | 无（不动 `State`） |
| 与既有测试 | 需处置 S1（插件改显式 root 读写）⇒ 改动面大 | **20 处零改动**（回退兼容） |
| 回滚口径 | 删 `_ctx_for`（但已改的插件声明要一并撤） | **删 set 调用即回退**（回退分支仍在） |
| 隔离强度 | 作用域级（**理论**最强） | task 级 = 请求级（**实际**等价） |
| 与 2.2 既有决策 | 2.2 明确**否决**过 `provide(Services.SESSION)` 通道（改显式参数） | 不与之冲突（主链路仍显式传参） |
| 反解耦风险 | `session_scope:` 为字符串约定，无类型/守卫约束 | 原语经 `agent.api` 导出，受分层守卫约束 |

### 4.1 为什么"作用域级更强"在本题**不成立**

隔离强度 **≠ 隔离机制的粒度**，而 = `机制粒度 × 读取方可达性`。

child 的隔离是"**谁拿到 child，谁才被隔离**"。而三个关键读取方（budget / approval / router）
**全都没有拿到 child**，于是它给出的**实得隔离度低于** ContextVar——后者虽只有 task 粒度，
但读取方**无论怎么拿到自己那个 ctx，都能读到正确的键**。

这是本分析最重要的一处反转：**粗粒度但可达，胜于细粒度但不可达。**

## 5. 建议

1. **R1 采用 ContextVar**（原语置 `agent/core/session.py` 或同目录，经 `agent.api` 导出）。
2. **主链路不动**：`chat.send → react.run` 的显式 `identity=` 参数线程化保持现状（`loop.py:392-396` 的设计意图不变）。
   ContextVar 只补**旁路**（事件回调 + 装配期捕获 ctx）这三处。
3. **`PERMISSION_MODE` 按会话分桶**（§3.5）——列为 G2 必做项，非可选。
4. **不采用请求级 child**；方案 §4 的核心支点（`session_scope:` + 工厂遮蔽）**建议就地归档**，
   其目标由 G2 的 router 承接、其残余需求由 ContextVar 承接。
5. 实施顺序：先写**跨会话并发测试**并确认"修复前应失败"（`test_session_concurrency.py`），
   再落地原语与 5 个接入点，最后全量回归。

## 6. 一处提法更正（供后续文档引用）

严格说，**R1 的真正第二候选不是请求级 child**，而是「**把 `identity` 显式传进旁路**」：

- 与主链路既有风格一致（2.2 已选显式参数）；
- 但旁路的两条通路都堵：事件回调**签名固定**（`(payload, next)`）+ payload 必须纯数据；
  装配期捕获的 `self._ctx` 无法在调用时替换。
⇒ 要打通需改 `tasks.invoke` / 事件契约 / 插件实例生命周期，**成本高于 ContextVar**，
且 ContextVar 的失败模式（缺失即回退默认）比"签名改造"更可控。

因此本文件的结论不变，但**推荐措辞**为：
> 旁路会话键的强隔离，选 **ContextVar（task 级）**；child 属已被 G2 取代的上一代方案，不再作为候选。
