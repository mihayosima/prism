# 生产就绪度评估（2026-10-01）

> 基于实际代码核实的评估，非印象判断。每项结论都标了 `file:line` 或核实方式。
> 只读评估，未改动任何生产代码。

---

## 0. 结论

**内核已达生产级，甚至在若干维度超过多数同类项目；缺的是「生产化外壳」，不是智能能力本身。**

这个项目的强项集中在**运行时内核**：对称卸载、SSOT 契约、软降级纪律、审计脊柱。
441 个测试里有相当比例是 AST 静态契约守卫——这在同类项目里极罕见，防回归能力很强。

短板集中在**对外服务化**：单会话、无租户、无沙箱、无健康检查、无优雅退出、无重试。

一句话：**这是一个"内核可靠、外壳还是原型"的状态。**

## 2. P0 — 阻断上线

### P0-1 单会话、无用户体系

```python
agent/run/chat.py:405    session_id = uuid.uuid4().hex[:8]     # build_app 里生成一次
```

- **全应用共用一个会话**：所有浏览器/用户共享同一份 chat history、同一份短期记忆、同一份预算累计。
- `/api/session/reset` 会清掉所有人的会话。
- 无认证（只有一个全局 `--token`）、无租户隔离、无配额归属。
- **改造量**：这是最大的一项。需要把 session 从"应用级常量"下沉为"请求级参数 + 存储键维度"，
  并让 short_term / work_memory / budget 的键都带上租户维度。

### P0-2 MCP 工具等同宿主权限，无沙箱

- `windows_mcp` 的 FileSystem / PowerShell 直接操作**宿主**文件系统。
- 唯一防线是 guard 的权限裁决，而默认值是全放行：

```python
agent/profiles.py:70    "permissions": {"default": "open", "task_allow": ["*"], ...}
```

- approval 插件能做"人在环中"，但是 opt-in，且 `approval.default` 虽为 `deny`，
  工具侧走的是 `permissions` 而非 `approval`。
- **改造量**：架构级。需要把 MCP 子进程放进容器/沙箱，配只读根、网络出口白名单、
  工作目录限制。代码层面能做的（收紧默认权限、强制审批）只是缓解，不是隔离。

### P0-3 SQLite 单文件，无法多实例

- `db_path: data/agent.db`（WAL），业务表与审计脊柱 `agent_events` 同库。
- 无法水平扩展；多副本部署会写冲突。
- **改造量**：中。审计脊柱与业务库分离（前者可换消息队列/OLAP），业务库换 Postgres。

## 3. P1 — 上线即痛

### P1-1 优雅退出只覆盖 Ctrl+C，不覆盖 SIGTERM ★

```python
agent/run/chat.py:925    server.install_signal_handlers = lambda: None
agent/run/chat.py:929    except (KeyboardInterrupt, asyncio.CancelledError):
agent/run/chat.py:932    finally: await c.teardown()
```

- 禁用了 uvicorn 自带信号处理器，却只 catch `KeyboardInterrupt`（SIGINT）。
- 容器 / K8s / systemd **默认发 SIGTERM** ⇒ `c.teardown()` 根本不执行
  ⇒ MCP 子进程变孤儿（本项目记忆里已实证过孤儿进程累积 6 天）。
- **改造量**：几行。注册 SIGTERM/SIGINT 双信号，触发 `server.should_exit` 后走既有 teardown。

### P1-2 LLM 调用零重试、零熔断、零降级

```python
agent/sys/llm.py:210    self._client = httpx.AsyncClient(timeout=90.0, ...)
```

- 全文搜索 `retry|backoff|tenacity` 无结果——只有超时，没有任何重试。
- 一次 429 / 5xx / 网络抖动即整轮失败；无备用模型切换、无断路器。
- `LlmProvider` 契约明写"失败一律 raise"（语义正确），但调用方没兜底。
- **改造量**：半天。加指数退避重试（仅对可重试错误）+ 超时后降级。

### P1-3 无健康检查与指标端点

- 已核实的端点清单里**没有** `/health`、`/metrics`、`/ready`。
- 无法接入负载均衡存活探针、容器 readiness、Prometheus 抓取。
- `/api/status` 是业务状态，不是健康检查（且它会触发业务查询）。
- 启动完成只靠 `print(..., file=sys.stderr)`，没有结构化就绪信号。
- **改造量**：半天。

### P1-4 可观测性停在"能审计"，不到"能运维"

- 已有：审计脊柱、预算账、口径漂移、水位遥测——**这部分做得好**。
- 缺：结构化日志（现为 `logger.warning` + print）、trace/request id 贯穿、
  指标导出、告警规则。
- 一次请求横跨 react → llm → tasks → MCP 多个插件，目前无法串联成一条 trace。
- **改造量**：数天。

## 5. 最短路径建议（按性价比排序）

| # | 动作 | 工作量 | 收益 |
|---|---|---|---|
| 1 | SIGTERM 优雅退出 | 几行 | 消灭孤儿 MCP 进程，容器可管 |
| 2 | `/health` + `/metrics` | 半天 | 可接入探针与监控 |
| 3 | LLM 重试 + 超时降级 | 半天 | 抖动不再整轮失败 |
| 4 | 收紧 `permissions.task_allow` 默认值 | 几行 | 从"默认全放行"改为显式白名单 |
| 5 | 结构化日志 + request id 贯穿 | 数天 | 可排查、可串联 |
| 6 | 会话/租户模型 | 最大 | 从单用户玩具变多用户服务 |
| 7 | MCP 沙箱 | 架构级 | 真正可对外 |

前 4 项加起来约一天，能消掉大部分"上线即痛"。
第 6、7 项决定了它**能不能对外服务**，而不是能不能跑起来。
