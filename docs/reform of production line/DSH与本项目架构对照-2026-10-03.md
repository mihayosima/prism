## 0. 结论摘要

**三句话版本**：

1. **DSH 比我们大 30 倍，但多出来的是"平台能力"不是"护栏"。**
   453K 行 TypeScript vs 我们 14,930 行 Python。但它的沙箱/审批/权限三件套加起来
   只占它 6 个 package；剩下的是 desktop 壳、cordis 动态插件、浏览器端 VM、子代理六后端、
   workflow VM、目标/后台任务、技能系统 —— **这些我们没有，也不需要**。

2. **在"护栏"这条轴上，DSH 的设计比 ours 精确一个量级，但我们的覆盖面更宽。**
   它把"模式 / 强度 / 谁问人 / 能不能重试"四件事切成互不重叠的正交旋钮；
   我们把三件事塞进两个瀑布 + 三份配置节，导致上一轮核出的重叠与矛盾。

3. **我们有一项 DSH 明确没有、且难造的东西：上下文治理。**
   `plugins/context/governor.py` 1216 行 + 8 个 context 事件
   （`governed` / `prefix-unstable` / `waterline` / `compact-decided` / `compact-applied` /
   `invariant-violation`）—— DSH 全树没有对应物。**这是我们的差异化资产，不要在照搬 DSH 时丢掉。**

## 2. 插件与能力模型

| 维度 | DSH | 本项目 | 差异性质 |
|---|---|---|---|
| 抽象 | **Cordis 框架**：`ctx` 上挂服务，插件 `apply(ctx)` | 自研 `Container` + `Context.provide/ctx.on` | 同构 |
| 依赖注入 | 声明式 `inject`，双 aggregate 防 `Context` 接口声明合并冲突 | `inject = [Services.EVENTS, Services.DB]` + AST 守卫 | 我们更严（6 条 AST 守卫） |
| 钩子形态 | `ctx.on(name, handler)` + waterfall | `ctx.on(name, handler, prepend=…)` + waterfall | 几乎相同 |
| 目录插件 | 无此概念（全部是 npm package） | `agent/plugins/<pkg>/` 按文件路径加载为 `agent_plugins.<pkg>` | ★ 我们有**双命名空间**遗留（已文档化取舍） |
| 启停 | 装/不装 package | 插件页 `set_enabled()` 写 state 文件 | 我们更成熟 |
| 事件目录 | 无集中目录（能力各自定义） | `core/events_catalog.py` **SSOT，40+ 事件 + 声明 mode + required seam** | ★ **我们更强** |
| 接线校验 | 无对应物 | `REQUIRED_SUBSCRIBER_EVENTS` + `SEAM_SUBSCRIBERS` + 装配期 fail-fast | ★ **我们独有** |

**结论**：我们的插件机制**在工程纪律上强于 DSH**（事件 SSOT + 接线校验 + AST 分层守卫，DSH 全无）。
DSH 的优势在别处 —— 它把插件**做到极致可组合**（沙箱是能力不是某个 executor 的私藏），
而我们把沙箱做成了目录插件，导致它与 guard 语义重叠。**这是可抄的一条。**

## 3. 护栏三件套（用户关心的核心）

### 3.1 角色划分对照

| | DSH | 本项目 | 是否对位 |
|---|---|---|---|
| 判"这次操作要不要做" | `approval`（四态 allow-once/rejected/cancelled/**unavailable**），走 `approval/request` waterfall | **approval**（模式 + 名单 + provider） | ✅ 对位 |
| 判"最多能碰到哪里" | `sandbox`（**不判 allow/deny**，只给 confinement + 自报 `full`/`partial`） | **sandbox**（判 allow/deny/ask + 名单 + risk） | ❌ **错位** |
| 硬规则前置 | 无独立第三层（`dsh-tools` 侧有工具名过滤） | **guard**（权限矩阵 + `LLM_PRE_CALL` + `TASKS_PRE_EXECUTE`） | ★ DSH 没有的第三层 |
| 档位打包 | `permission/preset` = (sandbox mode, approval policy) 二元组 | 无 | ❌ 缺 |
| 升级路径 | 拒后带更宽 `sandbox_permissions` + justification **重试一次**（新 tool call，grant 不持久化） | 无 | ❌ 缺 |

### 3.2 我们的三处错位（已核到行号）

| # | 问题 | 位置 | 后果 |
|---|---|---|---|
| **1** | sandbox 判 allow/deny ⇒ 落在 approval 那一格 ⇒ 与 guard **功能重叠** | 上一轮报告已核 | 每个 MCP 调用两条审计、行为零变化 |
| **2** | guard / sandbox / approval **三处各有一份名单配置**，语义重叠 | `config_schema.py:29-30`（permissions）、sandbox 节、approval 节 | 三份配置互相打洞，无单一真相 |
| **3** | 三个 `ask` 语义**互不相同且都半死** | guard `ask`=拒绝（"留给 approval"）；sandbox `ask`=拒绝（"改由审批插件"）；approval `ask`=真问人 | 两个假问人指向唯一真问人 |

### 3.3 DSH 少一层，我们多一层 —— 但那一层有价值吗

DSH 只有"硬规则在工具侧 + approval + sandbox"；我们有 guard / sandbox / approval。
**多出的 guard 层提供什么？**

| guard 独有 | 沙箱能否接住 |
|---|---|
| `LLM_PRE_CALL` 模型调用裁决（`guard.py:88`） | ❌ sandbox 完全不挂这个 seam |
| 内置工具（非 `mcp.*`）收窄 | ❌ sandbox 默认 `targets=["mcp.*"]` |
| 收窄模式（`default != "open"` 走 allow 白名单） | ⚠️ 语义上能替代 |

⇒ **guard 是唯一覆盖"模型调用"和"内置工具"的裁决者**。这解释了为什么它不该被简单停掉。

### 3.4 拼在一起的完整对照

| 能力 | DSH | 本项目 | 差距 |
|---|---|---|---|
| 硬规则先裁 | 工具侧过滤 | guard（prepend） | ✅ |
| 问人 | approval（**真问**，SSE + provider + 待答表 + 4 端点 + 会话分桶） | approval（同款） | ✅ **我们不弱** |

## 4. 会话日志与回放

| | DSH | 本项目 |
|---|---|---|
| 唯一真相 | **append-only 会话日志**，`findLast(events) ?? default` 折叠出有效状态 | `agent_events` 表（durable 落库） |
| 回放驱动测试 | ✅ 核心测试范式（"回放能重建当时一切"） | ❌ 无回放测试 |
| 崩溃恢复 | 日志本身即恢复源 | ✅ 快照 + `_probe_resume`（Redis 跨重启） |
| 状态折叠 | `findLast(events) ?? default` ⇒ **重启免疫、零外部配置存储** | 部分（`PERMISSION_MODE` 已分桶，但存 `ctx.state` 非日志） |
| 写纪律 | 纯追加，无 UPDATE | ⚠️ `core/audit.py:41-48` **手写 INSERT** 破了自己声明的"零 IO" |

**★ DSH 最值得抄的一条**：**把"有效状态"定义为日志的折叠结果，而不是一个需要同步的变量。**
我们已经有 durable 事件流，缺的只是 `findLast(events) ?? default` 这个读取范式 ——
它能一次性解决"状态存哪、重启怎么恢复、多会话怎么隔离"三个问题。

## 7. 三条不该抄的

1. **不要把模式写进稳定 system prompt。**
   DSH 有一次**公开记录的失败实验**：注入后模型从此拒绝尝试会被拒的操作，
   首个手工会话 12 轮里 5 轮**零工具调用** ⇒ **沙箱变软锁** ⇒ 该方案被移除。
   它最终用的是 capability-neutral 上下文 + append-only 快照（保 KV cache）。

2. **不要为"容器/微虚拟机"档位买单。**
   DSH 把沙箱**定义为只管文件效应**，明确排除网络与进程可见性。
   本机 Docker 可用（WSL2 后端）但那是"进程跑在别处"，属另一层议题。

3. **不要引入 npm package 形态。**
   我们已有目录插件 + 事件 SSOT + 接线校验，DSH 这三项都没有。
   照搬会**丢掉现有纪律**却换不到收益。

## 8. 一句话总结

> **DSH 的护栏设计比 ours 精确一个量级（正交旋钮 + 强度自报 + fail-closed），
> 我们的运行时工程比 DSH 完整一个量级（事件 SSOT + 接线校验 + 上下文治理 + 身份解析 + 断点续传）。**
>
> 该做的是**把 DSH 的护栏纪律搬进我们的既有骨架**，而不是照搬它的形态 ——
> 上一轮核出的重叠、错位、顺序矛盾，全部是"骨架对了、内容没对齐"造成的。
