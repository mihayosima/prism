## 1. 结论摘要（先给判断）

1. **你的修正成立，我上一版判错了**：我把「实现约束（apply 时固化）」误当成了「语义边界」。**上下文窗口、预算在语义上确实属会话/ run 级**，实现应当跟上语义，而不是让语义迁就实现。
2. **但「预算」要再细分一层**：配置名 `max_tokens_per_run` 自带答案——它是 **run 级**；而现状实现是**容器生命周期累计**（`budget.py:17`），比 run 级还粗。**正确顺序是：先落到 run 级（与命名一致、改动最小），再叠加会话累计额度**（后者是新语义，需新增额度维度）。
3. **好消息（成本远低于预期）**：`ContextGovernor` 是**纯参数容器、零跨轮状态**，窗口水位每次现算 ⇒ 「上下文会话级」只需**每会话构造一个 Governor 实例**，不必重写状态机；窗口**内容**本就是 run 级的（`task.chain` 每 run 新建），无额外隔离工作。
4. **坏消息（真正的硬骨头）**：**长期记忆 `agent_memories` 表无 session/tenant 列**（`tables.py:30`），且检索只按 `kind` ⇒ 「不同会话不同长期记忆」是**表结构级改造**（加列 + 迁移 + 全检索点过滤）。系统提示词同理（`SYSTEM_MEMORY` 是容器级单份文件加载）。
5. **对已落地内容的影响**：快赢 #0–#4 与 2.0 **基本不受影响**；**2.1 有 3 处必须返工**（详见 §5），且都是设计时就已埋下的 `_SNAPSHOT_TENANT` 常量与全前缀扫描问题——**不是回归，是 2.1 为 2.2 预留的接缝尚未接通**。

## 2. 粒度模型：修订为**四级**（修正此前的三层）

> 此前 §5.3 提的是 L0/L1/L2 三层；经你裁定，细化为四级，并把「上下文/预算」从 L1 下放。

| 层 | 语义 | 生命周期 | 典型键/状态 | 现状实现是否匹配 |
|---|---|---|---|---|
| **G0 进程级** | 这台进程怎么跑 | 进程 | `db_path`、`provider`/`model`、host/port、`--token`/`--hardened`、MCP 子进程 | ✅ 匹配 |
| **G1 容器级** | 这套装配怎么配 | 容器（rebuild 即换） | **插件启停**、`work_memory.required/ttl`、工具全集 | ✅ 匹配 |
| **G2 会话级** | 这个会话怎么管它的上下文／用什么身份叙事／用什么长期记忆 | 会话 | **上下文窗口参数与层 cap**、**系统提示词 / system_memory**、**长期记忆归属**、`permissions.*`、`react.*`（含 `tool_domains`） | ❌ **现落在 G1**（你指出的正是这点） |
| **G3 run 级** | 这一次 run 花多少钱、留多少链 | 单次 run | **预算额度 `max_tokens_per_run`**、`BUDGET_SPENT` 累计、`task.chain`、run 快照 | ❌ **现落在 G1**（容器累计） |

**关键辨析（预算）**：
- 命名即契约 —— `max_tokens_per_run` = **单次 run 上限**（G3）。
- 「会话级预算」是**另一件事**：一个会话内多次 run 的**累计上限**（G2），当前代码**根本没有这个维度**。
- 建议：**G3 先落地**（把容器累计改成 run 累计，改动最小、与命名一致）；**G2 会话累计**作为叠加额度，属新增能力，单独排期。

- **新增辨析**：预算的正确粒度是 **run 级（G3）**，「会话累计」是**新增维度**而非现有语义的搬家。

### 2.1 返工清单（3 项）

1. **`_SNAPSHOT_TENANT = "default"` 硬编码常量**（`loop.py:411` 注释已自陈「tenant 暂固定 default（2.2 扩展）」；`sys/chat.py:162` 另有一处重复定义）→ 改为由请求身份传入（`loop.run(..., tenant=)` 或由 ctx 取），并**消除重复常量**。
