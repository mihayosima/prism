## 3. 解耦性复核：结论成立

三条红线均通过，且不是"扫描器没写对规则"式的假绿——关键规则在最近一次改造里被修好过（`_resolve_relative` 修复了相对导入被整体丢弃的漏洞、`detect_cycles` 修复了用服务值查插件名导致图恒空的死代码）。本轮扫描的 0 违规是**修好之后的真实 0**。

依赖方向严格单向：`插件 → agent.api → core`，`sys` 与 `run` 亦只经 `api` 取用内核能力（`run`→`sys` 允许，属适配层调系统层）。

**非阻断、但值得知道的两点**

1. **双命名空间语义**（`sys/plugin_manager.py:10-16`）：目录插件登记在 `agent_plugins.*`，与常规导入路径 `agent.plugins.*` 的同名类**不是同一对象** ⇒ `isinstance` 跨插件判断会失败。这是有意取舍，但接入新插件/写诊断代码时必须用 `type(x).__name__` 或 `@plugin` 元数据比较。
2. **软耦合面**：`StateKeys` 与 `Events` 是允许的协作面。当前量健康，但后续插件增多时应优先走事件总线，别继续堆共享状态键。

## 4. 稳定性评估（按维度）

### 4.1 装配与生命周期 —— 做得好

- **装配 fail-fast + 完整回滚**：任一插件 `apply` 抛错 → 先释放该插件已注册的区间（防资源悬挂）→ 逆序回收全部已完成插件 → `root.teardown()` → 原样抛出（`core/container.py:275-312`）。不存在"部分装配成功"的中间态。
- **插件导入失败与装配失败区分对待**：导入失败是跳过 + warning（单插件损坏不拖垮发现，`sys/plugin_manager.py:189-193`）；装配失败才是 fail-fast。这个区分是对的。
- **优雅退出**：`run/chat.py:1239` 关掉 uvicorn 自带处理器，自注册 SIGTERM/SIGINT（Windows 回退 `signal.signal` + SIGBREAK），`finally` 中 `await c.teardown()` ⇒ 逆序 release + 杀进程树，不留孤儿。
- **状态文件损坏有兜底**：`plugin_manager._read_state` 会告警 + 备份为 `.corrupt`（S7 修复）。

### 4.2 资源管理 —— 做得好

- **MCP stdio 子进程**（`core/mcp_client.py`）：独立进程组、stderr 独立任务持续消费防管道写满、`_wait_loop` 常驻取退出码、`is_alive/dead_reason` 探活、插件层就地重启、`_kill_tree` 杀整棵树（Windows `taskkill /F /T`），start 半途失败也收干净。无句柄泄漏。
- **SQLite**（`sys/storage.py`）：WAL + `busy_timeout=5000` + `asyncio.Lock` 串行化 + 显式 `transaction()` 上下文管理器。零后台线程，规避 aiosqlite 的 loop-closed 竞态——选型正确。
- **Redis 不可用**：`plugins/work_memory` 自动降级 `InMemoryWorkMemory`，委托调用吞异常仅告警。

### 4.3 超时与重试 —— 做得好

- `sys/llm.py:213` `httpx.AsyncClient(timeout=90.0)`；可重试状态码 `{429,500,502,503,504}`；默认 `max_retries=3`、`retry_backoff_s=0.5`，退避带抖动（`:226-227,368-369`）。
- **流式仅"首帧前"重试**（`:288-290`）——避免把半截响应当完整结果，这个设计是对的，很多实现会踩坑。
- MCP 请求默认 120s，`wait_for` 超时即摘除 pending 防悬挂（`core/mcp_client.py:399-405`）。
- 小缺口：未读 429 的 `Retry-After`；无总时长预算（极端情况下 3 次重试叠加可达 ~5 分钟）。

### 4.4 并发与状态一致性 —— **最大短板**

- **会话隔离是"约定式"而非"强制式"**：`agent/core/session.py` 与 `scope_config.py` 提供了分桶能力，但运行期**不为请求建立子作用域**（`ctx.child/scope` 仅 `sys/progress.py:91` 内部使用）。`_session_key()` 从**容器级** `ctx.state` 读 `SESSION_KEY`（`sys/budget.py:50`），而该键由 `sys/chat.py:198` 直接写在**根 ctx** 上（代码注释自承"容器级，尽力而为"）。
  ⇒ **并发 A/B 交错时，A 可能读到 B 刚写入的会话键，预算记到别人的桶里。**
- **预算计数本身不是典型的 lost update**：`_pre` 的读（`budget.py:194`）与写（`:215`）之间**没有 await**，在单线程事件循环里是原子的；`_post` 同理（`:241-242`）。真正的窗口只有预警分支的 `await durable/emit`（`:210-211`，每会话仅触发一次）。所以"并发必丢更新"的说法**不成立**——真问题是上面的会话键串账。
- 残留共享槽：`SESSION_KEY`（`sys/chat.py:198`、`plugins/react/loop.py:431`）、`REACT_RUN_ID`（`budget.py:218`）。
- 现有并发测试（`test_budget_concurrent.py`）只覆盖**同会话内多 caller 分槽**，未覆盖**跨会话并发串账**。
- 生产代码零阻塞调用（无 `time.sleep`/`subprocess.run`/`requests`）。

### 4.5 错误处理 —— 有缺口

- **无全局异常处理**：全仓 `exception_handler` 零命中（`run/chat.py:543` 建 `FastAPI()` 后未注册）。未捕获异常落到 Starlette 默认 500 HTML，前端拿到非 JSON；`/api/settings`、`/api/plugins/*`、`/api/approval/*` 均无局部兜底（仅 `/api/chat` 有，`:702-703`）。
- **静默吞异常偏多**：生产代码约 33 处 `except Exception/BaseException: pass` 且无日志。多数是合理的"尽力而为"（幂等 ALTER TABLE、遥测失败），但有一处明显不该静默——见 §5 风险 3。
- 关键路径整体是**降级继续**而非崩溃：LLM 失败抛 `LlmUnavailableError` 回显前端；规划失败降级闲聊（`sys/chat.py:659-660`）；审计写失败仅 warning 不阻断（`core/audit.py:37-39`）。

### 4.6 可观测性 —— 偏弱

- 有分层 logger（`agent.*`），关键路径日志较全：审计失败、MCP 死亡带退出码、重启、监听器异常 `logger.exception`、插件导入失败。
- 但：**无结构化日志**（全仓无 `basicConfig`/`dictConfig`），**无 request_id / trace_id**，uvicorn `log_level="warning"`。
- **事后追溯困难**：`agent_events(seq,event,payload,at)`（`agent/tables.py:17-18`）无 `run_id`/`session` 列；LLM/工具失败不入账，只有 chat 层写 `CHAT_IN/CHAT_DONE`（`sys/chat.py:204`）⇒ 无法按一次请求串起完整链路。

## 6. 复核过程中的两个环境坑（会影响你的判断，记下来）

### 6.1 `--basetemp` 残留会导致批量假红（本次误报 209 项）

同一 `--basetemp` 目录复用时，pytest 只淘汰最旧的几个子目录，残留会污染后续运行：本次首轮**报 209 个 ERROR**，但**逐个单跑全绿**。换一个干净 basetemp 重跑即刻降到 **1 个红灯**。

> 判据：`--basetemp` 复用后出现成片 ERROR、而单跑通过 ⇒ 先换干净目录复测，别急着改代码。

### 6.2 安全删除开关的变量名

沙箱删除拦截的开关是 **`CODEBUDDY_SAFE_DELETE_SANDBOX`**（`=1` 启用 fail-closed），不是 `CODEBUDDY_SAFE_DELETE_ENABLED`。后者无效，设了照样拦。

```bash
CODEBUDDY_SAFE_DELETE_SANDBOX=0 python -m pytest agent/tests --basetemp=<干净目录> -q
```

即便关掉开关，`test_windows_mcp.py::test_plugin_self_heals_after_child_crash` 仍会红——它内部 `flag.unlink()` 走 trash 二进制，在本机返回 `Some operations were aborted`。**属环境噪声，非代码缺陷**：日志里 `MCP 子进程已退出（exit code 7）` 恰证明死亡感知逻辑本身是好的。

### 6.3 依赖环境说明

本机可见的三个 Python 解释器均**未安装**项目依赖（连 `httpx` 都没有）。本次复核在隔离 venv `<用户主目录>\.workbuddy\binaries\python\envs\default` 里装了 `fastapi/uvicorn/httpx/redis/pytest/fakeredis` 用于跑测试，**未触碰你现有环境**。

## 8. 补充（2026-10-02 13:40 进度盘点时新增）

### R8 · [高] 断点续传能力实际未生效（环境/配置层面）

- **现象**：阶段 2 断点续传（2.0 持久化快照 + 2.1 崩溃自动续接）代码已落地（`cd6d431`），但 Redis 探测返回 `ConnectionRefusedError [WinError 10061]`（积极拒绝 ⇒ 6379 无进程监听），而 `work_memory.required` 默认 `False`（`agent/profiles.py:81`、`agent/plugins/work_memory/__init__.py:58`）。
- **后果**：插件静默降级为 `InMemoryWorkMemory`（其自陈"跨进程/重启后失效"）⇒ **跨重启续传处于关闭状态，仅进程内有效**。文档承诺的能力与运行时实际可用性之间存在落差。
- **性质**：非代码缺陷，是「依赖未落地 + 降级开关默认关」的组合结果。与 §6.3 的依赖未安装问题同源。
- **解除条件**：起 Redis 服务，并将 `work_memory.required` 置 True（后者会让 Redis 不可用直接启动失败，属有意的 fail-fast 取舍，需明确裁示）。
