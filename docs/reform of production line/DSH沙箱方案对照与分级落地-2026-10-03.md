## 0. 一句话结论

**DSH 的"分级"不是隔离强度分级，是「文件效应模式」分级；而隔离强度是另一根正交轴。**
它把这两根轴拆开，各自暴露成一等公民（模式 ∈ 3 值；强度 ∈ {full, partial}），
再用 fail-closed 的探测 + 自报强度把"没有隔离"这件事变成**类型系统里可检查的事实**，
而不是文档里的一句承诺。

**它推翻了我上一轮的两个判断**：
1. 我说"按风险分级做不了" —— 错。DSH 按**文件效应**分，不按工具自报 risk 分。
2. 我建议"T2 = AppContainer" —— 错。DSH 明确记录了**为什么不用 AppContainer**（见 §3.3），
   那个理由直接否掉了 AppContainer 这条路。

**它给我们的最大资产不是分级本身，是三样工程纪律**：
`enforcement: full|partial` 自报、无后端即 `SANDBOX_UNAVAILABLE`、
"命令被拒" vs "沙箱坏了" 的错误分类。这三样我们目前**一样都没有**。

## 1. DSH 的两级轴（这是核心概念）

### 1.1 轴 A：文件效应模式（`SandboxMode`，3 个值）

| 模式 | 文件系统效应 | 明确**不**承诺 |
|---|---|---|
| `read-only` | 拒绝一切写（仅允许必要系统 sink） | — |
| `workspace-write` | 允许写「规范化工作区根」+「指定临时目录」 | — |
| `danger-full-access` | **绕过文件系统限制** | 网络、进程可见性**仍不在模式词汇表内** |

★ DSH 官方文档反复强调的一句关键界定：
> "These modes describe filesystem effects only. The official sandbox specification explicitly
> excludes network access and process visibility from the policy vocabulary."

**这条对我们极其重要**：我们上一轮设计的 T0–T4 里，T3 判据包含
`169.254.169.254` / `10.*` / `127.0.0.1`（内网与元数据）。
**在 DSH 的模型里，这些根本不属于沙箱该管的事** —— 那是出口管控（egress）的职责。
把它们塞进"沙箱分级"会导致职责混淆：沙箱一旦声称管了网络，实际又管不住，标注就又不诚实了。

### 1.2 轴 B：隔离强度（`SandboxEnforcement`，2 个值）

| 值 | 含义 |
|---|---|
| `full` | 后端**完整实现**了该模式承诺的所有文件隔离 |
| `partial` | 因 OS/内核版本限制，只能部分隔离 |

DSH 举的 `partial` 实例：老内核的 Landlock ABI；**Windows 的 ACL 边界**。

### 1.3 两轴正交，不是阶梯 ⚠️

```
                  强度=full          强度=partial
                ┌──────────────────┬──────────────────┐
  workspace-write│ Linux(bwrap/     │ Windows          │
  workspace-write│ Landlock)        │ (restricted token│
                │ 写=工作区         │  + capability SID)│
                │ 读=规则集强制      │ 写=工作区         │
                │ 网络=不承诺        │ 读=环境继承(不控) │
                │ 进程可见=不承诺    │ 网络=不承诺       │
                │ 控制台=隔离        │ 进程可见=不承诺   │
                │                   │ 控制台=不隔离     │
                ├──────────────────┼──────────────────┤
  read-only     │ 同上，零 grant     │ 同上，零 grant    │
                ├──────────────────┼──────────────────┤
  danger-full-  │  （不进入沙箱）    │                  │
  access        │                  │                  │
                └──────────────────┴──────────────────┘
```

**我上一轮的错误就是把这两轴压成了一根阶梯。** 压扁的后果是：Windows 上的
`workspace-write` 既不是"低一档"也不是"同一档的另一种实现"——
它是**同一个模式、同一个语义，但强度只有 partial**。
用阶梯表达会逼你撒谎（要么说它等于 Linux，要么说它等于"没隔离"）。

## 2. 逐后端实现（我们只关心 Windows，但对照必须完整）

| 平台 | 后端 | 机制 | 探测方式 |
|---|---|---|---|
| Linux | `bwrap`（Bubblewrap）优先 → 回退 `landlock-run` | bwrap namespace/mount；`landlock-run` 是 C11 二进制，直接调 Landlock UAPI，`no_new_privs` 后经 `execve` 继承 ruleset（`--ro` / `--rw`） | `--probe` 模式，仅在内核支持且 ruleset 创建成功时 exit 0 |
| macOS | `sandbox-exec` + 动态 Seatbelt profile | `read-only` 拒一切写（除字面量 `/dev/null`）；`workspace-write` 给规范化工作区根 + `/tmp` + 用户 temp 目录 `(subpath "…")` | 在 `read-only` profile 下真跑 `true`；二进制缺失或内核拒绝 ⇒ **fail closed** |
| **Windows** | `@deepseek-ai/dsh-sandbox-windows-acl` | Restricted Token + capability SID | 见 §3 |

`landlock-run` 的一个细节值得学：启动器失败 `exit 125`（`LAUNCHER_FAILURE_EXIT`），
与子进程自身的失败退出码**分开** —— 这就是 §5 那条"沙箱坏了 vs 命令被拒"的雏形。

## 3. Windows 后端源码级拆解（我们要抄的主体）

机制一句话：**把调用方 token 复制成 `WRITE_RESTRICTED` token，其 restricting SID 列表里
放一个 write SID（S-1-4-x-y），而这个 SID 的 Write ACE 只存在于工作区与会话私有临时目录上。**
Windows 只在「调用方正常权限」∧「restricting SID 交集」同时允许时才授予写。

DSH 明确记录这是对 `huoyaoyuan/windows-acl-restrict-poc`（固定在 `10e4dfb`）的移植。

### 3.1 Token 派生

`CreateRestrictedToken` flags：`WRITE_RESTRICTED` + `DISABLE_MAX_PRIVILEGE` + `LUA_TOKEN`
另：token 降到 **Low integrity**，被授予的目录带 **Low no-write-up label** 与环境删除 deny。

### 3.2 capability SID 的身份设计 ★ 这是最聪明的一处

| SID | 派生方式 | 生命周期 | ACE 策略 |
|---|---|---|---|
| **Workspace SID** | `workspaceWriteSid(规范化工作区路径)` —— **从路径确定性派生** | 每工作区每机器**只 materialize 一次** | **standing（永不撤销）** —— 跨会话/跨进程复用缓存 |
| **Temp SID** | `tempWriteSid(path)`，每活动会话一个 | 会话结束**可撤销** | `dispose()` 撤销 |

为什么这个设计重要：POC 每会话随机 SID ⇒ 每次都要全树传播 DACL（DSH 测量：**大树几十秒**）。
把身份从"会话"移到"工作区"，**这个成本一辈子只付一次**，后续每次 provision 命中
exact-ACE skip。**"身份即工作区"** 这个抽象是可直接搬走的。

### 3.3 为什么不用 AppContainer / mxc ⚠️ 直接否掉我上一轮的 T2 建议

DSH 在设计记录里写明选型理由：
- **AppContainer：完全无法做任意路径读**（arbitrary-path reads at all）⇒ 直接出局。
- **mxc（Windows Sandbox）：需要 Windows 11 24H2 底座，且要 wholesale host DACL 写**才能做任意路径读。

我们上一轮我把 AppContainer 列为 T2 —— **这个判断错了**。
受限 token 路线之所以选，恰恰是因为它**保留环境读权限**（"preserves ambient read and
network access while enforcing a strict intersection check on write and delete"），
这与"操作本机的助手"这个产品定位兼容；AppContainer 会把这个定位直接掐死。

### 3.4 Windows 后端的自承边界（DSH 逐条实测的，抄作业时必须一起抄）

| 边界 | 原因 |
|---|---|
| **写受限；读/网络/进程可见性完全不受限** | `WRITE_RESTRICTED` 只 intersect 写访问。⇒ `read-only` **无法单靠此机制表达**，需另配读侧策略 |
| **`read-only` 不是"零权限"，是"零 grant"** | keep-alive 组（logon SID + Everyone）在两种模式下都在 restricting 列表里 |
| **NUL 写入是环境赋予的（ambient）** | 设备 DACL 给 Everyone `0x1201BF`，两种模式下 `> NUL` 都能写。但 `Set-Content NUL` 在两种模式都失败（PowerShell/.NET 层效果） |
| **控制台隔离不可用** | restricted token 下 `CREATE_NO_WINDOW`/`CREATE_NEW_CONSOLE` 子进程在 DLL 初始化期死（`0xC0000142`）；补 console logon SID 也救不回来 |
| **`whoami` / token 检查 cmdlet 失败** | `GetTokenInformation` 对副本部分不可用 ⇒ 诊断噪声，非功能故障 |
| **部分功能静默不可用** | `Authenticated Users` 不在任一列表 ⇒ WMI 命名空间安全检查失败（`0x80041003`）⇒ `Get-ComputerInfo` 等**静默返回不完整结果而不报错** |
| **授予目录必须 caller-owned** | owner 隐含 `WRITE_DAC` 才是免提权改 DACL 的依据 |
| **FAT 卷在两种模式下都可写** | 目标若无安全描述符，restricted token 写检查通过（Everyone 在两个列表里）⇒ DSH 明示这是"legacy residue，不予处理" |
| **受限模式下 `pwsh` 跑在 ConstrainedLanguage** | `Add-Type`/COM/反射全废；core cmdlet 与 core 类型正常。DSH 把这个契约写进 **工具描述**教给模型 |
| **一个工作区只有一个写白名单** | write SID **就是**工作区身份；一个实例跨两个工作区 ⇒ 两个 grant 一起放宽。⇒ **必须按工作区路径一实例一个** |

## 4. 分级如何"按需隔离"：DSH 的实际做法

### 4.1 策略是**逐调用**解析的，不是进程启动时设一次

> "Sandbox policy is not set once at process start; it is resolved per capability call and
> passed along with the call. … A Bash running read-only and a restricted subagent needing
> workspace-write coexist; their policies don't interfere. The backend holds no state."

**这是与我们现状差距最大的一条。** 我们的 `PermissionMode` 已经是按会话分桶（ContextVar 覆盖不到、
改用分桶那次），但**沙箱模式还没有 per-call 通道** —— 现在根本没有"模式"这个状态。
要抄这条，得先有一个 `sandbox_mode` 的请求级上下文。

### 4.2 模式是**会话日志的一部分**（回放免疫）

`effective = findLast(events) ?? config default`
`sandbox/mode` 事件只追加到会话日志 ⇒ **重启免疫、多会话隔离、零外部配置存储**。

★ 与我们已定的断点续传范式同构（快照落在 `agent_events`/Redis），
但**多了一个此前没想到的收益**：`/permission` 预设切换天然可回放。

### 4.3 权限预设（Permission Preset）：把两个旋钮捆成档位

| 预设 | 沙箱 | 审批 |
|---|---|---|
| `workspace-write` | workspace-write | ask |
| `danger-full-access` | danger-full-access | never |
| 自定义例：`read-only-review` | read-only | ask |

预设事件只记"用户选了哪个"的**意图**，再分别调沙箱与审批各自的 setter，**两个旋钮独立更新**，
只有真变了的那个才追加事件。`custom` 是派生状态（当前组合对不上任何预设），**UI 可显示但不可切到**。

**这正好回答了用户最初的"分级"诉求**，而且比我上两轮的两套设计都干净：
分级 = 预设，而不是"每层一个独立机制"。

### 4.4 升级路径 = 一次审批后重试一次

- 被拒后模型可**带更宽的 `sandbox_permissions` + 一句 justification 重试一次** ⇒ 触发 `approval/request` 人审。
- **grant 不持久化，无 `allow_always`** ⇒ 拒绝即结束。
- **重试是一个新的 tool call**（新参数、新结果事实），**不是隐藏重入**。
- bash 工具的描述**教模型**：拒绝是策略结果，正确响应是"一次同轮重试 + 更宽权限 + 一句理由"。

### 4.5 审批的四态闭合 + fail-closed

`allowed-once` / `rejected` / `cancelled` / **`unavailable`（没人答 = 拒绝）**
per-session 策略 `ask`（默认）/ `never`（CI/无人值守，全拒，连应答者都不调）。
`approval/asked` 与 `approval/decided` 成对落日志，**不进模型对话记录**。
**没有审批服务 = 全拒，绝不挂起。**

## 5. 三条工程纪律（我们最该抄的部分，且与分级无关）

### 5.1 自报强度 `full | partial` ★

"这个信息是暴露出来的 —— 如果你的场景要求完整的文件系统隔离，看到 `partial` 就该谨慎处理，
而不能把它当成 `full` 使用。"

**这正是我上一轮"第 0 步：诚实标注"的正式化版本。**
差别在于：DSH 把它做成了**类型系统的一部分**（`SandboxEnforcement` 是返回值，不是文档），
所以它可以被断言、被测试、被 UI 渲染。我们的插件页现在显示 `enabled · assembled` + `error: null`，
看起来是健康的 —— **这是误导**。

### 5.2 无后端即 `SANDBOX_UNAVAILABLE` ★

`ctx.sandbox.confine()` 在没有任何可用后端时**直接抛**，不会静默降级到无隔离。
macOS 探测失败、seatbelt 二进制缺失、内核拒绝 ⇒ 全部 fail closed。

对应我们的现状：`plugins.sandbox` 是**准入网关**（纯逻辑，无进程概念），
所以这条对"未来的进程级档位"才适用。**但它必须写进新档位的第一条设计规则。**

### 5.3 "命令被拒" vs "沙箱坏了" 的错误分类 ★

DSH 有两组签名：
- `denialSignatures` —— "内核拒绝了某个文件操作"的 stderr 文本特征
- `runnerFailureRules` —— "启动器本身故障"的特征（`landlock-run:` 前缀 + exit 125）

**大多数"加个 wrapper"的方案忽略这一层。** 我们如果直接把 restricted token 套在
MCP 桥的 `create_subprocess_exec` 上，一定会出现这种情形：
**token 降级后子进程起不来**，错误长得像"MCP 桥挂了"，进而触发我们已有的 hang 自愈逻辑
⇒ **把基础设施故障误报成工具故障，然后自动重启桥**。这个坑现在就能预见到。

## 6. 本项目落地路径（分阶段，每阶段都可独立验证）

**前提**：与前两轮一致 —— 未经你批准不改生产代码；本节是待批方案。

### 阶段 0：诚实标注（零风险，fail-closed 的真正起点）

1. 沙箱插件的每个裁决事件带上 `enforcement` 字段，值域 `{full, partial}`。
   **当前所有 MCP 桥都是 `partial` 甚至更低**（现状：无任何进程级隔离）。
2. 插件页在 MCP 桥条目上直接显示隔离档位徽标，缺省显示 `⚠️ 无隔离`。
3. 测试：断言"当桥未声明档位时，UI/事件里不出现任何看起来健康的表述"
   （防数量塌缩 + 防谎报）。

**这一步的价值**：后面每上一档都是**可验证的改善**，而不是又一句文档承诺。

### 阶段 1：Windows restricted token（照抄 DSH §3）

- 新模块：`agent/sys/sandbox_win.py`（放 `sys/` 不放 `core/` —— 它是平台 IO，不是内核纯逻辑）
- 只做**写限制**：`read-only` / `workspace-write` 两模式，语义与 DSH 对齐
- **身份即工作区**：`workspaceWriteSid(规范化项目根)`，standing ACE，永不撤销
- 会话私有 temp：`data/sandbox/<sid>`，`dispose()` 撤销 ACE
- 挂载点：**只有一处** —— `agent/core/mcp_client.py:187` 的 `create_subprocess_exec`
  （那是唯一能施加档位的地方）；用 `creationflags` 之外加 token 传递
- **必须先解决的两个实测障碍**（见 §7）

### 阶段 2：per-call 策略 + 预设（对齐 §4.1 / §4.3）

- 新增请求级 `sandbox_mode` 上下文（三态语义与既有 `ctx.state` 三态一致）
- 预设 = `(沙箱模式, 审批策略)` 二元组，`/api/settings` 支持整档切换
- 档位切换落会话事件 ⇒ 免费获得回放/重启免疫

### 阶段 3：升级路径（对齐 §4.4）

沙箱拒绝 → 在工具结果里告诉模型"可带更宽权限重试一次" → 触发既有 approval 的 `_pre_task`
（**不重写审批链路**，与上一轮结论一致）→ 批准后重试，**不持久化 grant**。

### 不做的事（明确写下来，避免以后被当漏项）

- ❌ **容器档**：DSH 明确把"沙箱"定义为**只管文件效应**。容器/Egress 管控是另一层议题。
  本机 Docker 可用（WSL2 后端），但那是"进程跑在别处"，不是"限制文件效应"。
- ❌ **Windows Sandbox 档**：本机非管理员，装不了 Hyper-V 特性。
- ❌ **AppContainer 档**：DSH 已给出否掉它的确切理由（无法任意路径读）。
- ❌ **网络/内网/元数据判据**：不属于沙箱职责，应归出口管控（抄 WorkBuddy 的 `HTTP_PROXY` 注入思路）。

## 7. 两个必须先解决的实测障碍（DSH 已踩过，我们也会踩）

### 7.1 ★ `npx` 写 npm cache 会越界

我们的 playwright 桥默认是 `npx -y @playwright/mcp@latest`（已核实 `playwright_mcp/__init__.py:51-61`）。
`npx` 要写 `%LOCALAPPDATA%\npm-cache`，**不在工作区内** ⇒ `workspace-write` 下会直接失败。

DSH 的同类问题解法是**把子进程的环境重定向到私有目录**
（`SetEnvironmentVariableW` 改写 TMP/TEMP 给子进程）。
对应到我们：**spawn 桥时注入 `npm_config_cache` / `PLAYWRIGHT_BROWSERS_PATH` 指向会话私有目录**。
这不是绕过策略，而是**把策略要求的目录显式指出来** —— 正是 DSH 的做法。

### 7.2 ★ `uvx → uv → python` 孙进程的管道捕获

`mcp_client.py:253` 明确记录了 `uvx → uv → python` 启动链，并已用进程组整棵收尸。
而 DSH 自承：**受限 token 进程用 `stdio: 'pipe'` spawn 孙进程会 `EPERM`**
（named pipe 的默认 SD 模板问题；只有继承式/fd 式与匿名管道可用）。

**我们的形态**：由**未受限的父进程**（我们）创建带 PIPE 的受限子进程
⇒ 这是 DSH 的**主要 API 形态**（`sandbox.spawn({command, args, cwd})` 带捕获 stdio），
**不是** DSH 说的那个受限孙进程场景。所以**主路径应该可行**。
但 `uvx → uv → python` 这条链上，被限制的 `uv` 进程**自己** spawn `python` 时是否踩坑，
**必须实测** —— 这决定 `windows_mcp`（本机无 `uv`/`uvx` ⇒ 本轮起不来，但架构上存在）能否 confined。

### 7.3 DACL 全树传播成本

工作区实测 **5,577 个文件（不含 node_modules）/ 6,825（含）**。
DSH 测量"大树几十秒"。我们的规模远小于其压测量级，但 `web/node_modules` 若被纳入仍需实测。
**"身份即工作区"让这成本只付一次**（§3.2），所以这条是可接受的。

## 8. 与前两轮结论的关系（避免自相矛盾）

| 前一轮 | 本轮修正 |
|---|---|
| "按工具自报 risk 分级做不了（MCP 全 write）" | 错。DSH 按**文件效应**分，不看工具自报 risk |
