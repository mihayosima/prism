## 0. 一句话结论

> **循环内是草稿纸，循环结束是交卷；"裁多长的草稿"归上下文管理，"做到第几步"归工作记忆。**

### 1.1 ✅ 采纳（成立且现状缺失或需固化）

### 1.2 ⚠️ 修正后采纳

**修正-1：`react_budget` 口径与 governor 对齐。**
原式 `model_context_window - reserve_output - prior_tokens` 会**另立一套窗口口径**。
governor 已有 `input_budget() = max_context_tokens - reserve_output_tokens`（`governor.py:67`），
故应统一为：

```
react_budget(prior_tokens) = input_budget() - prior_tokens
```

——否则"会话级"与"循环级"两套窗口会在配置上打架。

**修正-2：不新写 `_trim_react_context`，改用 G1 的 `assemble`。**
原方案 §七给了手写裁剪器，§十又说"先把裁剪手写、等 S1 稳定后再接入 assemble"。
**但 S1（G1 分块装配）已于 2026-09-26 落地并通过全量回归**（210 passed）。
此时再手写一套裁剪 = **两套裁剪实现必然漂移**（口径、边界、clip 开销各不相同）。
故直接复用 `governor.assemble`，把 react 特有的策略表达为**块的元数据**：

- prior → `rigid=True`（入口已装配，循环内**绝不重裁** —— 正面满足原方案验收项"prior 不重复裁"）；
- chain → 可裁 messages 块，交由 governor 的 `_trim_messages` 统一执行；
- "老 Observe 首尾 clip" 与 "pinned 保留" → 见 §3.2b / §3.2c，**作为 governor 的通用能力**，而非 react 的私有逻辑。

**修正-3：`TaskContext` 字段要瘦身。**
原方案把 `working: dict` 放进 `TaskContext`，会与 `plugins.work_memory` 形成**双份真相**。
改为只持 `task_id` **引用**工作记忆（详见 §4）。

**修正-4：结论提取（原 §八）默认不做。**
见 1.3 驳回-3。

### 1.3 ❌ 驳回（认同用户原判者一并列出）

| # | 驳回项 | 理由 |
|---|---|---|

| R7 | **`TaskContext` 自持 `working` dict** | 见修正-3。进度态 SSOT 已在 `work_memory`，不复制 |

## 2. 为什么必须分开谈两件事（问题判据）

用户要求"明确工作记忆与上下文管理插件的职责"。判据只有一条：

> **问的问题不同，归属就不同。**
> - "这次喂给模型的**内容**该占多少 token、该丢哪几条？" → **上下文管理**
> - "这个任务**做到哪了**、下一步干什么？" → **工作记忆**

据此给出职责矩阵：

| 维度 | `plugins.context`（上下文管理） | `plugins.work_memory`（工作记忆） | `plugins.react`（循环本体） |
|---|---|---|---|
| 关注问题 | 内容**怎么裁**、占多少 token | 任务**进度**到哪了 | 下一步 Think 什么 |
| 持有数据 | 预算参数、装配报告（`AssemblyReport`） | `step` / `tool_trace` / `checkpoints` / `status` | 循环局部 `chain`（think/act/observe） |
| **是否含 token 语义** | **是（全仓唯一）** | **否**（只存进度字段，不算 token、不存正文） | **否**（只声明诉求，不自行计算） |
| 生命周期 | 无状态（纯装配函数） | 任务级（`begin` → `finish` 即 DEL） | 单次 `run()` 调用栈 |
| 是否跨进程 | 否 | **是**（Redis；不可达降级内存） | 否 |
| 结论归属 | — | — | 产出 `text` → 交 `chat` 落 `agent_messages` |

### 2.1 三条红线（本次必须钉死）

1. **工作记忆不存对话/推理正文，更不做裁剪。**
   它**不知道也不该知道**"模型窗口多大"。`chain` 是"喂给模型的内容"→ 属 react 局部状态，**不进 Redis**。
2. **上下文管理不做进度判断。**
   它不关心"任务完成没有"，只回答"给我一组块 + 一个预算，我告诉你保留什么"。
3. **react 是唯一的编排者。**
   它读写工作记忆（进度）、向上下文管理索取预算与裁剪（内容），**全部经 `ctx.has` / `ctx.get` 软依赖**。

### 2.2 由此纠正原方案的三处归属错误

| 原方案元素 | 原归属（错误） | 正确归属 |
|---|---|---|
| `TaskContext.chain`（推理链） | 混在 TaskContext 的 working 里 | **react 循环局部状态**（不持久化、不进 Redis、不进工作记忆） |
| `TaskContext.working`（任务进度） | TaskContext 自持一份 | **`plugins.work_memory`**（SSOT）；TaskContext 只持 `task_id` 引用 |
| 循环内裁剪规则（head/tail、pinned、keep_recent） | react 私有手写裁剪器 | **`plugins.context`**（策略参数 + 通用能力），react 只调用 |
| 结论提取与落库 | 工作记忆 / 新 LLM 步骤 | **react 产出 → chat 落 `agent_messages`**（owner 是 `short_term`） |

## 3. 修订设计

### 3.1 `TaskContext`（react 插件内部，不持久化）

```python
@dataclass(slots=True)
class TaskContext:
    prior: list[dict]        # 入口 prior（已装配；循环内 rigid，绝不重裁）
    chain: list[dict]        # 仅循环产生的 Think/Act/Observe
    task_id: str             # 指向 work_memory（进度 SSOT 的引用，非副本）
    step: int = 0
```

- **去掉 `working` dict**（修正-3）：进度查询一律 `wm.get(task_id)`，不落第二份真相。
- chain 条目沿用现有消息形态，增加两个**非持久化**元数据键，**归属截然不同**（校正③，详见 §3.6.3）：

| 键 | 归属 | governor 是否认识 | 用途 |
|---|---|---|---|
| `pinned`: `bool`（默认 `False`） | **通用元数据** | **是** | 任何 messages 块可携带；块内刚性保留 |
| `type`: `"think" \| "act" \| "observe"` | **react 私有语义** | **否（不碰）** | 仅 `_prepare_chain` 筛选"哪些要折叠" |

> 一句话：**governor 只认 `pinned`；`type` 是 react 的内务**——governor 代码里不出现 `"observe"` 字样。
> 注意 `type` 是本方案引入的**新**键；现状 chain 条目无 `type`，react 需在 append 时补打。
> 另需为每条 chain 条目补可选 `id`（供 pinned 降级追溯，见 §3.6.2）。

### 3.2 新增能力 —— **全部落在 `plugins.context`**

**(a) 预算查询扩展**（`ContextGovernor` + 配置可调）

```python
def react_budget(self, prior_tokens: int) -> int:   # input_budget() - prior_tokens
def react_keep_recent(self) -> int:                 # 最近 N 条 chain 原文保留（默认 6）
def clip_max_tokens(self) -> int:                   # 单条超此值即触发首尾折叠（默认 1000）
def clip_head_tokens(self) -> int:                  # 折叠后首部保留（默认 500）
def clip_tail_tokens(self) -> int:                  # 折叠后尾部保留（默认 500）
def react_min_chain_tokens(self) -> int:            # 循环内 chain 保底额度（默认 2048）
```

> 实现校正（编码期）：原设计命名为 `observe_*`，但 **§3.6.3 要求治理器不认识业务字样**——
> 方法名自带 `observe` 即自相矛盾。已改为中性的 `clip_*`（描述"折叠"这一通用操作，
> 与 `clip_head_tail` 同族），并由单测守卫（治理器源码内不得出现 `observe`）。
> 设置页**界面文案**仍可写"观察"，那是 UI 措辞，不进治理器代码。

> ⚠️ `react_budget` **可能为负**（`prior_tokens > input_budget()`）。该情形的处置见 **§3.6.4**
> ——决策在 **chat（调度层）**，不在 react。

对应配置键登记进 `agent/run/chat.py` 的 `_SETTING_SCHEMA`（`run/chat.py:92`）+ owner 映射
（`:101`）+ 默认值（`:109`）+ 前端 `keys` 列表（`:557`）——**沿用 G1 已建好的设置通道**，
`/api/settings` 保存后后台重建容器生效，无需新增界面。

**(b) 通用 `clip_head_tail(text, head, tail, budget)`**（governor 方法）

保留首 `head` / 尾 `tail` token，中段折叠为 `... [省略 N token] ...`。
**唯一实现**，供 react 准备 chain 时调用——不在 react 内重写一份。
（与现有 `_clip_hard`/`clip_text` 同族，clip 标注自身开销仍走 `_clip_hard` 的迭代收缩保上限。）

**(c) `pinned` 升级为**通用条目元数据**（`governor._trim_messages`）

规则：messages 块内 `m.get("pinned") is True` 的条目 → **刚性保留**（先占额度，不参与丢弃）。

- 边界（诚实标注，不静默）：pinned 在**块内先占额度**；额度用尽的剩余 pinned **降级为普通条目**，
  并在 `BlockReport.pinned_downgraded` 记录被降级条目 id（**精确语义与记录载体见 §3.6.2**）。
- 收益：react 只需在 Observe 上**打标**，裁剪策略由 governor 统一执行；
  未来 chat 等其他 messages 块也能复用（如锁定首条 user）。

### 3.3 react 侧改动（编排）

1. `ReactConfig` 仅新增 `react_keep_recent` 兜底默认；取值优先级 **governor > 本插件默认**。
   **折叠阈值（`clip_*`）不落本插件**——它是治理器的策略，本插件只调用其 `clip_head_tail` 原语；
   治理器无该接缝 → 不做折叠（与"无治理器退旧路径"一致）。
   > 实现校正（编码期）：原设计让 `ReactConfig` 也持 `observe_*` 兜底阈值，实为**死配置**
   > ——无治理器时根本不走折叠分支（走 `_trim`），故已删除，避免两处阈值漂移。
2. 新增 `_prepare_chain(chain, gov)`：对 `chain[:-keep_recent]` 中
   `type == "observe" and not pinned` 的条目逐条 `gov.clip_head_tail(...)`；
   **think / act 一律保留**（原方案 §六 判断正确：关键信息通常在 Think 里已转录）。
   **只折叠、不丢弃**——与 governor 的界线钉死于 **§3.6.1**。
3. 主循环替换 `_trim(messages, cfg.history_keep)`（`loop.py:162`）为 `_governed_context(...)`：

```
gov = ctx.get(Services.CONTEXT) if ctx.has(Services.CONTEXT) else None
if gov 具 assemble:
    blocks = [
        {"key":"react_prior","kind":"messages","present": bool(prior),
         "payload": prior, "rigid": True, "priority": 0},
        {"key":"react_chain","kind":"messages","present": bool(chain),
         "payload": _prepare_chain(chain, gov), "weight": 1.0, "priority": 10},
    ]
    msgs = [system] + gov.assemble(blocks).prior + [user]
else:
    msgs = _trim(messages, cfg.history_keep)     # 降级：逐字节不变
```

4. 每步后发 `CONTEXT_GOVERNED`（`stage="react"`）：携带链峰值 token / 裁剪次数 /
   pinned 数 / 各块实占——复用既有事件，**不新增事件**。
5. Observe 打 `pinned` 字段位：默认 `False`；由 `Observer` 接缝可注入标记（R5）。

> **不引入 coverage**：prior 与 chain 天然不相交，无需互斥；若传 coverage 仅作排序用，
> 且链内条目**无 `seq`**——governor 对无 `seq` 条目"信任调用方划分"（`governor.py:293`），不会误删。
> 这正面回应了原方案 R1/R2 的失败根因：**循环内不构造 seq/covers，也不伪装成有**。

### 3.6 关键语义钉死（评审补正 6 条）

#### 3.6.1 `_prepare_chain` 与 `_trim_messages` 的职责界线

> 校正①。方向正确，但**必须修正其中一句表述**——现状 `_trim_messages` 并非"只丢弃不折叠"。

| 层 | 职责 | 操作 | 丢弃 | 折叠 |
|---|---|---|---|---|
| `_prepare_chain`（react） | **块内准备** | 对 `chain[:-keep_recent]` 中 `type=="observe" and not pinned` 的条目**逐条**首尾折叠 | **否** | **是（逐条）** |
| `_trim_messages`（governor） | **预算裁剪** | 从旧到新丢弃，直至 ≤ 块额度；**末条**超额度时保底折叠 | **是** | **仅末条保底** |

**为什么不照搬"只丢弃不折叠"**：G1 现状 `governor.py:199-203` 已有"最新一条超预算 → `_clip_hard`
到预算"的**保底折叠**（语义"保对话不残"，且已有单测）。若按原建议改成"只丢弃"，
将**破坏 G1 既有行为与回归**。

故准确界线是：

- **逐条折叠**归 react（块内准备，不丢条目）；
- **整块丢弃 + 末条保底**归 governor（预算裁剪，不逐条折叠）。

两者**不重叠**：react 不丢条目，governor 不逐条折叠。按此写死，杜绝双重截断。

#### 3.6.2 pinned 超限：`downgraded` 的精确语义

**判定顺序**（关键：pinned 在**块内**先占，不参与全局 water-filling）：

1. governor 定出该 messages 块的额度 `alloc`（flex 块经 water-filling，rigid 块经刚性分配）；
2. **块内先用 pinned 条目、按原顺序占额度**，直到额度用完；
3. 额度用尽的**剩余 pinned → 降级为普通条目**，参与 `_trim_messages` 的正常丢弃；
4. 记录被降级的条目 id。

**记录载体（修正校正②的形式）**：原建议给的是裸 dict `report["downgraded"]`，与
G1 §2.6.6「`AssemblyReport` 是 dataclass，非裸 dict」的纪律冲突。改为在 `BlockReport` 上加字段：

```python
@dataclass(frozen=True)
class BlockReport:
    ...
    pinned_downgraded: list[str] = field(default_factory=list)   # 被降级的 pinned 条目 id
```

**条目 id 从哪来**：react 给 chain 条目带可选 `id`（如 `f"step{step}_observe"`）；
缺省时 governor 以 `f"#{块内序号}"` 兜底。

**空集即正常**：无降级时为空 list（字段不省略，便于消费方直接读）。

#### 3.6.3 `type` 与 `pinned` 归属统一

> 校正③。§3.1 与 §6 此前表述冲突，此处为准。

| 元数据 | 归属 | governor 认识 | 用途 |
|---|---|---|---|
| `pinned` | **通用元数据** | **是** | 任何 messages 块可携带；块内刚性保留 |
| `type`（`think`/`act`/`observe`） | **react 私有语义** | **否** | 仅 `_prepare_chain` 用于筛选"哪些要折叠" |

**governor 只认 `pinned`；`type` 是 react 内务，governor 代码里不出现 `"observe"` 字样。**

#### 3.6.4 `react_budget <= 0` 的行为

> 校正④。**采纳"压缩后再进"的意图，但修正执行者归属。**

`prior_tokens > input_budget()` 时循环内无空间。原建议让 **react 自行触发会话级压缩** ——
这会破坏已确立的纪律：压缩时机由 `plugins.short_term` 的 `compact_trigger_tokens` **单独决定**
（见 G0 注记）。react 反向指挥 short_term 属**职责越界**；且若历史未达阈值，`maybe_compress`
会 no-op，"压缩后再进"即成空转。

**正确归属：决策在 chat（调度层），裁决仍在 short_term（内容层）。**

```
# agent/sys/chat.py :: _send_via_react 之前
gov = ctx.get(Services.CONTEXT) if ctx.has(Services.CONTEXT) else None
if gov is not None and estimate_tokens(prior) > gov.input_budget():
    # 一次性尝试：复用既有压缩入口（阈值仍由 short_term 裁决），成功后重建 prior
    await self._safe_compress(ctx, session_id)
    prior = await self._build_prior(ctx, session_id, message)
    # 压缩后仍超 → 不重试（防抖/防死循环）；交 §3.6.5 刚性降级兜底 + 双通道标注
```

- **只尝试一次**，不做重试循环；
- 压缩后仍超 → **不拒绝进入**（否则多步能力整体失效），由 §3.6.5 兜底，保证仍可推理；
- 无 governor → 跳过该闸（退回现状）。

> **实现期核对（重要，修正了本条的前提）**：G1 装配后 prior 已被钳在
> ``input_budget - 保留额度`` 内，**常态下不会超预算**——本闸实际是**降级路径的兜底**
> （如 ``assemble`` 抛错退回无界拼接、或短期记忆缺失退回条数硬裁）。
> 故它不是热路径，只作安全网；相应地，验收项 12 用「令装配失败以构造该场景」来测。

**配套（本方案新增，非校正项）**：为防"prior 吃满预算 → chain 额度为 0 → 循环空转"，
`_build_prior` 装配时为循环**预留 `react_min_chain_tokens`**（默认 2048，可调）。
否则即便 prior 正常装配（≤ `input_budget`），仍可能挤掉全部 chain 空间。

#### 3.6.5 `prior` 在循环内 `rigid=True` 的准确语义

> 校正⑤。**rigid ≠ 绝对不裁。**

`rigid=True` 的语义是「**不参与可裁池**」（不被 water-filling 削减），**不等于「绝对不裁」**：

- G1 §2.6.2 已定义刚性超限处理：按 `priority` 升序分配，不足者标 `downgraded` + 双通道标注
  （`AssemblyReport.rigid_overflow` + `system_text` 显式标注段）。
- 技术核对：`assemble` 对 rigid 块先 `give = min(need, remaining)`，随后**仍调**
  `_trim_messages(payload, alloc)`（`governor.py:272-277`）——故 **rigid 块单独超预算时确实会被裁**。

**准确表述**：

> prior 以 `rigid=True` 入块 = 循环内**不参与常规裁剪**（不与 chain 抢 water-filling）；
> 但若 prior **自身**超预算，仍按 G1 刚性降级规则处理并**诚实标注**。

**真正的额度保证在 chat 侧**：`_build_prior` 已经过 `assemble`，其产物总量 ≤ `input_budget`
（且按 §3.6.4 预留了 chain 保底）。故循环内 prior 通常不超限；一旦超限即说明 chat 侧装配异常，
**应如实标注而非静默**。

据此，验收项 3 加限定：**「在 prior 未超预算时，prior 不重复裁」**。

#### 3.6.6 `CONTEXT_GOVERNED` 事件字段（`stage="react"`）定死

复用既有事件与既有字段（`sys/chat.py::_emit_governed` 已发
`stage/at/system_tokens/input_budget/total_used/redistributed/blocks/rigid_overflow`），
**循环专属字段收进 `react` 子对象**，避免与 chat 侧字段混淆：

```jsonc
{
  "stage": "react",                 // 固定字面量
  "at": "2026-09-26T13:00:00Z",
  "step": 3,                        // 循环步序（1-based）
  "input_budget": 20000,
  "total_used": 18320,              // 本步装配后实占（system + prior + chain）
  "system_tokens": 900,
  "redistributed": 0,
  "blocks": [                       // 与 chat 侧同结构
    {"key": "react_prior", "present": true, "reason": "ok",
     "requested": 15000, "allocated": 15000, "used": 15000},
    {"key": "react_chain", "present": true, "reason": "trimmed",
     "requested": 6000, "allocated": 5000, "used": 4820}
  ],
  "rigid_overflow": [],
  "react": {                        // ← 循环专属（唯一新增命名空间）
    "chain_tokens": 4820,           // 本步 chain 实占
    "chain_peak_tokens": 6400,      // 任务内峰值（累计 max）
    "clips": 7,                     // 累计逐条折叠次数
    "pinned": 2,                    // 本步 pinned 条目数
    "pinned_downgraded": 0,         // 本步被降级的 pinned 数
    "keep_recent": 6,               // 生效的最近保留轮数
    "budget": 5000                  // 本步 react 可用额度（= input_budget - prior_used）
  }
}
```

- **发送时机**：每步 Act+Observe 之后（与 `REACT_STEP` 同点），仅当 `plugins.context` 装配且具 `assemble` 时发；
- **失败不阻断**：发事件异常一律吞掉（沿用 `_emit_governed` 的 try/except 纪律）；
- **字段只增不改**：后续新增只在 `react` 子对象内追加，不改既有键语义。
- ⚠️ **通道属性（实现期核对）**：`CONTEXT_GOVERNED` 走 **EventBus live（`ctx.events.emit`）**，
  **不落 `agent_events`** 表——与 `durable(...)` 写审计不同。消费方（前端/诊断）须
  `ctx.events.on(ctx, Events.CONTEXT_GOVERNED, handler)` **订阅**，或在此处改走 durable
  （**本方案未改**，避免增加每步一次落盘开销）。测试亦据此断言（见 `test_react_context.py`）。

## 6. 风险与守卫

- **新增依赖边**：`react --软--> context`（此前 react 只软依赖 `work_memory`）。
  须在解耦守卫中登记方向；`context` **不得**反向 import react，也不得感知 `type=observe` 语义
  （`pinned` 保持通用词义，governor 代码内**不出现 `"observe"` 字样** —— 已统一，见 §3.6.3）。
- **两处 messages 裁剪的边界** → **已钉死，见 §3.6.1**：`_prepare_chain` 只逐条折叠、不丢条目；
  `_trim_messages` 只整块丢弃 + 末条保底折叠、不逐条折叠。
  ⚠️ **不能简化为"只丢弃不折叠"**——G1 现状的末条保底折叠有既有单测，改掉会破坏回归。
- **压缩责任边界**：§3.6.4 的预算闸由 **chat 发起**，但"是否真的压缩"仍由 `short_term` 的
  `compact_trigger_tokens` 裁决。react **不得**直接调用压缩入口（否则压缩时机出现第二个决定者）。
- **配置覆盖风险**：新增键必须同步 `_SETTING_SCHEMA` + 前端 `keys`，否则前端不可见 / 后端拒绝（沿用 G1 教训）。
- **回归风险**：`loop.py:162` 是每步都走的热路径，改动须保证"无 governor 分支"与旧实现**逐字节等价**。
