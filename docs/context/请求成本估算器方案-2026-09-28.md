# 请求成本估算器（统一账本）设计方案

- **编制时间**：2026-09-28 17:23（GMT+8）
- **状态**：已实施（彻底版，2026-09-28 17:50 落地；代码已改动并按 §7 校验通过）
- **关联**：`docs/governance/token口径对账-问题记录.md`（2026-09-27）、`docs/governance/上下文管理-遗留问题清单-2026-09-27.md`
- **一句话目标**：用**一个**核心层纯函数 `estimate_request_cost` 取代"三把尺子"，让上下文窗口分配（context）与成本护栏（budget）共用**同一份账本**，根治 tools/schema 预算低估（实测 est 18,865 vs 真实 25,513，偏差 ≈26%）。

---

## 0. 摘要

当前同一次 LLM 请求被三处用三种口径各量一遍、互不对账（"三把尺子"）：

| 尺子 | 位置 | 口径 | 实测同次调用 |
|---|---|---|---|
| 窗口预算 | `governor.py:94` `input_budget()` | 只算 messages，不认 tools/schema | messages 钳在 ~20k |
| 护栏放行 est | `budget.py:31-33`（tools 来自 `sys/llm.py:85` 名字列表） | `est(messages)+est(tools**名字**)+est(schema)` | **18,865** |
| 真实账单 | `sys/llm.py:103` `usage.prompt_tokens` | 完整 wire messages + 完整 tools JSON | **25,513** |

本方案引入**单一请求级成本估算原语**，使其与 DeepSeek 真实 `prompt_tokens` **同源**（发什么就算什么），并让 context 与 budget 都调用它——三把尺子退化为"一份账本、两种用途"。

**关键结论（前置澄清）**：该估算器**不做成插件**，落 `core` 公共层（与 `estimate_tokens` 同源同级）。理由见 §3。

---

## 1. 设计决策

### 1.1 归属：`core/tokens.py`（或并列 `core/request_cost.py`），非插件

| 候选位置 | 结论 | 理由 |
|---|---|---|
| `plugins/context`（目录插件，opt-in） | ✗ | budget（sys 恒定）若依赖它 → sys 依赖可停用组件；违反分层且破坏 budget 恒定可用 |
| `sys` 层新插件（如 Budget 同构） | △ | 可行但无收益：纯函数无生命周期，多一层 `ctx` 接线属过度设计 |
| **`core` 公共纯函数** | ✓ | 唯一能被 sys(budget) 与 plugins(context) 同时安全 import 的层；延续 `estimate_tokens` 自 `sys/llm` 迁入内核的既有方向（`tokens.py:3`） |

### 1.2 为何不违反 S3 红线

S3 红线（`context/__init__.py:18`）禁的是在别处另立"**窗口分配/裁剪**"逻辑。本估算器是**计量原语**（与 `estimate_tokens` 同级），context 仍是在其上做分配决策的**唯一**组件，红线无虞。

### 1.3 分层约束（K0）

`core/tokens.py:8` 钉死"本模块零依赖、零业务词；不得 import sys/plugins 树"。故估算器内部**不得 import `sys/llm` 的 `_wire_*`**，须自带与 wire 同构的序列化（或把 wire 形状下沉到 core，见 §4.2）。

---

## 2. 接口设计

```python
# core/request_cost.py 新增（与 estimate_tokens 同源，纯函数原语）
def estimate_request_cost(
    messages: list[dict],
    tools: list[dict] | None = None,
    schema: dict | None = None,
) -> int:
    """请求级 token 估算（与 DeepSeek 真实 prompt_tokens 同源）。

    - messages **必填**，按 wire 同构形状序列化；
    - tools 按 wire 同构形状序列化（description[:200] + parameters 骨架，
      与 sys/llm.py 原 _wire_tools 规则一致）；
    - schema 调用按 response_format json_object 计入（与 DeepSeekLlm 真实发送一致：
      仅置类型，不发送 schema 体本身）。
    调用方传原始内部结构即可，无需先 wire。
    无 tools/schema 时退化为 estimate_tokens(messages)，与现状一致。
    """
```

行为约定：
- 入参为空/None 的维度不计入（保证向后兼容）。
- 返回值与 `estimate_tokens` 同为**启发式估算**（非真实用量），但口径与线上 wire payload **结构一致**，从而消除"算法缺陷型偏差"，仅剩启发式 vs 真实用量本身的固有差（<5% 量级，可接受）。

## 3. 实现细节（两种力度，推荐 §3.2）

### 3.1 轻量版（复制 wire 规则到 core）

在 `core/tokens.py` 内实现 `_wire_messages_for_cost` / `_wire_tools_for_cost`，规则**手抄**自 `sys/llm.py:130-165` / `183-210`。
- 优点：改动面小，不动 `sys/llm.py`。
- 风险：两处序列化规则未来可能漂移（仍留"隐性双份"隐患）。

### 3.2 彻底版（下沉 wire 形状到 core，推荐）

将 `_wire_messages` 与 `_wire_tools` 的**序列化形状**下沉到 core（如并入 `core/tokens.py` 或新建 `core/wire.py`），`sys/llm.py` 改为调用 core 版本，`estimate_request_cost` 复用同一函数 → **零漂移**。

```python
# core/request_cost.py（实际落点；wire 形状自 sys/llm.py 原 _wire_messages/_wire_tools 整段下沉，零漂移）
def wire_messages(messages: list[dict]) -> list[dict]: ...   # 同原 sys/llm.py:_wire_messages
def wire_tools(tools: list[dict]) -> tuple[list[dict], dict]: ...  # 同原 sys/llm.py:_wire_tools

def estimate_request_cost(messages, tools=None, schema=None) -> int:
    payload: dict = {"messages": wire_messages(messages)}
    if tools:
        wired, _ = wire_tools(tools)
        payload["tools"] = wired
    if schema:
        payload["response_format"] = {"type": "json_object"}
    return estimate_tokens(payload)
```

> 注：`sys/llm.py` 的 `_wire_tools` 还返回 `name_map`（净化名↔原名映射）供回程还原；下沉时保留该返回值，`sys/llm.py` 照常使用，估算器只取第一项。

## 4. 接线改造

### 4.1 `sys/budget.py`（修复 26% 低估，直击根因）

```python
# budget.py:_pre
from agent.core.request_cost import estimate_request_cost
est = estimate_request_cost(
    payload.get("messages", []),
    payload.get("tools"),        # 现在是原始 tools 目录，不再是名字列表
    payload.get("schema"),
)
```

### 4.2 `sys/llm.py:85`（停止把 tools 压成名字列表）

```python
# 现状（问题源）
"tools": [str(t.get("name", "")) for t in (tools or [])],
# 改为
"tools": tools,   # 传原始目录，交由 estimate_request_cost 同构估算
```
（pre-call payload 仅用于预算估算，不再需要名字列表。）

### 4.3 `plugins/context`（窗口预算也认 tools/schema）—— 已按彻底版落地

`governor.assemble` **已有** `reserve_tokens` 形参（`governor.py:323,337`），直接复用，**无需改 governor 内部，也无需新增 GovernorLike 协议方法**（相比草案 v1 的 `reserve_request_overhead` 设计更收敛）：

- **native tools 发起点（真正危害点）**：`plugins/react/loop.py:_window` 装配时，`fn(blocks, reserve_tokens=estimate_request_cost(messages=[], tools=tools))`——`tools` 来自 `run()` 的 `visible_tools(ctx)`（即发给模型的 native 工具目录），与 `DefaultReasoner`（`components.py:108`）实际发出的 native 工具数组同源。
- **schema 附加项**：`sys/chat.py:_plan` 装配时，`_assemble(..., reserve_tokens=estimate_request_cost(messages=[], tools=None, schema=PLAN_SCHEMA))`——plan 调用带 `schema=PLAN_SCHEMA`，属请求附加项、不在 messages 预算内。

效果：窗口预算 `input_budget() − reserve_tokens` 先给 tools/schema 留位，messages 不再"假装 tools 不占空间"（对账文档 §五.1）；且只改消费方装配调用，治理器内部零改动、协议零膨胀。

## 5. 兼容与降级

- **无 tools/schema**：`estimate_request_cost` 退化为 `estimate_tokens(messages)`，budget 行为与现状一致（除 tools 不再被低估外）。
- **context 插件停用**：`ctx.has(Services.CONTEXT)` 为 False → `overhead=0`，退回现状（chat 已用 `_fallback_assemble` 兜底，见遗留清单 §五）。估算器仍在 core 可用，budget 不受影响。
- **预算护栏本身恒定**：估算器在 core，budget（sys）始终可 import，无"可停用断供"风险。

---

## 6. 风险与影响

| 项 | 说明 | 缓解 |
|---|---|---|
| budget 放行变严格 | tools 现在计入，长工具目录场景更早触顶（预期修复） | 回归 `test_budget_*`；`max_tokens_per_run=200000` 默认下影响微小；`LOW_BUDGET_PATCH(60)` 类场景需重测 |
| wire 下沉改动面 | `sys/llm.py` 复用 core wire 函数，需保证 `name_map` 行为不变 | 单测锁定 `_wire_tools` 输出形状 |
| 启发式固有差 | estimate 仍非真实用量 | 接受 <5% 固有差；真实 usage 仍由 `sys/llm.py:103` 入账对账 |

## 7. 验证与回归

1. **单测**：构造含 tools（带 description/parameters）的调用，断言 `estimate_request_cost` 与手工 wire 后 `estimate_tokens` 相等（零漂移）。
2. **对账测试**：用 `data/agent_chat.db` 中既有 `agent_budget_log` 真实 `prompt_tokens` 反向构造请求，断言估算偏差 < 5%（非算法缺陷）。
3. **回归**：`test_budget_concurrent.py` / `test_budget_refund.py` / `test_budget_reset.py` / `test_context_governor.py` 全绿。
4. **守卫更新**：`test_governor_has_no_business_wording` 扫描面扩到 `context/` 全目录（遗留清单 3.2），防止文档失真回归。
