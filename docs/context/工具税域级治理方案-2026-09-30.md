## 0. 摘要

**问题**：单轮请求里工具相关开销占单轮的 **90.3%**；其中「工具定义」这一项（native tools 附件）独占单轮的 **61.6%**。实测归因显示，native tools 内部有 **54.6%（换算占单轮 33.6%）是 JSON 空壳骨架**——这部分**无法靠精简描述消除，只能靠减少暴露数量消除**。

> **口径提醒（全文百分数一律标注分母）**：**54.6% 的分母是 native tools（1,740 / 3,186）**，**61.6% 的分母是单轮（3,186 / 5,176）**。两者分母不同，不可并排比较。凡出现「54.6%」即指 native tools 内部占比，「61.6%」即指该附件占单轮的比例。

**结论**：工具税的治理重心在**披露环节**（哪些工具、何时进入上下文），不在工具层。本方案选定**在投影层做域级裁剪**，隐藏的域对模型不可见、但**对检索可见**。

**收益**：按域裁剪后，单轮 native tools 由 3,186 降至 1,555~1,673（**省 1,513~1,631 tok/轮**，占单轮 29.2%~31.5%），且不牺牲可发现性。**另有一项与本方案正交的「目录卡去重」收益约 1,400 tok/轮（量级与域裁剪相当），见 §4.6 末。**

**边界**：不改插件、不改任务注册表、不改 guard/审批、不改执行面。改动集中在 `agent/plugins/react/` 的投影与 loop 内。

### 1.3 native tools 的成分分解（关键）

懒加载态 native tools = 3,186，逐项拆解（**校验：1,740 + 264 + 1,182 = 3,186 ✓**）。表中**同时给出两个分母**：`占 native tools` 与 `占单轮`（单轮 = 5,176）：

| 成分 | token | **占 native tools** | **占单轮** | 能否靠「工具层瘦身」消除 |
|---|---:|---:|---:|---|
| JSON 空壳骨架 | 1,740 | **54.6%** | **33.6%** | **不能**。固定包装 `{"type":"function","function":{"name":…,"description":…,"parameters":{"type":"object","properties":{…},"required":[…]}}}` |
| 工具名 | 264 | 8.3% | 5.1% | 不能（名字是契约） |
| 描述文本 | 1,182 | 37.1% | 22.8% | 能，但量级有限 |
| **合计** | **3,186** | **100%** | **61.6%** | 合计即 native tools 占单轮的比例 |

> **读法**：**「骨架 54.6%」的分母是 native tools**（占单轮 33.6%）；**「native tools 61.6%」的分母是单轮**。两者分母不同，**不可并排比较**——上一节 §1.1 的 61.6% 是后者。

**决定性推论：工具税是「数量驱动」，不是「schema 驱动」。**

骨架按 34.8 tok/条固定计价，与工具的参数多少无关（`_card()` 已把 `params` 清空，`wire_tools` 的 `properties` 随之恒为空）。因此：

- 单个工具再怎么精简描述，**最多动 37.1%**；
- 少暴露一个工具，**直接省 34.8 + 名字 + 描述 ≈ 68 tok**；
- **粒度越细分，工具越多，税越重**——「工具粒度不够细」是反向诊断。

## 2. 治理框架：四层栈

### 2.1 层与职责

| 层 | 决定什么 | 本项目对应物 | 现状 |
|---|---|---|---|
| **1 插件层** | 单个工具「长什么样」 | `playwright_mcp` / `windows_mcp` / 内置注册点 | 描述可精简、`risk` 标注失真（见 §8.1） |
| **2 聚合层** | **哪些工具被暴露** | `ctx.tasks` 注册表（`sys/tasks.py:100-240`） | **无「域」维度**，只有整插件启停 |
| **3 投影层** | **何时被看到** | `visible_tools`（`loop.py:220`）→ `_tools_for_step`（`loop.py:993`） | 懒加载已生效；**无域裁剪** |
| **4 上下文** | 结果位 | native tools 数组 | 3,186 tok/轮，61.6% |

### 2.2 外部主流三种做法

1. **渐进式披露（Tool Search / Lazy Loading）**：用桥接元工具替换全量工具定义，模型先搜、再看、后调。
2. **身份驱动的权限裁剪**：在连接层按身份过滤，未授权工具**不返回**。
3. **Gateway 聚合 + 搜索优先**：多下游服务器聚在一个端点后，默认只暴露搜索/调用元工具。

### 2.3 本项目对照

| 做法 | 本项目对应物 | 现状 |
|---|---|---|
| ① 渐进式披露 | `LAZY_META_TOOLS`（`loop.py:275-287`）+ `_tools_for_step`（`loop.py:993`） | ✅ **已实施且已生效**（§1.4）。差异：本项目只需**两件套** `tool_search` + `tool_load`，**不需要 `tool_call` 包装**——目标工具本身仍可直接调用 |
| ② 身份驱动裁剪 | 仅逐工具 `fnmatch`（`permissions.task_allow`）+ 整插件启停两极 | ❌ **缺「域」这一维度** |
| ③ Gateway 聚合 | `_partition_meta`（`loop.py:1000`）内联处理元工具 | ⚠️ **半个**：是 gateway 雏形，但 3 个元工具**硬编码常量**、无 group 概念、无配置面 |

**本项目的「MCP 层」不是一个进程，而是上述第 2、3 层合起来的这条链**：

```
ctx.tasks.catalog()  →  visible_tools()  →  _tools_for_step()  →  native tools
```

本项目只有 2 个 MCP 插件（playwright 25 / windows 20）与 2 个内置注册点，**统一汇聚点就是任务注册表**。因此「在 MCP 层治理」在本项目的落地形态就是「在这条链上治理」，**插件层零改动**。

## 3. 落点论证：为什么必须在投影层，而不是注册层

### 3.1 证据：渲染通道与检索通道共用同一个 `tools`

`agent/plugins/react/loop.py`：

| 通道 | 代码路径 | 数据源 |
|---|---|---|
| 全量目录 | `tools = visible_tools(ctx)`（:316） | 47 个 |
| **渲染**（喂模型） | `_window(..., tools=tools_step)`，其中 `tools_step = self._tools_for_step(tools, task)`（:420→:422） | 由 `tools` 投影 |
| **检索** | `_partition_meta(wm, task, out.tool_calls, tools)`（:493-494）→ `_tool_search(c, tools)`（:1012）、`catalog = {name: t for t in tools}`（:1009，供 `tool_load`） | **同样是全量 `tools`** |

**关键事实**：第 494 行传的是 **`tools`（全量）**，第 422 行传的是 **`tools_step`（已裁剪）**。「模型看得见多少」与「模型能搜到多少」**当前是两个数**，但**共用同一个全量来源**。

### 3.2 若在注册层裁剪 → 检索死锁

把域过滤写进 `visible_tools`（:316）⇒ `tools` 变瘦 ⇒ `tool_search` / `tool_load` **同步失明** ⇒ 被隐藏的工具**永远找不回来**。

外部方案 ②（Okta 式「未授权就不返回」）在**权限**语义下正确（越权不可见），但在**成本**语义下会造成死锁：模型既看不见、也搜不到，而它其实**有权调用**。

### 3.3 若在投影层裁剪 → 闭环成立

把域过滤加在 `_tools_for_step`（:993）⇒ 检索通道**零改动**即可用：

```
第一次对话（域 B 被隐藏）
   └→ 模型 tool_search("关键词")
        └→ 检索域 = 全量 → 命中域 B 工具
             └→ tool_load(names)
                  └→ task.loaded 增补
                       └→ 下一步 _tools_for_step 渲染放行 → 完整 schema 出现 → 可调用
```

**放行条件必须写成**（这是本方案唯一需要严谨实现的一行）：

```python
out.append(t if (t.get("name") in task.loaded) or _domain_of(t) in allowed
           else _card(t))
```

即**「已加载的工具永远渲染完整定义，不受域过滤影响」**。这样 `tool_load` 成功即**自动放行**该工具，**不需要再实现一套「域解禁」逻辑**。

**实现前提（须显式声明，不得默认）**：上述放行条件依赖 `_card(t)` 在多步任务里被**反复调用**（每步重新投影一次），因此：

> **`_card(t)`（`loop.py:266-270`）是幂等纯函数**：① 不修改入参，每次返回**新 dict**；② 源与投影层共用同一 `_slim_description`（`loop.py:211-217`，`splitlines()[0].strip()[:120]`），对已压成一行的描述**再压一次结果不变**，故 `_card(_card(t)) == _card(t)`；③ 保留 `risk` 与 `owner` 两个字段（`loop.py:269-270`，缺省 `"write"` / `""`）。**⇒ 重复投影不产生状态副作用，且域过滤所需的 `owner` 与风险裁剪所需的 `risk` 在任何投影阶段都拿得到。**

### 3.4 生命周期

- `task = TaskContext(...)` **每次 run 新建**（`loop.py:333`），`loaded` 是 run 级状态；`resume` 只恢复 `chain`/`head`（:339-360），**不恢复 `loaded`**。
- 因此：**同 run 内多步** → 第一步 load 一次，后续步骤持续可见；**跨轮（第二次对话）** → `loaded` 清零，需重新 `tool_search` + `tool_load`，但**检索照样命中**，只是多一次模型往返。
- `lazy_tools_max = 12`（`loop.py:1050`）是**单 run 装载上限**，超限需分批。

## 4. 方案设计：路线 2（域裁剪）

### 4.1 「域」是什么

**定义**：域 = 工具注册来源（`owner` 字段），即一个插件/注册点。

实测的四个域（`GET /api/tools`，2026-09-30 22:40 复算）：

| 域（owner） | 工具数 | 仅放行该域时 native | 该域卡片和 | 系统提示目录块 |
|---|---:|---:|---:|---:|
| `plugins.playwright_mcp` | 25 | **1,677** | 1,488 | 763 |
| `plugins.windows_mcp` | 20 | **1,559** | 1,370 | 659 |
| `plugins.approval` | 1 | 305 | 117 | 77 |
| `agent.tasks` | 1 | 234 | 45 | 24 |
| **全量** | **47** | **3,190**（元工具 195 恒在） | 3,020 | 1,488 |

> **口径更正**：旧稿此列记 `2,124 / 2,419 / 174 / 48`，**数值错误**（既与本文件 §4.6 自身矛盾，也不对应任何已知口径）。上表为项目纯函数（`estimate_request_cost` + `_card` / `render_tools`）实测值。
>
> **非加性**：4 张「卡片和」相加 = 3,020，+ 元工具 195 = 3,215 ≠ 3,190（差 25）——`estimate_request_cost` 对 JSON 数组的 `[` / `]` / 逗号只计一次，**分域求和会重复计入包装** ⇒ **验收一律用「同一函数的前后差分 Δ」，不得用分域求和**（详见《工具税域级裁剪实施方案-2026-09-30.md》§3.4）。

**为什么用 `owner` 而不是新造分组**：`TaskRegistry.catalog()` 已带 `owner` 字段（`sys/tasks.py`），插件注册时自动写入，**零新增元数据、零插件改动**。若将来需要更细的分组（如 `windows_mcp` 内部再分文件/窗口两类），可再引入显式 `group` 字段——但**本期不做**（避免插件层改动）。

### 4.2 生效点

| 位置 | 文件 | 改动 |
|---|---|---|
| 域过滤函数 | `agent/plugins/react/loop.py`（新增，模块级纯函数） | `_domain_of(t)` + `allowed_domains(ctx)` |
| 渲染投影 | `loop.py:993` `_tools_for_step` | 增 `allowed` 参数与放行条件（§3.3） |
| 调用点 | `loop.py:420` | 传入当前 allowed 集合 |
| 提示层 | `prompt.py:72` `build_system` | **同时裁两处**：`prompt_catalog` 改取放行域（`[_card(t) for t in tools_vis]`）+ 追加**域清单**（§4.4）。**只裁 native 而留名册 = 「隐藏」不成立**（模型仍从 `render_tools` 看到名字与描述） |
| **不改** | 插件、`ctx.tasks` 注册表、`visible_tools`、guard/approval | — |

### 4.3 放行域的来源与状态（**2026-09-30 22:46 更正**）

> **原稿此处写「新状态键 `StateKeys.TOOL_DOMAINS`，**会话级**」。实测不成立，已更正。**
> `ctx.state` 是**容器级**、不是会话级：`chat.py::_boot()` 只 `build_agent()` **一次**，
> 全进程持有同一容器（`_apply_rebuild()` 时整体替换）；`Context.state`（`core/context.py:104,121`）
> 是容器实例上的 `State()`，**所有请求共享**，且无 per-request child scope。
> ⇒ 写 `ctx.state` 会**串扰所有会话**，与「插件启停写共享 `agent_plugin_state.json`」同类。
> **故改为配置驱动，语义定为「实例级」**（改配置 → `POST /api/settings` 重建生效，无需重启）。

**配置键**（`agent.react` 节，按「三处同步登记」制度入设置页）：

| 键 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `tool_domains_enabled` | `bool` | `False` | **总开关** |
| `tool_domains` | `list[str]` | `[]` | **放行域白名单**（如 `["plugins.windows_mcp"]`） |

**语义**（`enabled` 且白名单非空 ⇒ 裁剪；否则 ⇒ 不裁剪）：

| 配置 | 行为 |
|---|---|
| `enabled=False`（默认）或 白名单 `[]` | **不裁剪**，逐字节等价现状 |
| `enabled=True` 且白名单非空 | 只放行白名单内的域（+ 元工具 + 已加载工具） |

- **不做「全隐藏」**：UI 上给不出该表达（空白名单即视为关闭），避免误操作把工具全关；如需全隐藏，可在调用点以代码表达（`allowed=set()`）。
- **回滚**：取消勾选总开关 ⇒ 语义回到 `None` ⇒ **逐字节回现状**，无需改代码。

#### 4.3.1 粒度差说明：域策略**实例级** vs `task.loaded` **run 级**（**有意为之**）

本方案内部存在**两个不同粒度**的状态，这是全案最需要澄清的一处：

| 状态 | 粒度 | 生命周期 | 性质 |
|---|---|---|---|
| `agent.react.tool_domains`（+ `_enabled` 开关） | **实例级** | 随容器重建而更新（改配置即重建） | **策略**（放行哪些域） |
| `task.loaded`（既有，非本方案新增） | **run 级** | 每次 `TaskContext(...)` 新建即清零（§3.4） | **装载工作集**（临时上下文） |

> 原稿把前者写成「会话级 state key」，经实测更正为「实例级配置」——理由见 §4.3。**注意**：粒度名称虽由「会话」改为「实例」，但「策略稳定 / 工作集易失」的**结论不变**，下方三条理由与 §4.6.1 的往返成本核算**均不受影响**。

**这是有意为之，不是遗漏**，理由三条：

1. **语义不同**：一个域策略是**配置**（稳定、幂等），一个装载集是**上下文内容**（易失、随任务走）。把策略做成 run 级会导致「每轮重新决策放行域」，与 §4.3 的默认态（不裁剪）冲突；把装载集做成长生命周期会让**新 run 的窗口夹带上一个任务的工具**，破坏任务隔离。
2. **与既有设计一致**：`loaded` 在**改造前**（懒加载，做法①）就是 run 级，本方案**不改变**这一既有事实——域裁剪只是在其上游多一个过滤条件，不引入新的粒度。
3. **前缀稳定要求**（§6.3-1）：域变更会改动 native tools 段，而 **run 级域翻转 = 每 run 都动前缀** ⇒ 缓存收益归零。**实例级配置 + 「变更集中在容器重建时点」**才符合成本纪律。

**由此产生的必然结果（非缺陷）**：**跨轮需重新 `tool_search` + `tool_load`**（§3.4 已述）。其代价**不在 §4.6 主表**，而在下节 §4.6 的「附加代价」中单独计量——**这正是本节与收口项联动的关键**：若某个域是高频域却仍被隐藏，则每 run 都要重付往返成本，§4.6 的净收益测算必须扣除它。

### 4.4 可发现性（前置条件，不可省）

模型第一步看不到域 B，**如果提示层不提域 B 存在，它不会去搜**。因此提示层的目录块之后必须追加一行域清单：

```
其它工具域（当前未展开，可用 tool_search 检索）：
  - plugins.windows_mcp（20 个）
```

否则「隐藏但可检索」在实践中退化为「隐藏即不可得」。**这是本方案能否成立的前置条件，不是可选优化。**

### 4.5 与既有机制的交互

| 机制 | 交互结果 |
|---|---|
| **plan 权限模式** | `visible_tools`（`loop.py:234`）**先**按 `risk == "read"` 裁剪，域裁剪（`_tools_for_step`）**在其之后**叠加——**执行顺序固定为「risk 裁剪 → 域裁剪」**（数据流：`visible_tools` 产 `tools` → 传入 `_tools_for_step`）。两者独立、正交。断言：`_card()` 保留 `risk` 字段（§3.3），故即便顺序反转也不丢字段，但**本方案锁定该顺序**以免 §7-5 断言漂移。**另见 §8.1 的 `risk` 标注失真问题** |
| **懒加载** | 域裁剪只决定「哪些域进入候选」，懒加载决定「候选里哪些是完整 schema」。**裁剪后工具数变少，`tool_search` 的命中率会提高**（干扰项减少）——这是附带收益 |
| **approval / guard** | **零感知**。真实调用仍走 `ctx.tasks.invoke` / `TASKS_PRE_EXECUTE`；域裁剪只改变**可见性**。隐藏域的工具若被直接调用（模型凭记忆），仍按既有规则被 guard 裁决 |
| **插件启停** | 独立机制。启停写全局共享期望态（`data/agent_plugin_state.json`），域裁剪是**实例级配置收窄**（改配置 → 重建）——两者层级不同，互不替代 |

#### 4.6.1 附加代价：「隐藏但被需要」的域每 run 需额外往返（**§4.3.1 粒度差的直接后果**）

上表只算了**静态体积**，**未扣**往返成本。因 `loaded` 是 run 级（§3.4），一个被隐藏的域若在某 run 里**真被用到**，模型需多走两步：

```
直接可见（不裁剪）：step N 直接调用工具
域被隐藏：        step N tool_search → step N+1 tool_load → step N+2 才能调用   （+2 次模型往返）
```

粗估（**假设：一次往返 ≈ 一次完整请求重发；不含 prompt cache 影响**）：

| 口径 | 单次往返 | +2 次往返 | 与省下的 1,513 相抵 |
|---|---:|---:|---|
| 未命中缓存（域裁剪后单轮 ≈ 3,663 tok） | ≈3,663 | **≈+7,326** | **净亏 ≈5,813** |
| 命中缓存（×0.2，见 §6.1 单价） | ≈733 | ≈+1,465 | 净亏 ≈ −48（基本抵消） |

⇒ **盈亏平衡点（该域被用到的 run 占比）**：未命中口径约 **17%**、命中口径约 **50%**。

> **结论**：域裁剪对**低频域**是纯赚（不用的轮省 1,513、用的轮代价可忽略）；对**高频域是负收益**。**这正好与 §5 的取舍准则同向**——**只隐藏「确认不用」的域；高频域应留在白名单内或改用路线 1**。
>
> **不确定度**：往返代价高度依赖 §6.3 尚未验证的服务端缓存行为，故上式给出的是**区间而非定值**；实施前应用 `agent_budget_log.cache_hit` 校准。

**附带可叠加项（正交，非本方案内容）**：同一份目录卡被**计费两次**——`render_tools(_card…)` 进系统提示 1,488，`wire_tools` 又进 native tools 3,186。若系统提示只保留一行发现指引、不挂名册，可再省约 1,400 tok/轮（**量级与域裁剪本身的 1,513 相当**）。**此项与域裁剪互不依赖，可分别决策；决策者若只看 §0 摘要，勿遗漏此项。**

## 5. 备选路线对比：路线 1（粒度合并）

| 维度 | **路线 2（域裁剪，本方案推荐）** | 路线 1（粒度合并） |
|---|---|---|
| 作用层 | 投影层（`_tools_for_step`） | 注册层（合并为复合工具） |
| 手段 | 按域隐藏 + 检索可回溯 | 25 个原子工具 → 3 个复合工具 |
| 实测体积 | 3,186 → **1,555~1,673**（−47.6%~−51.2%） | 3,186 → 约 1,729（−45.7%，playwright 25→3） |
| **参数精度** | **无损**（完整定义按需加载） | **有损**（复合工具的参数面收敛，精度下降） |
| 可发现性 | 保留（可 `tool_search` 回溯） | 保留（但模型需先理解复合语义） |
| 改动面 | 投影层 + loop，**插件零改动** | **插件层大改**（与上游 MCP 契约脱钩） |
| 与上游契约 | 不冲突 | **冲突**：playwright 25 个工具系沿用上游 MCP 契约，非本仓库设计 |
| 回滚 | 置 `None` 即回到现状 | 需回滚插件代码 |
| 新增工具 | 自动落入对应域，**无额外成本** | **新工具即归零**（需重新设计复合工具） |

**取舍准则**：
- **某域是常用域（几乎每轮都会用到）** → 路线 1 更合适（常驻也能瘦身）；
- **某域是低频域（偶尔用到）** → 路线 2 更合适（默认隐藏、按需检索，精度无损）。

**本方案推荐路线 2**，理由：改动面小、精度无损、可回滚、与上游 MCP 契约不冲突，且**新增工具不产生额外治理成本**。

## 6. 成本核算：与既有成本账本对齐（不可跳过）

### 6.1 为什么不能只看 token 量

`Token成本优化实施方案-2026-09-29.md` §2.1 已确立本项目成本函数：

```
成本 = 命中 token × ¥0.2/M  +  未命中 token × ¥1/M  +  输出 token × ¥2/M
```

**miss 单价是 hit 的 5 倍**，且该文档 §2.3 的杠杆排序为「前缀稳定 > 输出控制 > 入链即刻瘦身 > 事后压缩」。因此**省 1,513 tok/轮 ≠ 省 1,513 tok 的钱**，必须换算到 hit/miss 口径。

### 6.2 已实证的有利条件：`tools` 在请求序列的尾部

- `agent/sys/llm.py:21` **直接 import 自 core**：`from agent.core.request_cost import wire_messages as _wire_messages, wire_tools as _wire_tools` ⇒ 真实发送与 `estimate_request_cost` **逐字节同构**；
- `sys/llm.py:230-245` 的 payload 构造顺序为：`model → messages → temperature → max_tokens → tools → tool_choice → …`；
- ⇒ **`tools` 排在 `messages` 之后**，其后仅有 `tool_choice` / `stream` / `stream_options`（数十 token）。

**推论**：域裁剪只改动 `tools` 段及其后，**不触碰** `system + prior + prompt + chain` 这一段前缀。

### 6.3 待验证项 —— ✅ **已于 2026-09-30 23:08 实测完毕**（一次性只读探针，直连 provider、不装配容器、不写 `data/`；关键数字已固化于本节与实施方案 §10）

1. ~~**服务端前缀缓存的切分粒度未验证**~~ → **✅ 已实测，结论最有利**。
   - **方法**：同一 `messages`（含 system 与 user 逐字节相同），**只替换 `tools` 数组**（全量 47 卡 → 仅 windows 20 卡），前后各发一次，读 `usage.prompt_cache_hit_tokens`。
   - **实测**：命中 **4,736 → 2,048**（miss 1,454 ≈ 被删掉的 27 张卡的体积）；同字节复现则回到 **4,736/236**。
   - **判据达成**：「miss 仅小幅增加」——**miss 增量恰好等于被改动的那段 tools，而 system/messages 段全额保住** ⇒ **缓存按 token 前缀切分，且 `tools` 段位于 `messages` 段之后**（与 §6.1 核实的 payload 构造顺序 `model → messages → temperature → max_tokens → tools` 一致）。
   - **⇒ 双重好消息**：① 域裁剪省下的 native tools token 是**真实净省**（该段本就在 miss 区，不会因前缀命中而打折）；② §6.3-1 原判据担心的「域变更须只在会话开始时发生一次」这一约束**天然成立且代价可忽略**（域策略已是实例级配置，只在 `_apply_rebuild()` 时变更）。
2. ~~**懒加载已经引入的前缀变化「从未计量过」**~~ → **✅ 已首次量化**。
   - **方法**：`messages` 保持不变，按 `loaded=0/1/2/3` 依次构造 `_tools_for_step` 的输出各发一次。
   - **实测**：`loaded` 每增长即改写 tools 段 ⇒ 该步 **tools 段整段 miss**（首见 miss **2,933**；同字节复现则 4,736/236）。
   - **结论**：**懒加载每步的前缀代价 ≈ tools 段全长**（当前 47 卡配置下约 3,000 tok/次）。这是**既有成本，不是域裁剪引入的**——域裁剪只改 tools 段的**内容**，不改变「该段每步都在变」这一事实；且裁剪后该段**变小**，反使这段的 miss 成本同比下降（1,513/轮）。

> **本节结论（更新）**：域裁剪的费用收益**已定论** —— 因 `tools` 段天然处于「每步 miss」区，省下的 1,513（native）+ 725（系统提示目录）**按 miss 计价**，是全价收益；域变更的前缀代价可忽略（结论 1）。
>
> **附带发现（值得单独记账）**：G0-3 顺带暴露了**「搜索疲劳」的实测形态**——一次隐藏域任务的真实模型轨迹为 `tool_search` × 2~6 → `tool_load` → 调用，即隐藏域每次 run 需多付 **2~6 次**模型往返（§4.6.1 原按固定 +2 次估算，属**乐观下界**）。

## 8. 风险与未决问题

### 8.1 `risk` 标注失真（**独立议题，但会放大域裁剪的收益判断**）

`plugins/playwright_mcp/__init__.py:94-104` 与 `plugins/windows_mcp/__init__.py:82-85` 注册时**未传 `risk`**，`TaskRegistry.register` 默认 `risk="write"`（`sys/tasks.py:136`）⇒ **47 个工具中 45 个被标为 write**，其中包括 `browser_snapshot` 等纯只读工具。

**影响**：`plan` 模式（`loop.py:234`）只保留 `risk=="read"` ⇒ 实际只剩 2 个工具 ⇒ **plan 模式基本不可用**。

**与域裁剪的关系**：域裁剪**不依赖** `risk`；但两者都作用于同一投影链。修正 `risk` 会**降低审批门槛**（更多工具视为只读）——属**安全决策**，须由用户裁定，**本方案不擅自处理**。

### 8.2 其他风险

| 风险 | 缓解 |
|---|---|
| **搜索疲劳**：高频域每次 run 都要重新 `search`+`load`，往返成本未进 §4.6 主表 | **与 §4.3.1 / §4.6.1 联动处理**：① 只隐藏低频域（§5 取舍准则）；② 高频域留在白名单或改用路线 1；③ 若需保留隐藏，考虑把 `loaded` 在**同会话内跨 run 复用**（会引入任务隔离问题，须单独评估，本方案不做） |
| **执行顺序**：域裁剪与 plan 的 `risk` 裁剪在同一链上，顺序影响结果 | **锁定「risk 裁剪（`visible_tools:234`）→ 域裁剪（`_tools_for_step`）」**，且已断言 `_card()` 不丢 `risk`/`owner`（§3.3）⇒ 顺序反转亦安全，但固定顺序以免断言漂移 |
