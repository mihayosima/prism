## 一、原始四点问题 × 排查结论对照

| 用户原始判断 | 排查结论 | 方案落点 |
|---|---|---|
| 1. MCP 没有对产物有效管理、未按需提取 | 输出侧已有 guard_source 裁剪 + 懒加载未启用；**病根在输入回灌**（章节原文作为工具参数进链重放） | 三期（回灌瘦身 + 懒加载）+ 二期（入链即刻瘦身） |
| 2. React 单次循环缺乏次数控制 | `max_steps=8` 只限次数不限体积；`keep_recent=6` 豁免区 > 任务粒度（2 章/run≈4-5 条）→ 折叠永不生效 | 二期（折叠解锁）+ 一期 C3（阈值统一到治理器） |
| 3. 工作记忆未压缩、一股脑塞给模型 | 工作记忆根本不进提示词（澄清）；但 checkpoint 引用读不回，渐进披露只做一半 | 一期 C6（披露块登记）+ 五期（读回工具） |
| 4. 上下文管理器未履行职责、缺周期涨落 | 「达到上限百分之几触发压缩」机制不存在；治理器裁剪挂 1M 配额恒不触发 | 一期（职责重建）+ 零期（前缀稳定） |
| 5. 上下文管理器盲点未优化 | 治理器自身五处结构性缺位（只有裁剪无压缩、块登记不完整、无水位判定、刚性块无上限、无完整性校验） | 一期 C1~C6 |
| 6.（v1.2）**过早压缩不合理** | 实测证实：压缩省的是 hit（¥0.2/M），代价是 miss（¥1/M），短 run 回本需 **2.7 步** | 撤回调小窗口建议；C3 加回本判定 + 冷却期；优化主杠杆改为前缀稳定 |

**关键事实**（改变方案优先级）：
- DeepSeek-V4 上下文 1M，`max_context_tokens=1M` 与能力一致，无需回调；
- 前缀缓存：run 内命中 96~99%（¥0.2/M），**续接时前缀破坏命中骤降 18~21%**（¥1/M）；
- 昨晚整晚实际 ≈ ¥0.40；优化的意义在放大防护（更贵模型）、速度与预算纪律。

## 二、成本函数与优化优先级（v1.2 新增，先立规矩再谈手段）

### 2.1 成本函数

```
成本 = 命中token × ¥0.2/M  +  未命中token × ¥1/M  +  输出token × ¥2/M
       └── 便宜货（5×）        └── 贵货              └── 最贵（10×）
```

**推论（本方案全部决策的依据）**：
1. **token 总量 ≠ 成本**。重放但命中的 token 单价只有 ¥0.2/M；一个 token 重放 10 次也只值 ¥2/M，而它**只要 miss 一次就抵 5 次命中的钱**；
2. **压缩是用贵货换便宜货**：压缩减少的是「命中部分的重放量」（便宜货），制造的是「前缀突变的 miss」（贵货）——方向本身不利；
3. **唯一纯赚的操作是不破坏前缀而提升命中**；任何会改变前缀的动作（压缩/折叠/重新检索/字节漂移）都必须**先算回本**。

### 2.2 昨晚实测三情形（deepseek-flash 牌价）

| 情形 | 计算 | 费用 | 结论 |
|---|---|---|---|
| **A 现状** | 62.9 万 hit + 17.3 万 miss + 5.1 万 out | **¥0.4015** | 基线 |
| **B 前缀稳定（零期）** | 续接首步 12.6 万 miss 转 hit | **¥0.3006** | **省 ¥0.1008（−25.1%），纯赚、零风险** |
| **C 触发式压缩** | 单次罚金 ¥0.0096、每步省 ¥0.0036 | 回本 **2.7 步** | 昨晚各 run 仅 2~9 步且触发点在第 5~6 步之后 → **剩余步数普遍不足 → 净亏** |

> 回本步数与阈值无关（恒 2.7 步 = 5×D/(W−D) 在 r=0.4 下的定值），只与「压回比」有关——这再次说明：**压缩的代价结构由单价差决定，不因阈值选择而改善**。

### 2.3 杠杆排序（v1.2 修订，取代 v1.1 的「总量优先」）

| 序 | 杠杆 | 机制 | 昨晚可省 | 性质 |
|---|---|---|---|---|
| **1** | **前缀稳定** | 续接不破坏前缀 → 12.6 万 miss 转 hit | **¥0.10（−25%）** | 纯赚、无副作用 |
| **2** | **输出控制** | 输出 ¥2/M（最贵），占昨晚 25% | 最多 ¥0.05 | 纯赚（收尾纪律） |
| **3** | **入链即刻瘦身** | 大参数**从未进链** → 前缀自始至终不含它，**无突变罚金** | hit 部分省（¥0.2 档，金额小） | 纯赚（但收益量级小） |
| **4** | **事后压缩** | 低频、大回落、带回本判定 | 短 run ≈ 0 或负 | **仅在超长 run 有净收益** |

**因此：「把窗口调小让裁剪复活」这条建议撤回**——它把第 4 项（最差杠杆）变成主要行为，而真正的钱在第 1、2 项。

### 2.4 附：为什么「调小 max_context_tokens」不可取

- 若调到明显低于实际链长（如 2~3 万）：每 2~3 步就触发一次压缩 → 每次罚金 ¥0.0096 且要 2.7 步才回本 → **反复付罚金，总费用上升**；
- 若调到 5 万：昨晚链峰值 4.7 万 < 5 万 → 几乎不触发 → **无效果、也无害**，但给人"已经止血"的错觉；
- 正确做法：**阈值不追求小**，而是设为「超长任务兜底线」（见 C3 默认 96k），并叠加回本判定与冷却期，确保**永不提前压缩**。

## 三、方案总纲（六期，依赖排序）

```
零期 前缀稳定性（纯赚，最高优先，独立）
      │
一期 上下文管理器职责重建（盲点专项，核心·架构）
      │  ├─ C1 块策略契约（压缩能力上收治理器调度）
      │  ├─ C2 记账完整性（消灭 reserve 黑洞）
      │  ├─ C3 水位与周期状态机（双窗口 + 回本判定 + 冷却）
      │  ├─ C4 刚性块绝对上限
      │  └─ C5 管线完整性契约
      └─ C6 工作记忆披露块
      │
二期 入链即刻瘦身 + 经济压缩（兜底语义，在 C1/C3 契约下由 react 提供实现）
      │
三期 懒加载（+ 观察侧瘦身验证）
      │
四期 观测与验收（以 miss 总量与总费用为主指标）
      │
五期 功能盲点补全（由 C5 契约驱动）
```

> v1.1 中的「零代码止血项：调小窗口」**已撤回**，理由见 2.4。

## 四、零期：前缀稳定性（独立，最高优先，纯赚）

**目标**：续接首步缓存命中从 18~21% 恢复到 ≥90%（对应 ¥0.10 / −25%）。

**改动点**：
1. **prior 冻结**：run 开始时对 prior（summary+history+memory 检索结果）拍字节快照存入 `TaskContext`；run 内所有步与链存档使用同一快照；续接恢复时直接读存档快照，**不重新检索记忆、不重新截短**。
2. **链存档/恢复不再变异**：`_archive_chain` 存的已是治理后形态；resume 恢复后打「已治理」标记，`_prepare_chain` 对已治理链跳过二次折叠（幂等短路）。
3. **序列化确定性**：wire 层统一 `ensure_ascii=False`、字段顺序固定。

**涉及文件**：`plugins/react/loop.py`、`sys/chat.py`。
**预期收益**：续接 12.6 万 miss → hit，省 ¥0.1008（实测口径）。

## 五、一期：上下文管理器职责重建（盲点专项，架构核心）

> v1.0 主线是「react 自己折叠 + 前缀稳定 + 回灌瘦身」——**在治理器外面打补丁**。本期正面修复治理器自身的职责缺位。

### 5.1 治理器现状：五处结构性缺位（实测）

| # | 缺位 | 现状证据 | 后果 |
|---|---|---|---|
| **B1** | **只有「裁剪」动词，没有「压缩」动词** | `BlockSpec` 仅 8 个字段，无策略与回调；全仓无 `policy`/`on_compact`/`compact_at` | 压缩能力散在消费方（short_term 自定 12k、react 自定折叠），治理器无从统一调度，策略各自为政、无法观测 |
| **B2** | **块登记不完整（预算黑洞）** | `loop.py` 块列表仅四块；native tools 经 `reserve_tokens=estimate_request_cost(tools=...)` **先扣却不登记** | 「扣了预算但不可裁、无上限」的内容存在；长期记忆在 react 路径不提交、工作记忆根本不提交——**谁不进登记谁永远没人管** |
| **B3** | **无水位/周期判定** | 全仓无 `load_ratio`/`waterline` 概念 | 「涨到窗口 X% 触发压缩」机制不存在；用户设计的周期涨落无判定主体 |
| **B4** | **刚性块无绝对上限** | `rigid` 先占额度全由 `input_budget()`（1M 派生）决定，无 per-block cap | rigid 降级机制形同虚设，prior/system 可膨胀 |
| **B5** | **无管线完整性校验** | 无 `required_blocks`/`missing_blocks` | 消费方漏报无人发现——功能盲点长期隐形的结构性原因 |

**共同本质**：治理器当前是「**被动分配器**」（给多少裁多少），不是「**主动管理者**」（该有什么、该压到多少、有没有漏报）。

### 5.2 六项补全（C1~C6）

#### C1 块策略契约（BlockPolicy）——给治理器「压缩」动词

`BlockSpec` 新增四个**可选**字段（缺省 → 行为与现状逐字节一致）：

| 字段 | 语义 |
|---|---|
| `cap_tokens: int = 0` | 块**绝对上限**（0=不限）；刚性块也受限 |
| `compact_at: int = 0` | 压缩**触发阈值**（绝对 token，0=不主动压缩） |
| `compact_floor_ratio: float = 0.4` | 压缩后回落目标（相对阈值） |
| `on_compact: Callable[[payload, int], payload] \| None` | **压缩回调**：治理器只调用，不理解内容 |

**治理器职责**：判定（超阈值 **且**满足回本条件，见 C3）→ 调用 → 记账 → 报表。
**纯度守护**：回调由消费方注入，治理器不 import 任何插件、不感知业务语义。

#### C2 记账完整性——消灭 reserve 黑洞

- `assemble()` 新增 `attachments`（请求附加项：native tools schema 等）参与计量；
- 报表新增 `unaccounted_tokens = 真实请求估算 − 已登记总量`；超 5% → 遥测标红。

#### C3 水位与周期状态机（v1.2 修订：双窗口 + 回本判定 + 冷却）

**双窗口拆分**：

| 字段 | 语义 | 默认 |
|---|---|---|
| `max_context_tokens` | **能力硬上限**（总闸） | 1,000,000 |
| `working_window_tokens` | **经济兜底线**（v1.2 由 24k **上调**） | **96,000** |

> v1.1 把 `working_window_tokens` 设为 24k，按 2.2 实测会导致短 run 反复压缩（净亏）。v1.2 上调为 96k：**普通任务（链 < 6 万）完全不触发**，只在超长任务兜底；主人仍可在设置页按需下调（下调前请先看回本判定）。

**三重触发条件（全部满足才压缩）**：
1. 链 token > `compact_at`（默认 = `working_window_tokens × window_high_ratio`，96k×0.7 ≈ 67k）；
2. **回本判定**：预计剩余步数 ≥ `5×D/(W−D)`（保守取 r=0.4 时恒为 2.7 步）——剩余步数不足则不压；
3. **冷却期**：距上次压缩 ≥ 回本步数，防反复压缩。

**水位评估面**：`assess(blocks) -> WaterlineReport{load_ratio, level, actions}`，`level ∈ {low, high, critical}`，`load_ratio` 以 `working_window_tokens` 为基数（**不再是 1M**）；`level=high` 且通过回本判定才给 `actions`。
**纪律**：水位**现算**，治理器**不持跨请求可变状态**（守住零状态）。

#### C4 刚性块绝对上限

- 默认 `rigid_cap_system_tokens=8000` / `rigid_cap_prior_tokens=8000` / `rigid_cap_prompt_tokens=2000`（可配）；
- 超 cap → 有 `on_compact` 则压缩；无则硬裁 + 沿用既有 overflow 双通道标注。

#### C5 管线完整性契约——把隐形盲点变成可见告警

- `required_blocks`（react 路径 `["react_system","react_chain"]`；chat 路径 `["memory","history","summary"]`，可配）；
- 缺失 → `AssemblyReport.missing_blocks` + 遥测告警。

#### C6 工作记忆披露块

- 工作记忆以「目录块」登记：进度一行 + 检查点索引（cap 300）；模型读到折叠标记可用五期读回工具按需展开。

### 5.3 涉及文件与测试

| 文件 | 改动 |
|---|---|
| `plugins/context/protocols.py` | `BlockSpec` 加 4 个可选字段；`BlockReport` 加 `compact_triggered`；`AssemblyReport` 加 `unaccounted_tokens`/`missing_blocks`；新增 `WaterlineReport` |
| `plugins/context/governor.py` | `_coerce` 支持新键；`assemble()` 接入 cap/compact（含回本判定与冷却）/attachments/完整性校验；新增 `assess()` |
| `run/chat.py` | 设置页同步登记 `working_window_tokens`/`window_high_ratio`/`window_low_ratio`/`rigid_cap_*`（`_SETTING_SCHEMA` + `_PLUGIN_OF_KEY` + `_SETTING_DEFAULTS` + 前端 keys 数组） |
| 消费方 `plugins/react/loop.py`、`sys/chat.py` | 以 dict 传新键 + 提供 `on_compact` 回调（**无需 import 契约类型 → 内核零改动**） |

**测试**：缺省逐字节等价（防回归）；压缩在「超阈值但剩余步数不足」时**不触发**；冷却期内不重复压缩；`assess()` 水位正确；rigid 超 cap 标注；缺必需块命中 `missing_blocks`；既有纯度守卫全绿。

### 5.4 纪律与兼容

- 治理器**零业务语义**（回调注入）、**零状态**（水位现算）、**内核零改动**（dict 通道）、**全字段可选+缺省等价**。

## 六、二期：入链即刻瘦身 + 经济压缩（兜底语义）

> v1.2 明确区分两种动作——**性质完全不同，不可混为一谈**：

| 动作 | 时机 | 前缀代价 | 性质 |
|---|---|---|---|
| **入链即刻瘦身** | 条目**首次入链时**即定型（大参数只留 `path + N 字`） | **零突变**（前缀自始至终不含原文） | 源头减量，纯赚 |
| **事后压缩** | 链超阈值时回头改动历史条目 | \*\*一次性全 miss 罚金（需 2.7 步回本）\*\* | 兜底，仅超长 run |

### 6.1 入链即刻瘦身（A，主要手段）

- 写类工具的大字符串参数在**入链当步**即折叠为「已写入 path，N 字」（完整参数已入工作记忆 checkpoint，无损承诺成立）；
- 同时取消 `keep_recent` 对 act 条目的豁免（原豁免区 6 条 > 任务粒度 4~5 条，实测导致折叠零生效）；
- **零突变**：因原文从未成为前缀的一部分，不存在缓存重建代价。

### 6.2 经济压缩（B，兜底）

- 仅由 C3 三重条件触发（超阈值 + 回本判定 + 冷却）；
- 实现为 `react_chain` 块的 `on_compact`：一次性折叠全部可折条目 + 旧观察首尾折叠 + 更旧条目收缩为「调用元数据行」，回落至 `compact_floor_ratio`；
- 遥测：压缩触发/回落幅度/罚金估算入 governed 事件。

## 七、三期：懒加载（+ 观察侧瘦身验证）

1. 设置页将 `lazy_tools` 置 true——工具 schema 每步 2.2k → 按需加载；开启后其体积变化由 C2 记账直接可见；

## 八、四期：观测与验收（v1.2 指标修订）

**主指标（费用导向）**：
1. **总费用 ≤ 基线 80%**（昨晚基线 ¥0.4015；零期单独即可达 −25%）；
2. **miss 总量 ≤ 基线 50%**（17.3 万 → ≤8.6 万）；
3. **续接首步命中率 ≥ 90%**；
4. **压缩次数符合低频预期**（一个 run 0~1 次），且每次压缩后**实际后续步数 ≥ 回本步数**（事后可核）。

**次指标（纪律与可见性）**：
5. token 总量下降（仅作参考，非目标）；
6. `unaccounted_tokens ≈ 0`、`missing_blocks` 为空；
7. 零 400、零截断回归。

## 十、风险与回退

| 风险 | 缓解 |
|---|---|
| **过早/过频压缩反而变贵** | C3 三重条件（阈值 + 回本判定 + 冷却）；默认阈值 96k 使普通任务不触发 |
| 折叠误伤关键信息 | 无损承诺（原文在 checkpoint）+ think 条目保留 + 末位保底 |
| **改动破坏前缀导致命中下降** | 所有改动以「零期字节一致」为前提回归对拍；入链瘦身在前缀形成前完成 |
| 治理器加策略契约致复杂度上升 | 全字段可选、缺省逐字节等价 + 分批启用（先只读观测） |
| 水位判定引入状态 | `assess()` 纯函数、现算 |
| 双窗口并存引起配置混乱 | 文档+设置页明确分工：1M=能力上限（总闸）、96k=经济兜底线 |

## 十一、实施顺序建议

1. **第一批**：零期（前缀稳定，**纯赚且能立刻省 25%**）+ 一期 C2/C5（只读观测，照亮盲点）；
2. **第二批**：一期 C1/C3/C4（策略契约 + 水位 + 刚性 cap，压缩受三重条件约束）；
3. **第三批**：二期（入链即刻瘦身，零突变减量）+ 一期 C6；
4. **第四批**：三期（懒加载）；
5. **验收**：四期指标；**五期**随 C5 告警逐项补全。

每批一次全量回归 + 服务重启；改动集中在 `plugins/context/`、`plugins/react/loop.py`、`run/chat.py`。
