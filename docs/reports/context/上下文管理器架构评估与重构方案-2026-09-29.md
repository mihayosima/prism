## 〇、勘误（v1.1 → v2.0）

本章是本次详化的第一要务。三处逻辑错误若不纠正，后续所有优先级排序都会建立在错误数值上。

### E-1 价目口径错误：5 倍被当成价差，实际是 30 倍

| 项 | v1.1 及此前各文档所用 | 官方实际（2026-08-17 调价后生效） |
|---|---|---|
| 缓存命中输入 | ¥0.2 / M | **¥0.05 / M**（空闲）· ¥0.10 / M（高峰） |
| 缓存未命中输入 | ¥1.0 / M | **¥1.5 / M**（空闲）· ¥3.0 / M（高峰） |
| 输出 | ¥2.0 / M | **¥4.5 / M**（空闲）· ¥9.0 / M（高峰） |

来源：DeepSeek 官方定价页（附录 A-1）。

**错误的精确成因**（比「用了错数字」更值得记录）：旧文档的**未命中 ¥1 / 输出 ¥2 其实是调价前（2026-08-17 之前）的真实价目**，但**命中价被写成 ¥0.2，而调价前实为 ¥0.02——放大了 10 倍**。于是：

- 价差从真实的 **50 倍**（0.02 vs 1，调价前）被压缩成看起来的 **5 倍**；
- 而在调价后的今天，正确价差是 **30 倍**（0.05 vs 1.5）。

**两个都必须记住的结构事实**（后续所有比值型规则都由此而来）：

1. **价差不随时段变**：高峰 = 空闲 × 2，故 `miss/hit = 30`、`out/hit = 90` 在峰谷两侧完全相同；
2. **价差不随模型变**：Pro = Flash × 3（命中 0.15/0.30、未命中 4.5/9.0、输出 13.5/27.0），三个比值逐项相同。

> **推论**：任何以「比值」表达的决策规则（回本步数、闸门阈值）**与模型选择、时段选择无关**，只需一套参数。这使本方案的经济学部分具备跨模型稳定性。

> **方法论教训（沉淀为规则）**：凡进入设计文档的**单价、费率、价差比**，必须附官方来源链接与查阅日期；凡结论依赖价差比（如回本步数），必须**以公式而非数值**写入正文，数值只作示例。本次勘误的根源就是「数值写进结论、公式被省略」。

### E-2 「清除不破坏缓存前缀」是错的

v1.1 决策 D3 的理由写作「清除不破坏缓存前缀；压缩重写历史必致 miss」。**该前提不成立**。

Anthropic 官方上下文编辑文档明确：*"Tool result clearing: Invalidates cached prompt prefixes when content is cleared."*（清除同样会使被清除点之后的缓存前缀失效）。

**正确的差异**（这才是「清除优先」的真实理由）：

| 维度 | 清除 clear | 压缩 compact |
|---|---|---|
| 缓存前缀失效 | **失效**（变更点之后） | **失效**（变更点之后） |
| 额外推理成本 | **零**（纯机械编辑） | 一次摘要调用，输出按 ¥4.5–9/M 计费 |
| 信息损失 | 仅丢内容本身（可留占位） | 有损改写，细节不可复原 |
| 确定性 | 完全确定 | 依赖摘要模型，结果不稳定 |
| 可精确控制释放量 | 可（`clear_at_least`） | 不可 |

> 结论：**「清除优先于压缩」依然成立，但理由是「零推理成本 + 零信息失真 + 确定性」，不是「缓存无损」。**本体论上两者在缓存代价上同构，都遵守同一个回本公式（见 3.3）。

### E-3 回本步数不是「恒 2.7 步」，而是 `n* = ρ · r/(1−r)`

v1.2 用错误的价差（5 倍）算出「回本恒 2.7 步」，并把「恒」当作结论。正确公式（推导见 3.3）：

```
n* = ρ · r / (1 − r)        ρ = (miss − hit) / hit = 29（官方价目）
                            r = 压缩后残留比（如 r = 0.4 表示压回 40%）
```

| r（压回比） | 0.2 | 0.3 | 0.4 | 0.5 |
|---|---|---|---|---|
| **n\*（所需剩余步数）** | **7.2 步** | **12.4 步** | **19.3 步** | **29.0 步** |

**结论反转**：不是 2.7 步，而是 7~29 步。本项目实测 run 长度为 2~9 步且压缩最早在第 5~6 步才可能触发——**剩余步数普遍不足，事后压缩在 run 内几乎必然净亏**。v1.2 的定性结论（短 run 压缩不划算）成立且更强，但数值必须换成上表。

### E-4 附带修正：「周期涨落」的正确粒度是 run，不是 step

原方案把「荷载上升 → 压缩 → 回落」设想为 step 粒度。但本次查证发现：**run 内的追加式增长是全系统命中率最高的区域**（实测 96~99%），在此处压缩等于把最便宜的一段（hit，¥0.05）改写成最贵的一段（miss，¥1.5）。

> **修正后的周期定义**：涨落以 **run 为周期**——run 内单调上升（append-only，高命中，不干预）；run 边界做「前缀重建 + 压缩决策」（该时刻本就要付一次前缀代价，压缩的**边际罚金被摊薄**）。详见 3.5 与 4.5。

## 一、结论（TL;DR）

**不需要重制。建议「2.0 演进式重构」——保留骨架与契约兼容面，按职责分层扩建。**

四句话说明理由：

1. **骨架是对的**：`assemble()` 的「注册制过滤 → 刚性先扣 → water-filling 回吐 → 块内裁剪 → 互斥输出」管线、零状态纪律、纯度纪律（唯一持有 token 语义）、零特权（只走 `core.tokens`）——四条是全仓解耦纪律的承重墙，有 36 项测试 + 逐字节等价对拍护航。推倒重写等于把已验证资产归零。
2. **缺陷是「职责面缺位」，不是「数据结构错」**：缺的是记账、水位、压缩调度、清除、完整性校验、全景视图——**六项都是「加动词」，不是「改骨架」**。`BlockSpec` 是纯数据 dataclass（扩字段缺省即等价）、`assemble()` 是纯函数（扩参即兼容）、消费方**根本不 import 治理器类型**（鸭子契约），三点合起来意味着扩建的兼容成本接近于零。
3. **唯一真正的结构性问题**：契约是**单向 pull**，治理器无法声明「应该有哪些块」，漏报永远无人发现——这正是盲点长期隐形的机械成因。修它需要**新增一个方向**（声明式注册），依然是「加契约面」而非「改骨架」。
4. **本次详化产出一项高价值修复与一项关键设计纠正（均在现有骨架内落地）**：
   - **F-1（续接前缀错位，修复项）**：易变的 `react_prompt` 块排在庞大的 `react_chain` 之前，导致每次「继续」续接时**整个链约 3 万 token 全部 miss**。实测三例：31,065 / 31,483 / 31,101。修复后整晚费用可降 **35.0%**（¥0.5215 → ¥0.3388）。
   - **F-2（设计纠正，v2.1 重建）**：v2.0 的「思考链不参与治理」结论**已撤回**（范畴错误／漏算 F-1／回本视界错误，见 2.4.2）。重建后的模型是**单元原子性三成员**——思考链**是头号治理目标**，但只能与 `tool_calls` / `tool results` **同进同退**，唯一合法形态是**整单元替换为过程摘要**，执行点固定在 **run 收尾存档点**。链压缩由此从「明确不做」变为 **P2 的核心动作**。

**重制的唯一合理触发条件**（当前均不满足，见第三章）：跨 provider 差异化管理、多智能体共享窗口、流式增量装配成为硬需求时。若 T1 未来成立，**应只重制 `Compactor` 单元**而非整个治理器——故新架构已把「可替换的执行器」作为前提（见 4.3）。

**关于子 agent / 多 agent 的拓展性**（详见第七章）：2.0 骨架**天然可承载**——无状态现算意味着并发安全近乎免费，声明式注册天然支持「每个 agent 声明自己的块清单」。但四个补强点必须**预先留位**：`scope` 作用域参数、配额树（长在 budget 侧）、前缀共享策略、隔离交付契约。**`scope` 参数建议在 P1 就加**（留位成本近零，事后补则波及全部消费方）。**须警惕的反模式**：让子 agent 的轨迹进入父窗口——那会把本次成本事故放大成乘法级灾难。

### 2.3 新发现 F-1：续接前缀错位（本次详化最高价值发现）

**代码事实**（`plugins/react/loop.py`）：

```python
# 第 557-567 行：四个块提交
{"key": "react_system", ... "priority": -10},                                    # text
{"key": "react_prior",  ..., "coverage": (0, 1)},                                # rigid
{"key": "react_prompt", ..., "coverage": (1, 2)},                                # rigid ← 易变
{"key": "react_chain",  ..., "coverage": (2, 3)},                                # 可裁 ← 体积主体

# 第 584 行：输出按 coverage.lo 排序 → [system] + prior + prompt + chain
window = [{"role": "system", "content": asm.system_text}] + list(asm.prior)
```

**续接路径**：`sys/chat.py:209-211`

```python
res = await ctx.react.run(ctx, message, session_id=session_id,
                          prior=prior, resume=is_resume_intent(ctx, message))
```

`is_resume_intent()` 把「继续」类消息识别为续接（`chat.py:119-129`），但**传入 react 的 `prompt` 仍是用户本次的原始消息**（「继续」），而上一轮 run 的 `prompt` 是任务原文（「写一部 3 万字小说…」）。

**后果**：续接请求的消息序列为 `[system, prior, "继续", 存档链]`，与上一轮最后的请求 `[system, prior, 任务原文, 链]` 的**第一个差异点落在 `prompt` 块**——而 `prompt` 位于链之前，故**整条链（约 3 万 token）全部失效**。

**实测证据**（`agent_budget_log`，2026-09-29 02:00–02:20）：

| run | 首步 in | 首步 miss | 说明 |
|---|---|---|---|
| 24309f6e | 25,111 | 17,687 | 冷启动 |
| 7cbf23f9 | 38,745 | **31,065** | 续接 |
| 2bb1a4c5 | 39,547 | **31,483** | 续接 |
| 5206061b | 39,549 | **31,101** | 续接 |

三次续接首步的 miss 高度一致地落在 **3.1 万**——恰为链的体积量级，而非 `prior` 块（约 0.6k）。

**该读数能证明什么、不能证明什么（避免过度归因）**：

- **能证明**：失效点**不在链内部**，而在链之前的头部区域（若失效点落在链中，miss 会显著小于链长）；
- **不能证明**：头部区域中到底是哪一块先变了 —— `prompt`（本次消息 vs 任务原文）**必变**，`prior`（chat 层 summary + history）**也大概率会变**（会话推进导致 `covers_up_to_seq` 与内容更新）。两者都位于链之前，故**修复必须同时覆盖**，只冻结其一不足以对齐前缀。

**修复方向**（详见 6.1 P0-2）：**头部快照冻结**。

- **原理**：run 内要保持 append-only 高命中，**增长块必须位于消息序列末尾**（链是增长块 → 链必须在最后）。因此 `[system, prior, prompt]` 三者**全部**必须跨 run 逐字节稳定，别无选择。
- **做法**：首次进入某会话的 react run 时，把 `{system_text, prior, prompt}` 作为**头部快照**随链存档；续接时**原样复用**该快照作为头部三块，把用户本次的「继续」消息**追加为链尾的新 user 轮**。
- **为什么语义仍然正确**：续接时所有新增信息（上一轮结论、本次指令）都在链里——上一轮结论是链的最后一条 assistant 轮，本次指令是新追加的 user 轮，信息零丢失；头部快照只是「会话开场的固定上下文」。
- **降级**：存档中无头部快照（旧存档）→ 退回现行为，如实回退不伪造。

**收益实测**：可挽回 miss 126,028，整晚费用 ¥0.5215 → ¥0.3388，**降幅 35.0%**。

> **为什么不能靠「交换块序」解决**（必须记下的否决论证）：若把 `prompt` 移到链之后，run 内每步的新增内容就插在 `prompt` 之前，于是**上一轮请求的整段序列不再是新请求的前缀**——run 内命中率会从 96~99% 崩掉。**「增长块必须在最后」是一条硬约束**，它同时排除了「把易变块移到链后」这条看似聪明的捷径。参见第 9 章命题 4。

### 2.4 新发现 F-2（**已撤回**）与重建：单元原子性三成员

> **本节状态**：v2.0 的原结论已作废，v2.1 重建。原结论「思考链不参与任何清除/压缩/改写」是**错误的**——经驳回后复核，确认存在三处推理缺陷（见 2.4.2）。本节保留撤回论证以便回溯，并给出重建模型（2.4.3）。

#### 2.4.1 原结论（v2.0，**作废，勿再引用**）

v2.0 曾论证：思考链**生成**按输出计价 ¥4.5/M、**重放**按输入计价且位于 append-only 区 → 走 hit 价 ¥0.05/M，比值 **90:1**；故「清理思考链省 token」在钱上几乎无收益，且引入两类风险（400 风险、缓存失效）。结论被写死为「**思考链不参与任何清除/压缩/改写**」。

#### 2.4.2 三处推理缺陷（撤回依据）

| # | 缺陷 | 具体错在哪 |
|---|---|---|
| **R-1** | **范畴错误**（最致命） | 拿「生成单价」与「重放单价」相比得出「重放很便宜」，但**生成成本已经沉没**，不在任何未来决策的可控范围内。治理决策的正确对象是「**这条链在余生还会被重放多少次**」，而非「重放单价是否低于生成单价」。以沉没成本为分母，必然得出「什么都不用动」的荒谬结论——**且该结论恰好把体量最大的治理对象设为禁区**。 |
| **R-2** | **漏算 F-1，把问题留在原地** | 「重放走 hit 价所以便宜」的前提是**前缀命中在**。而 v2.0 自身在第 2.3 节已发现 F-1（续接时整链 miss 3.1 万）——那一刻思考链是**按 miss（¥1.5）计价**的，正是全链条最贵的输入。忽略相邻发现的直接后果：F-1 修复后，链内体积才是残余 miss 的主要来源，而**思考链恰是链中最大体量成分**。 |
| **R-3** | **回本视界错误** | 用「单 run 的剩余步数」做回本判据，而长会话的回本视界是**全生命周期剩余重放次数**（跨 run、跨续接），远大于单 run 步数；短视界必然系统性低估重放收益，进而把「该压」判成「不必压」。 |

> **方法论教训（沉淀为规则，与 E-1 的教训同族）**：凡「要不要治理某对象」的判断，**不得以该对象的历史成本作为比较项之一**（沉没成本）；比较项只能是「治理动作的代价」与「未来重放次数的节省」。E-1 的教训是「数值必须配公式」，本条的教训是「**比较基准错了，结论必然反向**」。

#### 2.4.3 重建模型：单元原子性三成员

思考链**是头号治理目标**（体量最大、质量危害最强），但**不能单独动**。原因在于 wire 层面一条更硬的结构约束：

```
一个原子单元（wire unit）＝
  [assistant{ content, reasoning_content }]   ← 上半部：思考链 + 正文
+ [assistant.tool_calls]                      ← 配对头
+ [role=tool 的 results]                      ← 配对尾
```

三条纪律（缺一即违反不变量 I-2）：

| # | 纪律 | 含义 |
|---|---|---|
| **U-1** | **同进同退** | 三成员只能**整体保留**或**整体替换**；不得只删思考链、只删 `tool_calls`、只留回灌。9-28 的 400 是「下半部被拆」（I-1），9-29 的 400 是「上半部丢失」——**两次事故同属一条不变量**。 |
| **U-2** | **只允许整单元替换为过程摘要** | 唯一的合法压缩形态：把一次「思考 → 调工具 → 看结果」**原子替换**为一段自产的过程摘要（保留结论与关键产物，丢弃原始字节）。**禁止截断、禁止改写、禁止部分保留。** |
| **U-3** | **执行点 = run 收尾存档点** | 替换只在 `plugins/react/loop.py` 的链存档点（`_archive_chain`）发生：**run 内一律不动**（保 append-only 高命中），**在新 run 发出第一条请求之前**完成落位。 |

**为什么执行点必须是收尾存档点**（三条理由）：

1. **run 内纪律不可破**：run 内是 96~99% 命中区，任何改写都会把便宜段（hit）改成昂贵段（miss）；
2. **存档点本就产出「下一次请求的链副本」**：替换在此发生**不引入额外重建**，是零附加成本的改造点；
3. **天然满足「一 run 一次」**：与 4.3 中「冷却结构化」的无状态解法严丝合缝，无需任何记忆字段。

**官方约束（决定「能否整块剥离」的分界线）**：`reasoning_content` 的**回传义务取决于该请求是否携带 `tools`**（官方来源见附录 A-8）——

| 请求形态 | 是否带 tools | 思考链回传义务 | 对应端点 |
|---|---|---|---|
| ReAct 循环 | **是** | **必须回传**（9-29 01:27 实测报错原文即为此） | `react·loop` |
| 计划 / 叙述 | 否 | 可剥离（无工具配对语义，传入亦被忽略） | `chat·plan` / `chat·narrate` |

> 这条分界线是**整单元替换合法性**的判据来源：带 tools 的形态下，替换后的过程摘要必须**同时覆盖三成员的信息**（调用意图、参数要点、结果要点），否则回传义务不满足；不带 tools 的形态下，思考链可独立剥离。**登记为实验 X-2。**
>
> **旁证（Anthropic 同构）**：其 400 禁令针对「latest assistant message cannot be modified」，并另提供服务端 thinking 清除策略——即「**历史思考块可清、最新一条不可改**」是两家共有的同构约束，反过来说明「整单元移除（assistant 整条消失）→ 无回传义务 → 构造上合法」的路径成立。

**与 I-1 的关系**：I-1 守单元的**配对形状**（`tool_calls` ↔ `tool results`），I-2 守单元的**内容原子性**（含思考链）；两者互为表里，`execute` 前后同时校验。

> **开放问题（登记为实验 X-2）**：实测「整单元替换为过程摘要」在**带 tools / 不带 tools** 两种形态下的 400 边界与语义可续性。这是 P2 链压缩的前置实验，**必须先于 P2 开启 `compact_mode=on`**。

## 三、成本模型（修正版）

### 3.1 三价模型

```
单次请求成本 = hit × h + miss × m + out × o
官方价目（元/百万 token，Flash 空闲）：h = 0.05, m = 1.5, o = 4.5
比值：h : m : o = 1 : 30 : 90
```

三个必须内化的推论：

1. **token 总量不是成本**。1 万个 hit token（¥0.0005）与 1 万个 miss token（¥0.015）差 30 倍，与 1 万个输出 token（¥0.045）差 90 倍。
2. **miss 是全链条最贵的输入**。而本项目 miss 的唯一稳定来源是「前缀重建」（续接、压缩、任何非末尾改写）。
3. **输出是第二大成本项，且几乎无人管理**。

### 3.2 实测重算（33 笔账单，2026-09-29 02:02–02:09）

| 项 | 数量 | 单价 | 金额 | 占比 |
|---|---|---|---|---|
| 缓存命中输入 | 629,632 | ¥0.05/M | ¥0.0315 | 6.0% |
| 缓存未命中输入 | 173,187 | ¥1.5/M | **¥0.2598** | **49.8%** |
| 输出 | 51,175 | ¥4.5/M | **¥0.2303** | **44.2%** |
| **合计** | | | **¥0.5215** | 100% |

> 对照旧口径（错误价目）算出的 ¥0.4015——误差 30%，且成分结构完全不同（旧口径下 miss 占 43%、输出占 20%）。

**关键读数**：hit 只占 6%。这意味着**「压缩以省 token」在钱上几乎无空间**，而**「消除 miss」与「控制输出」才是钱的去向**。

### 3.3 回本定理（推导）

设：链长 `W`，压缩后残留 `R`，压回比 `r = R/W`，剩余步数 `n`。

- **一次性罚金**：变更点在链内（非末尾），其后全部 token 需按 miss 重新处理。相对理想命中态，多付 `R × (m − h)`。
- **每步节省**：后续每步少发送 `W − R` 个 token，而这些本按 hit 计价，故节省 `(W − R) × h`。
- **回本条件**：`n × (W − R) × h  >  R × (m − h)`

```
n* = ρ · r / (1 − r)          ρ = (m − h)/h = 29
```

三处必须写明的边界条件：

1. **仅当变更点在链中（非末尾）时该公式成立**。若在末尾追加（append-only），罚金为 0——这正是「入链即刻瘦身」之所以「纯赚」的数学原因。
2. **前提是链之前的 `[system, prior, prompt]` 前缀仍然命中**。若此处已因 F-1 失效，则罚金被淹没、压缩的相对代价看起来变小——**先修 F-1，再谈压缩，否则两个效应互相污染**。
3. **`r` 越小罚金越小但节省也越少，`n*` 随 `r` 单调上升**；`r → 1` 时 `n* → ∞`（几乎不释放，纯付罚金）。

### 3.4 杠杆排序（按实测金额，重排）

| # | 杠杆 | 实测/上限收益 | 性质 | 落地批次 |
|---|---|---|---|---|
| **1** | **续接前缀对齐（F-1）** | **−¥0.1827 / −35.0%**（实测可挽回 miss 126,028） | **纯赚，零信息损失** | **P0** |
| 2 | 生成侧控制：**`reasoning_effort` 档位**（见 2.4.4）+ 回应去冗余 | 上限 ¥0.2303（44.2%），可及部分待测（实验 X-1 / X-5） | 纯赚（**同时**减少输出成本与后续重放量） | 三期实验 |
| 3 | 入链即刻瘦身（大参数不入链） | 金额小（hit 档，上限约 ¥0.03）；**价值在质量与上限风险** | 纯赚 | P2 |
| 4 | 事后清除 / 压缩（含**链内整单元替换**） | run 内为**负**（`n*` = 7.2~29 步）；仅超长 run 与 run 边界有意义 | **条件性（成本）＋ 纯赚（质量）** | P2（shadow 先行） |

> **对 v1.2「入链即刻瘦身可省 20~30%」的修正**：该估计建立在错误价目上。按其真实计价档（hit，¥0.05/M）重算，**降 token 量的金额收益不足总费用的 6%**。它依然值得做，但理由要换成三条非成本理由：①降低撞 1M 能力上限的硬失败风险；②改善上下文质量（见 3.5）；③降低 TTFT 延迟。

> **对杠杆 4 的补充（v2.1）**：杠杆 4 的**成本收益**确实是条件性的（受 `n*` 约束），但**思考链（链内最大体量成分）的治理价值主要在质量战线**（3.5），不受 `n*` 约束——信噪比的改善是「纯赚」。v2.0 的 F-2 错误正是把这条质量账误记到成本账上，从而得出「不做」的结论（详见 2.4.2）。

### 3.5 成本与质量是两条战线（本方案的战略定位）

| 战线 | 主指标 | 本项目的病根 | 对应方案 |
|---|---|---|---|
| **成本** | 总费用（¥） | miss（前缀重建）+ 输出冗余 | P0 前缀对齐；三期输出实验 |
| **质量与可靠性** | 有效上下文比（信号/噪声） | 链无界增长（**思考链是头号体量源**，见 2.4.3）；刚性块无 cap；黑洞未登记 | P1/P2 水位与 cap；**P2 链内整单元替换（头号目标）**；P0 记账 |

**质量战线的证据链**（附录 A-3）：Chroma 2025 对 18 个前沿模型的系统研究发现**全部退化**且退化**远早于**文档上限；Stanford 的 lost-in-the-middle 显示相关文档从第 1 位移到第 5~15 位时准确率掉 30%+；且**逻辑连贯的输入比打乱的输入更伤性能**（连贯文本制造了更可信的干扰项）。

> **推论**：把 1M 窗口塞到 40 万 token，省下的钱有限（hit 便宜），付出的质量代价可能很大。**上下文治理的主要理由不是省钱，而是保持信噪比。** 这为 P1/P2 的水位与 cap 提供了独立于成本的价值论证——即使某天价目变得极度便宜，治理器依然必要。

## 四、目标架构（Context Governor 2.0）

### 4.1 分层总览

```
┌─ 消费方（不 import 治理器类型，纯属性面 / dict 入参） ──────────────┐

                               ▼
┌─ 契约面 protocols.py（三组） ────────────────────────────────────┐
│  A 被动查询组（现有 12 方法，冻结不动）                          │

                               │

│  │  Ledger   │ │ Waterline │ │ Compactor │ │ Inspector │        │
│  │  记账     │ │  水位判定 │ │  执行器   │ │  视图与   │        │
```

**拆分原则**：门面 `ContextGovernor` 仍是**唯一对外实例**（接缝注入不变、`Services.CONTEXT` 不变、36 项测试的接口不变），四个单元是**内部模块**——「拆分」对消费方与守卫完全透明。

**实施纪律**：四单元**先做纯搬迁**（行为零变，仅把现有方法搬家），再逐项加能力。这样每一步都可对拍。

### 4.2 契约面三分组（字段级详化）

#### 4.2.1 `BlockSpec` 扩展

```python
@dataclass(frozen=True)
class BlockSpec:
    # ---- 既有字段（不动）----
    key: str
    kind: str                                   # "text" | "messages"
    present: bool
    payload: str | list[dict] = ""
    weight: float = 0.0
    priority: int = 100
    rigid: bool = False
    coverage: tuple[int, int] | None = None
    # ---- 2.0 新增（全部有缺省 → 旧调用逐字节等价）----
    layer: str = ""                             # "" = 由 rigid 推导（见 4.4）
    cap_tokens: int = 0                         # 0 = 无 cap，沿用预算派生
    compact_at: int = 0                         # 0 = 不参与自动压缩触发
    compact_floor_ratio: float = 0.4            # 压缩后的目标残留比 r
    on_compact: Callable[[Any, int], Any] | None = None
    regenerable: bool = False                   # True = 内容可清除后重建 → clear 候选
    volatile: bool = False                      # True = 每次请求内容可能变 → 前缀规划用
```

**兼容规则（硬约束，须写成测试）**：

| 规则 | 断言 |
|---|---|
| 所有新字段缺省时，`assemble()` 输出与 v1.3 逐字节相同 | 复用既有对拍测试 + 新增「全缺省 vs 显式等价」用例 |
| `layer == ""` 时必须等价于 `layer = "resident" if rigid else "runtime"` | 单元测试直断言推导函数 |
| `_coerce()` 必须支持新字段的 dict 形式 | 新增 dict 入参用例 |

#### 4.2.2 `declare` 与 `BlockDecl`（补上缺失的方向）

```python
@dataclass(frozen=True)
class BlockDecl:
    key: str
    kind: str                       # "text" | "messages"
    owner: str = ""                 # 消费方自报标识（仅作归集与告警归属）
    required: bool = True           # True = 本阶段必须有；缺失进 missing_blocks
    layer: str = "runtime"
    cap_tokens: int = 0

class GovernorLike(Protocol):
    ...
    def declare(self, decls: list[BlockDecl], *,
                phase: str = "default",
                scope: str | None = None) -> None: ...
```

- **幂等**：同 `(scope, phase, key)` 重复声明以最后一次为准（启动期声明，运行期不应变）。
- **用途**：①`missing_blocks` 完整性校验（漏报变红灯）②`unaccounted_tokens` 归属参考 ③`/context` 视图的「应有 vs 实有」对照。
- **为什么不违反零状态纪律**：`declare` 属**配置期**行为（与 `from_config` 同级），是启动期一次性注入的**只读常量**；「零状态」约束的是**运行期不得记忆历史**。文档与代码注释必须把这句写清楚，否则未来维护者会误以为破坏纪律。

#### 4.2.3 `assess` 与 `WaterlineReport`

```python
@dataclass(frozen=True)
class WaterlineReport:
    used: int
    working_window: int             # 经济基数（新增配置字段）
    capability_window: int          # 能力上限（max_context_tokens）
    load_ratio: float               # used / working_window
    level: str                      # "normal" | "high"
    suggested: str                  # "none" | "clear" | "compact" | "evict" | "clip"
    gates: dict[str, Any]           # 各闸判定明细（可审计、可回放）

class GovernorLike(Protocol):
    def assess(self, used: int, *,
               working_window: int | None = None,
               remaining_steps: int | None = None,
               phase: str | None = None,
               scope: str | None = None) -> WaterlineReport: ...
```

**算法**：

```
w       = working_window or 配置 working_window_tokens
ratio   = used / max(1, w)
level   = "high" if ratio >= window_high_ratio else "normal"
suggest = "none" if level == "normal"
        else 依 4.2.4 决策表给出（无候选块时回落 "clip"）
gates   = {
  "threshold":  {"passed": level == "high", "ratio": ratio, "high": window_high_ratio},
  "timing":     {"at_run_teardown": phase == "run_teardown"},
  "payback":    {"required_steps": n*, "remaining_steps": remaining_steps, "passed": ...},
  "release":    {"clear_at_least": ..., "expected_release": ...},
}
```

> **`remaining_steps` 由消费方传入**（治理器不认识「循环」「步数」这类业务概念——它只做除法）。缺省 `None` 时 `payback` 闸判定为 `passed=False`（保守不压）。**v2.1 补充其语义**：执行点定在 run 收尾存档点后，本参数指「**下一次 run 的预计剩余步数**」——消费方可用「上一次 run 的实际步数」或会话级估算传入；无法估算即不传（闸不过，保守不压）。

#### 4.2.4 `Action` 与 `plan`（决策表）

```python
@dataclass(frozen=True)
class Action:
    kind: str                       # "keep" | "clear" | "compact" | "evict" | "clip"
    target: str                     # 块 key
    scope: str | None = None
    expected_release: int = 0
    reason: str = ""
    payload: Any = None             # 交给 execute 的透传参数（如目标残留比）

class GovernorLike(Protocol):
    def plan(self, report: WaterlineReport, *,
             blocks: list[BlockSpec] | None = None,
             mode: str | None = None) -> list[Action]: ...
```

**决策表**（自上而下，首个命中即返回；`mode` ∈ `off|shadow|on`，缺省读配置）：

| 序 | 条件 | Action | 说明 |
|---|---|---|---|
| 1 | `mode == "off"` 或 `level == "normal"` | `keep` | 不做任何动作 |
| 2 | 存在 `regenerable=True` 且 `layer ∈ {on_demand, runtime}` 的块，且预计释放 ≥ `clear_at_least_tokens` | `clear` | **首选**：零推理成本 |
| 3 | 存在 `layer == "on_demand"` 且内容可重取（懒加载场景） | `evict` | 卸载按需块 |
| 4 | `timing.at_run_teardown == True` 且 `payback.passed == True` 且有 `on_compact` 的块 | `compact` | 仅 run 收尾存档点（即下一个 run 请求发出之前）；需过回本闸 |
| 5 | 其余 | `clip` | 保底：不做结构性改动 |

**顺序理由**：`keep → clear → evict → compact → clip` 是**「代价从低到高、可逆性从高到低」**的排序，与 Anthropic 官方建议（清除优先于压缩）一致，且符合本项目实测（压缩罚金 30 倍）。

**shadow 模式**（默认）：`plan` 照常计算，`execute` **不执行**，只把决策与理由写入遥测。这是让「压缩阈值」用真实数据校准的唯一安全方式。

#### 4.2.5 `execute` 与 `ApplyResult`

```python
@dataclass(frozen=True)
class ApplyResult:
    applied: list[str]                       # 已执行的动作描述
    skipped: list[tuple[str, str]]           # (target, 跳过原因)
    released: int                            # 实际释放 token
    invariants: dict[str, bool]              # 四条不变量的校验结果
    degraded: bool                           # 是否有失败降级

class GovernorLike(Protocol):
    def execute(self, actions: list[Action], blocks: list[BlockSpec],
                *, mode: str | None = None) -> tuple[list[BlockSpec], ApplyResult]: ...
```

**执行纪律（三条，写成测试）**：

1. **失败即降级为 keep**，绝不半途破坏结构；
2. **执行前先校验、执行后复校**：四条不变量任一失败 → 回滚该动作并记 `degraded=True`；
3. **`on_compact` 由消费方提供**，治理器只调用、不理解其内部（纯度）；回调抛异常 → 该动作跳过，其余继续。

### 4.3 内聚单元四件（职责/结构/算法/失败模式）

#### Ledger 记账

- **职责**：把「预算花在哪」变成可查询的事实。
- **三本账**：
  1. **块账**（既有 `BlockReport` + 新字段 `layer` / `cap` / `reason`）；
  2. **附件账**（`AttachmentReport`：tools schema / response_format / 图片等**请求附加项**）；
  3. **真实账**（估算 vs 真实，接 `cost_factor`，为 EWMA 提供样本）。
- **关键新增量**：
  - `unaccounted_tokens = input_budget − Σ块used − Σ附件used`（**预算黑洞的唯一显式出口**）；
  - `stable_prefix_tokens`：**首个 `volatile=True` 块之前的字节数**——缓存友好度的直接度量（F-1 的体检指标）；
  - `AttachmentSpec.claimed_tokens`：消费方用 `core.request_cost.estimate_request_cost` 算好后传入；治理器**不重复实现**（零特权），可选 `payload` 供 Inspector 复算交叉校验（两把尺子）。
- **失败模式**：`unaccounted < 0` → 说明重复计账，记 `warn` 不抛错；`unaccounted > 阈值` → 记 `warn`。

#### Waterline 水位

- **职责**：判定「当前荷载相对经济基数处于什么位置、该不该动作」。
- **结构**：**两态 + 时机规则**（不是三态机，理由见下）。
- **算法**：见 4.2.3。
- **为什么不是三态机（重要逻辑闭合点）**：原设计含 `cooling` 态，但「是否刚压缩过」需要记忆 → 与「零状态」纪律冲突。
  **解**：把冷却**结构化**——**每个 run 至多压缩一次，且仅在 run 边界（收尾存档点）**。这样「冷却」是规则的自然推论，无需任何状态。（v2.1 修正：原写「run 入口」，后按 U-3 的物理执行点统一改为「收尾存档点」——二者是同一边界的两个视角，挂钩点必须在收尾侧，因为链副本在那里产出。）
- **失败模式**：`working_window <= 0` → 拒绝构造（构造期校验，与现有 `max_context_tokens <= 0` 同纪律）。

#### Compactor 执行器

- **职责**：把 `plan` 的决策落到块上，并守住不变量。
- **优先级**：`clear > evict > compact > clip`（代价递增）。
- **接口**：`compact(block, target_tokens, on_compact) -> (new_payload, released)`。
- **压缩粒度 = 原子单元（v2.1 新增，硬约束）**：当目标块是 `react_chain` 时，`compact` **不得**在消息序列上任意切分——切分单位固定为 **wire 原子单元**（`[assistant{reasoning_content}] + [tool_calls] + [tool results]`），且唯一合法动作是「**整单元 → 过程摘要**」的原子替换。切点落在单元内部（即 2.4.3 所禁的「半改」）一律判为 **I-2 违规并回滚**。
- **执行点 = run 收尾存档点（v2.1 新增）**：链内替换由 `react` 在 `_archive_chain` 处触发（见 4.5），治理器只提供 `compact` 原语与校验，不决定触发时机——时机属消费方语义（零业务语义纪律）。
- **provider 可替换**：`Compactor` 是唯一与「厂商上下文原语」相关的单元。当前 DeepSeek 无服务端清除 API，故实现为客户端编辑；**若未来接入 Anthropic，只需替换本单元**（对应重制判据 T1）——这正是「不重制整个治理器」的底气所在。
- **失败模式**：`on_compact` 返回类型不符 → 视为失败，保留原 payload，记 `skipped`；不变量校验失败 → 回滚。

#### Inspector 视图与不变量

- **职责**：①`/context` 式分类视图 ②四条不变量断言 ③前缀稳定性体检。
- **视图样例**（由 `AssemblyReport` + `LedgerReport` 直接渲染，**不新增状态**）：

```
上下文占用  scope=default  phase=loop  step=3
  resident   常驻     2,253 tok   5.8%   ✓ 字节冻结
  on_demand  按需       902 tok   2.3%   ⚠ 未登记（黑洞）
  memory     记忆       581 tok   1.5%
  input      输入        12 tok   0.0%   ✗ 未入账
  runtime    运行时  36,214 tok  93.0%   ⚠ 未压缩（阈值 96,000）
  ────────────────────────────────────────────────
  合计 39,962 / 能力窗口 1,000,000（4.0%）/ 经济窗口 96,000（41.6%）
  估算 39,962  vs  真实 58,290   ×1.46
  稳定前缀 2,846 tok（volatile 块：react_prompt）→ ⚠ 其后仍有 36,214 tok 受影响
```

- **不变量断言**（见 4.6）。
- **失败模式**：视图渲染失败不得影响装配（纯只读旁路）。

### 4.4 块模型五层（替代 rigid/flex 二分）

| 层 | 归属 | 策略 | cap 建议 | 现行对应 |
|---|---|---|---|---|
| `resident` 常驻 | 系统提示 / 输出格式 | 硬 cap，超限压缩 + 双通道告警 | 8,000 | `rigid=True` |
| `on_demand` 按需 | 工具 schema / 记忆召回 | 可 evict（懒加载） | 8,000（懒加载关）/ 2,000（开） | ⚠ 预算外黑洞 |
| `memory` 记忆 | 长期 / 短期摘要 / 工作记忆 | 可 summarize | 4,000 | 部分 flex |
| `runtime` 运行时 | ReAct 轨迹 | 可 clear / compact（**仅 run 收尾存档点，且整单元替换**） | 余额 | flex（w 1.0） |
| `input` 输入 | 用户当前输入 / 附件 | cap 且保护首条 + 最近 1 条 | 单条 2,000 | 无 cap |

**缺省推导**（兼容关键）：`layer == "" → "resident" if rigid else "runtime"`。

**cap 语义**：`cap_tokens > 0` 时，该块分配上限取 `min(预算派生, cap_tokens)`；超限走既有「刚性超限双通道」路径（`rigid_overflow` + `system_text` 显式标注），**绝不静默截断**。

> **为什么 cap 必须绝对值而非比例**：本次事故的机械成因正是「所有阈值随窗口按比例放大 42 倍后全部失灵」。cap 是绝对量级概念（「系统提示不该超过 8k」），与窗口无关。

### 4.5 生命周期：涨落以 run 为周期

```
run 内（append-only，高命中 96~99%）
  链 25k → 38k → 48k …    ← 不干预（压缩在此处是净亏，见 3.3）
        │
        ▼  run 边界（最自然的压缩时机）
  ┌──────────────────────────────────────────────┐
  │ ① 前缀对齐：复用原 prompt，续接消息入链尾     │  ← F-1，P0
  │ ② 水位判定：assess(used) → normal / high      │  ← P1
  │ ③ 决策：plan() → clear / compact / keep       │  ← P2（默认 shadow）
  │ ④ 执行：execute() → 不变量校验 → 落位         │  ← P2
  │ ⑤ 链压缩执行点：run 收尾存档点（_archive_chain）│  ← P2，整单元替换（2.4.3）
  └──────────────────────────────────────────────┘
        │
        ▼
  新 run 从低位起步 → 再次单调上升 → 再一次边界回落
```

**三个闸（重述，全部无状态）**：

1. **阈值闸**：`load_ratio = used / working_window ≥ window_high_ratio (0.70)`。`working_window_tokens` 默认 **96,000**（经济基数，与 1M 能力上限解耦）。
2. **时机闸**：仅 `phase == "run_teardown"`（run 收尾存档点）。**这是「冷却」的无状态实现**——一 run 一次。（v2.1：由「run 入口」统一为「收尾存档点」，见 2.4.3 U-3。）
3. **回本闸**：`remaining_steps ≥ n* = ρ·r/(1−r)`。`remaining_steps` 由消费方传入；缺省视为不通过。

**为什么阈值取 96,000 而非 24,000**：实测正常 run 的链峰值为 4.7 万，96k 阈值保证**普通任务永不触发压缩**（压缩只作为超长任务的兜底）；而 24k 会让每个 run 都在亏损区反复压缩。**这是 3.3 公式的直接推论，不是拍脑袋。**

### 4.6 四条不变量（断言化，不可绕过）

| # | 不变量 | 检查时机 | 失败处置 |
|---|---|---|---|
| **I-1** | **配对完整**：任何裁剪/清除后，`role=tool` 必有前置 `assistant.tool_calls`（9-28 实测 400 的根因） | `execute` 前后各一次 | 回滚该动作，记 `degraded` |
| **I-2** | **单元完整（原子性）**：`[assistant{reasoning_content}] + [tool_calls] + [tool results]` 三成员**不得单独增删改**；合法形态只有「整单元保留」或「整单元替换为过程摘要」（9-29 实测 400 的根因＝违反本不变量） | 同上 | 回滚 |
| **I-3** | **前缀稳定性可测**：任何改变历史字节的动作必须被记录，且 `stable_prefix_tokens` 可查询 | 每次装配后 | 记录 + 告警（不阻断） |
| **I-4** | **预算守恒**：`Σ块used + Σ附件used + unaccounted = input_budget`（允许 ≤ 容差） | 每次装配后 | 记录 + 告警 |

**I-2 的精确表述**（v2.1 由「思考链完整」升级为「单元完整」，两者合并）：一个 wire 原子单元 = `[assistant{reasoning_content}] + [tool_calls] + [tool results]`，其合法状态只有两种——**整体保留（字节不变）** 或 **整体替换为过程摘要（显式开关，原子替换）**；**任何半改一律非法**，包括：只删思考链、只删 `tool_calls`、只留回灌、截断其中任一成员。
**为什么与 I-1 合并表述**：I-1 守单元的**配对形状**，I-2 守单元的**内容原子性**；9-28 的 400 是下半部被拆（I-1 域），9-29 的 400 是上半部丢失（I-2 域），**两次事故同属一条不变量**——分开表述会让维护者误以为「思考链可以单独动」。执行 `execute` 时两者同时校验。
**合法剥离的分界线**（见 2.4.3）：`reasoning_content` 的回传义务取决于请求是否携带 `tools`——带 tools（`react·loop`）必须回传，替换后的摘要须覆盖三成员信息；不带 tools（`chat·plan` / `chat·narrate`）可独立剥离。

## 五、设计决策 D1~D8（逐条含证据与替代方案）

| # | 决策 | 理由（含证据） | 替代方案与否决理由 |
|---|---|---|---|
| **D1** | **双窗口解耦**：`max_context_tokens`（1M 能力上限，总闸）vs `working_window_tokens`（96k 经济基数） | 一个字段承担两个量纲 → 窗口放大即全阈值失灵（本次事故根因）；且经济阈值有独立于成本的**质量论证**（context rot，附录 A-3） | 替代：把 `max_context_tokens` 调小。**否决**：会把「能力」与「经济」再次混为一谈，且实测普通任务不触发（无效） |

| **D4** | **压缩三重闸**（阈值 + 时机 + 回本），且默认 `shadow` | 实测 `n*` = 7.2~29 步，run 内压缩净亏；shadow 让阈值可用真实数据校准 | 替代：无闸自动压缩。**否决**：为省 token 反而增费 |
| **D5** | **声明式注册 + 完整性校验**（`declare` / `missing_blocks`） | 单向 pull 无漏报发现能力 → 盲点长期隐形（结构性成因） | 替代：人工排查。**否决**：已证明隐形不会被发现 |
| **D6** | **三账本记账**（块/附件/真实）+ `unaccounted_tokens` | tools schema 现在是「扣预算但不登记」的黑洞；三把尺子 1.7x 漂移已实测 | 替代：只记块账。**否决**：黑洞继续隐形 |
| **D7** | **不变量断言化**（I-1~I-4） | 9-29 两起 400 的修复本就等于业界不变量，但只是补丁（Claude Code 三级压缩把同类规则作为系统级保护） | 替代：继续打补丁。**否决**：同一类错误会第三次发生 |
| **D8** | **阶段化装配**（`phase`） | 治理器需知道「本阶段该有哪些块」才能校验与定策（`missing_blocks` 的前提） | 替代：按 key 前缀猜阶段。**否决**：把业务语义塞进治理器 |

**三条纪律不变**：零状态（水位现算 + 冷却结构化）· 零业务语义（只认形状与自产标记）· 零特权（只走 `core.tokens`）。

**P1 实施要点（可供 P2 直接依赖的事实）**：

- **cap 解析优先级**：`BlockSpec.cap_tokens > 0` 显式优先；否则按 `effective_layer()` 取层配置（`resident`→`resident_cap_tokens`、`on_demand`→`on_demand_cap_tokens`、`input`→`prompt_cap_tokens`）；`memory` / `runtime` **无 cap**（0）。故旧调用方（未标 layer）行为不变，唯有 `rigid=True` 的块会推导为 `resident` 而受 8000 上限约束——实测既有测试全部落在 cap 内，**零回归**。
- **cap 与预算的关系**：cap 是**分配上限**（参与 water-filling，未用满的 cap 余量自然回吐公共池），与 `input_budget` 正交；刚性块超 cap 走**刚性超限双通道**（`rigid_overflow` + `system_text` 显式标注段），可裁块超 cap 记 `trimmed`——**两处都不静默截断**。
- **`assess` 无状态**：结果只依赖入参 + 实例的**只读配置**；`phase == "run_teardown"` 是「一 run 一次」冷却的无状态实现（非时间戳记忆）。react 在**收尾存档点**（`_archive_chain` 之后）发 `CONTEXT_WATERLINE`，与 P2 链压缩⑤**同一时机闸**。
- **`scope` 语义**：不透明归集键——只作 `(scope, phase)` 声明表的键、只回填报告；**治理器绝不据此分支控制流**。

**P2 实施要点（可供 P3 直接依赖的事实）**：

- **`plan` 决策表顺序＝`keep → clear → evict → compact → clip`**：代价从低到高、可逆性从高到低，与 Anthropic「清除优先于压缩」一致（本项目实测压缩罚金 **30 倍**）。`off` → 恒 `keep`；`level != "high"` → 恒 `keep`；`clear` 候选须 `regenerable` 且层 ∈ `{on_demand, runtime}` 且 Σ释放 ≥ `clear_at_least_tokens`；`evict` 候选须 `layer == on_demand` 且 `regenerable`；`compact` 须 `timing.at_run_teardown && payback.passed` 且有 `on_compact`；否则 `clip`。
- **`execute` 三纪律**：①`mode != "on"` 直接回报（`skipped` 记 `shadow` / `mode_off`，**不落位**）；②逐动作**执行前校验 → 执行后复校**，四条不变量（I-1/I-2/无缩减/回调异常）任一失败 → **回滚该动作**并记 `degraded=True`；③`on_compact` 由消费方提供，治理器**只调用不理解**，回调抛异常只跳过该动作、其余继续。
- **压缩粒度＝原子单元（硬约束）**：`_compact_messages` 只做「**整单元 → 过程摘要**」；`pinned` 单元与**最新单元**强制入保留集，其余从最新往回按**整单元**纳入，累计超 `target` 即断；`drop_idx` 只含**完整单元**（切点落在单元内部即判 I-2 违规并回滚）。
- **三模式缺省 `shadow`**：照常 `plan` 但 `execute` 不落位，决策与理由写 `CONTEXT_COMPACT_DECIDED`——**这是校准阈值的唯一安全方式**（P2 验收：shadow 运行一周、≥3 个 run 正收益证据方允许开 `on`）。
- **收尾执行点**：`_govern_at_teardown` 接在 react **两处收尾**（收敛路径 + 触顶路径）的 `_archive_chain` **之前**——存档即「下一次请求的链副本」，在此替换不引入额外重建。`CONTEXT_WATERLINE` 仍在 `_archive_chain` **之后**发（P1 既有）。两者共用同一时机闸 `phase == "run_teardown"`。
- **配置三处登记**（与 P1 同纪律）：`agent/core/config_schema.py`（`agent.context` 节加 `compact_mode: str` / `clear_at_least_tokens: int`）→ `agent/profiles.py`（`BASE_AGENT_CONFIG` 单一真相源）→ `agent/run/chat.py`（`_SETTING_SCHEMA` / `_PLUGIN_OF_KEY` / `_SETTING_DEFAULTS` + 设置页前端 `select`）。构造期校验 `compact_mode ∈ COMPACT_MODES`、`clear_at_least_tokens ≥ 0`。

**P3 相对设计稿的四处实施说明**（均为兼容/可测性调整，不改变设计意图）：

| # | 设计稿原文 | 实施取值 | 理由 |

**P3 实施要点（四批收口）**：

- **Inspector 模块** `agent/plugins/context/inspector.py`：**纯数据 + 纯函数**（stdlib-only，不 import 任何插件/内核实现）；只认契约词汇（token 数、层名、不变量 ID），``stage`` / ``scope`` 是**不透明归集键**。
- **四条不变量分工**：I-1/I-2 在 **装配对象面**（`execute` 内，需 messages 原始对象 → 回滚）；I-3/I-4 在 **记账面**（`check_invariants` 纯函数 → 记录 + 告警不阻断）。I-3 判据＝「存在 volatile 块且稳定前缀为 0」（头部即易变）；中段 volatile（react 的 prompt）**不判违规**，仅作视图体检行（「其后仍有 N tok 受影响」）。
- **运行时告警接入点**：chat `_emit_governed` 与 react `_emit_window` 装配后**软调用** `gov.check_invariants(payload)`；违规 → 记日志 + 发 `CONTEXT_INVARIANT_VIOLATION`（复用 P2 已登记事件，**不新增事件常量**）。诚实路径下 I-3/I-4 恒绿，不产生噪声。
- **门面与解耦**：`GovernorLike.ledger` / `render_ledger`（+ `entry` / `render_entry` / `check_invariants`）经服务**软调用**（`getattr(gov, ..., None)`）；注入实现不提供即降级跳过——run/react **零插件 import**。
- **遥测载荷补字段**：`blocks[].layer` / `blocks[].cap`（视图分类）+ `budget_raw`（I-4 自证）；均为**追加**，旧消费方零影响（`getattr` 兜底）。
- **视图渲染纯只读旁路**：渲染 / 校验失败一律吞掉并记日志，**绝不影响装配与答复交付**。

## 七、子 agent / 多 agent 拓展性

### 7.1 四维度评级（针对 2.0 骨架的承载能力）

| 维度 | 评级 | 说明 |
|---|---|---|
| **并发安全** | **优** | `assemble` 纯函数、无共享可变状态（`declare` 为配置期只读）；多 agent 并发调用无需加锁 |
| **作用域隔离** | **良（需留位）** | 契约已加 `scope`（P1-6）；治理器把 `scope` 当**不透明归集键**，不作控制流分支 |
| **配额仲裁** | **中（需外挂）** | 治理器只管「窗口内怎么分配」，**跨 agent 的总配额属 budget 侧职责**，需在其上建配额树 |
| **前缀共享** | **需设计** | 同模型多 agent 可共享 resident 段（系统提示/工具集）；**但绝不可共享轨迹** |

### 7.2 四个补强点

- **E1 `scope` 留位**（P1-6，成本近零）：三方法 + `declare` 加 `scope`。**事后补则波及全部消费方**——这是唯一「必须提前做」的一项。
- **E2 配额树**（长在 `budget` 侧）：`(parent_scope) → {child_scope: 子配额}`，子 agent 从父配额**预借**，未用尽时归还。治理器只向 budget 查询「本 scope 可用多少」，不自己管树。
- **E3 前缀共享策略**：子 agent 的请求 = `[共享 resident] + [子任务指令] + [子链]`。**共享段必须字节冻结**（同 F-1 纪律）；子链**独立、不进父窗口**。
- **E4 隔离交付契约**：子 agent 只回**摘要 + 元数据尾**给父窗口（Claude Code 子代理的确切形态：*"the entire subagent conversation is then discarded"*），**绝不回灌子轨迹**。

### 7.3 反模式警告（必须写进代码注释）

> **让子 agent 的轨迹进入父窗口，会把本次成本事故放大成乘法级灾难。**
> 本次事故的量级是「一条链重放 N 次」；若 3 个子 agent 的链都进父窗口，则父窗口体积 × 4，且每一步重放 4 条链——**代价从线性变乘法**。

### 7.4 业界对标（附录 A-2 证据）

| 实践 | 数值/形态 |
|---|---|
| Claude Code 子代理 | 各自独立 context window；只回摘要；**中间步骤永不进父窗口**；子代理**描述**合计超 **15,000 token** 时启动告警（描述本身也占上下文） |
| 多 agent 收益 | Anthropic 多 agent 研究系统相对单 agent 提升 **90.2%**（以隔离探索噪声为代价换来的） |
| 建议工具面 | 子代理工具集默认受限（继承父权限 + 缩小集合） |

## 附录 B 术语

| 术语 | 含义 |
|---|---|
| **能力窗口** | 模型单次请求物理上限（1M） |
| **经济窗口** | 治理器判断压缩时机的基数 `working_window_tokens`（默认 96k），与能力窗口解耦 |
| **清除 vs 压缩** | 清除 = 移除历史条目（不改写其余字节、零推理成本）；压缩 = 重写为摘要（多一次推理、有损）。**两者的缓存代价同构** |
| **原子单元（wire unit）** | 一次工具调用在消息序列中的完整形态：`[assistant{reasoning_content}] + [tool_calls] + [tool results]`。**三成员同进同退**，只允许整体替换为过程摘要（见 2.4.3 U-1） |
| **过程摘要（unit summary）** | 整单元替换的目标形态：把一次「思考 → 调工具 → 看结果」压缩为一段自产记录，保留结论与关键产物、丢弃原始字节。**链压缩的唯一合法产物**（U-2） |
| **回本步数 n\*** | 压缩罚金需多少步的 hit 节省才能补回：`ρ·r/(1−r)`，ρ=29 |
| **稳定前缀** | 首个 `volatile=True` 块之前的字节数——缓存友好度指标 |
| **unaccounted** | 扣了预算但未登记为块或附件的部分（现状：tools schema），记账盲区 |
| **in-band 标记** | 写入链内的自产元数据（如压缩标记），使「无状态」下仍可表达时序信息 |
| **shadow 模式** | 只计算决策与理由、不执行，用于用真实数据校准阈值 |
