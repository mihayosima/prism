## 二、口径与账本不一致

### 2.1 token 估算入参两套 ★高
- **治理器**：`_block_tokens`（`governor.py:209`）对 messages 块按**整 dict** 估：`sum(estimate_tokens(m))`
  —— 含 `role` / `seq` 骨架开销。
- **内容层**：`truncate.py:87` 按 `m.get("token_count") or estimate_tokens(content)` —— **只算 content**。
- **后果**：同一批消息在「装配预算」与「内容裁剪」两处算出**不同账面**，差异随条目数线性增长（每条 ~10 token 骨架）。

### 2.2 `input_budget()` 是「每次装配」预算，不是「每请求」预算 ★高
- `input_budget() = max_context_tokens − reserve_output_tokens = 24000 − 4000 = 20000`。
- 该值被**独立**用于 plan / narrate 的 system 装配（`sys/chat.py:444` / `521`）与 prior 装配（`sys/chat.py:295`）
  —— **二者相加无任何约束**（结构上允许 2×）。
- 当前各块规模小，尚未触发越界；但这是「三把尺子」的**姊妹问题**（详见 `token口径对账-问题记录.md`），
  也是「毫无征兆撞顶」的结构性成因之一。

### 2.3 字符口径残留 ★中
| 位置 | 口径 | 场景 |
|---|---|---|
| `memory/__init__.py:312,321` | `max_chars=1200` | 记忆注入 |
| `memory/__init__.py:206` | `text[:4000]` | 记忆提取器 |
| `sys/chat.py:478` | `desc[:60]` | 单步路径的工具描述 |
| `react/prompt.py::render_tools` | `desc[:80]` | react 路径的工具描述 |

与 S3「token 语义唯一归属 `plugins.context`」冲突。
**另注**：S4 已清掉 react 侧 2000 字符口径，但上述四处**不在 S4 范围内**，依然存在。

### 2.4 省略标注两套格式 ☆低
- `core/tokens.py:19`：`[...省略 {n} tokens...]`
- `short_term/truncate.py:58`：`[...省略 {n} 行 / {m} tokens...]`

语义并不完全重叠（后者带行数），但**格式不统一**，UI / 日志侧难以统一解析。

### 2.5 首尾截断三套实现 ☆低
`core/tokens.clip_text`（按字符比例） · `short_term/truncate.truncate_content`（按行 50% / 20%） ·
`governor.clip_head_tail`（按 token 头尾，已复用 `clip_text_hard`）。
S4 已让 `clip_text_hard` 成为**定点硬裁的唯一实现**，但前三者仍是各自算法，未收口。

### 2.6 收窗语义多头 ☆低
`pick_history`（已死） · `react._trim`（条数，`loop.py:145`） ·
`short_term/truncate.truncate_messages`（recent_rounds） · `HISTORY_LIMIT = 12`（降级，`sys/chat.py:59`）。

## 三、守卫与文档失真

> 这一类**解释了为什么上述问题能长期潜伏**。

### 3.1 `context/__init__.py` 文档自相矛盾 ★高
- 第 **13** 行仍写 `observe_*`（S3 已全局改名为 `clip_*`）。
- 第 **19-20** 行却自称「**不感知业务语义**（不认识"任务进度"，也不认识 `observe` 之类字眼；`pinned` 是通用元数据）」。
- **同一文件里，上文说"方法叫 `observe_*`"，下文说"不认识 observe"** —— 直接违反 S3 红线，对读者构成误导。

### 3.2 守卫测试有范围缺口 ★高（与 3.1 同因）
- `test_governor_has_no_business_wording`（`test_context_governor.py`）读取的是
  `PLUGIN_DIR / "context" / "governor.py"` —— **只扫 `governor.py`，不扫 `context/__init__.py`**。
- 因此 3.1 的失真**无法被守卫发现**。
- **修法**：把扫描面扩到 `context/` 全目录（至少纳入 `__init__.py`）。

### 3.3 两处重复的测试定义 ★高（断言静默失效）
| 文件 | 重复函数名 | 后果 |
|---|---|---|
| `test_context_governor.py` | `test_s3_settings_registered_in_all_three_places` ×2 | 后者覆盖前者，**前者断言不执行** |
| `test_react_context.py` | `test_react_context_edge_is_soft_and_one_way` ×2 | 同上 |

Python 中后定义覆盖前定义 → 测试"看起来有 2 项覆盖、实际只跑 1 项"，**且不报错**。
S4 时曾"去重"过一次，但**不彻底**，遗漏了这两处。

## 四、机制性缺口

### 4.1 循环内只折叠 observe，不折叠 agent 自产出 ★高
- `react._prepare_chain` 只对**老的、未 pinned 的 observe** 做折叠。
- Think / Act 产出（尤其"写长文"时逐段生成的正文）**不折叠** → chain 被自己写出的内容撑爆。
- **实证**：会话 `ea3563de` 写 3 万字小说，输入 180k / 输出 17.8k（**~90% 额度用于每步重发已有正文**）。
- 属 **S5 候选**（见 `token口径对账-问题记录.md`），现有机制对此**无针对性**。

### 4.2 压缩器看不见 react chain
- `short_term.compactor` 只扫 `agent_messages`（跨轮会话历史）。
- 按 S3 设计，循环内 chain **绝不写入 `agent_messages`** → 内容层治理对循环内**完全失效**。
  虽属设计使然，但意味着 4.1 **没有兜底**。

### 4.3 摘要软上限可被突破 ★中
- `compress_summary_to_budget`（`truncate.py:171`）中，受保护区 `_PROTECTED = {feedback, unresolved}`（`truncate.py:21`）
  在压缩时**永不裁**；且 `misc` **不在**优先级列表 `_PRIORITY_LOW_TO_HIGH`（`truncate.py:19`）内。
- **后果**：受保护区 + `misc` 可致摘要**无界超出软上限** —— 软上限退化为"建议值"。

### 4.4 `pinned` 机制全链路空转 ☆低（dormant）
- 全仓**无 `pinned=True` 生产方**：`components.py` 只产出默认 `"pinned": False`（`components.py:158`）。
- 因此 S3 的「先占 / 降级 / `BlockReport.pinned_downgraded`」目前**仅由测试驱动**，生产中不会发生。

### 4.5 `_trim_messages` 的 pinned 先占破坏"连续贪心"的配对连续性 ☆低（dormant）
- pinned 条目先占额度后，其前置 `act` 可能被丢弃 → 产生"**孤儿 observe**"（工具结果无对应调用）。
- 当前因 4.4（无 pinned 生产方）而 dormant，但机制上存在。
