# 记忆架构分层方案 — 评估

> 评估对象：用户提出的 4 层记忆架构（系统记忆 / 长期记忆 / 工作记忆 / 短期记忆）。
> 评估立场：仅评审方案可行性，不含详细设计。对照 `<用户主目录>/Desktop/agent` 当前代码现状。

## 0. 总体判断

4 层模型**成立，且比现状更清晰**。其本质是按「寿命 / 作用域」做了正交切分：

| 层 | 寿命 | 当前代码现状 |
|---|---|---|
| 系统记忆 | 永久（重启重载） | `PLAN_SYSTEM` / `ANSWER_SYSTEM` 硬编码于 `sys/chat.py:36-49`；react 的 `build_system`（`plugins/react/loop.py:34,126`）亦为常量 |
| 长期记忆 | 跨会话持久 | `plugins.memory` 已存在；但 `agent_entities` / `agent_memory_edges` 两张表**全代码库零读写**（已实锤） |
| 工作记忆 | 任务级（结束即失效） | **当前完全没有**——react 仅在闭包内持有 `messages/steps/tool_trace`，外加 `StateKeys.REACT_LAST`（`loop.py:220`） |
| 短期记忆 | 会话级持久 | `agent_messages` 表 + `HISTORY_LIMIT=12` 硬裁，无压缩 |

分层边界与「时空寿命」对齐，逻辑自洽；且与已落地的 G0 `ContextGovernor` 预算切片天然咬合（system 刚性 / 记忆 10% / 历史 60% / 本轮=工作记忆）——治理器正是 4 层的统一装配点。这是方案最大的加分项。

---

## 1. 逐层评估

### ① 系统记忆（文件）— 合理，两点须警惕

- **合理**：把硬编码提示词外置为文件，对开发者管理是实打实的改进。
- **风险 1（声明 ≠ 强制）**：文件描述的是「能力边界」，但**强制边界仍在 guard 矩阵（代码）**。文件只是人读 / 人改的声明，不能替代强制——否则会给人「改文件就生效」的错觉。
- **风险 2（token 成本）**：「全量注入」若文件较大，且 plan / answer / react 三套 system 都注入，token 成本会三倍叠加。需明确拼装规则：静态文件作底座，动态块（tools / env / memory）追加其后。

### ② 长期记忆（三表 + 双索引）— 方向对，但「三表」含义必须敲死

- 当前 `agent_memories` 已自带两个索引（`tables.py:34-35`：按 `kind`、按 `last_accessed_at`）——这已接近「双索引」。
- **关键歧义**：所提「三表」是**激活现有 entities / edges（图谱化召回，大工程）**，还是**重定义三张有意义的表**？两张死表这一轮必须明确处置（补落库 或 删），不能再悬空。
- **「双索引」建议落成**：
  - (a) `kind + created_at` 分类 / 时效召回索引；
  - (b) **FTS5 全文索引替代 Python 端 `_tokenize` 扫描**（`plugins/memory/__init__.py:61` 的纯词面召回现为 O(N) 内存扫）——这才是性能层面的真改进。

### ③ 工作记忆（缓存）— 真实补空白，但生命周期要钉死

- 这是当前唯一完全缺失的层，补上是合理的。
- **须明确「任务结束」的边界信号**：`send()` 一次？还是 react `run()` 一整轮？建议以 `session_id + run_id` 为键，并加**兜底 TTL / 驱逐**防任务结束信号丢失导致泄漏。

### ④ 短期记忆（会话表 + 滚动摘要）— 与 G1 一致，摘要存储待定

- 滚动摘要正是原 G1 规划的增量摘要；**存储建议独立 `session_summaries` 表**（session → summary 版本），而非回写 messages 特殊 role。
- **须定一笔流转**：摘要压缩后 = 注入「会话前情」，且可作为**晋升长期记忆的候选**喂给 `remember()`。这条链路要让方案说清。

---

## 2. 跨层 / 集成

- 4 层现已超出单一 `plugins.memory` 插件范围，成为跨组件的架构。建议明确：各层独立可替换 / 可注入（与 D2 接缝同构），由 `ContextGovernor`（G0 已建）统一装配 LLM 窗口。
- 治理器预算切片已预先覆盖 3 层（system / 记忆 / 历史），工作记忆映射到「本轮消息」——G0 + 4 层模型完全对齐，无需返工治理器。

---

## 3. 落地前必须澄清的 7 个决策点

1. **系统记忆文件形态**：单文件 还是 目录多文件（identity / capabilities / boundaries 分置）；「全量注入」的拼装规则。
2. **系统记忆描述 vs guard 强制**：声明 ≠ 强制，强制留代码。
3. **长期记忆「三表」确切定义**：激活图谱 or 重定义；死表处置（补 or 删）。
4. **「双索引」精确定义**：是否含 FTS5 替代内存扫描。
5. **工作记忆生命周期绑定**：run_id / session_id 边界 + 缺失信号兜底驱逐。
6. **短期记忆滚动摘要存储位置** + 是否晋升长期记忆。
7. **工作记忆与短期历史在 react 中的重叠边界**：in-flight steps vs finalized turns。

---

## 4. 一句话结论

4 层骨架站得住、且与既有 G0 治理器无缝衔接，可以推进；但「三表 / 双索引」和「工作记忆生命周期」两处若不先澄清，详细设计阶段极易返工。建议先就上述 7 点拍板，再出详细方案。

## 5. 系统记忆（第 1 层）—— 已落实

用户已敲定下述决策并落地实现（代码未提交，待统一节奏）：

### 锁定决策
- **① 声明层，不碰 guard**：文件只注入文本，guard 矩阵强制行为不变。
- **② 不枚举工具**：文件只写身份/边界叙事，具体工具仍由 `ctx.tasks.catalog()` 实时注入，防漂移。
- **A 文件形态**：目录 `agent/plugins/system_memory/*.md`（内容随插件走，自包含），**显式按文件名排序**（不依赖文件系统枚举顺序），**扁平、不递归**子目录。
- **B 外部路径覆盖**：配置 `agent.system_memory.dir` 指向外部目录时**完全覆盖**默认目录（非合并）。
- **C 不热重载**：仅启动加载（boot 时读入缓存）；未来刷新由显式命令触发。
- **D 静态底座一致**：系统记忆作为各阶段 system 提示的静态底座（chat 规划/解说 + react 多步）；动态块（tools/env/memory）按原模式裁剪追加。
