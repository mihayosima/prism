## 0. 一句话结论

**配置要从「容器级一粒沙」拆成「默认 → 容器 → 会话 → run」四级继承链；拆分的技术支点不是改造插件，而是启用内核既有的 `Context` 作用域遮蔽机制——插件只需多声明一行「我可按会话重建」的工厂，适配层机械执行，消费方零感知。**

---

## 1. 问题定义

单会话时代存在恒等式 **容器 == 会话**，于是「设置」在用户心智里天然是会话级的；但实现上它是**容器级固化**的：改一次影响所有会话（且会触发全局容器重建）。多会话一进来，这个错位立刻变成三类事故：

| 事故 | 表现 |
|---|---|
| **语义错** | 用户在会话 A 把 `max_context_tokens` 调到 64K，会话 B 的窗口跟着变 |
| **爆炸半径失控** | 改任何一个设置项都要 `_apply_rebuild()` 重建**整个容器**，所有在线会话的进行中 run 一起失去容器（隐患 H8） |
| **无法差异化** | 不同会话不能有不同的上下文窗口、预算、系统提示词 |

## 2. 现状核实（逐条对照代码，非印象）

### 2.1 配置的三层来源与固化点

| 环节 | 落点 | 事实 |
|---|---|---|
| CLI 基础配置 | `run/chat.py:57-62` `_cfg(args)` | 仅 `db_path` + `llm.provider/model` |
| 用户覆盖 | `run/chat.py:66-87` | 单文件 `data/agent_plugin_config.json`，形态 **`{"plugins.<名>": {键: 值}}`；`_save_overrides` 用 tmp+replace 原子写 |
| 默认值 | `profiles.py:31` `BASE_AGENT_CONFIG` | 唯一真相源 |
| 合并 | `run/chat.py:89-112` `_merge_cfg` | `plugins.X` 桶 → `agent.X` 节并入 |
| 校验 | `core/config_schema.py` | `agent` 节严格校验，拼错键装配期 fail-fast |
| **固化点** | **`plugins/context/__init__.py:50-54`** | **`ContextGovernor.from_config(cfg)` 在 `apply` 期构造并 `provide(Services.CONTEXT, governor)`** |

### 2.2 设置页的四张表（关键：它们正在漂移）

- `_SETTING_SCHEMA`（`chat.py:117-157`）：键 → (类型, 下限, 上限 / choice / list / bool)
- `_PLUGIN_OF_KEY`（`chat.py:158-188`）：键 → 插件 id（存储路由）
- `_SETTING_DEFAULTS`（`chat.py:191-230`）：键 → 默认值（注释反复强调"与 `BASE_AGENT_CONFIG` 同源"——**靠人肉维持同源**）
- `_CTX_DEFAULTS`（`chat.py:190`）：context 键默认值的中间变量

⇒ **同一批键的元数据被拆成四张表、靠注释约束同源**。新增 scope 若再开第五张表，漂移风险不可接受（见 §6.1 的合并建议）。

### 2.3 生效路径：改任何设置都要重建容器

`POST /api/settings`（`chat.py:917-944`）→ `_save_overrides` → **`await _apply_rebuild()`**。
`_apply_rebuild`（`chat.py:425-435`）是「新建容器 → 旧容器 teardown → `c.set(c2)()`」的**全局切换**。

### 2.4 三条决定性机制事实（本方案的技术支点）

| # | 事实 | 落点 | 含义 |
|---|---|---|---|
| **M1** | `config` 是经 `builtin` 由 `provide()` 注册的**服务**；`ctx.config` ≡ `__getattr__` → `get("config")` | `profiles.py:128-131`、`container.py:153-155`、`context.py:181-187` | child 上 `provide("config", 会话值)` **即覆盖 `ctx.config`** |
| **M2** | `get()` 走**自身 → 父链**；`provide()` 仅**同作用域**冲突（子作用域可遮蔽父） | `context.py:130-154` | child 的 `provide` 天然遮蔽容器级服务，**消费方零改动** |
| **M3** | `ContextGovernor` 是**纯参数容器、零跨轮状态**（`self._*` 全为配置；水位每次现算） | `governor.py:155-190`、`protocols.py:19-31` | 会话级窗口 = **用会话 config 现造一个 Governor**，无需状态迁移与实例池 |

### 2.5 一处必须承认的坑

`State` 是纯 `__dict__`，**无父链回退**；`child()` 会新建 `self._state`（`context.py:104`、121-122）。
⇒ 若 run 跑在 child 上，`ctx.state[PERMISSION_MODE]` 为空 → `Approval.mode()` 退回 `default`（`approval/__init__.py:199`），**每个新会话都丢掉已设的 plan/auto 模式**。这是启用 child 的**直接副作用**，必须显式处置（§7.2）。

## 3. 粒度模型：四级继承链

```
G0 default   BASE_AGENT_CONFIG（代码内默认值）
      ↓ 覆盖
G1 container 覆盖文件 container 桶（== 现状全部设置，语义不变）
      ↓ 覆盖
G2 session   覆盖文件 sessions[session_key] 桶（本方案新增）
      ↓ 冻结
G3 run       run 启动时快照一次，全程不变（N1 硬约束）
```

**继承而非替换**：会话未设置的键自动继承容器级；容器未设置的继承默认。故**存量配置语义逐字节不变**——这是"完美迁移"的第一块基石。

### 3.1 预算的细分（命名语义必须先厘清）

`max_tokens_per_run` **命名本身是 run 级**，但现状是 `budget.py:17` 自陈的「容器生命周期累计」，比 run 级还粗。因此：

- **阶段 A（本批）**：落到 **G3 run 级**（与命名一致、改动最小）
- **阶段 B（另排）**：再加「会话内多 run 累计」（G2 累计维度），属新增能力，不是语义搬家

## 4. 核心技术支点：会话作用域 = 请求级 child + 工厂遮蔽

### 4.1 为什么必须是「请求级」而不是「会话级持久 child」

`provide()` 同作用域重复注册抛 `ServiceConflictError`（`context.py:133`）。一个会话有多次请求，若复用同一个持久 child，第二次请求再 `provide` 同键即崩。

⇒ **child 生命周期 = 请求级**；身份是会话级，但作用域是请求级。

**这反而更好**：每次请求用**当前最新**配置现造 child ⇒ 改会话设置**下一个请求即生效，永不 rebuild**。

### 4.2 适配层不能 import 具体插件类（解耦红线）

若 `run/chat.py` 写 `from agent.plugins.context.governor import ContextGovernor`，就形成「适配层 → 具体插件」的反向依赖，违反解耦。

**正解：插件自声明工厂，适配层机械执行。**

```python
# 插件侧（以 context 为例，改一行）
ctx.provide(Services.CONTEXT, governor)
ctx.provide(f"session_scope:{Services.CONTEXT}", ContextGovernor.from_config)
#         ↑ 约定前缀：声明「本服务可按会话重建，工厂如下」
```

```python
# 适配侧（run/chat.py，零插件知识）
for k in c.root.keys():
    if not k.startswith("session_scope:"):
        continue
    target = k[len("session_scope:"):]
    child.provide(target, c.root.get(k)(session_cfg))
```

`context` 插件的 docstring 本就写明「接缝 `ctx.get("context.governor")` 可注入替换」（`context/__init__.py:8`）——本方案是**沿用既有接缝设计**，不是新造机制。

### 4.3 哪些服务能会话化：看它是「参数快照」还是「资源句柄」

| 类型 | 例 | 能否会话化 |
|---|---|---|
| **参数快照**（纯配置 → 实例，无跨轮状态） | `ContextGovernor`、`ReactConfig`、approval 策略/名单、预算额度 | ✅ 声明工厂即可，**插件零逻辑改动** |
| **资源句柄**（连接/子进程/文件） | Redis client（`work_memory`）、MCP client（`windows_mcp`/`playwright_mcp`）、DB | ❌ 容器级；会话化会 ×N 放大资源（MCP 子进程单容器就 10 个） |

⇒ **分类标准不是"这个设置想不想按会话调"，而是"它背后是参数还是资源"**。这正是方案不违背解耦的原因：资源型服务根本不动。

## 6. 存储格式演进与「完美迁移」七条纪律

### 6.0 v1 → v2

```jsonc
// v1（现状）
{ "plugins.context": {"max_context_tokens": 24000}, "plugins.react": {...} }

// v2（目标）
{
  "version": 2,
  "container": { "plugins.context": {...}, "plugins.react": {...} },
  "sessions": {
    "u1:s1": { "plugins.context": { "max_context_tokens": 64000 } }
  }
}
```

### 6.1 先合并四张表为一张（消除漂移，建议同批做）

```python
_SETTING_META: dict[str, dict] = {
    # key: {type, min, max, plugin, scope, default}
    "max_context_tokens": {"type": int, "min": 1024, "max": 1_000_000,
                           "plugin": "plugins.context", "scope": "session", ...},
}
```
`_SETTING_SCHEMA` / `_PLUGIN_OF_KEY` / `_SETTING_DEFAULTS` 改为**由它派生**的兼容视图（存量调用点零改动），新增 scope 不再开第五张表。

### 6.2 迁移七条纪律（"完美"= 无损 + 可回滚 + 不静默）

1. **读时兼容 v1**：无 `version` 键 → 判为 v1 → 把全部 `plugins.*` 桶归入 `container`。**返回值语义与现状逐字节一致**。
2. **读 v1 不写回**：不改原文件。迁移逻辑出 bug 也不损伤存量数据。
3. **首次写 v2 先备份**：原文件复制为 `agent_plugin_config.json.v1.bak` 后再写。
4. **版本守卫**：`version > 支持上限` → 打 ERROR 并退回空配置（**不崩、不静默**）；理由写进日志。
5. **禁止双写**：不同时保留平铺 `plugins.*` 副本——两处真相源必漂移。旧代码读 v2 会丢设置这一风险，用**备份 + 版本守卫 + 部署顺序**管理，而非用冗余换兼容。
6. **scope 只能收窄不能凭空产生**：v1 全部归 `container`，**没有一个键被"猜测"成会话级**。
7. **会话桶有上限**：`sessions` 条目数设上限（建议 200）+ LRU 淘汰，防长期运行无限膨胀（风险 M5）。

## 7. 生效路径与两个必须写死的约束

### 7.1 两条生效路径（根治 H8 的一半）

| 改动 | 动作 | 是否 rebuild |
|---|---|---|
| **container 级键** | `_save_overrides` → `_apply_rebuild()`（现状）+ **重建保护**（H8：有 run 在跑时 drain 或 409） | 是 |
| **session 级键** | `_save_overrides` 写 `sessions[sk]` → **不 rebuild**，下个请求建 child 时自动生效 | **否** |

### 7.2 run 级冻结（N1，硬约束）

会话级配置**只在 run 边界被读取并快照一次**，run 全程不变。防飞行中改配置导致：窗口抖动、token 计量漂移、「已消费 > 新额度」。

### 7.3 坑的处置：`State` 无父链（三选一）

| 方案 | 做法 | 评价 |
|---|---|---|
| **S1（推荐）** | child 仅承载 **config/服务覆盖**；需要跨请求持久的量（`PERMISSION_MODE`、`BUDGET_SPENT`）**显式读写 `ctx.root.state`** | 显式优于隐式，插件改动点少且语义清晰 |
| S2 | 内核提供 seed 白名单 + 结束回写 | 插件零改动，但引入"哪些键 seed"的新配置面 |
| S3 | 改 `State` 支持父链回退 | 隐式共享有跨会话污染风险，与 2.2 隔离目标相悖 |

## 8. 解耦落点表（写入哪里，不写哪里）

| 组成 | 落点 | 是否为插件 |
|---|---|---|
| 身份值对象 + 键构造 | `core/session.py`（**已落地**） | ❌ 核心原语 |
| scope 元数据 `_SETTING_META` | `run/chat.py`（设置页定义处，就近） | ❌ 适配层 |
| v1/v2 读写 + 备份 + 版本守卫 | `run/chat.py` `_load_overrides`/`_save_overrides` | ❌ 适配层 |
| 有效配置解析（四级继承） | `run/chat.py` `_resolve_effective_config(ident)` | ❌ 适配层 |
| 请求级 child 构造 + 工厂遮蔽 | `run/chat.py` `_ctx_for(request)` | ❌ 适配层 |
| **"我可按会话重建"工厂声明** | **各插件 apply 内一行** `ctx.provide(f"session_scope:{SVC}", factory)` | ✅ **插件唯一改动** |
| 窗口/预算服务的**消费** | **零改动**（父链遮蔽） | ✅ |
| 前端：作用域标注 + 会话选择 | `web/src` 设置页 | — |

⇒ **插件总改动量 ≈ 每个参数快照型服务一行声明**；消费方零改动。这是本方案"不违背解耦"的实质。
