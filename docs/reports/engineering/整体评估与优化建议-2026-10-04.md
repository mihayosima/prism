## 0. 一句话结论

架构底座**相当健康**（分层零逆向依赖、SQL 零注入面、async 零阻塞、注释密度与质量罕见地高），
真实风险集中在**一处**：`agent/run/chat.py` —— 它是全仓最大、最复杂、最贴近用户的文件，
却只有 **42% 行覆盖**。这既是当前最大的质量缺口，也是唯一值得优先投入的重构点。

## 3. 优化项（按优先级）

### P0-1 · `run/chat.py` 覆盖率 42%，是全仓最大盲区

- **实测**：822 语句 / 479 未覆盖（42%）。对比 `core/` 84–100%、`sys/` 86–97%、`plugins/` 80–100%。
- **集中缺口**：722-771、829-921、973-1007、1143-1208 等大段——基本是全部路由处理逻辑。
- **根因**：`_serve()`（339 行，cc=42）是一个**巨型闭包工厂**。它在函数体内定义 `_Box`、`_session_cfg`、`_identity`、`_sse` 等嵌套函数，再由 `_register_probes/_register_approval/_register_resources/_register_routes`（分别 271/263/221 行）注册 handler，handler 通过闭包捕获 `active_runs`、`c.root`、`pm` 等状态。**脱离真实 uvicorn 进程就无法构造这些闭包**，故几乎不可单测。
- **为什么这条最要紧**：本项目已实证过这个盲区会漏真 bug——「路由存在」不等于「端点能跑」（曾出现全绿测试掩盖 `/api/approval/pending` 500）。42% 覆盖意味着每改动 HTTP 层都在盲改。
- **建议（不是"再切碎"）**：
  1. 把 `_serve` 内的**纯逻辑**继续外提为模块级函数（`_identity`、`_budget_view`、`_sse`、`_session_busy`、`_acquire_session_run` 已是模块级，这个方向是对的，继续即可）；
  2. `_register_*` 里的 handler 改为**工厂函数 + 显式依赖参数**，而非闭包捕获。这样 handler 可脱离 HTTP 直接调用；
  3. 目标：把 `run/chat.py` 提到 70%+，优先覆盖 `/api/chat`、`/api/chat/stream`、`/api/approval/*` 的错误路径。
- **注意**：记忆中已有结论——`_serve` 与 `governor.assemble` **不该再拆**（已过度碎片化）。此处建议的是「提升为模块级 + 依赖显式化」，与「切碎成更多小函数」不同，不冲突。

### P0-2 · `sys/audit.py` 覆盖率 0%

4 行语句全部未覆盖。文件极小，补一个测试成本极低，建议顺手补掉。

### P1-3 · 数据库路径有两套默认值

- `agent/profiles.py:32` → `"db_path": "data/agent.db"`
- `agent/run/chat.py:68` → `--db` default `"data/agent_chat.db"`

**实况**：两个库都真实存在且 schema 完全相同（9 张表、13 条迁移记录），但
`data/agent.db` **9 张表全部 0 行**（仅 migrations 有 13 行），`data/agent_chat.db` 才是活跃库
（events 393 / budget_log 69 / memories 86 / messages 27）。

后果：用 profile 启动写到 A 库、用 chat.py 启动写到 B 库，数据看起来"凭空消失"。
**建议**：`db_path` 默认值收敛为单一常量真源，两处引用它。

### P1-4 · WAL 无主动 checkpoint

- **实况**：`agent_chat.db` 320KB，而 `agent_chat.db-wal` **4.0MB（12.5×）**。
- 配置：`journal_mode=WAL`、`wal_autocheckpoint=1000`（SQLite 默认，约 4MB 才触发）。
- 影响：读放大（每次查询要扫 WAL）+ 磁盘持续增长；进程被强杀时 WAL 残留。
- **建议**：在 `SqliteDb.close()` 前显式 `PRAGMA wal_checkpoint(TRUNCATE)`，并对长驻进程增加定时/计数触发的 checkpoint。成本低、收益明确。

### P1-5 · 事务锁不可重入，且 `_in_tx` 是实例级全局

- 当前 4 处 `transaction()` 无嵌套，**现在安全**。
- 但 `_lock` 是 `asyncio.Lock`（不可重入），`_in_tx` 是实例属性被所有协程共享。
  任何人未来加一处嵌套 `async with db.transaction(...)` ⇒ **静默死锁**，且无断言、无日志、无超时。
- **建议**：加嵌套深度计数，二次进入直接抛明确异常（或改可重入设计）。改动量 <10 行，属于典型的"便宜保险"。

### P1-6 · 前端零单元测试

- 3,699 行 TS/Vue，**无任何单测框架**（无 vitest/jest，无 `*.test.*`/`*.spec.*`）。
- 现有保障来自 7 个自研契约脚本（`check-sse-contract`、`check-api-contract`、`check-card-payload` 等），
  覆盖的是**契约**而非**逻辑**。
- 后端 15,611 行测试 vs 前端 0 行，是明显的不对称。
- **建议**：优先给 `settings.logic.ts`（610 行，最大）、`useStreamMessage.ts`（309）、`api/client.ts`、`api/sse.ts` 补单测。

### P2-7 · 测试耗时偏长，且有环境依赖

- 全量 2m33s。单点最慢：`test_windows_mcp.py::test_plugin_reports_unavailable_when_restart_fails` **11.44s**。
- 一批用例固定 ~2.16s：本机 **Redis 不可达**（6379 不通、docker 不可用），`work_memory` 相关测试走连接超时。
  这也部分解释了 `work_memory/__init__.py` 仅 68% 覆盖（走的是降级分支）。
- **建议**：Redis 不可达时用内存桩短路，或打 `@pytest.mark.redis` 默认跳过，把环境依赖与逻辑测试解耦。

### P2-8 · 复杂度热点（真实热点与结构性热点要区分）

### 6.2 两个判断被实测推翻（★ 记录以免重复论证）

- **WAL checkpoint 是伪需求**：原判断「WAL 4MB 需主动 checkpoint」。实测写入 500 条后 WAL 2MB，
  `conn.close()` 后 **WAL 文件被 sqlite3 自动删除**。故 4MB 是 `wal_autocheckpoint=1000` 的
  **运行期稳态**，不是泄漏，且进程退出会自动清理 ⇒ **已回退**该改动（不留无效代码）。
- **两个库是刻意隔离，不是 bug**：`data/agent.db`（`build_agent()` 离线/嵌入式用法）与
  `data/agent_chat.db`（服务器入口）分离，避免长驻进程与离线用法争 WAL、避免离线写入污染服务端账本。
  ⇒ **不强行统一**（统一会让现有服务端数据不可见），改为在代码里写明原因。

### 6.3 踩到的两个自己挖的坑

1. **嵌套保护的检查位置**：首版把 `if _tx_depth > 0` 写在 `await _lock.acquire()` **之后**——
   死锁就发生在 acquire 那一句，永远走不到检查（实测仍超时）。必须在 acquire **之前**判。
   且判定须用 **task 归属**（`asyncio.current_task()`），不能用"锁是否被占"——
   后者会把「另一协程正在事务中、本协程正常排队」误判为嵌套。
2. **副作用式守卫会随修复一起失效**：`test_followup_topics` 曾断言
   `_coerce_setting("tool_domains", None) == ["None"]`，借这个**缺陷**提醒「默认值必须是 [] 而非 None」。
   修掉缺陷后该断言必然失效 ⇒ 已改为**直接断言默认值** `== []`（防护更明确，且不依赖缺陷行为）。
