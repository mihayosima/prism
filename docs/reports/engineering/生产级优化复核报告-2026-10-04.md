## 1. 【P0 可用性】DB 层"假异步"：同步 sqlite 阻塞整个事件循环

**证据** — `agent/sys/storage.py` 的 `SqliteDb` 是 `ctx.db` 唯一实现，其 `execute/query/executemany/transaction/start/close` 全是 `async def`，但内部直接调用同步 `sqlite3`：

```
async def query(self, ctx, sql, params=()):
    async with self._lock:
        cur = self._conn.execute(sql, params or ())   # storage.py:54  同步！冻结 loop
```

12 处同步语句：`storage.py:38,41,42,47,50,54,71,74,89,95,97,108`。唯一正确卸载的反例是 `plugins/approval/providers.py:96`（`await asyncio.to_thread(...)`）。

**热路径命中**：`durable()` 每事件写（`core/audit.py:42`）、`Budget._post` 每次 LLM 调用后写（`sys/budget.py:270`）、recall/context 每请求读（`plugins/memory/__init__.py:543`、`sys/short_term/*`）、以及 `/api/events`、`/api/perms`、`/ready` 等路由。

**为什么是 P0**：asyncio 事件循环单线程协作式调度。**任意一处同步 sqlite 调用期间，整个进程所有并发请求全部冻结**（runebook.dev / hivebook.wiki 明确："calling a blocking DB driver inside a coroutine freezes every task"）。叠加 `busy_timeout=5000`：`BEGIN/COMMIT/execute` 一旦遇到锁争用（如外部进程持有锁、或 WAL checkpoint），可阻塞**最长 5 秒 = 整服务停摆**，且所有不相关端点一起变慢——这是共享循环停顿的典型特征。

**对标（实测数据）**：`async-concurrency.com` 用 Python 3.14 实测：0.6s 的 sqlite 查询，直接用 `sqlite3` 最坏事件循环停顿 **604ms**，改用 `aiosqlite` 仅 **1ms**。aiosqlite 把每个连接放到独立后台线程，通过队列串行化调用，满足 sqlite 线程亲和（aiosqlite.readthedocs.io）。

**建议（两条路线，均不破坏现有 API）**：
- **最小改动**：`SqliteDb` 每个方法体用 `await asyncio.to_thread(self._conn.xxx, ...)` 包裹同步调用（Python 3.9+，与 `approval/providers.py:96` 同款）。保留单连接 + `asyncio.Lock` 串行化，改动面小。
- **正规化**：迁移到 `aiosqlite`（每连接独立后台线程，天然线程安全，无需 `check_same_thread=False`）。代价：每查询约 55µs 线程切换开销（10k 点查 0.08s→0.55s）——但消除事件循环停顿，对"多并发请求服务型"应用净收益显著；且应按 aiosqlite 实践"用 IN 列表/批量 fetchall 减少往返"。

**连带项（次要）**：`run/config_store.py:_save`（`:100/:102` 写 + `:95` v1 备份 `copyfile`）被 `POST /api/settings` 调用、`sys/plugin_manager.py`（`:224` write_text、`:161` rmtree、`:208` read_text）被插件管理路由调用，均为同步文件 IO 阻塞 loop。建议同样 `to_thread` 化。其余（system_memory loader glob、llm `_resolve_key`、playwright `which`、sandbox makedirs）为启动期一次性，严重度低。

## 2. 【P0 安全】鉴权默认关闭 + 跨会话数据泄露

**2a 鉴权 opt-in** — `run/chat.py:1499`：
```
_token = str(args.token or "")
if _token:                       # 仅当显式传 --token 才注册
    ... @app.middleware("http") _auth_mw
```
默认 `python -m agent.run.chat`（无 `--token`/`--hardened`）时所有 `/api/*` 完全无认证。token 中间件本身是全局、`/api/*` 全量拦截、`hmac.compare_digest` 常量时间比较——这部分**合规**（正面项），但"默认零鉴权"违反生产默认 deny-by-default 原则（pyinns 2026："rate limiting and security headers are non-negotiable... in 2026"；zeriflow 强调默认安全）。

**2b 跨会话泄露** — `run/chat.py:955`：
```python
@app.get("/api/events")
async def _events(request_id: str = "", limit: int = 120):
    if request_id:
        rows = await c.root.db.query(..., "WHERE request_id=? ...", (request_id, cap))
    else:
        rows = await c.root.db.query(..., "FROM agent_events ORDER BY seq DESC LIMIT ?", (cap,))
```
`/api/events`、`/api/context`(`:977`)、`/api/tools`(`:1013`) 三路由**未调用 `_identity()`**（对比 `:1392` 定义与 13 个正确调用点 `703/742/826/...`）。当 `request_id` 为空，`/api/events` 返回**全部会话的事件账本**（含 prompt / 工具调用 / 思考内容）。即使开了 token，所有会话共用同一 token ⇒ 任一会话可读他人数据。

**对标**：多租户/多会话隔离必须"从凭证推导身份 + 每行 `WHERE session=?`"，且在数据访问层强制，使"漏写 WHERE"也 fail-closed（skillveris.com；nuvikatech RLS 实践：行级安全策略在数据库层兜底，应用 bug 也不会跨租户返回行；返回 404 而非 403，不确认记录存在）。

**建议**：
- 会话作用域作为**全局 `Depends`** 注入（而非逐路由 `_identity()`），避免"忘记调用即无会话作用域"。
- `/api/events`、`/api/context` 等敏感读端点强制 `WHERE session=?`，未知会话返回空/404。

## 3. 【P0 安全】错误响应回吐内部异常原文

**证据** — `run/chat.py:1451`：
```python
@app.exception_handler(Exception)
async def _on_unhandled(request, exc):
    return JSONResponse({"error": str(exc), "kind": type(exc).__name__}, status_code=500)
```
且 `/api/chat`(`:723`)、`/api/chat/stream`(`:789/:812`) 均 `yield _sse("error", {"error": str(exc)})`。`str(exc)` 可能含 SQL 片段、文件路径、内部模块名。

**对标**：生产错误响应应为通用文案 + `request_id`，内部细节只落日志（johal.in 全局中间件模式；oneuptime/kowashlab：`"message": "An unexpected error occurred", "request_id": ...`，`logger.error(..., exc_info=exc)`）。sameralqaisi.me 强调"never leak the upstream error text... return a correlation id instead"。

**建议**：统一异常响应结构 `{error:{code,message}, request_id}`，仅回吐 `request.state.request_id`；完整堆栈写入日志。`/api/chat/stream` 的流式错误也只回 `request_id`，不回 `str(exc)`。

## 4. 【P1 安全】输入校验 / 安全响应头 / 限流 缺失

**4a 请求体无校验** — 全部写端点用 `body: dict` 原始字典（`:695/714/731/820/856/917/1159/1166/1172/1258`），无 Pydantic 模型、`message` 无长度上限、无请求体体积上限（全仓 `rate/limit/throttle/content_length/body_size` 零命中）。对标：FastAPI 的 Pydantic 集成是"genuine security advantage... leverage it on every endpoint"（zeriflow）；应建模并设 `max_length`。

**4b 安全头缺失** — 仅 HTML 响应设 `Cache-Control: no-store`（`:1557`），SSE 设 `no-cache`（`:816`）。**JSON API 全量缺失** `HSTS / CSP / X-Content-Type-Options / X-Frame-Options`，含会话敏感数据的 `/api/*` JSON 可被代理/浏览器缓存。对标：2026 生产**强制**全局 `SecurityHeadersMiddleware`（`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Strict-Transport-Security`、`Content-Security-Policy`、`Referrer-Policy`，且敏感 JSON 应 `Cache-Control: no-store`）—— pyinns / engineersofai / skillmd 一致。

**4c 限流缺失** — 无任何 per-IP / per-session 限流。对标：SlowAPI 或 fastapi-limiter + Redis 后端是生产标配（pyinns 2026）。

**建议**：① 全局 `SecurityHeadersMiddleware`（含 `no-store`）；② 写端点改为 Pydantic + `max_length`；③ 接入限流（至少 per-session 防资源耗尽）。

## 5. 【P1 并发】H2 仍部分未修 + 后台任务/关闭/幂等

**F1 流式端点 TOCTOU（HIGH）** — `run/chat.py:743` 查忙与 `:798` 登记 `active_runs[run_id]` 之间夹两个 `await`（`yield` + `async with tap_progress`）。非流式 `/api/chat` 的"查忙→登记"是同步临界区（`:704→712` 无 await，自保）；但流式路径两个同会话并发请求可**都通过 `:743` 查忙**（对方尚未登记），随后都登记 ⇒ 同一会话两个 run 并发 ⇒ 互相覆盖 `react_chain:{session_key}`，即 H2 文档所述静默数据损坏。需把"查忙→登记"用同一把 `asyncio.Lock` 包成原子区。

**F2 后台重建任务未持引用（MEDIUM）** — `run/chat.py:1149` `asyncio.create_task(_bg_rebuild())` 返回值未存集合、无 `done_callback`，与 `sys/chat.py:197` 点名"裸 create_task 会被 GC 中途回收"同款反模式；容器重建可能静默丢失。建议参照 `sys/chat.py:_spawn_bg`（入 `self._bg` 集 + done_callback 自清理 + `ctx.effect(driver.drain)`）。

**F3 优雅关闭不排空在途 run（MEDIUM）** — `run/chat.py:1606` 只 `cancel server.serve()` 任务，`finally` 调 `c.teardown()`；但 `active_runs` 里的 worker 任务是独立 asyncio 任务，关闭路径**未 await** ⇒ 在途 run 被粗暴取消（本轮回复丢失、MCP 调用吃 `ConnectionError`）。对标：优雅关闭是"有限等待排空在途再退出"（ayokoding ex-51；oneuptime；smarttldr：`drain_tasks(timeout)` + `server.close()` + `gather(return_exceptions)`）。建议：置 `shutting_down` 标志 → 拒新请求 → 排空 `active_runs` worker → 再 teardown。

**F4 无幂等键（MEDIUM）** — `/api/chat`(`:694`)、`/api/chat/stream`(`:730`) 每次新造 `run_id`，无 `Idempotency-Key`、无去重表 ⇒ 客户端重试/双击再跑一轮，工具副作用（写文件等）二次执行。对标：POST 变更端点应要求客户端生成 UUID 幂等键，服务端用 Redis `SET NX EX` 原子占锁 + 存储响应重放（how2.sh；yoo.be；dev.to："add them to every endpoint that creates/updates/deletes"）。

**F5/F6（LOW）** — `McpStdioClient._notify`(`:416-419`) 写 stdin 不 `await drain`（依赖后续 `_request` 顺带冲刷）；运行期无看门狗回收假死子进程（仅请求级 120s 超时 + 关闭期整树杀）。可接受，记一笔。

## 6. 【P1/P2 数据】事务 / 错误可见性 / 迁移 / 索引

**6.1 记忆插件 ALTER 仍静默吞错（违背自有纪律，MEDIUM）** — `plugins/memory/__init__.py:587-594`：
```python
for col, decl in MEMORIES_EXTRA_COLUMNS:
    try:
        await db.execute(ctx, f"ALTER TABLE agent_memories ADD COLUMN {col} {decl}", ())
    except Exception:
        pass                      # 静默！ALTER 失败原因永远不可见
try:
    await db.execute(ctx, MEMORIES_SESSION_INDEX, ())
except Exception:
    pass
```
本项目 2026-10-04 已确立"失败必须可见"纪律：`storage._ensure_events_columns`、`budget` 补列均已改 `logger.warning + 计数`。此处**漏做**，违反一致性。**建议**：对齐为 `warning + 计数`（仅 `duplicate column` 视为正常幂等）。

**6.2 `remember()` 循环 upsert 不成事务（MEDIUM）** — `plugins/memory/__init__.py:454-460`：
```python
for kind, texts in (("fact", out["facts"]), ("intention", out["intentions"])):
    for t in texts:
        await self._store.upsert(ctx, MemoryItem(...))   # 各自 autocommit
```
中途异常 ⇒ 部分 facts/intentions 已落库的不一致状态，无回滚。建议包一层 `transaction()`。

**6.3 迁移 `agent_012_message_fields` 裸 ALTER 自相矛盾（MEDIUM）** — `tables.py:66-69,113` 把两列 ALTER 留在 `MigrationRegistry`（无容错、失败整组回滚）；而同文件 `BUDGET_LOG_FIELDS`/`EVENTS_EXTRA_COLUMNS`/`MEMORIES_EXTRA_COLUMNS` 都已改为"DDL 给新库 + 容错 ALTER 补旧库"并绕开 `MigrationRegistry`（`:73-79,120-127,141-149`）。若该列已存在于存量库（早期运行时加过），`agent_012` 的 ALTER 报 `duplicate column` → 整组回滚 → 名字不登记 → **每次启动失败**。建议移出 `MigrationRegistry`，改与 `BUDGET_LOG_FIELDS` 同款容错 ALTER。

**6.4 N+1 删除（LOW）** — `wipe()`(`:565-572`)、`prune()`(`:558-562`) 先全量 SELECT id 再逐条 `delete`。改为 `DELETE ... WHERE id IN (...)` 或 `executemany`。

**6.5 索引缺口（LOW）** — `agent_events` 仅 `request_id` 有索引，`session`/`run_id` 补列未建索引；`agent_memories` recall 的 `(session, last_accessed_at)` 缺复合索引（受 `LIMIT 2000` 兜底，影响小但大表下会全扫+排序）。

**6.6 潜在缺陷** — `storage.py:86-100` `transaction()` 用 `asyncio.Lock`（**不可重入**），嵌套事务会死锁（当前无嵌套用法）；`storage.py:38` 未设 `check_same_thread=False`（当前单线程安全，但一旦有人把某 DB 调用 `to_thread` 化即报错）。两者均"当前不触发"，列入技术债待观察。

## 8. 建议落地优先级（待用户授权后分批实施）

- **P0（可用性+安全，先）**：① DB 层 `to_thread`/`aiosqlite` 卸载；② 鉴权默认开启 + 敏感读端点会话隔离（`WHERE session=?`）；③ 统一异常响应去内部细节。
- **P1（并发+数据一致性）**：④ 流式端点查忙→登记加锁；⑤ 记忆插件 ALTER 改 warning+计数、对齐自有纪律；⑥ `agent_012` 迁移改容错 ALTER；⑦ `remember()` 包事务；⑧ 安全头中间件 + 请求体 Pydantic + 限流。
- **P2（健壮性）**：⑨ 幂等键；⑩ `_bg_rebuild` 持引用 + done_callback；⑪ 关闭排空在途 run；⑫ N+1→批量删除、补复合索引。
