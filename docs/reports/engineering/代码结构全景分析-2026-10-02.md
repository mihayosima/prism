## 0. 一句话总览

**这是一个「内核极薄、能力全在插件」的分层系统，分层纪律执行得比多数同类项目严格；但它有一个反复出现的结构性毛病——文档/注释承诺的约束，代码里往往没有对应的强��机制。** 后文 §8.3 专门分析这个模式。

## 2. 静态结构：四层各自是什么

### 2.1 `agent/core/` —— 内核（零业务词）

| 模块 | 职责 |
| --- | --- |
| `container.py` | `@plugin` 装饰器、Kahn 拓扑排序、`capture/release` 区间回收、装配失败回滚、对称 teardown |
| `context.py` | `Context`（`get()` 走父链 / `provide()` 同作用域唯一）、`State`、`CURRENT_PLUGIN` |
| `events.py` + `events_catalog.py` | 事件总线：`emit`（遥测，fire-and-forget）/ `waterfall`（能力闸门，不调 `next()` 即否决）；`REQUIRED_SUBSCRIBER_EVENTS` 接线守卫 |
| `mcp_client.py` | MCP stdio 客户端（子进程组、stderr 消费、死亡感知、`_kill_tree`） |
| `session.py` | `SessionIdentity` 三元组 + 键构造 + 白名单净化 |
| `scope_config.py` | 配置继承/淘汰的**纯规则**（`merge_overrides` / `evict_lru`） |
| `tokens.py` / `request_cost.py` | token 估算与请求装配原语 |
| `audit.py` / `tables.py` | `durable()` 审计落库；DDL 与迁移登记 |
| `errors.py` / `contract.py` / `services_catalog.py` / `state_keys.py` | 错误族、接缝契约、服务键 SSOT、状态键 SSOT |

### 2.2 `agent/sys/` —— 系统层插件（8 个，恒定装配、不可停用）

`events`（事件总线服务）· `tasks`（工具注册表 + `invoke` 闸门）· `storage`（SQLite + 迁移）· `llm`（provider + 重试）· `budget`（成本护栏）· `guard`（权限）· `loop`（任务驱动）· `chat`（会话驱动）。

★ 注意两个易误解点：`agent/chat` 的 `layer` 标的是 **business**（它是编排器，不是系统机制）；`agent/sys/progress.py` **不是插件**（只是事件桥，无 `@plugin`）。

### 2.3 `agent/plugins/` —— 业务插件（9 个目录插件，opt-in）

`react`（ReAct 循环，最大）· `context`（上下文治理）· `short_term`（对话历史）· `memory`（长期记忆）· `work_memory`（任务进度 + 快照）· `approval`（审批）· `system_memory`（文件身份）· `windows_mcp` / `playwright_mcp`（MCP 工具桥）。

★ **`layer` 标签与来源正交**：plugins 目录下的 7 个仍是 `layer="system"`，只有两个 MCP 桥是 `business`。

### 2.4 `agent/run/` —— 适配层

`chat.py`（FastAPI + 24 端点 + 单端口托管前端 dist）· `config_store.py`（覆盖配置 v1/v2 + 会话分桶）。

★ **挂载顺序是硬约束**：`/api/*` 与 `/health`、`/ready`、`/metrics` 必须先注册，`app.mount("/", StaticFiles)` 必须最后——否则 catch-all 会把接口吞成 index.html。

## 3. 动态结构：一次 `/api/chat` 的旅程

★ 已抽查验证调用链：

```
POST /api/chat
  → run/chat.py::_chat(:711)
  → _identity(request, body)(:512)          ← 解析会话身份（头 X-Session-Id）
  → sys/chat.py::ChatDriver.send(:193, 收 identity= 显式参数)
      ├─ 有 Services.REACT → _send_via_react(:210)
      │     ├─ is_resume_intent → _probe_resume(:253)   ← 崩溃续接探测
      │     └─ ctx.react.run(..., identity=ident)(:310)
      │           → plugins/react/loop.py::run(:388)
      │                 while steps < max_steps:
      │                   Think  _reasoner.reason → ctx.llm.complete
      │                            ↳ LLM_PRE_CALL waterfall：guard(prepend) + budget 裁决
      │                   无 tool_calls → 收敛 return
      │                   Act    _actor.act → ctx.tasks.invoke
      │                            ↳ TASKS_PRE_EXECUTE waterfall：guard
      │                   Observe _observer.observe → 回灌
      │                 _archive_chain / snapshot_save(:600-607)
      └─ 否则单步 _plan/_execute/_narrate
  → 写短期记忆 + durable(CHAT_DONE) + 回 ChatReply
```

**★ 会话身份的传递方式是「显式参数线程化」，不是共享状态**——`loop.py:392-396` 的注释写明了原因：「不塞 ctx.state 是因为它容器级且并发共享会互相覆盖」。`ctx.state[SESSION_KEY]` 只在两处作为「尽力而为」的提示存在。

这个设计选择很关键：**主链路是安全的，问题只出在旁路**（见 §8.2 的 R1）。

## 4. 扩展机制：插件体系

### 4.1 两种形态

| | 系统层（`sys/*.py`） | 目录插件（`plugins/<name>/`） |
| --- | --- | --- |
| 加载方式 | `profiles.py` 直接 import | `PluginManager` 按**文件路径** `exec` |
| 模块名 | `agent.sys.x` | `agent_plugins.<pkg>` |
| 可否停用 | 否（恒定装配） | 是（期望态文件控制） |
| `isinstance` | 正常 | ★ **恒为假**（同一个类被定义两次） |

★ **双命名空间的代价（重要）**：对目录插件做 `isinstance(x, agent.plugins.X.Cls)` **永远失败**。类型判断必须用 `type(x).__name__` 或 `@plugin` 元数据。这是有意的取舍，但会持续制造"看起来合理却不对"的代码。

### 4.2 生命周期

`apply(ctx)`（装配期，注册服务/订阅）→ `start(ctx)`（装配后，拓扑序）→ `status(ctx)`（插件页自述，**仅 4 个插件实现**：react / approval / 两个 MCP 桥）→ `run(ctx, **params)`。

★ **`run()` 目前没有执行入口**：`run/chat.py` 里只有 `GET /api/plugins` 与 enable/scaffold/remove，**不存在 `/api/plugins/run`**。`_candidate_runnable` 会探测并把 `runnable: true` 报告给前端，但没有任何地方能触发它。属**半成品扩展点**。

### 4.3 「可换接缝」怎么实现

`React.apply` 用 `ctx.get("react.reasoner") or DefaultReasoner` 取实现——注入即换、缺省内置。与 `ctx.llm` 选 provider 同构。这是本项目"能力可替换"的统一手法。

## 5. 状态与持久化

### 5.1 SQLite：8 张表，★**只有 2 张有 `session_id`**

| 表 | owner | session_id |
| --- | --- | --- |
| `agent_events`（审计账本） | 内核 | ❌ |
| `agent_budget_log`（预算账单） | budget | ❌（列由**运行时 ALTER** 追加，不在 DDL） |
| `agent_migrations` | storage | ❌ |
| `agent_memories` / `agent_entities` / `agent_memory_edges`（长期记忆图谱） | memory | ❌ |
| `agent_messages`（短期转写） | short_term | ✅ |
| `agent_session_summaries`（会话摘要） | short_term | ✅ |

★ **这是会话隔离的真实边界**：2.2/G2 让**运行时状态**按会话分桶了，但**大多数持久化表仍无会话维度**。长期记忆（3 张表）、审计账本、预算账单都是全局的。

### 5.2 ★ 迁移是 forward-only，且**表结构真相源被分裂成两处**

- `tables.py` 的 `MIGRATIONS` 是主渠道，`MigrationRegistry.apply` 幂等、按组包事务、**无 down/回滚**；且有"防脏武"校验（已应用但未定义的迁移 → 拒启）。
- 但 `agent_budget_log` 的 `run_id`/`cache_hit`/`reasoning_tokens`/`session` 四列**不在 DDL**，而由 `budget.py:172-178` 在运行时 `ALTER TABLE` 追加、`try/except` 尽力而为。
- ⇒ **想知道一张表的完整结构，得同时看 `tables.py` 和插件代码。** 这是实打实的结构债。

### 5.3 Redis 键空间（4 种）

| 键 | 内容 | TTL |
| --- | --- | --- |
| `wm:{task_id}` | run 内进度（step/tools/checkpoints） | 3600s，finish 时删 |
| `wm:idx:{session}` | 活跃任务索引（set） | 随键 |
| `run_snapshot:{tenant}:{user}:{session}:{run}` | 每轮快照（JSON） | 86400s |
| `run_snapshot_finished:{tenant}:{task_id}` | 收尾兜底确认 | 300s |

`InMemoryWorkMemory` 与 `RedisWorkMemory` 接口完全一致、可互换（仅收尾后 TTL 语义微异）。

### 5.4 配置文件：三处，各自独立

| 文件 | 格式 | 损坏处置 |
| --- | --- | --- |
| `agent_plugin_config.json` | v1 平铺 / v2 `{version,container,sessions}` | ★ 转存 `.corrupt`（我今天修的） |
| `agent_plugin_state.json` | `{enabled,removed}` | 告警 + 转存 `.corrupt` |
| `*.db` | SQLite（WAL） | — |

★ 实测：本机 `agent_plugin_config.json` **仍是 v1 平铺**（无 `version` 键）——符合"读 v1 不写回、只在写操作时升级"的设计。

**7 个视图**：chat / events / perms / plugins / memory / tools / settings。

★ 视图可见性用 `section[data-view]{display:none}` + `.active{display:flex}`，**必须用 `:class` 不能用 `v-show`**（`v-show` 只切内联样式，会被 CSS 覆盖）。

## 8. 分析

### 8.1 结构上做得好的（有证据，不是客套）

1. **分层是"可机检的"而非"口头的"**——靠 AST 守卫而不是 code review 来保证。这在同类项目里少见。
2. **装配失败不留残骸**：`capture/release` 区间语义让"半装配"可回收（`container.py:266-312`）。
3. **两套事件语义分得很清**：`emit`（遥测，失败不阻断）vs `waterfall`（闸门，可否决）。guard/budget 都挂在 waterfall 上，权限与成本走同一条可拦截通路。
4. **`durable` 与 `emit` 分离**：审计落库不走总线，避免"审计失败拖垮业务"。
5. **依赖方向可验证地单向**，插件只经 `api.py`。
6. **主链路的会话身份走显式参数**，绕开了共享状态陷阱——这是本项目在并发上做对的关键一招。

### 8.2 结构性债务（按性质分类，非按严重度）

| 类别 | 项 | 证据 |
| --- | --- | --- |
| **隔离边界不清** | 8 张表中仅 2 张有 `session_id`；长期记忆/审计/预算账单是全局面 | `tables.py` |
| **真相源分裂** | 表结构散在 `tables.py` 与插件运行时 ALTER 两处 | `budget.py:172-178` |
| **半成品扩展点** | `run()` 无执行入口，但 `runnable` 元数据已上报前端 | 无 `/api/plugins/run` |
| **孤儿端点** | `GET /api/context` 无前端消费者 | 无 ContextView |
| **巨型文件** | `loop.py` 1300 行、`run/chat.py` 1290 行 | — |
| **容器级共享槽** | `ctx.state[SESSION_KEY]` 被 3 读 2 写（**R1**） | `router.py:51` / `budget.py:50` / `approval:209` / `chat.py:198` / `loop.py:431` |
| **死分支** | approval 的 `default="deny"` 在出厂 `allow=["*"]` 下不可达 | `policy.py:32-42` |
| **双命名空间陷阱** | 目录插件的 `isinstance` 恒假 | `plugin_manager.py:10-16` |

### 8.3 ★ 一个反复出现的模式：「文档承诺 > 实现」

这是本次全景分析**最有价值的发现**——它不是单个 bug，而是一种**反复出现的模式**：

| # | 承诺/描述（文档或注释） | 实际 | 位置 |
| --- | --- | --- | --- |
| 1 | 「apply 期读某服务**必须**已声明 inject——未声明则报错」 | ★ **无任何校验机制**（`context.py` 完全不含 inject；只能靠拓扑序+运气） | `container.py:7` |
| 2 | 「`child/scope` 是通用 GC 单元」 | 生产代码**只有 1 处**在用（`progress.py:91`），其余仅测试 | `context.py:7` |
| 3 | 插件「可一键运行」 | **无 `/api/plugins/run` 端点** | `docs/specification/插件说明书:95` |
| 4 | react/memory 插件「默认启用」 | 代码级默认是**全关**（state 文件缺失 → `enabled=[]`）；"启用"指的是仓库里那个 state 文件 | `react/__init__.py:6` |

**为什么这值得单独提**：今天我已经在别处撞到过同一个模式——`配置粒度细分与迁移方案` 声称的现状已被实现超越、`_SETTING_META` 声称"靠注释维持同源"、CI 前的"测试全绿"其实靠 `data/` 残留撑着。

**这个模式的实际危害**：它让"读文档"这种低成本认知方式变得**不可靠**。而项目的文档量是 65 篇——量大到很容易让人以为读文档就够了。

**我的建议**：给关键承诺加**可机检的断言**（本项目已经有 `test_agent_purity`、`test_contracts` 这类守卫，把这套手法用在这些"口头承诺"上即可）。例如"apply 期必须声明 inject"若真想要，就写一个 AST 测试；不想要，就把 `container.py:7` 那句改成如实描述。

### 8.4 对我此前判断的修正

- **需要修正的**：我在复核报告里把「会话隔离是约定式而非强制式」的印象泛化了。★ 实际上**主链路（`chat.send` → `react.run`）用的是显式 `identity=` 参数线程化，是安全的**；问题**只存在于旁路的 `ctx.state[SESSION_KEY]`**（3 读 2 写）。R1 的范围因此比我原先描述的**更小、更聚焦**。
- **得到印证的**：`approval` 的"默认拒绝是死路径"（旧报告 F-4）★ 实测成立；跨重启续传此前未生效（R8）成立于当时的 Redis 缺失。
- **新增认知**：迁移无回滚 + 表结构双真相源，是此前没识别到的结构债。

## 9. 结论

这个项目的**静态架构是健康的**：分层清晰、边界可机检、装配与回收对称、事件语义分明。它的主要问题不在"结构设计"，而在**两处落差**：

1. **实现落差**——文档承诺的约束缺强制机制（§8.3，4 处已证）；
2. **覆盖落差**——会话隔离在运行时不完整（持久化层 6/8 表无 `session_id`）。

而**唯一真正的架构级缺陷仍然是 R1**，且本次分析把它定位得更准了：**不是"会话隔离没做"，而是"旁路还有一条共享槽"**。范围收窄意味着修复成本比原先估计的低。

**建议的处理顺序**：
1. **R1**（旁路共享槽 → ContextVar，见审查意见 §4）——范围已收窄，成本低；
2. **表结构真相源统一**（把运行时 ALTER 收进 `tables.py`）——消除结构性隐患，改动小；
3. **文档承诺对齐**（§8.3 四处，二选一：加断言或改措辞）——防止后来者继续被误导；
4. 其余（巨型文件拆分、孤儿端点、`run()` 入口）属可选优化。
