> 标注：✅ 采纳 / ⚠️ 采纳但校正 / ❌ 拒绝 / 🔧 v3.0 修订

- **D1 键空间 `wm:` / `run_snapshot:` 独立** ✅（同 v2.0）。
- **D2 快照点只在 Observe 之后** ✅。
- **D3 单 key 单 JSON 原子** ✅。
- **D4 续传副作用语义** ✅，docstring 声明。
- **D5 幂等标记 `act_intent`/`act_done`** ⚠️🔧 **必要性采纳 + 论证修正 + 降级落点**：
  - **修正 v2.0 的错误论证**：D2（Observe 后快照）压的是"不重跑**已完成**轮"，**压不住"重跑当前进行中轮"**。崩溃发生在当前轮 Act 执行中途时，续传从上轮 Observe 后恢复 → **重跑整个当前轮 Think+Act**（含那个执行一半的 Act）→ **当前轮 Act 副作用可能重复发生**（不是"已发生"）。v2.0 的"该轮副作用已在世界发生"措辞不准确，修正为："**最多重跑当前轮，当前轮 Act 副作用可能重复发生**"。
  - **降级仍成立**：首版接受该重跑风险、只做声明（D4），`act_intent`/`act_done`（含"无配对 → 标 unknown 交人工"）作为 **2.1 增强项或并入 2.3**，是否纳入 2.1 首版**待用户裁定**。修正论证后此决策才有依据。
- **D6 自动续接触发时机** ⚠️🔧 **落点校正 + 论证已确证**：
  - 落点：`sys/chat.py:229 _send_via_react`（业务驱动层）。
  - **论证确证（回应"未核实"）**：`sys/chat.py:187-190` react 分支 `return await self._send_via_react(...)` 与单步 `_plan`（L192）**互斥**——走 react 即 `return`，永不执行 `_plan`；且 plan 只在 `ctx.react.run` 内部第一轮才发。故在 `_send_via_react` 内 `ctx.react.run` 调用前探测，**确在 plan 花钱前**，D6 不落空。
- **D7 断连 vs 崩溃区分** ✅。
- **D8 多未完成 run 选最新** ✅。
- **D9 新消息处理** 🔧 **拒绝排队 + 采纳"意图分流"**：
  - **不排队**（维持 v2.0）。
  - **但必须意图分流**（修正 v2.0"按现有 resume 语义追加链尾"的歧义——现有 resume 语义（`sys/chat.py:147`）只在 `is_resume_intent` 命中时触发，是新触发条件，不能笼统引用）：
    - M2 命中"继续"意图 → 续接 M1，新消息追加链尾（现有语义）；
    - M2 是**新任务**意图 → **不自动续接 M1**（M1 snapshot 标 `orphaned`，保留至 TTL 供审计/手动找回），正常处理 M2。
  - **明示取舍**：HTTP 单请求-单回复下，M1 的自动续接机会让位于 M2 的新任务语义（避免"我要查天气，却在写代码"的困惑）。这是不可避免的取舍，写进 docstring。
  - **`reply.notice` 为新增**（`ChatReply`（`sys/chat.py:160-169`）无此字段）→ 落点见 §4 表。
- **D10 required 与 2.1 可用性** 🔧 **澄清矛盾**：
  - **生产默认 `True`（配置模板/示例）**；**dev 默认 `False`（保兼容）+ 启动醒目 WARNING**。二者是"模板默认"与"代码兜底"之别，不矛盾。
  - **写死**：`required=True` 且 Redis 不可用 → **启动直接失败**（非告警）——这才是 required 语义；`required=False` 才降级 InMemory。
  - 2.1 验收 = `required=True` + 真 Redis 下跑崩溃续接；`required=False` 只验逻辑。
- **D11 键设计一次到位 `run_snapshot:{tenant}:{task_id}`** ✅。
- **D12 快照 TTL 共享** ✅（`snapshot_ttl_s` 默认 86400）。
- **D13 budget 不回滚** ✅。
- **D14 snapshot 无 10 条截断** ✅ 被 D3 吸收；**但新增 D19 处置 chain 膨胀**。
- **D15 读优先级** 🔧 **补具体冲突场景**：
  - 自动续接 → 读 `run_snapshot`；显式"继续" → 读 `react_chain`。
  - **唯一冲突场景（写死）**：**进程重启后用户显式说"继续"且 `run_snapshot` 未 finished** → **优先 `run_snapshot`**（更新）+ warn。其余场景两者不并存，本规则不触发。
- **D16 snapshot_* 失败路径** 🔧 **消除矛盾**：
  - `snapshot_save / load / list` → 走"吞异常仅告警"（复用 `work_memory/__init__.py:72-112` 门面纪律）；
  - **`snapshot_mark_finished` 不走吞异常路径**，**单独实现**："收尾后重试一次；仍失败 → ERROR + 写独立确认键 `run_snapshot_finished:{tenant}:{task_id}`（短 TTL）防误判崩溃"。二者不可兼得，v2.0 表述已修正。
- **D17 Redis 连接模型** ✅ 已核实：`from_url` 连接池，无单连接锁（P5 成立）。
- **D18 崩溃续接验证** 🔧 **写死崩溃语义**：
  - 主验证 = 进程 A **`kill -9`**（**不是"优雅退出但漏调 mark_finished"**——那是断连语义）→ 进程 B 读 `run_snapshot` 自动续接。
  - `CancelledError` 仅作断连续接补充。
  - 约束：真 `kill -9` 双进程需**真 Redis**（fakeredis 是进程内、无法跨进程 TCP）；CI 无 Redis 时明写"崩溃续接未做端到端验证，仅逻辑单测"，**不假装测了**。
- **D19 chain 截断策略（v3.0 新增）** ✅：
  - `run_snapshot` 的 value 含 `chain`，条目数随轮数增长（G9）。**写死截断**：**保留最近 N 轮 + 头部快照 `head`**（N 默认 20，可配置 `snapshot_chain_keep`；续传只需链尾近轮 + 头部，中间老轮可截）。
  - 不能依赖 `_prepare_chain` 折叠（只折单条、不减条目，`loop.py:667`）。
