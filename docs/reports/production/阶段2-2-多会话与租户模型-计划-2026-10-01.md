## 1. 目标与范围（v2.0 修订）

**目标**：把「**服务端全局单会话**」改造为「**客户端可携带的会话身份 + 租户/用户命名空间**」，并**闭合多会话带来的隔离缺口**——不只是把身份接进去，还要确保**一个会话看不见、碰不到另一个会话的东西**。

### 范围内（本次做）

**A. 身份与键（原 v1.0 内容）**
1. `SessionIdentity(tenant, user, session)` 值对象 + `task_id` 编解码 helper（SSOT）。
2. 会话身份由请求携带；租户/用户由服务端配置（信任边界见 §3）。
3. 全链路线程化：`/api/chat`、`/api/chat/stream`、`/api/session(/reset)`、`/api/status`、`/api/memory`。
4. 快照 `tenant` 由硬编码改解析值（键结构不变，遵 D11）。
5. 前端携带并持有会话标识；「新会话」= 轮换标识。

**B. 隔离闭环（v2.0 新增，通读代码后补）**
6. **快照探测按会话收敛**（H1，硬伤）：`snapshot_list` 必须按 session 前缀扫描。
7. **审批按会话隔离**（H2，硬伤/安全）：待答表、`session_allow/deny`、应答归属校验。
8. **取消归属校验**（H4）：`/api/chat/cancel` 只能取消本会话的 run。
9. **进度流过滤挂钩**（H3）：`tap_progress` 增 `accept` 过滤器（向后兼容）+ 关键事件补 `run_id`。

### 范围外（本次不做，明确记录）

- **真实的鉴权 → 身份映射**（token → tenant/user）：当前只有单个共享 `--token`，无用户体系。
- **预算 / `ctx.state` 的并发归组重构**（H5/H6）：内核级改动，留 2.4 独立项（见 §10 待裁定）。
- **`durable` 事件表的会话维度**（H7）：不新增列，仅建议在已有 payload 补字段。
- 2.3 回滚 + saga。

## 3. 身份模型与信任边界

### 3.1 值对象

```
@dataclass(frozen=True, slots=True)
class SessionIdentity:
    tenant: str   # 部署/组织命名空间
    user: str     # 终端用户
    session: str  # 会话（一次对话线程）
```

放置于新文件 `agent/core/session.py`（与 `core/state_keys.py` 同层，SSOT），并在 `agent/api.py` 导出。

### 3.2 来源与信任边界

| 维度 | 来源 | 理由 |
|---|---|---|
| `tenant` | **服务端配置** `agent.session.tenant`（默认 `"default"`） | 客户端可伪造 ⇒ **不可**由请求头决定 |
| `user` | **服务端配置** `agent.session.user`（默认 `"default"`）；未来由 token→身份表派生 | 同上 |
| `session` | **客户端请求头** `X-Session-Id`（客户端生成 UUID），缺省回退服务端默认 | 无隔离语义，伪造只影响自己 |

### 3.3 兼容与校验

- 缺失 → 回退 `("default","default", 服务端默认 session)`，保证 `--once`、离线测试、旧客户端**零回归**。
- `session` 走**字符白名单** `^[A-Za-z0-9_-]{1,64}$`，非法回退默认（防键空间注入与解析歧义）。

## 4. 键设计（D11 张力与取舍）

### 4.1 张力

D11 要求键结构 `run_snapshot:{tenant}:{task_id}` **不变**。但若机械把 `task_id` 扩成 `{tenant}:{user}:{session}:{run}`，键中会 **tenant 重复**。

### 4.2 推荐方案（P-a）

```
session_key = f"{user}:{session}"                    # 无 tenant
task_id     = f"{session_key}:{run_id}"              # {user}:{session}:{run}
快照键      = run_snapshot:{tenant}:{task_id}        # 结构不变（D11 ✓）+ 前缀天然含 user/session
工作记忆键  = wm:{task_id}
会话索引    = wm:idx:{session_key}
链存档键    = react_chain:{session_key}
```

- 4 元身份由「**键前缀 tenant** + **task_id 三元组**」表达，无重复。
- 与既有 `snapshot_*(tenant, task_id, ...)` 形参语义**完全一致**，2.2 只换取值来源。
- **H1 的解法天然内建**：扫描前缀可取到 `run_snapshot:{tenant}:{user}:{session}:`（比 tenant 级小几个数量级，同时消除串扰）。

### 4.3 备选（P-b，不推荐）

`task_id = {tenant}:{user}:{session}:{run}` + 快照键改 `run_snapshot:{task_id}`：违反 D11、需改动已落地键结构。

### 4.4 已知限制（如实记录）

- `wm:{task_id}` **不含 tenant**：单容器单 `work_memory` 下无碍；跨租户共享 Redis 需走 `work_memory.prefix` 分片（本轮不做）。
- 短期记忆键以 `session_key` 为键 → 获得 **user/session 级**隔离；tenant 级隔离同样留待 P-b 或前缀方案。

### 5.1 是否需要新增插件？—— **不需要**

| 2.2 组成 | 归属 | 为什么不是插件 |
|---|---|---|
| 值对象 + 编解码 | `core/session.py` | 核心原语（无 IO、无生命周期、无服务注册），与 `StateKeys`/`Events` 同类 |
| 身份解析（请求头 + 配置） | `run/chat.py` | 适配层，依赖 HTTP `Request`；插件不应感知 HTTP |
| 快照 tenant 消费 | 既有 `react` + `work_memory` | 接缝已就位（`snapshot_*` 本就带 tenant） |
| **审批隔离** | 既有 **`approval` 插件** | 待答表本就由它 own，隔离应落在 owner 插件内 |
| 会话标识持有 | 前端 `api` 层 | 前端产物 |

**不做成插件的理由**：插件 = 可插拔能力（注册 Services/Events、有 enable/disable 与生命周期）。身份是横切原语，做成插件会引入「插件依赖插件」的耦合。**唯一将来可能需要 `plugins/identity` 的场景**：可插拔身份提供方（token→身份映射 / SSO / 目录同步）——属「能力」而非「原语」，本轮不做。

## 5.2 容器 vs 会话：边界与「什么时候才需要多容器」（新增）

> 用户提问「多会话是不是多容器」触发本节。结论：**不是**，且 2.2 **不应**用多容器实现。

### 两者的实际边界（代码事实）

| | **容器（Container）** | **会话（Session）** |
|---|---|---|
| 是什么 | **装配单元**：`build_agent(config, plugin_mgr)` → `assemble()` → `start()`（`profiles.py:113`、`run/chat.py:307`） | **逻辑标识**：仅一个字符串，用作短期记忆键与 `task_id` 前缀 |
| 拥有什么 | 一套插件实例、一套 MCP 子进程、一个 `EventBus`、一份 `ctx.state`、一份预算额度 | 什么都不拥有，只是**分桶维度** |
| 数量（现状） | **1 个**：`uvicorn.Config(app,…)` 单进程（`run/chat.py:1013`），**无 workers 参数** | **1 个**：`session_id = uuid.uuid4().hex[:8]` 是 `create_app` 闭包常量（`run/chat.py:416`） |
| 隔离强度 | **进程/内存级**：跨容器不共享任何 `ctx.state`（`budget.py:17` 明写「每容器隔离」） | **键级**：同一容器内按 `session` 分桶（H1/H2/H4 正是补这个） |

`Context` 本身是**层级化**的（`context.py:114 root` / `229 child` / `104 self._state`），但当前只在容器内部使用，**没有被用来做会话隔离**。

### 什么是「多容器」（真正含义）

**同一时刻并存多个 Container 实例**。两种形态：

1. **多进程/多实例部署**（这才是生产常见形态）：uvicorn `workers>1`、多副本、多机。每个进程各 `build_agent` 一次 ⇒ 天然多容器。**当前代码不支持**（`run/chat.py:1013` 无 workers；且 `active_runs`/`session_id` 都是进程内闭包变量）。
2. **单进程内并存多容器**：技术上可行（`Context` 支持层级），但 `_Box`（`run/chat.py:394-413`）**只支持替换不支持并存**——`_apply_rebuild`（L425-435）是「新建 → 旧 teardown → `c.set(c2)`」的**全局切换**，由设置页插件启停/配置保存触发（L858/872/926/943）。

### 什么情况**才需要**多容器（判据）

满足任一即可考虑，**否则用会话分桶**：

1. **配置集不同** —— 容器是配置装配单元。不同租户/场景需要不同插件集、工具集、模型、权限 ⇒ 必须不同容器（`_merge_cfg(args)` 是全局单份）。
2. **强安全边界** —— 要求租户间不共享内存、不共享 MCP 子进程、不共享文件系统权限（会话分桶做不到进程级隔离）。
3. **故障隔离** —— 一个容器崩溃/MCP 子进程失控不影响其他。
4. **独立配额** —— 每容器独立预算（`max_tokens_per_run` 是**容器生命周期累计**额度，`budget.py:17`）。
5. **水平扩展** —— 吞吐不够要多副本。

### 为什么 2.2 **不**用多容器

- **成本被放大 N 倍**：每容器一套 MCP 子进程（#1 优雅退出实测单容器就回收 10 个）+ 一份内存 + 一次装配耗时。
- **2.1 的续接会失效**：跨容器恢复要求快照在**外部** Redis 且 `required=True`；否则 A 容器崩、B 容器读不到内存态快照。（2.0 已留 `required` 开关，将来进多容器时打开即可。）
- **引入路由/粘滞问题**：`session_id` 是进程内常量，多容器后客户端请求打到哪个容器不确定 ⇒ 需会话粘滞或外部会话路由。
- **H8 会放大**：`_apply_rebuild` 是全局切换，多容器后「改一次设置」的爆炸半径不可控。

⇒ **2.2 = 单容器 + 多会话（键级隔离）**；多容器留给「水平扩展 / 强隔离」阶段（建议 2.5+），届时的前置是把 Redis 置 `required=True` 与会话粘滞。

## 5.3 配置作用域治理：把「看起来是会话级」的设置真正分好层（新增，关键子议题）

> 触发问题：**「现在的设置都是针对单一容器的，事实上那些设置都是针对于单一会话，如何解决这个问题？」**

### 5.3.1 问题本质

单会话时代 **容器 == 会话**，这个恒等式让「设置」在用户心智里天然是会话级的。多会话后恒等式失效，但实现的**作用域仍是容器级**——因为设置经 `_save_overrides`（`run/chat.py:82`）落到**全局单文件** `data/agent_plugin_config.json`（L66），再由 `_merge_cfg`（L89-100）在 `build_agent` 时并入 config ⇒ **容器级固化**，改一次影响所有会话。

### 5.3.2 决定性代码事实（三条，决定方案形态）

| # | 事实 | 落点 | 含义 |
|---|---|---|---|
| F1 | **config 是「服务」不是属性**：`builtin={"config": cfg}` → `Container.__init__` 用 `provide("config", cfg)` 注册（L154）；`Context.get()` **走父链**（`context.py:145-154`） | `profiles.py:128-131`、`container.py:153-155`、`context.py:145-154` | ⇒ **child context 可直接 `provide("config", 会话值)` 覆盖**，下游 `ctx.config` 自动拿到会话级。**通道成本极低** |
| F2 | **`State` 无父链回退**：`State` 是纯 `__dict__`（`context.py:43-77`），且每个 Context 各自 `self._state = State()`（L104） | `context.py:43-77`、`104` | ⇒ child 的 `ctx.state` 是**全新空字典**：好处是 per-session 状态天然隔离（可直接治 H5/H6 预算串号）；**坑**是读 `BUDGET_SPENT` 会得 0 而非 root 累计值，`/api/status`（`chat.py:527`）也看不到 child 的累计 |
| F3 | **代码已预留 per-session 接缝且自陈问题**：`loop.py:315-316` docstring 原文——「前向契约：将来若真有 per-session 通道，可在**此处**优先读取（注意 `ctx.state` 实为**容器级**而非会话级，直接写它会串扰所有会话）」 | `plugins/react/loop.py:315-318` | ⇒ 设计上早已知此问题；`_tool_domains`（L318）是**运行时读 `ctx.config`** ⇒ 一旦通道就位，工具域裁剪**立刻**可按会话隔离（天然验证点） |

### 5.3.3 配置的三层作用域（分类是解法的前提）

| 层 | 何时读 | 典型键 | 改了是否需要 rebuild |
|---|---|---|---|
| **L0 进程级** | 启动参数 | `db_path`、`provider`/`model`、host/port、`--token`/`--hardened` | 重启进程 |
| **L1 容器·装配级** | `apply()` 时读一次**固化** | `context.*`（窗口/裁剪，含设置页大半）、`short_term.*`、`budget.*`（`max_tokens_per_run`）、`work_memory.*`、`approval.*`、`system_memory.*`、**插件启停** | **是**（`_apply_rebuild`） |
| **L2 会话·运行级** | **每次调用**读 `ctx.config` | `llm.*`（`llm.py:365/463/492`）、`permissions.*`（`guard.py:16`）、`react.*`（`loop.py:318/412`）、`loop.deadline_s`（`sys/loop.py:62`） | **否** |

**关键且残酷的事实**：设置页（ `_SETTING_SCHEMA`，`chat.py:117-220`）里用户最想「按会话调」的键（`max_context_tokens`、各类 ratio、`clip_*`、`max_tokens_per_run`）**恰恰都属 L1 装配级**（`_PLUGIN_OF_KEY` L158-170 把它们路由到 `plugins.context`），而 `plugins/context/__init__.py:51` 是 **apply 时读一次固化**。

⇒ **「把所有设置都做成会话级」既不现实也不安全**，必须分层。

### 5.3.4 解法（推荐：通道 + 分层标注 + run 级冻结）

**Step 1 — 建会话级配置通道（基础设施，低成本，建议纳入 2.2）**

```python
# run/chat.py：请求级 context
def _ctx_for(request, identity):
    ov = _session_overrides(identity.session)          # 该会话的覆盖，空则返回 root
    if not ov:
        return c.root
    child = c.root.child(f"session:{identity.session}")
    child.provide("config", deep_merge(c.root.config, ov))   # F1：provide 覆盖，get 走父链
    return child
```
- 所有 handler 由 `c.root.xxx` 改为 `_ctx_for(request).xxx`。
- **必须处理 F2**：child 的 `state` 是空的 ⇒ 需要「state seed」策略：把 root 的**只读共享量** seed 进 child，或明确「预算累计仍写 root、额度从 child config 读」。

**Step 2 — 给每个设置键标注 scope（与 `_PLUGIN_OF_KEY` 并列）**

新增 `_SCOPE_OF_KEY: dict[str, "container" | "session"]`（`run/chat.py`）：
- `session`：`llm.*`、`permissions.*`、`react.*`（含 `tool_domains`）、`loop.deadline_s`
- `container`：`context.*`、`short_term.*`、`budget.*`、`work_memory.*`、`approval.*`、插件启停
- 存储拆分：`data/agent_plugin_config.json` → `{"container": {...}, "sessions": {"<sid>": {...}}}`

**Step 3 — container 级键的语义呈现与保护（治 H8）**
- 前端标注「**全局生效（影响所有会话）**」，去掉「这是我的设置」的错觉；
- 有 run 在跑时 **拒绝（409）或 drain**，禁止静默换容器。

**Step 4 — 「run 级冻结」（关键设计约束，务必写死）**
会话级配置**只在 run 边界生效**，run 启动瞬间快照一份 config 供该 run 全程使用。
- 理由：避免「飞行中改配置」导致的窗口抖动、token 计量漂移、预算「已消费 > 新额度」错乱。

**Step 5（可选，建议独立阶段 2.6，不在 2.2 做）— 热生效改造**
把 `context`/`react`/`short_term`/`budget` 等从「apply 固化」改成「运行时读 `ctx.config`」。
- 收益：改设置不必 rebuild（顺带**彻底消除 H8**）+ 更多键可下沉为会话级；
- 代价：工作量大；必须配 Step 4 的 run 级冻结才安全。**不建议与 2.2 混做。**

### 5.3.5 与已有隐患的联动

- **H5/H6（预算串号 / 一个会话耗尽别人预算）**：F2 的 child state 隔离 + 会话级额度 ⇒ 天然解法（额度取 child config，累计写 child state）。
- **H8（全局换容器）**：Step 3 保护；Step 5 才是根治。
- **H1（快照跨会话）**：会话级通道让 `_probe_resume` 可按会话精确扫描（与 P-a 键设计协同）。

### 5.4 需要新增「系统 session 插件」吗？—— **不需要**（2026-10-02 追加判定）

**结论：不新增 `plugins/session`（system 层）也不新增 `Services.SESSION` 以外的任何插件形态。**

三条硬理由（均已核实，非印象）：

1. **身份是请求级，不是装配级**：既有服务（`llm`/`db`/`events`…）都是**装配期注册一次的单例**；而身份**每个请求都不同**。插件的 `apply()` 在装配期**根本拿不到当前会话**——它最多只能提供一个「会话管理器」，而调用方每请求仍须显式取得身份，插件帮不上忙。
2. **system 层插件照样可启停卸**：`test_memory.py:40` 注释明证「本插件语义上是系统组件（layer=system），照样可启停卸」。一旦 `plugins.session` 被禁用，所有消费身份的插件（react 的 `task_id`、approval 的归属、work_memory 的快照键）**全部崩溃或静默退化**。⇒ **一个「禁用即全局崩溃」的东西本质上是内核，不是插件**；硬套插件外壳只会换来脆弱。
3. **装配顺序会变脆**：身份是比 `events`/`db` 更底层的依赖（连 `task_id` 都由它决定）。做成插件就要保证它最先装配，而现有装配按目录/优先级扫描 ⇒ 引入隐性顺序耦合，正是解耦要避免的东西。

**身份传播的推荐通道（替代「全链路函数参数线程化」）**：

每请求在 child context 上 `provide(Services.SESSION, ident)`，消费方以 `ctx.get(Services.SESSION)` 自取
⇒ **无需改 `react.run` / `chat.send` / 各插件的函数签名**（原「线程化」方案要动多处签名）。

- 落地成本：内核加一个常量 `Services.SESSION = "session"`，**并同步 `Services.ALL`**（`services_catalog.py:38` 的 `ALL` 供 **AST 契约测试比对**，漏改会被 `test_services_contract` 拦下）。
- 权衡（须裁定）：隐式上下文 vs 显式参数。建议**并存**——保留 `react.run(session_id=...)` 既有显式参数，同时提供 ctx 通道，逐步过渡。

**将来什么情况才需要（判据，满足其一再立）**：
- 需要**持久化会话注册表**（会话列表/元数据/最后活跃、跨重启可见）；
- 需要**会话生命周期事件**（`SESSION_CREATED`/`EXPIRED`/`CLEANED`）；
- 需要**会话配额与清理策略**（与配置方案 §6.2 纪律 7 的 `sessions` 上限 200 + LRU 配套）；
- 需要 **UI 会话管理页**。

当前是**隐式会话**（客户端带 `X-Session-Id` 即存在会话），无注册表需求 ⇒ **YAGNI**。届时形态应为 **目录插件（business，opt-in，可降级到单会话 default）**，而非 system 层。
