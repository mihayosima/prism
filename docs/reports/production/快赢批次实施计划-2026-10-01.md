## #1 SIGTERM/SIGINT 双信号优雅退出  ⏱ 几行（但需 Windows 兼容）

**问题**（文档 P1-1 / F 多处）：
- `agent/run/chat.py:925` `server.install_signal_handlers = lambda: None` 禁用了 uvicorn 自带信号处理器；
- `chat.py:929` 仅 `except (KeyboardInterrupt, asyncio.CancelledError)`——**只捕获 SIGINT**；
- SIGTERM（容器/K8s/systemd 默认）直接杀死进程 → `c.teardown()`（含 MCP 子进程回收）**永不执行** → 孤儿 MCP 进程累积（与 09-25"孤儿累积 6 天"同源）。

**做法**（保留"禁用 uvicorn 处理器"，自己注册双信号）：
- 在 `chat.py:925` 之后、启动 `server.serve()` 之前，注册信号处理：
  - **POSIX**：`loop.add_signal_handler(signal.SIGTERM, _graceful)` + `add_signal_handler(signal.SIGINT, _graceful)`；
  - **Windows 兼容**（v1.1 修正）：`asyncio` 在 Windows 上 `add_signal_handler` 抛 `NotImplementedError` → 回退 `signal.signal`。但 `signal.signal` 的 handler 在主线程同步执行，直接设 `server.should_exit=True` **不一定能唤醒**正在 `await server.serve()` 的事件循环。正确写法：
    ```python
    signal.signal(signal.SIGTERM, lambda *_: loop.call_soon_threadsafe(_graceful))
    signal.signal(signal.SIGINT,  lambda *_: loop.call_soon_threadsafe(_graceful))
    ```
    把实际置位动作经 `call_soon_threadsafe` 扔回事件循环线程，确保 `should_exit` 被消费。
- `_graceful()`：打 `logger.warning("received signal, shutting down")` → 置 `server.should_exit = True` → `loop.call_soon_threadsafe(lambda: task.cancel())`（保证即便 serve 阻塞也触发退出）。
- 现有 `except (KeyboardInterrupt, asyncio.CancelledError): pass` + `finally: await c.teardown()` 保持不变——取消 serve 任务后 `await task` 抛 `CancelledError` 被捕获，`finally` 照常 teardown（含 MCP 子进程回收）。

**验证**（v1.1 修正 Windows 口径）：
- **POSIX**：起服务 → `kill -TERM <pid>` → 日志出现 `shutting down` 且**进程退出码 0**；
- **Windows**（v1.1 关键）：`taskkill /F` 是**强杀**（`TerminateProcess`），会**绕过** Python 信号 handler，无法验证优雅退出。须用 `taskkill /PID <pid>`（不带 `/F`，发起终止请求）或 `GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT, pgid)` 触发控制台中断；观察日志出现 `shutting down` 且退出码 0；
- 确认 MCP 子进程树被回收（`_diag_mcp/tree.py` 或进程表无 `uvx/uv/windows-mcp` 残留孤儿）；
- 回归：SIGINT（`Ctrl+C`）行为不变。

**风险**：中。Windows 信号语义与 POSIX 不同，须实测两种注册路径；`signal.signal` 在 asyncio 主线程可用，但 handler 内只能做线程安全操作（`call_soon_threadsafe`）。**不引入任何新依赖**。

## #3 LLM 调用重试 + 超时降级  ⏱ 半天

**问题**（文档 P1-2）：`agent/sys/llm.py` 的 `DeepSeekLlm.complete` 对 `client.post`（:249）/ `client.stream`（:291）只有单次 `timeout=90.0`，**零重试零熔断**；一次 429/5xx/网络抖动即整轮失败。

**做法**（在 provider 内部加重试，不碰 `LlmService` 的预算/审计链路）：
- 抽出"网络调用"与"响应解析"两层（当前解析内联在 `complete` 里，需小重构）：
  - 非流式：`_post_once()` 只做 `client.post` + 状态码判定，返回 `(status, body)`；
  - 流式：`_stream_once()` 只做 `client.stream` + 逐行收集，返回聚合后的 `(content_acc, tool_acc, usage, finish, reasoning_acc)`；
  - 解析（`_wire_call` / `_parse_json` 等）在重试成功后**只执行一次**。
- 新增 `_with_retry(coro_factory)`：对**可重试错误**做指数退避 + 抖动，封顶 `max_retries`（默认 3）、`retry_backoff_s`（默认 0.5）：
  - 可重试：`resp.status_code in (429,500,502,503,504)`、`httpx.TimeoutException`、`httpx.ConnectError`、`httpx.TransportError`、连接中途断开；
  - **不重试**：400/401/403（含模型名错误等，重试无意义）、本地 `CapabilityNotImplemented`；
  - 末次仍失败 → 抛 `LlmUnavailableError`（消息带 `last_status`/`last_error`），自动落入 `LlmService.complete` 现有失败路径（`llm.py:113` `except Exception` → durable `LLM_CALL_FAILED` :117 + emit :118 + budget 同步退款 :96 → 原样抛出 :119）。**失败路径零改动**。
- **超时降级语义（v1.2 已定，采 D2）**：重试耗尽后**抛 `LlmUnavailableError` 并沿用现有失败路径**，不引入备用 provider 切换。
  - 在 `agent/core/errors.py` 新增 `LlmUnavailableError(AgentError)`（纯类型、零逻辑）；`DeepSeekLlm.complete` 重试耗尽时 `raise LlmUnavailableError(f"llm unavailable after {n} retries; last_status={...}; last_error={...}")`。
  - 向上 `chat.py:633` / `components.py:165` 的 `except AgentError` 因子类关系照常捕获，无需改动。
  - **不引入备用模型/占位 provider**：避免"当前用哪个 provider"隐藏状态及随之而来的 budget 归组、audit 归因、错误语义改写（均属阶段 2，不混进快赢批次）。
- 把重试参数接入 `config.agent.llm`（默认值即上述），不改公开行为。

**验证**：
- 单测：`DeepSeekLlm` 注入 `httpx.MockTransport`，模拟"前 2 次 503、第 3 次 200" → 断言返回正确结果且只成功调用 3 次；
- 单测：模拟 400 → 断言**立即抛错、不重试**；
- 单测：模拟"3 次全 503" → 断言抛 `LlmUnavailableError` 且消息含 `last_status=503`；同时断言 `LLM_CALL_FAILED` durable 事件已落（验证复用现有失败路径，而非另起炉灶）；
- 冒烟：真实 `--once` 一条消息跑通（沿用 `deepseek-flash`）；
- 回归：全量测试 + `npm run check` 零新增失败。

**风险**：中。需小重构 `complete` 的内联结构；流式重试边界（v1.1 固化三档）须精确实现：
- **可重试**：① 连接建立失败（`httpx.ConnectError` / `httpx.TimeoutException` 发生在 `client.stream(...)` 的 `__aenter__` 阶段）；② 连接已建立、但在收到**首个有效 `data:` 帧之前**断开；
- **不可重试**：③ 已收到首个有效 `data:` 帧之后断开 → 原样抛出（避免半截结果被当成完整响应）；
- 实现上重试只发生在 `_stream_once` 内部、尚未 `yield`/累积任何内容之前；一旦进入 `async for line` 并消费到首个 `data:` 帧，后续异常不再重试。
保留 `stream_on` 默认行为不变。
