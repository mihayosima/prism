## 0. 结论先行

**一句话：内核是生产级的、甚至是同类里罕见的；「对外服务壳」是原型级的。当前不是「能不能跑」，而是「敢不敢对别人开放」。**

实测快照（2026-10-01）：

| 项 | 数值 | 说明 |
|---|---|---|
| 后端规模 | 111 个 `.py`，23,192 行 | `agent/` 已去除 `__pycache__` |
| 前端规模 | Vue3 + TS + Vite，约 3,796 行 | 7 个视图（无 router / 无状态库） |
| 测试 | **442 收集 / 441 通过 / 1 失败** | 失败项来自「测试滞后于特性」，非本次回归（详见 §5.7） |
| 提交 | 60 个，迭代到 2026-10-01 | 9-24 至今生产力极高，几乎每天一个主题 |
| CI / 容器化 | **无** | 无 Dockerfile / Makefile / .github / k8s / systemd |

差距的本质不是缺智能能力，而是缺**五样外壳**：可靠性语义（重试/熔断）、租户模型（会话归属）、隔离与安全（沙箱/鉴权默认值）、运维面（健康/指标/优雅停机/结构化日志）、规模化（多实例/CI/负载验证）。

## 1. 代码结构总览

### 1.1 分层（import 边界是一等约束）

```
agent/                          ← 运行时本体（独立可自举，零外部引擎依赖）
├─ api.py                       唯一公共出口：Context / @plugin / Container / EventBus / errors / LlmProvider
├─ core/                        内核实现 —— 零依赖、零业务词（test_agent_purity 强制）
│    container / context / events / errors / contract / audit / tokens / request_cost
│    / mcp_client / config_schema / event_wiring / events_catalog / services_catalog / state_keys
├─ sys/                         系统层插件（随 build_agent 恒定装配）：events/loop/llm/tasks/storage/budget/guard/chat/plugin_manager/progress
├─ plugins/                     目录插件（来源=目录 ⇒ 可启停卸；layer 只是语义标签）
│    memory / react / windows_mcp / approval / context / short_term / work_memory / system_memory / playwright_mcp
├─ fixtures/llm.py              离线确定性 LLM 夹具（零触网）
├─ run/chat.py                  入口：FastAPI + 网页 harness + 无头 --once
├─ profiles.py                  BASE 配置 + SYS/BUSINESS 插件 + build_agent 装配链
├─ tables.py                    agent_* 表 DDL / migrations
└─ tests/                       47 个文件、442 项测试
web/                            Vue3+TS+Vite 前端（7 视图；dist 已构建、单端口 8720 托管）
```

架构骨架是「slim Cordis」：无特权内核 + 一切皆插件 + 事件总线三域（durable/live/capability）+
capability 接缝（`agent/llm/pre-call`、`agent/tasks/pre-execute`）挂策略。这一套是**真实落地**的，
不是文档承诺——§3 有证据。

### 1.2 一次请求的旅程（data flow）

```
POST /api/chat (run/chat.py:486)
  └─ chat.send(ctx, message, session_id)          单全局 session（run/chat.py:405,511）
      ├─ _plan      LLM(system: <!--chat:plan--> + 记忆块 + 工具目录) → JSON 意图/工具
      │               └─ ctx.llm.complete  → waterfall agent/llm/pre-call（guard 先裁、budget 后裁）
      │               └─ 落 durable agent/chat/in（audit.py durable）
      ├─ 执行     tasks.invoke(ctx, name, caller=…)  → waterfall agent/tasks/pre-execute（guard）
      │               └─ schema 校验（tasks.py:74-104）→ handler → source clip（tokens.py guard_source）
      ├─ 解说     LLM(system: <!--chat:answer--> + 证据) → markdown
      ├─ 短期记忆 写 agent_messages（最近 ~6 轮回喂）
      └─ 若已装配 react → 委托多步循环（chat.py ctx.has("react") 软感知）
```

多步循环（react）每轮：Think（`ctx.llm` + tools=工具目录）→ 模型返回 tool_calls 则 Act（`ctx.tasks.invoke`）
→ Observe 结果回灌 → 无 tool_calls 即收敛。工具异常/被拒转观察回灌，**永不抛出**（§4）。

### 1.3 规模与内聚

- 核心核心 `core/` 的 import 全量审计：**仅 stdlib**（asyncio/json/subprocess/logging…），零第三方、零业务包。
- `plugins/` 内每个插件自持表 / 配置 / 事件，`tables=()` 者卸载零残留（react）。
- 目录插件管理：desired（`data/agent_plugin_state.json`）/ actual / delta，插件页启停卸后重建容器即生效。

## 4. 本次独立核实新增的发现（前版未系统覆盖）

这些是**我逐行读代码 + 亲测确认**的、前一份评估没点透或没提到的：

### F-1 「测试全绿」的陈述已失真 —— 现场 1 项失败 ★

`python -m pytest` 实际结果为 **441 passed / 1 failed（48s）**，与 README「103 项全绿」、架构文档「82 项」的旧快照都不符（详见 §5.7）。

### F-2 react 的容器级状态键在并发下互串 ★

`loop.py:411` 写 `ctx.state[REACT_RUN_ID]`、`loop.py:1218` 写 `REACT_LAST`；而 `loop.py:316-317`
**作者自己注释**「ctx.state 实为**容器级**而非会话级，直接写它会串扰所有会话」。chat 对 `ctx.react.run`
直接 await 无锁（chat.py:237）→ 同一容器两个会话并发时 run_id / 状态互相覆盖（预算归组 F2 亦受影响）。
单 run 内无状态，**并发下不隔离**。（负责任的判断：这是「单会话现状」下暂时无害、一旦多会话就炸的暗雷。）

### F-3 MCP 桥「活着但卡住」无自愈

`mcp_client.py:399` 调用超时（120s）后只 pop future 抛错，**不向卡死的子进程发取消**；
`is_alive` 只查「进程还活着」（mcp_client.py:169-172）不查「是否在响应」→ 卡死的 MCP server 每 120s
超时一次、永不触发 `_restart`。崩溃自愈强，**hang 自愈缺失**。

### F-4 approval 的「默认拒绝」是死路径

`approval/__init__.py:37-43` 出厂配置 `allow=["*"]`，而 `policy.py:40-41` 的 allow 命中在
`policy.py:42` 的 default 之前 → `default="deny"` 永远轮不到；且 `provider="auto-deny"` 也让 ask
落 auto-deny。fail-safe 语义写得很对，但 **出厂默认配置把它吃掉了**。真正的默认拒绝要用户删 `*` 或切 plan 模式。

### F-5 记忆图谱表建而不用

`memory/__init__.py:370` 声明 `agent_entities/agent_memory_edges`，LLM 也确实提取了
`entities/relations`（memory/__init__.py:212-218），但 `remember()` 只落 facts/intentions、
写入时 `entity_ids=[]` **恒空**（memory/__init__.py:265-271）→ 图谱是纯预留。调用方如按文档以为有图谱会拿空。

### F-6 无鉴权下管理端点裸奔 ★

`--token` **默认关闭**（run/chat.py:45）。此时：
`POST /api/plugins/scaffold` 匿名**写插件文件**（run/chat.py:814 → plugin_manager.py:158-163）、
`POST /api/plugins/remove` 匿名 **shutil.rmtree 删目录**（run/chat.py:820）、
`GET /api/events` 裸吐会话与裁决（run/chat.py:648）、`GET /api/perms` 吐权限矩阵。
本地工具型可接受；**但凡部署成一个服务，这就是默认的任意代码写入 + 信息泄露**。

### F-7 配置校验只覆盖节、不覆盖插件的键

`config_schema.py:50-59` 的 `_any` 宽松节（memory/react/approval/short_term/windows_mcp…）**不校验任何键**——
这些核心插件节里拼错键会静默落到默认值，与 core 节 fail-fast 的纪律不一致。

### F-8 `Container.start()` 无失败回滚

`container.py:314-322`：第 k 个插件 start 抛错时，前 k-1 个已启动插件**不回收**、容器仍 `_assembled=True`。
与 `assemble()` 的对称回滚（container.py:300-312）不对称——是文档宣称之外的语义缺口。

### F-9 孤儿错误类型 / 错误族不统一

- `errors.py:68` 定义 `EventDispatchError` 但 `events.py` **从未 raise**（emit 用日志吞、waterfall 原样传播）。
- `mcp_client.py:215` 的 MCP `isError` 抛裸 `RuntimeError`，不落 `AgentError` 族 → 跨模块 error 类型不一致。

### F-10 durable 审计的静默降级

`audit.py:29-31`：无 db（内存装配）时直接 `return`，审计事件丢失且无提示；写失败仅 warning 日志
（audit.py:37-39）。生产侧误判「已落盘」的风险。

### F-11 前端契约检查不在任何 CI

`web/tools/check-*.mjs`（7 个 Node 静态契约脚本，web/package.json:10-16）**从不在 pytest 或任何 CI 中运行**；
`web/dist` 在 `.gitignore:31` 不入库。契约守卫保护了后端，前端侧只有靠人 `npm run build`。

### 5.7 测试状态快照与溯源 ★（本次实测）

```
python -m pytest → 441 passed, 1 failed, 48.03s
FAILED agent/tests/test_work_memory.py::test_react_writes_and_clears_work_memory
```

**根因（已定位，非本次回归）**：`test_work_memory.py:184` 断言完成任务后 `impl._store == {}`；
但 9-29 引入的「链存档/继续」特性（`_archive_chain`，loop.py:1189-1210）在收尾时会把
`react_chain:{session_id}` 键写进工作记忆并**故意不 finish、靠 TTL 过期**（loop.py:1200 注释原文）。
测试写于 `b60aa48`（早于特性），断言与新的「为续接留链」语义冲突 → 测试滞后，不是代码回归。

**意义**：① 仓库当前不是 442 全绿；② 测试滞后于特性这一事实，本身打破了项目「架构守卫把行为锁死」的

无主动清理、仅靠访问时 TTL 检查（backend.py:115-119），长期运行会累积。**修复方向**：改测试断言
（断言含 `react_chain:...` 键）或给 `finish` 语义补一条「归档键生命周期」文档约定，二选一，勿两者都做。

## 6. 相对生产级 agent，缺的到底是什么（把差距翻译成能力）

1. **可靠性语义**：请求级 retry/backoff/断路器/备用 provider —— 现在一次抖动 = 整轮失败。
2. **归属模型**：用户 / 租户 / 会话 / 预算 四维身份 —— 现在三者粘死在进程级。
3. **隔离与安全基线**：默认最小权限、MCP 沙箱、管理端点的鉴权护栏 —— 现在默认全开。
4. **运维面**：health/metrics/优雅停机/structured log/trace —— 现在补上 1~2 天价值的代码就能换骨。
5. **规模化证据**：并发测试、负载测试、并发 DB 写压力 —— 现在「并发安全」未被任何测试背书。

**这一判断与旧报告一致，且本文新增了 5 处旧报告没抓到的具体缺口（F-1/F-2/F-3/F-4/F-6），
其中 F-1（测试未全绿）是最该先处理的一项。** 其它（F-7…F-11）属于质量债，不阻断。

| 4 | 收紧 `permissions.task_allow` 默认 + 管理端点至少默认拒绝写操作 | 几行 | 从默认全放行改显式白名单 |
| 5 | 结构化日志 + request id 贯穿（紧跟现有 durable 脊柱） | 数天 | 可排查、可串联 |
| 6 | 会话/租户模型（P0-1，最大） | 大 | 从玩具变多用户服务 |
| 7 | MCP 沙箱 + hang 自愈（F-3） | 架构级 | 真正可对外 |
| 8 | CI（跑 pytest + web check + build dist）+ Dockerfile | 1 天 | 可复用、可回归 |
| 9 | 并发/负载测试（多会话 react、并发 DB 写） | 2-3 天 | 给规模化的安全背书 |

第 0–4 项加起来约 **2 天**，能消掉大部分「上线即痛」并恢复可验证基线；
第 6、7 项决定**能不能对外服务**；第 8、9 项决定**敢不敢躺着升级**。
