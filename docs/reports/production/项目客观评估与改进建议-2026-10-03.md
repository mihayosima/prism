## 2. 做得好的地方（应当保持，不要在改造中破坏）

1. **分层是真的，不是口号。** `core`(2,851 行) ← `sys`(2,636) ← `plugins`(7,131) ← `run`(1,628)，`core/` 内部依赖经 AST 遍历**零环**，全部导入只指向 `core` 自身。`sys→core` 仅 1 处有意 shim（`sys/audit.py:10`）且在守卫白名单里显式登记，注释写着"删掉它即可摘掉豁免——不要往里加第二个名字"。
2. **6 条 AST 守卫**（`tests/test_plugin_decoupling.py:107-145`）覆盖 core→sys/plugins、sys→plugins、插件横向、插件→sys、插件→core、run/assembly→core，且能正确解析相对导入（`_resolve_relative:71-81`），修掉了历史上 `from ..other import X` 的绕过漏洞。
3. **零裸 except。** AST 全量扫描生产代码：**0 处** `except: pass` / `except Exception: pass`。13 个自定义异常全部继承 `AgentError` 并携带上下文（`ServiceNotFoundError` 附可用键清单、`CyclicDependencyError` 含可读环路径）。
4. **async 无阻塞污染。** 扫全部 `AsyncFunctionDef` 内的 `time.sleep`/`subprocess.run`/`open()`，初筛 7 处命中**全为误报**（实为 `await asyncio.sleep`）。唯一的真实阻塞读（`approval/providers.py:84,96`）已正确走 `asyncio.to_thread`。LLM 用 `httpx.AsyncClient` 而非 requests。
5. **无自起后台线程。** 零 `threading.Thread`、零模块级 `asyncio.run`、零模块级 `signal.signal`（全在 `_serve` 运行时函数内 `chat.py:1414-1418`）。SQLite 同步驱动 + `asyncio.Lock` 串行化，是对 aiosqlite 跨 loop 竞态的正确规避（`sys/storage.py:20-22` 有注释说明）。
6. **测试不打桩被测逻辑。** `MagicMock` 0 次、`Mock(` 0 次、`patch(` 仅 1 次；替身是 11 个手写 `class _Ctx` + 3 个 `_Stub`。这比常见"mock 桩掉被测逻辑"健康得多。skip/xfail = 0（无跳过掩盖）。
7. **运维基建齐备。** 多阶段 Dockerfile、非 root（uid 10001）、`HEALTHCHECK`、`/health`+`/ready`+`/metrics` 三端点、Redis AOF、`/api/*` 鉴权 + SPA 豁免清单、text/html `no-store`。这些很多项目都没有。
8. **上下文治理器是这个仓库最成熟的模块**：`context/governor.py`(1,216 行) + `core/tokens.py` 的 EWMA 校准（夹在 [0.5,3.0]、样本≥5 才生效、偏差>25% 落审计），并且留有 `docs/governance/token口径对账-问题记录.md` 记录真实事故账单。**这个"发现偏差→修→留账"的闭环是团队最该保留的习惯。**

## 3. 高危缺陷（4 项，按修复优先级）

### ★★★ H1　ReAct 循环的取消路径不收尾 → 快照状态污染 → 下次请求误自动续接

**位置**：`agent/plugins/react/loop.py::run`（392-721）

**事实**（已逐行核实）：收尾动作 `set_current_run_id("")` / `ctx.state[REACT_RUN_ID]=""` / `wm.finish` / `snapshot_mark_finished` 只出现在 **2 条正常返回路径**上——`:617-618`（找到答案）与 `:717-718`（触顶 exhausted）。整个 `run` **没有 `try/finally`**。

**后果链**：请求被客户端取消或 `reasoner.reason()`(577) / `actor.act()`(632) 抛 CancelledError → 四步收尾全部跳过 → 快照停留 `status="running"` → 而 `sys/chat.py:280-298` 的 `_probe_resume` **只认 `status=="running"`** ⇒ 下一次请求把**已取消的 run 当作崩溃残留自动续接**。

**为什么这条排第一**：它不是崩溃，是**静默的错误状态延续**——用户取消了一次对话，几十秒后新开一轮却收到"继续上次"的提示，且续接的是一个已被丢弃的上下文。日志里看不出异常。

**建议**：把 `run` 的函数体拆成 `_run_inner` + `run` 包装，`run` 用 `try/finally` 统一收尾，并区分"正常完成"与"被取消"两种收尾语义（取消时快照应标 `cancelled` 而非留着 `running`）。这同时解决 H1 与记忆里登记的另一条隐患。

---

### ★★ H2　同会话并发无锁 + 无幂等键 → 状态互相覆盖 + 工具副作用重复

**位置**：`agent/run/chat.py`（全文 grep `Lock()` / `idempot` **零命中**）

**事实**：
- `run_id` 由服务端 `uuid4().hex[:8]` 生成（`chat.py:835`），**客户端无法指定** ⇒ 无幂等键。
- 两个同 session 请求共享归档键 `react_chain:{session}`（`loop.py:1261`）与容器级 `ctx.state` ⇒ 链存档互相覆盖。
- `_probe_resume`(262) 会把**另一个正在跑的 run** 标 orphaned（301-302）。
- `_apply_rebuild`(611-622) 在 `active_runs` 有在跑任务时 teardown 老容器并 `c.set(c2)`，**在跑 worker 持有的旧 ctx 被抽走**。

**建议**：① per-session `asyncio.Lock`（注意：**不能**简单加锁，得先处理 `_apply_rebuild` 与锁的顺序，否则死锁）；② 接受客户端传 `run_id`（校验归属）或加 `Idempotency-Key`，重投时返回已有 run。

---

### ★★ H3　工具调用无超时，deadline 只在每步开头检查

**位置**：`agent/sys/tasks.py:183`（`await cmd.invoke(effective)`）、`loop.py:532`

**事实**：`cmd.invoke` **没有 `asyncio.wait_for` 包裹**（已核实 `tasks.py:175-195` 全文）；`deadline_s` 只在 react 循环顶部检查 ⇒ **单个卡死的非 MCP 工具可无限超出 120s 预算**。MCP 工具靠客户端 120s 兜底，纯 Python 工具**完全无超时**。

**建议**：在 `tasks.invoke` 内加 `asyncio.wait_for`，超时时长按任务声明或用剩余预算推导（用剩余预算比固定值更好，能保住总预算语义）。同时加"事件循环卡死"的可观测信号（`span_ms` 已有，可加个 slow-task 审计事件）。

---

### ★★ H4　SSE 队列无界，慢客户端可吃满内存

**位置**：`agent/run/chat.py:836` `q: asyncio.Queue = asyncio.Queue()`（全仓唯一一处，已核实）

**事实**：`tap_progress` 里 `progress.py:90` 的 `q = queue if queue is not None` 意味着**传了就直接用**，于是 `maxsize=1024` 的丢帧保护被完全绕过。慢客户端/断网客户端 ⇒ 队列无限增长。

**建议**：给 `asyncio.Queue` 加 maxsize，满了走丢弃最旧帧（丢 telemetry 优于丢答案）或直接断开该订阅。

## 5. 工程化欠账（4 项）

1. **依赖完全不锁版本**：`pyproject.toml:6-11` 全为 `>=` 开放区间（`fastapi>=0.139`、`uvicorn>=0.51`…），`Dockerfile:51-53` 直接 `pip install` 浮动版本 ⇒ **构建不可复现**。前端有 `package-lock.json`（`npm ci`），Python 侧连 `requirements.txt` 都没有。这是生产化最硬的欠账。
2. **零 lint/format/静态类型检查**：无 ruff/flake8/black/mypy 配置（`[tool.*]` 只有 setuptools 与 pytest）。前端也无 eslint/prettier，唯一静态检查是 `vue-tsc --noEmit`，且 `tsconfig.json:6` 开了 `strict` 但 `allowJs: true` 且无 `noUnusedLocals`。`package.json:17` 的 `check` 还漏了 `check:direct` 与 `check:single` 两个脚本。
3. **插件基类无元数据 schema 校验**：忘写 `name` 会**静默用类名注册**（`container.py:133`）。重名/服务键冲突/任务重名/参数类型校验都有（container.py:214/224、tasks.py:137/74-104），但插件元数据本身是"裸奔"的。
4. **仓库卫生**：`.gitignore` 覆盖到位（`data/`、`local_secrets.json`、`--basetemp` 残留目录都已排除），但两项开发残留被跟踪——`langgraph input/`（目录名含空格，脚本易踩坑）与 `.workbuddy/`（20 个文件，含历史开发日志与一次 PAT 泄露的记录）。对公开仓库是信息泄露面。
