## G1 · 第一梯队（零风险，可立即执行）

### G1-① 文档承诺对齐（4 处）

**目标**：消除「文档说了、代码没做」——让"读文档"重新可信。
**做法**：每处**二选一**（补可机检断言 / 改成如实措辞），**不做第三种处理**（留着不改是最坏选项）。

| # | 位置 | 现状 | 建议处置 |
| --- | --- | --- | --- |
| 1 | `agent/core/container.py:7` | 称「apply 期读某服务**必须**已声明 inject——未声明则报错」 | **改措辞**。实际无任何校验（`context.py` 不含 inject），只有拓扑序保证。改为如实描述「inject 决定 apply 顺序；未声明则可能拿到 default」 |
| 2 | `agent/core/context.py:7` | 称 `child/scope` 为通用 GC 单元 | **改措辞**并加注：生产代码当前仅 `sys/progress.py:91` 一处在用；或标注为「预留能力」 |
| 3 | `docs/specification/插件说明书:95` | 称插件「可一键运行」 | **二选一**：(a) 补 `/api/plugins/run` 端点（半成品补全）；(b) 改为「`run()` 为预留钩子，当前无执行入口」。**建议 (b)**——`run()` 的实际用途未明，补入口属于新功能而非修文档 |
| 4 | `agent/plugins/react/__init__.py:6`、`memory` 同类处 | 称「默认启用」 | **改措辞**为「目录插件默认 **opt-in**（state 文件缺失即全部停用）；本仓 `data/agent_plugin_state.json` 已启用」 |

**验收**：4 处改动后，`grep` 复核措辞与代码一致；全量测试无新增失败（纯文档/注释改动，不应影响任何用例）。
**回滚**：纯文本改动，`git revert` 即可。
**附带收益**：可考虑为第 1 条**补一条 AST 守卫**（若确实想要该约束）——但这属新增强制，建议**不在本批**做，避免混淆"对齐描述"与"新增约束"两件事。

### G1-② 表结构真相源统一

**目标**：消除「看一张表的完整结构要翻两个文件」。
**现状**：`agent_budget_log` 的 4 列（`run_id` / `cache_hit` / `reasoning_tokens` / `session`）不在 `tables.py` 的 DDL，而由 `budget.py:172-178` 在**运行时 ALTER** 追加。

**★ 关键陷阱（已实测，决定了做法）**：
不能简单照搬 `agent_012_message_fields` 的"迁移式 ALTER"。原因：
- 迁移机制 `MigrationRegistry.apply`（`storage.py:101-128`）**无容错**，语句失败 → 整组回滚；
- 而**存量库那 4 列已经存在**（被运行时 ALTER 加过）⇒ `ALTER TABLE ADD COLUMN` 必然报错 ⇒ **迁移失败 ⇒ 服务起不来**。
- SQLite 不支持 `ADD COLUMN IF NOT EXISTS`，迁移条目又只接受裸 SQL，无法写条件逻辑。

**采用做法（方案 k，成本最小且零风险）**：
把 ALTER 语句**搬进 `tables.py` 定义**，`budget.py` 改为从 `tables.py` 导入执行：

```python
# agent/tables.py（新增）
#: agent_budget_log 的演进列（F2/P3）。**为什么不走 MIGRATIONS**：存量库这些列已由
#: 早期运行时 ALTER 加过，而迁移机制无容错（失败整组回滚）⇒ 会直接导致启动失败。
#: 故保留运行时 ALTER 的容错语义，但把**定义**收到此处，使表结构真相源仍在本文件。
_BUDGET_FIELDS = [
    ("run_id", "TEXT"), ("cache_hit", "INTEGER"),
    ("reasoning_tokens", "INTEGER"), ("session", "TEXT"),
]
```

```python
# agent/sys/budget.py（改动）
from agent.tables import _BUDGET_FIELDS      # 或经 api 转出的只读视图
for col, decl in _BUDGET_FIELDS:
    try:
        await ctx.db.execute(ctx, f"ALTER TABLE agent_budget_log ADD COLUMN {col} {decl}", ())
    except Exception:                        # noqa: BLE001 —— 已存在/表未建 → 尽力而为
        pass
```

**分层归属（已核实）**：`agent/sys/storage.py:13` 早已 `from agent.tables import MIGRATIONS` ⇒ **sys → tables 是既有允许的导入方向**；`tables.py` 自述位于「内容层，不受纯度守卫扫描」。故 `budget.py` 从 `tables.py` 取常量与该先例一致，无需新增例外。

**验收**：
1. `grep -rn "ALTER TABLE agent_budget_log" agent/` 只命中 `tables.py` 一处 + `budget.py` 的循环；
2. 全量 500 项无新增失败；
3. 起一次服务，确认 `agent_budget_log` 表结构不变（列集合与改动前一致）。

**回滚**：把常量搬回 `budget.py` 即恢复原状。

### G2-① 新增会话键原语

**落点**：`agent/core/session.py` 旁新增（或同文件内），**经 `agent.api` 导出**。

```python
# 语义：ContextVar 按 asyncio task 隔离 ⇒ 一个 HTTP 请求 = 一个 task ⇒ 天然强隔离
_SESSION_VAR: ContextVar[str] = ContextVar("prism_session_key", default="")

def set_current_session_key(sk: str) -> None: ...      # 请求入口调用
def current_session_key(ctx=None) -> str:
    """ContextVar 优先；缺失回退 ctx.state（兼容既有测试与旧调用点）。"""
```

**要点**：
- 回退分支是**兼容关键**——现有大量测试用 `c.root.state[StateKeys.SESSION_KEY] = …` 写法，有回退它们**零改动**。
- 不改变 `ctx.state` 结构 ⇒ **不丢容器级状态**（这是相对"请求级 child"的核心优势）。

## G3 · 第三梯队（按需择一，G2 之后）

### G3-a 可观测性（原路线图 #5，数天）—— **已实施完成（2026-10-02 23:0x）**

- **结构化日志**：引入统一 formatter（不引第三方库，用 stdlib `logging` + JSON formatter 即可，避免新增依赖）；
- **request id 贯穿**：入口生成 → `ContextVar` 承载（**与本批 G2 同一手法，可复用**）→ 日志与 `durable` 事件都带上；
- **账本补列**：`agent_events` / `agent_budget_log` 加 `run_id` / `session` 列（幂等迁移；此处**可以**走迁移机制，因为是新增列而非已存在的列——但需先确认存量库无此列）。

**验收**：给定一个失败请求，能从日志与账本拼出完整链路。

#### 落地实况（与上面原方案的差异已核对）

| 项 | 原方案 | 实际 | 原因 |
| --- | --- | --- | --- |
| 账本补列走**迁移** | 建议走迁移 | **DDL + 容错 ALTER**（`tables.EVENTS_EXTRA_COLUMNS` + `sys/storage.py` 逐列容错） | 新库的列由 DDL 带上 ⇒ 迁移那条 ALTER 会**再加一次** ⇒ duplicate column ⇒ 整组回滚 ⇒ 服务起不来。走迁移就必须同时把列从 DDL 删掉（两条路径互斥），那样在"列已存在、迁移未登记"的库上仍会炸。取舍详见 `agent/tables.py` 注释 |
| 覆盖面 | `agent_events` + `agent_budget_log` | 只做 `agent_events` | 账单表早有 `run_id`/`session`（G2 已落）；`agent_budget_log` 缺的是"按请求查"，而账单行本来就带 task_id |
| 载体 | ContextVar | 同（`core/obs.py`，复用 G2 的 `trace_fields`） | —— |
| 新增面 | —— | `core/obs.py`（原语 + JSON formatter + record factory + 计数器）；`--log-level` / `--log-format`；`/api/events?request_id=`；`/metrics` 增进程计数；每请求一行访问日志 | 访问日志与计数器是"能运维"的最小闭环 |

**实测收益**（端到端脚本 `.workbuddy/obs_live_check.py`）：一次普通对话可按 rid 取回 **20~30 条事件、11~13 类**
（`agent/chat/in|done`、`react/start|step|final|archived`、`context/governed|waterline|compact-decided`、
`permission/decision`、`memory/remembered`…）⇒ P1-4 说的「跨 react→llm→tasks→MCP 拼不出一条 trace」已闭合。

**残留（如实登记）**：访问日志里的 `session` **恒为空**——会话键在下游 task 绑定，而
`BaseHTTPMiddleware` 让下游跑在另一个 task ⇒ 绑定不回流。**关联键是 rid**；要看会话请查
`/api/events?request_id=<rid>` 的 `session` 列（已有用例覆盖）。

### G3-b 长期记忆会话化（表结构级）

- `agent_memories` / `agent_entities` / `agent_memory_edges` 加 `session` 列 + 迁移 + **全检索点过滤**；
- 风险：检索点分散，漏一处 = 跨会话泄漏 ⇒ 需先做一次"检索点清单"再动。

### G3-c 阶段 2.3 回滚 / saga（独立能力）
