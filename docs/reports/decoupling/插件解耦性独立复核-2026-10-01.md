## 1. 先说清楚这套解耦是怎么做到的

四层 + 四条 sanctioned 通道，方向严格单向：

```
plugins/*  ──►  agent.api  ──►  core
   │                ▲
   │                │
   └── ctx.<svc> ───┘   （运行期软依赖，非 import）
        + ctx.has() 守卫 + Events 总线 + StateKeys 共享键
```

| 通道 | 机制 | 是否受守卫 |
|---|---|---|
| ① 服务 provides/inject | `Services.*` 常量 + 容器拓扑排序 | ✅ `test_services_contract` |
| ② 运行期门面 | `ctx.<key>` + `ctx.has(Services.X)` | ⚠️ 仅约定，无静态检查 |
| ③ 事件总线 | `Events.*` + `ctx.on` | ✅ `test_contracts` |
| ④ 共享状态 | `StateKeys.*` | ⚠️ 只覆盖 5/10 键（见 P2-2） |

**软降级纪律执行得很干净**：`sys/chat.py` 里 13 处 `ctx.has(Services.X)`，
`react/loop.py` 对 CONTEXT / WORK_MEMORY 全部 `ctx.get(...) if ctx.has(...) else None`，
`run/chat.py` 的 `_approval_or_none()` 同样先判后取。这是全仓最值得肯定的一处。

## 2. P1：已存在、但守卫抓不到的违规

### P1-1 · `sys` 层绕过 `agent.api` 直连 `core`（4 处）

红线「插件绕过 api 直连 core」只判定 `src.startswith("plugins/")`。
**`sys → core` 不在任何一条判定里**，于是下面 4 处畅通无阻：

| 文件:行 | 直连内容 | api 是否已有出口 |
|---|---|---|
| `agent/sys/budget.py:25` | `from agent.core.request_cost import estimate_request_cost` | ✅ **有**（`api.py:28` 已导出）→ 纯冗余违规 |
| `agent/sys/chat.py:36` | 同上 | ✅ **有** → 纯冗余违规 |
| `agent/sys/llm.py:21` | `from agent.core.request_cost import wire_messages, wire_tools` | ❌ 无 → api 出口缺口 |
| `agent/sys/audit.py:10` | `from agent.core.audit import durable, now_iso` | 兼容 shim（已声明废弃），可接受 |

另：`agent/profiles.py:22` 直连 `core.config_schema` —— 但 profiles.py **根本不在扫描范围**（见 P2-3）。

**修法**：前两行改成 `from agent.api import estimate_request_cost`；
第三行要么把 `wire_messages/wire_tools` 补进 `api.__all__`，要么明确承认「sys 可直连 core」并写进守卫白名单。
不建议拖 —— 前两处是零成本可修的。

### P1-2 · `run` 层是**完全没有规则**的一层

`_layer()` 对 `agent/run/chat.py` 返回 `"run"`，而三条红线的判定条件是
`src == "core"` / `src == "sys"` / `src.startswith("plugins/")` —— **`run` 一个都不匹配**。
也就是说 `run/` 可以 import `core`、`sys`、`plugins` 任意一层，零告警。

当前实际依赖只有三行，尚且干净：

```python
from agent.api import AgentError, Services, StateKeys          # ✅
from agent.profiles import BASE_AGENT_CONFIG, build_agent       # ✅
from agent.sys.progress import tap_progress                     # ⚠️ 直连 sys 实现
```

`tap_progress` 未从 `api` 导出，所以这行也是 **api 出口缺口**。
历史教训值得记：2026-09-26 审查 P1 就抓到过 `run/chat.py` 直连 `agent_memories`
—— 说明这一层出过事，只是当时靠人眼发现的，守卫至今没补。

### P1-3 · `LlmProvider` 契约**双份定义**

```python
agent/core/contract.py:11   class LlmProvider(Protocol):  interface_version = (1, 0)  async complete(...)
agent/sys/llm.py:24         class LlmProvider(Protocol):  interface_version = (1, 0)  async complete(...)
```

两份字节级同构（`interface_version` 与 `complete` 签名完全一致）。
而 `sys/llm.py:18` **已经在从 `agent.api` 导入别的名字**，
`api.py:11` 也**已经导出** `LlmProvider` —— 纯粹是没顺手用。
改契约时只改一处就会静默漂移。

## 3. P2：洞开着、当前无违规的盲区

### P2-1 · 相对导入完全不扫描（最危险的洞）

```python
elif isinstance(n, ast.ImportFrom) and not n.level and n.module:
#                                     ^^^^^^^^^ 所有相对导入被丢弃
```

全仓 30 处相对导入**一条都没进过依赖图**。
目前它们全是包内导入（`from .loop import ...`），所以无违规 ——
但插件只要写一句 `from ..other_plugin import X`，横向耦合就成立了，
**扫描器与守卫测试同时静默**。而目录插件恰恰是以包形式加载的（`agent_plugins.<pkg>`，带 `__path__`），
这种写法语法上完全合法。

### P2-2 · StateKeys SSOT 守卫只覆盖 5/10 个键

`test_decouple_guards._STATE_KEYS` 只有 5 个值：

```
budget_spent / budget_pending_est / react_last / permission_mode / loop_running
```

`StateKeys` 里还有 **`budget_warning`、`llm_cost_ratio`、`react_run_id`** 三个未被守卫
（`{bridge}_tools` / `{bridge}_error` 是模板串，无法字面量比对，属合理豁免）。
即：谁要是写了 `ctx.state["budget_warning"]`，SSOT 守卫不响。

### P2-3 · `coupling_scan.py` 的环检测恒为真（死代码）

```python
graph = {p: [d for d in deps if d in inject and d != p] for p, deps in inject.items()}
```

`deps` 是**服务值**（`"llm"`, `"db"`…），`inject` 的键是**插件名**（`"plugins.react"`…），
`d in inject` 恒为 False ⇒ `graph` 恒为空 ⇒ 环检测永远返回 `[]`。

实测验证：`graph(非空项) = {}`，`detect_cycles(...) = []`。
报告里那句「**inject 依赖图无环**」是**空转结论**，不构成任何证据。

### P2-4 · `profiles.py` 不在扫描范围

两个扫描器的筛选条件都是 `rel.parts[0] in ("core","sys","plugins","run") or rel.name == "api.py"`。
`agent/profiles.py` 两者都不满足 ⇒ 整文件不可见。
而它恰好是**装配清单所在地**（`SYS_PLUGINS` / `BUSINESS_PLUGINS`），也是 P1-1 里直连 core 的地方。

### P2-5 · `agent_migrations` 表无归属声明

`TABLE_OWNER` 登记了 6 张表，`agent/tables.py` 建了 8 张，
`agent_migrations` 既不在 `TABLE_OWNER` 也不在 `KERNEL_TABLES`。
当前只有 `sys/storage.py`（迁移豁免文件）碰它，实际无违规；
但规则是「未登记的 owner ⇒ 直接放行」，新表默认不受保护。

## 4. P3：设计取舍（不是 bug，但要知道代价）

### P3-1 · 新增插件要动内核 4 处 SSOT —— 可插拔性的真实瓶颈

`PluginManager.scaffold()` 声称「一个业务 = 一个插件」，但插件只要碰下面任一样，
就必须回头改**内核**文件：

| 需求 | 必须改的内核文件 |
|---|---|
| 自己的服务键 | `core/services_catalog.py`（`test_services_contract` 强制 ∈ `Services`） |
| 自己的事件 | `core/events_catalog.py`（`Events` + `EVENT_MODE`，且 `test_contracts` 禁止孤儿常量） |
| 自己的配置节 | `core/config_schema.py`（`validate_config` 遇未知键直接 `ConfigError`）+ `profiles.py` |
| 自己的共享状态键 | `core/state_keys.py` |

`scaffold()` 生成的模板插件**没有配置节**，正因为它一旦读 `ctx.config["agent"]["x"]` 就会让
`validate_config` 抛「未知配置键」。这是 SSOT 集中化换来的收益（拼错即 fail-fast）
与代价（插件不真正自足）之间的取舍，建议至少写进插件开发文档，别让人踩。

### P3-2 · 两个 MCP 插件 `inject` 为空却在用 `ctx.tasks`

`windows_mcp` / `playwright_mcp` 的类体里**连 `inject = []` 都没写**，
但 `apply()` 里直接 `ctx.tasks.register(...)`（`windows_mcp:112`、`playwright_mcp:125`）。

现在不炸，是因为 `profiles.build_agent` 先 `add(*SYS_PLUGINS)` 再装目录插件，内核恒先装配。
但这层保障**不在契约里**：声明缺失 ⇒ 依赖顺序不可被机器校验，一旦装配顺序调整就是隐患。

### P3-3 · 配置命名空间分裂

```
绝大多数插件：ctx.config["agent"]["<plugin>"]
两个 MCP 插件：ctx.config["<plugin>"]        ← 顶层独立节
```

`config_schema.py:58-59` 专门为它们开了顶层 `"windows_mcp": "_any"` / `"playwright_mcp": "_any"`。
是有意为之，但意味着「插件配置在哪」有**两套答案**，设置页 / 配置编辑器必须特判。

### P3-4 · 跨插件门面契约覆盖率 1/4

`core/contract.py` 只定义了两个 Protocol，其中**只有 `ReactResultLike` 被消费方真正引用**
（`sys/chat.py:237`）。其余接缝全是无类型的：

| 消费方 → 提供方 | 调用面 | 有无契约 |
|---|---|---|
| `sys/chat` → react | `ctx.react.run` | ✅ `ReactResultLike` |
| `sys/chat` → memory | `ctx.memory.remember` / `.context` | ❌ |
| `sys/chat`、`react/loop`、`run/chat` → context | `gov.assess` / `.memory_budget` / `.ledger` | ❌ |
| `react/loop`、`run/chat` → work_memory | `wm.begin/get/update/checkpoint/finish/list_active` | ❌ |

更尴尬的是：`GovernorLike`（`plugins/context/protocols.py:284`）和
`WorkMemoryLike`（`plugins/work_memory/backend.py:41`）**都定义了 Protocol，但定义在提供方插件里** ——
消费方因为 import 红线根本引用不到，只能当注释看。
结果就是「提供方改名 ⇒ 测试不红，运行期才断」。

### P3-5 · 前端文案硬编码插件 id（7 处展示文案）

`settings.logic.ts` / `tables.logic.ts` 里写死了 `plugins.react` / `plugins.context` /
`plugins.approval` / `plugins.memory`。仅出现在 UI 文案，**不在逻辑分支**，风险低；
但插件改名后会出现「已启用」提示与实际插件 id 对不上的陈旧文案。

## 6. 复核方法说明

- 逐文件精读：`api.py`、`core/{contract,context,state_keys,services_catalog,events_catalog,events,event_wiring,config_schema}.py`、`profiles.py`、`sys/plugin_manager.py`、`tables.py`；
- 反向 grep 校验：跨插件 `ctx.<svc>` 调用面、门面方法调用面、`ctx.config` 命名空间、SQL 表名、`from agent.core` / `agent.sys` 的所有生产代码引用；
- 对扫描器自身做空转验证（注入 `inject` 数据跑 `detect_cycles`、对含相对导入的文件跑 `imported_modules`），确认盲区不是推测；
- 未跑 pytest（当前环境无 pytest 包），全部结论均为静态可复核证据，已标注文件:行号。
