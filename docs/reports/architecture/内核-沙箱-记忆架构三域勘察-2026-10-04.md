# 内核 / 沙箱 / 记忆架构 三域勘察

## 0. 结论摘要

| 域 | 总体评价 | 最值得做的一件事 |
|---|---|---|
| **系统内核** | 扎实。Cordis 式容器 + 事件双模式 + rid 贯穿，设计自洽、注释诚实 | 内核无高危项；只有「可选项」 |
| **沙箱** | 收口干净，但**子进程工作目录未设**，是 enforcement=none 最具体的爆炸点 | **加 cwd + 环境重定向**（低成本、单点接入） |

按「严重性 × 成本」排序的推荐顺序：**记忆 C3 → 沙箱 B1 → 记忆 C1 → 记忆 C2 → C7**。

## 1. 系统内核（`agent/core/`）

### 1.1 现状：该肯定的是真扎实

逐文件读完后，内核的设计质量高于我此前的预期，以下几处是**真实的工程投入**，不是文档承诺：

- **`container.py`**：`inject` 拓扑（Kahn）+ 环检测带可读环路径（`_find_cycle:367`）；装配失败**对称回滚**——先释放失败插件的 effect 区间（`:285`），再逆序回收已完成插件（`:304`），最后 `root.teardown()`。这是正确的半途失败语义，很多框架不做。
- **`context.py`**：`capture()/release()` 用「服务键集快照 + effect 数」划插件区间（`:262`）——比"记录做了什么再撤销"更不易漏。子 ctx 服务沿父链解析、关闭后只放行 default（`:149`）防跨作用域泄漏。
- **`events.py`**：`emit` 与 `waterfall` 双模式语义分明；fire-and-forget 任务进 `self._tasks` 并在 `aclose()` 取消等待（`:162`）——**没有常见的"teardown 后残留任务"问题**；`required_seams` 在运行期兜住「闸门静默打开」（`:134`）。
- **`session.py`**：身份片段白名单 `[A-Za-z0-9_.-]{1,64}`，显式禁 `:` 与 glob 通配符（`:48`），并说明禁用理由（否则 `snapshot_list` 前缀扫描会越权命中他人会话）。这是**安全设计而非样式选择**。
- **`obs.py`**：用 `LogRecordFactory` 一处注入 rid/session/run，使 10+ 处既有 `logger.xxx()` **零改动**带上请求标识（`:98`）——典型的"不指望所有人改写调用点"的正确做法。

### 1.2 内核的已知破戒与新发现

**(a) `durable()` 内核直写 SQL —— 已知，补一条影响面**

`core/audit.py:42-48` 手写 `INSERT INTO agent_events`，破了内核自声明的"零 IO"。此前记录只说"破戒"，这里补实测影响面：`durable` 是 `agent_events` 的**唯一写入点**（有守卫测试断言），因此**它一旦失败，审计是全丢而不是部分丢**；而它的失败处理是静默计数 `agent_event_write_errors_total` + 一条 warning（`:50-53`）。

⇒ 可选项：把该计数挂到 `/metrics` 或健康检查。当前有人看才知道丢了。

**(b) 新发现：`emit` 的 fire-and-forget 无并发上限**

`events.py:115` 对每个 async 监听器 `create_task` 并登记进 `_tasks`，但**没有 cap**。守望的是"取消"，不守"堆积"。若某个高频事件（如 `agent/chat/*`、工具调用事件）挂了多个 async 监听器，瞬间可产生大量 task。当前生产监听器数量有限，属**潜在风险而非现存故障**。

⇒ 可选项：加一个 `_MAX_INFLIGHT`（如 256），超出记 `agent_events_dropped_total` 并跳过。**不建议**改成串行——会丢掉 emit 的隔离语义。

**(c) 与既有记录一致的未决项（不再论证）**

`_matches` 只支持类型规约无枚举（`config_schema.py:104`），枚举先例在设置层 `_coerce_setting` 的 choice 分支——**已裁定不为单键扩 core 能力**。

**(d) 插件热装卸的边界**

`plugin_manager.py` 只有 `load()` / `set_enabled()` / `remove()` 等**状态文件操作**，没有 `Container` 的单插件 `reload()`；启停的生效路径是整体重建容器。这与"目录插件可启停卸"的语义不冲突（重建即可），但意味着**插件页点启用后有装配窗口**，此期间请求会打到未装配的容器。属已知设计，非新缺陷。

**内核结论：没有需要立即动的高危项。** 若一定要改，(b) 的成本最低、收益明确。

## 2. 沙箱

### 2.1 收口质量：好，且纪律一致

`plugins/sandbox/__init__.py` 转 confinement 后：恒放行（`:264`）、两轴正交（`:141-142`）、`_ENFORCEMENT_CEILING` 三档全 `none` 不谎报（`:148-152`）、`enforced_by` 区分策略故障与基础设施故障（`:253`）。这套设计的价值在于**它让"没做"变成可见的一等事实**，而不是插件页上一片绿。我不建议动它。

### 2.2 ★ 新发现：MCP 子进程的工作目录未设 —— 这是 enforcement=none 最具体的后果

**实测核实（grep 全仓）：**

```
agent/core/mcp_client.py:187  asyncio.create_subprocess_exec(...)
    —— 未传 cwd 参数（全仓 mcp_client / playwright_mcp / windows_mcp 均无 cwd 字样）
```

⇒ 每个 MCP 子进程**继承宿主 cwd = 项目根**。而项目根里放着：

| 文件 | 内容 |
|---|---|
| `local_secrets.json` | **明文 API key**（64 字节，未入库） |
| `data/agent.db` · `data/agent_chat.db` | 全部对话转写、审计事件、长期记忆 |
| `data/agent_plugin_state.json` · `agent_plugin_config.json` | 插件启停与配置 |
| `.workbuddy/` | 项目记忆与验证脚本 |

再叠一层：`core/mcp_client.py:69` 的 `child_env()` **主动剥掉宿主的安全删除守卫变量**（`_HOST_SAFE_DELETE_ENV`，`:58-66`）。剥除本身有正确理由（第三方进程不该继承宿主防护，否则批量删除守卫 `SystemExit(1)` 会打死 MCP server），但**副作用是 MCP 子进程在项目根拥有不受宿主守卫约束的读写删能力**。

⇒ 这不是理论风险：`enforcement="none"` 的准确含义就是**"一个 MCP server 可以读走 `local_secrets.json`、可以删掉 `data/agent_chat.db`"**。此前文档把它写成"无进程级隔离"，抽象；现在可以写成具体路径。

### 2.3 建议：cwd + 环境重定向（低成本，单点接入）

**为什么它比 restricted token 更该先做：**

- restricted token 已实测可行，但要重做 `create_subprocess_exec` → `CreateProcessAsUserW` 封装，**要重做管道和 uvx→uv→python 整棵收尸**（`mcp_client.py:253`），成本高；
- cwd/环境重定向**只动两个已有函数**（`child_env` + spawn 点），不动进程创建机制，收尸逻辑零影响；
- 而且它是 restricted token 的**前置步骤**——先把落点收拢到会话私有目录，将来加 token 时才有"允许写的那一块"可指。

**做法：**

1. `child_env()`（`mcp_client.py:69`）增加重定向项：`TMP`/`TEMP`、`npm_config_cache`、`PLAYWRIGHT_BROWSERS_PATH`、`XDG_CACHE_HOME` → 指向 `data/sandbox/<session_key>/`；
2. spawn 点（`:187`）增加 `cwd=` 参数，指向同一目录（opt-in，默认 `None` 即保持现状，避免破坏依赖 cwd 找配置的 server）；
3. **诚实上报**：这**不是** enforcement——重定向不阻止乱写，仍可被绝对路径绕过。故 `_ENFORCEMENT_CEILING` **不变**（仍 `none`），只在审计载荷里**新增两个字段** `cwd` / `env_redirected`，让"落点在哪"可查。

> 这一点与既有纪律一致：本项目宁可报 `none` 也不谎报。把重定向报成 `partial` 就重蹈了"插件页看起来健康"的覆辙。

**收益量化（可辩护）：** 把 `local_secrets.json` 与 `data/*.db` 从 MCP 子进程的**相对路径可达范围**中移除。攻击者/失控工具仍可用绝对路径访问，但**误伤面**（脚本按相对路径写临时文件、缓存写满项目目录）消失——而后者是实践中更高频的一类。

## 3. 记忆架构

四插件**完全独立、无跨插件 import**（已核实），唯一编排者是 `sys/chat.py`。

| 插件 | 存储 | 表/键 | 会话维度 |
|---|---|---|---|
| `system_memory` (81) | Markdown 文件，启动读入内存拼串 | 无表 | ✗ |
| `short_term` (782) | SQLite | `agent_messages` / `agent_session_summaries` | ✓ |
| `work_memory` (567) | Redis（降级进程内 dict） | `wm:{task_id}` / `run_snapshot:*` | ✓ |
| `memory` (388) | SQLite | `agent_memories` | ✗ |

### 3.1 ★★ C3：长期记忆无会话维度 ⇒ 跨会话/跨租户串味（最该修）

**实测核实：**

- `agent/tables.py:32-38`：`agent_memories` 无 `session` / `tenant` / `user` 列（只有 kind/last_accessed_at 有索引）；
- `MemoryItem`（`memory/__init__.py:85-98`）无该字段；
- 写入 payload（`sys/chat.py:245-247`、`:339-345`）不带会话信息；
- 召回 `recall()`（`:292-306`）不过滤任何身份。

⇒ **后果**：A 用户在会话里说的事实，会出现在 B 用户会话的 `[相关记忆]` 注入块里（`chat.py:637`）。这不是"性能问题"，是**正确性与隐私**问题，且随使用时长单调恶化（见 C1：记忆永不淘汰）。

注意 `short_term` 和 `work_memory` **都有**会话维度，唯独长期记忆没有 —— 不一致本身也是线索：这不是刻意设计，是漏做（与既有记录 §7「长期记忆会话化，仍未做」一致，此处补的是实测证据）。

**修法要点**（勿踩既有坑）：加列必须走「DDL + 逐列容错 ALTER」双写（定义 `agent/tables.py`，执行 `sys/storage.py:149-172`），且该路径**失败全静默无日志** ⇒ 需同时补日志，否则列没加上会表现为"召回仍串味"却查不到原因。

### 3.2 ★★ C1：`prune()` 的淘汰条件在数学上永不成立（实测）

`memory/__init__.py:335-344`：`prune(older_than_days=30, min_score=0.25)`，判定式是
`age > 30 and score("", m, now) < 0.25`。

而 `score()`（`:228-238`）在**空查询**时 `lex = 0.5`（`:231` 的 `if not q_toks` 分支），并非 0。代入实测：

```
age=  30d  score(空查询)=0.2949  -> 保留
age=  60d  score(空查询)=0.2611  -> 保留
age= 180d  score(空查询)=0.2569  -> 保留
age=3650d  score(空查询)=0.2569  -> 保留
理论下界（age→∞, accessed_count=1）= 0.2569  ≥ min_score 0.25
```

**根因**：`0.50 × lex(0.5) = 0.25` 恰好等于阈值，其余三项恒非负 ⇒ 任何未被标 `invalid_at` 的记忆**永远删不掉**。

**叠加事实**：`prune` 生产侧**零调用**（grep：仅 `tests/test_memory.py:117`），无调度器、无 TTL；`remember` 路径从不设 `invalid_at`。

⇒ **`agent_memories` 表只增不减，`prune` 语义上是死代码。** 结合 C3：串味范围随使用时长单调扩大。

**修法**：两选一——
① 空查询时不给词面基线（`lex = 0`），使 score 下界 → 0.0069，条件可达；
② 淘汰判据改用「年龄 + accessed_count」而非打分（更易解释、可单测）。
我倾向 **① + 加调度**：改一行即可让既有语义生效，且不动打分公式在真实查询下的行为。

### 3.3 ★ C2：entities / relations 提取了就丢（死表 + 白花 token）

- `EXTRACT_SYSTEM`（`:50-56`）明确要求 LLM 输出 `entities` / `relations`；
- `MemoryExtractor.extract`（`:216-217`）如实解析出来；
- `remember`（`:265`）**只遍历 `facts` / `intentions`** ⇒ entities/relations 被丢弃；
- `tables.py:40-47` 建了 `agent_entities` / `agent_memory_edges`，全仓**零 INSERT**（已 grep 核实，仅建表 + 插件 `tables` 声明 + 测试引用）。

⇒ 两重代价：**每轮一次 LLM 调用白输出两项**（直接计入工具税/成本），加上两张永空的表。

**修法**（成本低）：要么从 `EXTRACT_SCHEMA`/`EXTRACT_SYSTEM` 里删掉这两项（**立刻省钱**，且诚实——当前就没用），要么真正落库。若要"图记忆"，那是另一个量级的工程，不该夹带在优化里做。推荐先删。

### 3.4 C4：`recall` 全表载入 + 逐条 touch

`valid()`（`:176-180`）`SELECT *` 全表，`recall` 在 Python 侧全量排序后取 top-8（`:294-298`），再对这 8 条**逐条 UPDATE**（`:301`）。

⇒ 每轮对话：1 次全表读 + 8 次写。记忆量小时无感，结合 C1（永不淘汰）会**随时间线性恶化**。且 `invalid_at` 无索引（只有 kind/last_accessed_at），过滤仍走全扫。

**修法**：`ORDER BY ... LIMIT` 下推到 SQL（但打分含 `math.exp`，需把新鲜度项写成 SQL 表达式或退化为"先按 last_accessed_at 取候选 N 条再打分"——后者简单且够用）；`touch` 合并为单条批量 UPDATE。

### 3.5 C7：压缩任务裸 `create_task`，无引用

`sys/chat.py:255` 与 `:354`：

```python
asyncio.create_task(self._safe_compress(ctx, session_id))
```

对比 `core/events.py` 的做法（登记进 `_tasks` + `aclose()` 取消等待），这里**没有引用、没有追踪** ⇒ 容器 teardown 时不会等它，进程退出即丢压缩。后果不算严重（下一轮会再触发），但**与内核既有纪律不一致**，且是"为什么有时候历史没压缩"的解释之一。

同类：`run/chat.py:1064` 的 `_bg_rebuild()` 也是裸的。

### 3.6 其余（低优先）

- 同一轮对话写三份：原文 `agent_messages` + 提炼 `agent_memories` + `work_memory` 快照含 chain。内容不同但同源，**是否该合并是产品决策，不是缺陷**，不建议为"去重"而合并（会丢掉各自的时间语义）。
- `system_memory` 每轮拼 3 次无缓存（`chat.py:628`/`:717`/`loop.py:420`）——量小（81 行插件），收益低。
- 四个记忆插件**均无 `status()`**（已核实），插件页上看不到记忆运行态；而 guard/approval/sandbox/mcp/react 都有。属一致性缺口，非故障。
