## 三、guard 三态裁决：机制在，但 ask 是死路（⚠️ 本调研最关键发现）

### 3.1 机制现状

`agent/sys/guard.py:19-47` 的 `_decide()` 已支持三态：

- 配置路径：`config["agent"]["permissions"]["risk"]["read"|"write"|"danger"]` → `"allow" / "deny" / "ask"`；
- 判定顺序：deny 名单 → 显式 risk 策略 → default open → 收窄模式走 allow 名单；
- 行为锁定：`agent/tests/test_guard_risk.py:86`（`test_risk_ask_denied_with_hint`）明确断言——**命中 ask 时按拒绝处理，reason 须含 "ask"**。

### 3.2 定性修正（v1.2）：「死路」仅限 guard 的 risk="ask" 配置路径

`guard.py:80-86`：guard 判 `ask` 时**不调 `next()`，直接返回 `{"denied": True}` 短路**。guard 以 `prepend=True` 挂在 `agent/tasks/pre-execute` 最前。

v1.0 曾据此断言「approval 永远拿不到球」——**该推断过度推广**。拓扑序推演：`agent.approval` 字母序先于 `agent.guard` apply（同为零入度节点按 pid 排序），guard 后 apply 且 prepend ⇒ 链序恒为 **`[guard, approval]`**。于是：

- guard 对任务**放行**（默认 open 矩阵下的绝大多数任务）→ 调 `next()` → **approval 收到调用**；
- guard **硬否决**（deny 名单 / 收窄模式拒绝）→ 短路 → approval 不被调用 ⇒ 设计稿 AC-7「guard deny 时 approval 不问人」**天然成立**；
- guard 命中 `risk.*="ask"` → 短路拒绝 → approval 不被调用——**这一条**才是死路，但它本就不是 approval 的接缝：guard 的 ask 配置语义 = **无 approval 时的 fail-safe 兜底**（无人问就拒绝，安全）。

结论：**ask 的来源是 approval 自身名单（`approval.ask` 工具名 fnmatch）+ 模式（auto/plan）**，与 guard 的 risk 配置分属两界、不应混用（同时配置时 guard 先短路，问人无从发生——对外文档需写明）。

### 3.3 解法定型（v1.2）：维持 v1 原案 append 挂载，guard 与 `tasks.invoke` 一行不动

v1.1 的「prepend 链首包裹式」**撤销**（误修：它反而会让 approval 抢在 guard 之前问人，破坏 AC-7）。定型方案 = 设计稿 v1 原案：

- approval 以**默认 append** 挂 `agent/tasks/pre-execute`，排在 guard 之后；
- 判定流程：guard 硬规则先裁 → 放行后 approval 按自身名单 + 模式判 `allow/deny/ask`；
- `ask` → 调 provider 问人 → 批准 → `next()` 放行；拒绝/超时/异常 → 一律 `{"denied": True}`（fail-safe）；
- 卸载/停用 approval ⇒ 回到现状（guard 兜底），零残留。

> 教训记录（方法论）：v1.0 的「死路」结论来自只看 guard 短路分支、未推演**装配序下链的实际形状**；v1.1 的「链首包裹式」来自在同一错误前提上设计解法。修正手段是**拓扑序推演 + 行为级实测**（`test_approval.py` 锁定「guard 硬否决的任务 approval 不问」）。

## 四、其余缺口（❌ 均未实现）

1. **`plugins/approval` 插件整体不存在**——目录、policy 三态判定、providers（auto-deny/auto-allow/CLI/web）、待答请求表（call_id → Future 注册表）、超时与 fail-safe、`agent/approval/asked|answered|timeout|mode_changed` 四类 durable 事件，全部为零；
2. **`tasks.invoke` 不支持参数改写回读**：只读 `decision["denied"]`，不读 `decision["kwargs"]`（updated_input 机制无法工作）；
3. **approval 拒绝与 react 连拒终止耦合未定义**：拒绝 → `denied=True` → `rejected[name]` 计数（loop.py:272-276）→ 同工具 3 次拒绝终止整轮——**"用户拒绝"会被当成"工具死循环"**，合理语义应是"读拒绝理由、换方案继续"；
4. **plan 模式软硬两层皆空**：可见集恒全量（软约束空）、approval 不存在（硬兜底空）→ 目前 plan ≡ default；
5. **通道半通**：SSE 出站 + 取消已实施（`run/chat.py` 的 `/api/chat/stream`、`/api/chat/cancel`），但 `PROGRESS_EVENTS` 不含 `agent/approval/pending`，前端收不到弹窗信号；**入站应答通道（人回答批/驳）完全没有**；
6. **一轮多次 ask 无批量确认机制**，挂起与 cancel 的交互也未定义。
