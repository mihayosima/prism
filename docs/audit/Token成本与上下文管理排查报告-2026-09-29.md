## 一、问题陈述

3 万字小说任务（《长夜剑歌》，9-29 凌晨 02:02–02:09，会话 a9d8e16c）单次消耗约 80 万输入 token，且未在预算预警前完成。用户判断：agent 调用 MCP 的过程中，生成的原文被原封不动多次作为请求发送，造成 token 爆炸。本报告按模块排查根因，并给出修复方案。

**成本结构公式**：总成本 ≈ Σ（步数 × 当步窗口）——「步数」与「窗口」两个乘数在此事件中均无有效闸门。

## 三、四模块排查结论

### 3.1 MCP —— 部分成立，病根在输入侧

- **输出侧已有管理**：`guard_source` 源头护栏将单条工具结果裁至 8192 token；懒加载（tool_search/tool_load 元工具）已实现但 `lazy_tools=False` 未启用。
- **真正的漏洞在输入回灌**：写文件的章节原文作为工具**参数**进入 act 条目，之后每步请求原封重放。工具描述 schema 每步约 2,253 token（33 步 ≈ 7.4 万，占 9%）。

### 3.2 React —— 成立，归因最重

- **`keep_recent=6` 豁免区是致命伤**：「一个 run 写 2 章」仅产生 4~5 条链条目，全部躺在豁免区内——act 折叠首轮 `act_folds=0`、观察折叠 `clips=0`，章节原文整轮每步裸重放。
- **`max_steps=8` 只限次数不限体积**：8 步跑满，步步全量重放。
- **跨 run 全链重放**：每次续接首步即 38.7k~39.5k。

### 3.3 工作记忆 —— 不成立（澄清）

工作记忆根本不进提示词（块构成仅 react_system/prior/prompt/chain），检查点只是折叠标记的内部回溯源。真正进请求的是链上的 act 原文，账记在 MCP 输入回灌与 React 头上。

### 3.4 上下文管理器 —— 成立，机制失效的根源

- `max_context_tokens` 被配置为 1,000,000 → input_budget 实测 90~99 万，而实际窗口 1.5~4.7 万——**荷载率 1.5%~4.7%**，治理器裁剪触发条件 `used > allocated` **恒为假**，丢弃整晚为 0。
- 80% 预算预警锚在运行预算（80 万才响），对 3 万字任务而言报警即烧完。

## 四、DeepSeek-V4 规格修正与缓存账单发现

### 4.1 规格修正

用户查证属实：DeepSeek-V4（Flash/Pro）上下文均 **1M**、最大输出 384K。此前「64k 硬限」为 V3 时代规格，作废。因此 `max_context_tokens=1M` 与模型能力一致，**不再是配置错误**；「恢复 24k 工作窗口」的建议撤回，改述为「经济压缩阈值」（见 §七）。

### 4.2 缓存账单（颠覆性发现）

`agent_budget_log.cache_hit` 字段实为**命中 token 数**（此前误当布尔值）。实测：

| 指标 | 数值 |
|---|---|
| 总输入 | 802,819 |
| 缓存命中 | 629,632（78.5%）→ 按 Flash 牌价 ¥0.2/M |
| 未命中 | 173,187 → 按 ¥1/M |
| 输出 | 51,175 → 按 ¥2/M |
| **整晚实际花费（deepseek-flash）** | **≈ ¥0.40**（Pro 约 ¥3.9） |

关键模式：
- **run 内步进命中 96~99%**（每步仅 miss 500~2,000 新增 token）——前缀缓存把「原文重放」打了大折；
- **续接/冷启动首步命中骤降 18~21%**，约 3 万 token 按原价重付——**续接时前缀被破坏**（prior 块 run 间变化 / 链存档恢复字节不一致），整链缓存失效。

**结论：真正烧原价的不是重放本身，而是续接时的前缀失效。**

## 五、周期涨落分析：缺下降沿

33 笔账单的时间序曲线呈**棘轮**形态而非**波动**：
- run 内严格单调上升（16.5k→25.6k、25.1k→37.6k、39.5k→47.8k），无一次压缩回落；
- run 间基线棘轮式抬高（16k→25k→38.7k→39.5k），因存档链全量重放。

**装配（assemble）本身每笔都正确执行**；缺失的是下降沿的触发器：
1. 治理器丢弃式裁剪挂在不触发的 1M 配额上；
2. run 内折叠被 `keep_recent=6` 豁免区挡住；
3. 系统中不存在「达到窗口百分之 X 触发压缩」的主动机制。

**缓存经济学约束**：上升沿命中 96~99%（¥0.2/M，便宜）；每次压缩 = 前缀突变 = 一次性全 miss（¥1/M 重建）。盈亏平衡：压缩掉 D 个 token、窗口 W，需后续约 **4(W−D)/D 步**回本（W=40k、压至 15k → 约 2.4 步）。故正确周期形态为**低频、大回落**（涨到阈值一次性压缩），不可每步折叠。

## 六、上下文装配管线审计（对照 11 段参考模板）

参考模板：`[系统提示]→[工具定义]→[输出格式]→[长期记忆]→[任务目标+计划]→[RAG结果]→[短期记忆摘要]→[工作记忆]→[最近N轮对话]→[ReAct轨迹]→[用户当前输入]`

| 模板段 | 现状 | 说明 |
|---|---|---|
| 系统提示 | ✓ react_system | rigid=True，永不裁（合理） |
| 工具定义 | ⚠️ 预算外 | native tools 仅 reserve 占位、从不裁剪（约 2.2k/步；懒加载未开） |
| 输出格式 | ✓ 并入系统提示 | 随刚性块豁免 |
| 长期记忆 | ✗ **react 执行窗口没有** | 仅 chat 规划与非 react 路径注入（limit=5 条）；react prior 只装 summary+history——功能盲点 |
| 任务目标+计划 | ✓ react_prompt + prior | 计划以非结构化形式躺在历史里 |
| RAG 结果 | — | 无此管线 |
| 短期记忆摘要 | ✓ summary 块（weight 0.10） | short_term compactor 生成 |
| 工作记忆 | ✗ **完全不进窗口** | 更深盲点：折叠标记「见 checkpoint step_N」但模型无工具可读回——渐进披露只做了一半 |
| 最近 N 轮对话 | ✓ history 坑（weight 0.60） | 可逆截短 + 治理器配额 |
| ReAct 轨迹 | ✓ react_chain（weight 1.0） | **本次事故主角**：唯一体积巨大又本该被调度的块，三条回落路径全部断电 |
| 用户当前输入 | ✓ react_prompt | rigid |

## 七、各记忆模块截断/折叠/压缩策略盘点

| 模块 | 截短 | 折叠 | 压缩 | 触发阈值 | 评价 |
|---|---|---|---|---|---|
| 短期记忆 | ✓ truncate_view 可逆截短（工具结果 6k、文件 12k） | — | ✓ LLM 摘要（五类分预算 80~150） | **compact_trigger_tokens=12000（绝对 token 数）** | **全系统设计最正确**：阈值远小于窗口、必然触发、有降级链 |
| 长期记忆 | ✓ 召回 limit=5 + max_chars | — | — | 无自动压缩；prune（30 天+低分）需手动 | max_chars 从 1M 派生为天文数字，实际靠 5 条封顶 |
| 工作记忆 | — | — | — | TTL 3600 秒 | 不进窗口，无 token 策略 |
| ReAct 轨迹 | ✓ 末位保底硬裁 | ✓ act 参数折叠 + 观察首尾折叠 | ✗ 无 LLM 压缩 | keep_recent=6（条数）+ act_fold（单参数）；丢弃阈值=1M 配额恒不触发 | 三策有两策断电 |
| 窗口总体 | — | — | — | **「达到上限百分之几触发压缩」机制不存在** | 80% 预警锚在运行预算；治理器只被动裁剪 |

## 八、盲点清单（汇总）

1. **ReAct 轨迹不受任何有效 token 阈值控制**（折叠豁免区 + 丢弃断电 + 无 LLM 压缩）——本次成本事故主角。
2. **续接前缀失效**：每次「继续」约 3 万 token 按原价重付（命中骤降至 18~21%）。
3. **无主动周期压缩机制**：唯一正确的范式（短期记忆 12k 绝对阈值）未推广到 react 链与窗口总体。
4. 工具定义在预算外且懒加载未启用（约 9% 开销）。
5. 工作记忆 checkpoint 引用读不回（渐进披露反向缺失）。
6. 长期记忆不在 react 执行窗口（功能盲点，非成本）。
7. 孤儿索引：redis `wm:idx:*` 无 TTL，任务键过期后残留。
