## 一、审计结论（摘要）

**「覆盖面不足」成立**，且不足体现在**四个独立维度**，不是单点缺块：

| 维度 | 结论 | 一句话证据 |
|---|---|---|
| **① 段覆盖** | **不足** | 11 段经典模板中，**4 段完全无块**（输出格式、工作记忆、RAG、附件），1 段半覆盖（工具定义：文本块有、native 数组无） |
| **② 端点覆盖** | **不足** | 4 个装配端点（plan / prior / narrate / react）各管一段，**无整轮全景账本**；治理器每次只看见一个端点的块 |
| **③ 对象覆盖** | **不足** | 治理器只治理「块」，不治理「请求附加项」——tools schema 与 response_format **扣预算却不登记、不可裁、无上限**（reserve 黑洞） |
| **④ 生命周期覆盖** | **不足** | 只治理「当下这一步」，不治理「跨步/跨轮演化」——无水位、无压缩契约、无覆盖率校验、无前缀稳定性约束 |

**总量化的尴尬事实**：四个端点共提交 **13 个块**（chat 侧 8 个 + react 侧 4 个，其中 memory 复用）；但**真正参与可裁池（flex）的只有 3 个**——`summary`（w=0.10）、`history`（w=0.60）、`react_chain`（w=1.0）。其余 10 个块全部 `rigid`，而 rigid 的降级阈值又锚在 1M 窗口上（详见前置报告），**实际等于全部豁免**。

**与业界标尺对比**：Anthropic / Claude Code / Manus / MemGPT 等生产级实现，其上下文管理器的职责面普遍包含**七项能力**（记账、分层、选择、压缩、清除、隔离、可观测）；本插件**只具备其中 2 项半**（压缩的一半 = 折叠；记账的一半 = 预算分配）。

**一个重要的正向对拍**：我们 9-29 凌晨修复的两起 400——「裁剪以配对原子单元」（`_pair_units`）与「思考链回传」（`reasoning_content`）——**恰好对应 Claude Code 三级压缩系统中被专门保护的两条不变量**：「切割点必须保持 tool_use / tool_result 配对」「thinking block 必须完整」。说明修复方向与业界一致；但业界是把这两条作为**系统级不变量**（配切割点计算、9 段式摘要模板），我们只是打了两个补丁，**尚未上升为治理器的结构性约束**。

## 二、代码实况：治理器现在到底管什么

### 2.1 能力面（`governor.py` 实测清单）

| 类别 | 方法 / 字段 | 说明 |
|---|---|---|
| 预算派生（10 项） | `input_budget` / `memory_budget` / `history_budget` / `react_budget` / `source_clip_budget` / `react_keep_recent` / `react_min_chain_tokens` / `clip_max_tokens` / `clip_head_tokens` / `clip_tail_tokens` | **全部按比例从 `max_context_tokens` 派生**（memory 10% / history 60% / 余额给 react） |
| 装配（1 项） | `assemble(blocks, reserve_tokens=, cost_factor=)` | 刚性先占 → water-filling 分配 → 块内裁剪 → coverage 互斥 → 报告 |
| 历史收取（1 项） | `pick_history(messages, budget, keep_first)` | 从新到旧贪心；**已从 chat 调用链移除**（保留供未来复用） |
| 块内准备（4 项） | `clip_head_tail` / `_clip_hard` / `_trim_text` / `_trim_messages` | 折叠（首尾保留）与丢弃（配对原子 + 末位保底） |
| 权重默认值 | `_DEFAULT_WEIGHTS = {memory: 0.10, tools: 0.20, history: 0.60, summary: 0.10}`；`_DEFAULT_WEIGHT = 0.10` | **按块 key 硬编码的默认权重表**——治理器内唯一认识块名的地方 |
| 契约（4 类型） | `BlockSpec`（8 字段）/ `BlockReport`（9 字段）/ `AssemblyReport`（5 字段）/ `Assembly`（3 字段） | 见 `protocols.py` |

**关键观察**：治理器**没有任何「块之外」的概念**——没有附件、没有水位、没有压缩策略、没有完整性清单、没有跨端点账本。它的全部世界观就是「调用方交上来的一批块」。

| 端点 | 触发者 | 提交的块（key / kind / rigid / weight / priority / coverage） | reserve（扣预算不登记） |

| **chat·prior** | `sys/chat.py::_build_prior` | `summary`(msgs, flex w=0.10, cov=(0,covers]) · `history`(msgs, flex w=0.60, cov=(covers,hi]) | `react_min_chain_tokens` |
| **chat·narrate** | `sys/chat.py::_narrate` | `answer_head`(text, rigid) · `memory`(text, flex) | — |
| **react·循环** | `plugins/react/loop.py::_window` | `react_system`(text, rigid, p=-10) · `react_prior`(msgs, rigid, p=0) · `react_prompt`(msgs, rigid, p=5) · `react_chain`(msgs, flex w=1.0, p=10) | native `tools` 数组 |

### 2.3 治理器视野之外（盲区清单）

| # | 对象 | 现状 | 后果 |
|---|---|---|---|
| Z1 | **native tools schema** | 仅 `reserve_tokens=estimate_request_cost(tools=...)` 占位 | 扣预算、不可裁、无上限；每步约 2.2k 不可见 |

| Z5 | **工具输出（观察）** | 源头 `guard_source` 8192 裁，但**不进装配账本** | 观察体积变化在治理报表中不可见 |
| Z6 | **RAG 结果** | 无此管线 | 模板第 6 段为空 |
| Z7 | **附件 / 多模态** | 无 | 未来接入时无登记位 |
| Z8 | **本轮用户输入（chat 路径）** | 直接 `messages + [user]`，不经 assemble | 未参与预算（react 路径已修好：`react_prompt` 是块） |
| Z9 | **跨端点全景** | 每次 `assemble` 只见一个端点的块 | 无法回答"这一轮 plan+react+narrate 各占多少" |

## 四、业界实践调研（对标标尺）

### 4.1 Anthropic《Effective Context Engineering for AI Agents》

- **核心命题**：上下文是**有限的注意力预算**；随着 token 增长，召回精度下降——称为 **context rot**（Chroma 研究：关键内容位于窗口中段时性能下降可超 30%，与斯坦福「Lost in the Middle」一致）；
- **目标函数**：找到**最小的、信号最强的** token 集；
- **四大策略**：
  - **Write**（写出去）：scratchpad / 长期记忆 / **文件系统作为上下文** / 复述目标；
  - **Select**（选进来）：语义检索、知识图谱、**动态工具加载（按需而非全量）**；
  - **Compress**（压下去）：compaction、**工具结果清除**、层级摘要；
  - **Isolate**（隔离开）：子 agent、沙箱、状态对象隔离；
- **推荐装配顺序**：系统指令 → **相关记忆与知识** → **工具定义** → 对话历史——稳定、高优先级者在前；
- **结构建议**：系统提示用分节（`<background_information>` / `<instructions>`）而非 if-else 硬编码；
- **代理级纪律**：每次调用/子 agent 只给**最小必要上下文**，其余靠工具**显式取用**。

### 4.2 Anthropic API：三层上下文管理原语（2026 现役）

| 原语 | 机制 | 运行位置 | 关键参数 |
|---|---|---|---|
| **Context editing**（`clear_tool_uses_20250919`） | **外科式清除**旧工具结果，**保留「发生过调用」的占位** | 服务端、客户端指定 | `trigger`（token 或 tool_uses）/ `keep`（保留最近 N 对）/ **`clear_at_least`（最小释放量，防止无谓打掉缓存）** / `exclude_tools`（保护清单，如 memory）/ `clear_tool_inputs`（**连调用参数一起清**） |
| **Clear thinking**（`clear_thinking_20251015`） | 清除历史 thinking 块，保留结论 | 服务端 | `keep`（all / 最近 N 轮） |
| **Compaction**（`compact_20260112`） | 跨阈值时**整体摘要替换**历史 | 服务端、自动 | `trigger`（默认 150k，floor 50k）/ `instructions`（自定义摘要要点）/ `pauseAfterCompaction` |

**官方对比口径**：editing 是「外科」（丢掉指定陈旧结果、其余完好），compaction 是「重写」（整段历史换成摘要）。**编辑保留最近精确细节，压缩保留全局梗概**。官方内部 agentic-search 评测：**memory + editing 比基线提升 39%**（editing 单独 29%）。
**应用判据（官方给的诚实测试）**：若任务在少数轮次内结束、输入从未超过 50~100k，则触发条件根本不响，**短 agent 不必启用**；若在用缓存，需把 `clear_at_least` 调到「每次清除释放量明显大于缓存重建成本」——**与我们 2.2 节算出的「回本步数」是同一件事**。

### 4.3 Claude Code：三级渐进式压缩 + 上下文可见性

| 级别 | 机制 | 成本 | 缓存影响 |
|---|---|---|---|
| **MicroCompact** | ① *Cached 模式*：经 `cache_edits` **在服务端缓存的 prompt 前缀中删除旧工具结果**，不重发完整 prompt → 近零 miss；② *Time-Based 模式*：距上条助手消息 >60 分钟（缓存 TTL 约 5 分钟~1 小时已凉）→ 本地把旧工具结果替换为 `[Old tool result content cleared]` | 近零 | ①零 miss；②缓存已凉，无影响 |
| **SessionMemoryCompact** | 平时每轮 fork 子 agent 抽取关键信息写入 session memory 文件；需要压缩时**直接复用**该文件替代旧消息 | 后台少量 API | — |
| **FullCompact** | API 生成**九段式结构化摘要**（Primary Request / Key Concepts / Files & Code / Errors & Fixes / Problem Solving / **All User Messages** / Pending Tasks / Current Work / Next Step） | 每次一次完整 API | 支持 **`from` 模式**（保前半段、压后半段 → **缓存前缀不变，照常命中**）与 `up_to` 模式（压前头、保最新 → 缓存失效）——**压缩方向本身就是成本决策** |

**三条被专门保护的完整性不变量**（与本次审计直接相关）：
1. **切割点必须保持 `tool_use` / `tool_result` 配对** ←→ 我们的 `_pair_units`（400-fix A）✓ 方向一致；
2. **thinking block 必须完整**（不得从中间切断）←→ 我们的 `reasoning_content` 回传（400-fix B）✓ 方向一致；
3. **可清除工具清单**：Read / Bash / Grep / Glob / WebSearch / WebFetch / Edit / Write **可清**；Agent 结果、用户消息、系统消息、助手分析文本 **不可清**——**信息优先级的显式分级**。

**可观测性**：Claude Code 提供 **`/context` 命令**，按类别列出 token 占用（system prompt / tools / MCP servers / memory files / messages），并提示「未使用的 MCP server 仍占 token，禁用可省空间」。**这正是我们缺失的「记账面」**。

**阈值**：默认约 95% 触发；官方建议在 **70% 主动管理**，80% 收尾；阈值可用 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` 覆盖；压缩前有 **PreCompact hook** 供外部保存关键状态。

### 4.4 Manus《Context Engineering for AI Agents》

- **KV-cache 命中率是生产 agent 最重要的单一指标**（Claude Sonnet 缓存 ¥0.30/M vs 未缓存 ¥3/M，差 10 倍）——与我们的 5 倍价差结论同源；
- 三条提高命中的纪律：**前缀稳定**（勿在系统提示开头放秒级时间戳）、**只追加不改写**、**确定性序列化**（JSON 键序不稳定会静默破坏缓存）；
- **掩蔽而非移除**工具：动态增删工具会失效其后全部缓存，也让模型困惑；改用 logits 掩蔽 / 响应预填充约束动作空间，并给工具统一前缀（`browser_` / `shell_`）；
- **文件系统作为终极上下文**：压缩必须**可恢复**（留 URL、留路径，不留全文）；
- **复述（recitation）**：用 todo.md 把目标反复写到上下文末尾，对抗 lost-in-the-middle；
- **保留错误**：失败的调用与堆栈留在上下文里，模型才能更新内在信念（错误恢复是真正的 agent 行为指标）；
- **警惕 few-shot 固着**：上下文过于单一时模型会模仿既有模式 → 引入受控多样性。

### 4.5 MemGPT / Letta：OS 虚拟内存类比

- 主上下文（RAM，每轮必见）/ 召回存储（SSD，可搜索的近期历史）/ 归档存储（磁盘，向量化长期知识）；
- **memory block** 是可编辑的持久字符串；模型用工具自己管内存（`core_memory_append` / `core_memory_replace` / `archival_memory_insert` / `archival_memory_search` / `conversation_search`）；
- 「memory-as-interrupt」：记忆操作像 `read()` 系统调用一样插入循环；
- 常见失败模式：**memory rot**（写多于读，检索被陈旧事实淹没）、**memory poisoning**（外部内容入记忆后被再次摄取）、**citation loss**（记不住是哪一轮说的）——对应解法：定期整合（sleep-time agent）、冲突检测、**每条记忆带来源引用（session/turn id）**。

### 4.6 Harness 层实践（Claude Code / Codex / Junie）

- **分层装配**：系统提示 → 工具定义 → 记忆文件 → 对话历史 → 当前用户消息；
- **Codex 的严格优先级栈**：服务器控制 system > 工具定义 > 开发者指令 > 用户指令（级联 `AGENTS.md`，**32 KiB 上限**） > 对话历史——**每层都有硬上限**；
- **Claude Code 三层记忆**：轻量级索引（每条约 150 字符，**始终加载**）→ 按需拉取的详细主题文件 → 仅通过搜索访问的原始记录；**MEMORY.md 双限 200 行 / 25KB**；
- **JetBrains Junie 观察屏蔽**：隐藏旧工具输出，但**保留工具调用的可见性**；
- **子 agent 委托**：每个子 agent 只回传 1,000~2,000 token 的压缩摘要；
- **别把确定性逻辑放进上下文**：能用 hooks / 代码规则 / 工具约束表达的，就不该让模型反复读取。

### 4.7 提炼：生产级上下文管理器的「七项能力」标尺

| 能力 | 含义 | 代表实现 |
|---|---|---|
| **① 记账** | 全景登记：窗口内**每一项**（含 tools / schema / 附件）都有归属与额度 | Claude Code `/context`；Codex 分层上限 |
| **② 分层** | 按稳定性/使用频率分级：常驻 / 按需 / 运行时 / 记忆 / 系统外 | 分层装配范式；Claude Code 三层记忆 |
| **③ 选择** | 按需取用而非全量灌输（JIT 检索、动态工具、描述符常驻） | Anthropic Select 策略；Claude Code grep/glob |
| **④ 压缩** | 阈值触发的摘要/折叠，**保留决策与未决项** | compaction；九段式摘要 |
| **⑤ 清除** | 外科式删陈旧结果但**保留调用占位**，且**清除要值得** | `clear_tool_uses` + `clear_at_least` |
| **⑥ 隔离** | 子 agent / 沙箱 / 状态对象隔离 | 子 agent 摘要回传 |
| **⑦ 可观测与不变量** | 分类视图 + **配对完整 / 思考链完整 / 前缀稳定** 三类校验 | `/context`；切割点配对守卫 |

## 五、差距矩阵（治理面 × 业界标尺）

| 能力 | 业界做法 | 本项目现状 | 差距 |
|---|---|---|---|
| ① 记账 | 全项登记 + 分类视图 | 只登记「块」；tools/schema 以 reserve 占位不登记（Z1/Z2）；无分类视图 | **大** |
| ② 分层 | 常驻/按需/运行时/记忆/系统外五层，各有硬上限 | 只有 rigid / flex 二分；rigid 无 per-block 上限 | **大** |
| ③ 选择 | JIT 检索、动态工具、描述符常驻 | `lazy_tools` 已实现但默认关；无 JIT 检索；工作记忆无披露 | **中**（机制在、未启用） |
| ④ 压缩 | 阈值 + 结构化摘要 + 保留决策 | 有折叠（clip_head_tail / act 折叠）；**阈值锚在 1M 恒不触发**；无 LLM 摘要类压缩用于链 | **中** |
| ⑤ 清除 | 服务端外科清除 + `clear_at_least` 保护缓存 | 无「清除」概念；丢弃式裁剪是**客户端重写**（必然破坏前缀） | **大**（且方向不利） |
| ⑥ 隔离 | 子 agent / 沙箱 | 无（单循环） | 中（非必需） |
| ⑦ 可观测与不变量 | `/context` + 配对/思考/前缀三类校验 | 有 `CONTEXT_GOVERNED` 遥测（块级）；**配对与思考完整性靠补丁而非不变量**；无前缀稳定性校验 | **中** |

**可裁池统计**：13 个块中仅 3 个 flex——治理器的「管理面积」实际只有 **23%**。

## 六、治理面补全建议（G1~G5，与 v1.2 方案 C1~C6 的对应）

> 本节回答主人所问的「完善上下文治理面」——按**四个覆盖面维度**组织，与 `Token成本优化实施方案-2026-09-29.md` v1.2 的 C1~C6 一一对应。

### G1 段覆盖：把 11 段补齐（对应 C6 + 五期）
| 缺口 | 补法 |
|---|---|
| 工具定义（双轨割裂） | react 的 native tools **登记为块**（或 C2 附件），并支持 `lazy_tools` 目录卡投影；chat 侧 `tools` 文本块与 native 数组统一口径 |
| 输出格式 | schema 登记为块（`kind=text`，rigid + cap），不再只 reserve |
| 长期记忆（react 内） | react prior 增加 `memory` 段（limit=3、cap 1200 token），与 chat 侧同源 |
| 工作记忆 | 提交**目录块**（进度一行 + 检查点索引，cap 300），配 `read_checkpoint` 读回工具（渐进披露两半） |
| 附件/多模态 | 预留块位（`kind=attachment`），先登记、后可裁 |
| 用户当前输入（chat） | chat 路径本轮 user 也过 assemble（与 react 对齐，保证记账一致） |

### G2 端点覆盖：整轮全景账本（对应 C2 的扩展）
- 一轮对话的四个端点共享一个 `RoundLedger`（run/轮次级）：记录各端点的块占用、reserve 占用、真实估算；
- 治理器新增只读查询 `ledger()`；`CONTEXT_GOVERNED` 遥测附**轮次级汇总**——从此可回答「这一轮钱花在哪个端点」。

### G3 对象覆盖：消灭 reserve 黑洞（对应 C2）
- `assemble(attachments=[...])`：tools schema / response_format / 其它附加项**登记为附件**（计量 + 可声明 cap + 可清除）;
- 报表新增 `unaccounted_tokens`（真实估算 − 已登记），超 5% 遥测标红。

### G4 生命周期覆盖：水位 + 压缩契约 + 清除优先（对应 C1 / C3 / C4）
- **C1 块策略契约**：`cap_tokens` / `compact_at` / `compact_floor_ratio` / `on_compact`——给治理器「压缩」动词；
- **C3 水位**：双窗口（1M 能力上限 / 96k 经济兜底）+ `assess()` 无状态水位 + **回本判定 + 冷却期**（与官方 `clear_at_least` 同源）；
- **C4 刚性 cap**：system 8k / prior 8k / prompt 2k，杜绝刚性膨胀；
- **清除优先于压缩**：优先用「工具结果清除（保留调用占位）」而非「历史改写」——前者对前缀的扰动面小得多；若供应商将来支持服务端清除类接口，应优先接入（保持客户端历史不变，零重发）。

### G5 可观测与不变量（对应 C5 + 新增）
- **C5 完整性契约**：`required_blocks` + `missing_blocks` 告警——把 Z1~Z8 这类盲点变成红灯；
- **分类视图**：仿 `/context`，在设置页或遥测中输出「各段 token 占用 + 可裁性 + 命中率 + 压缩次数」；
- **三条不变量升级为断言**（本次审计的最重要收获）：
  1. **配对完整性**：`tool_calls` 与 `tool_results` 同进同退（已在 `_pair_units`，建议加断言 + 单测覆盖所有切点）；
  2. **思考链完整性**：thinking 块不得从中间切断（`reasoning_content` 已随链，建议加"截断不得切开 thinking 块"的断言）；
  3. **前缀稳定性**：run 内 prior/链序列化字节一致（零期目标，建议加对拍测试）。
