## 1. 结论摘要

1. **"复杂任务不收敛"不是参数问题，是四类瓶颈叠加**：步数配额、串行 act、上下文折叠失忆、无计划状态。单纯把 `max_steps` 调大只会换个地方撞墙。
2. **业界（Claude Code / Codex）默认没有步数闸**，用「预算 + 自动压缩 + 用户中断」替代。本项目不能直接照搬，因为**有效窗口差 1~2 个数量级**（24K vs 200K~1M），且**生产里上下文压缩从未真正执行**（`compact_mode` 默认 `shadow`）。
3. **业界都没有独立的"意图识别模块"**——是否规划由模型自己决定（给模型一个工具，而不是加一个规则分类器）。**建议不做意图分类器**。
4. **本项目的规划缺口首先在系统提示词**：`REACT_SYSTEM` 通篇没有一句规划引导，模型"直接开做"是被提示词允许的。
5. **改动前必须先建度量基线**：触顶率、步数分布已可统计（`agent/react/exhausted` 事件**确实落库**），当前**没有取过基线**，改完无法证明改善。

## 2. 现状实证

### 2.1 「一步」的精确定义（先统一口径，否则讨论无效）

**一步 = 一次模型推理往返（`_reasoner.reason`），不是一次工具调用。**

| 环节 | 代码坐标 | 说明 |
|---|---|---|
| 步数递增 | `react/loop.py:719` `steps += 1` | 位于窗口装配之后、模型调用之前 |
| 模型推理 | `react/loop.py:761` | 一次 LLM 往返 |
| 工具执行 | `react/loop.py:824-825` | 本轮**全部** `tool_calls` 在同一步内执行完 |
| 观察入链 | `react/loop.py:842-847` | 多条结果**合成一条** observe 消息 |
| 每步写盘 | `wm.update` / `checkpoint` / `snapshot_save` | 每步一次 Redis 写，是隐性成本 |

由此得到三个容易搞错的推论：

- **`max_steps=8` 是 8 次模型往返，不是 8 次工具调用。** 工具调用次数理论无上限，只受 `deadline_s` 约束。
- **"没调工具"也算一步**：模型首轮直接回答 ⇒ `steps=1`、自然收敛、`exhausted=False`（`loop.py:782`）。纯聊天轮就是 1 步。
- **真实瓶颈不是"8 次不够"，而是"模型通常一轮只吐 1 个调用"**，于是 8 步只换来 8 次工具调用；再叠加串行 act（见 2.3），每步还要付完整 IO 时延，**deadline 往往比步数先撞线**。

### 2.2 闸的位置与触顶路径

| 闸 | 默认值 | 代码坐标 |
|---|---|---|
| `max_steps` | **8** | `react/__init__.py:65`（配置节 `agent.react`） |
| `deadline_s` | **120.0** | `react/__init__.py:66` |
| `max_rejects` | **3**（同一工具被拒次数） | `react/__init__.py:68`；判定 `loop.py:839` |
| 预算闸 | 每步走 `ctx.llm` 天然生效；预警提示 `BUDGET_TIGHT_SYSTEM` | `loop.py:751-757` |
| 上下文 | `max_context_tokens=24000`、`reserve_output_tokens=4000` | `profiles.py:58` |

循环条件 `while steps < cfg.max_steps`（`loop.py:715`）。**`break` 各有原因，不只是"步数用完"**：

| `break` 点 | 原因 |
|---|---|
| `loop.py:718` / `764` | 超时（deadline） |
| `loop.py:762` | 模型调用被 guard/预算拒（`CapabilityNotImplemented`） |
| `loop.py:769` | 推理异常（`hard=True`） |
| `loop.py:839` | 同一工具被拒超过 `max_rejects` |

只有循环条件自然耗尽才走 `while...else`（`loop.py:878`）⇒ 由 `finalize_on_exceed`（默认 `True`，`loop.py:86`）再答一次（`loop.py:889`）。**触顶行为是诚实的**（如实说明已完成/还缺/为何停），但语义上仍是半截答案。

### 2.3 四类收敛瓶颈

**瓶颈一：配额过紧。** `max_steps=8` / `deadline_s=120`；子 Agent 更紧（`SUBAGENT_MAX_STEPS=6` / `SUBAGENT_DEADLINE_S=60`）。

**瓶颈二：串行 act（最隐蔽）。**
```python
# react/components.py:151
return [await self._one(ctx, c, timeout_s) for c in calls]
```
模型一轮输出 N 个独立调用 ⇒ **省了步数，没省时延**。这是"让模型一次吐多个调用"这一省步数手段失效的直接原因。

**瓶颈三：上下文折叠导致失忆。** `react_keep_recent=6`（`loop.py:90`）+ `_prepare_chain` 的老观察首尾折叠 ⇒ 早期结论被折 ⇒ 重复试错吃步数。

**瓶颈四：没有计划状态。** 全仓**没有** TodoWrite / 待办类工具 ⇒ 任务分解只活在 `chain` 里，一折叠即失忆；`approval` 插件的 plan 是"提交计划给人审批"，不是任务分解。

### 2.4 关键修正一：`risk` 元数据缺失，按 risk 并发不能先做

先前我建议「Actor 按 risk 并发（只读并发、写串行）」，对齐业界 `readOnlyHint` 语义。**勘察后发现前提条件不成立**：

- 全仓 `risk="read"` 显式标注**只有 3 处**（`approval/__init__.py:138`、`:290`，`subagent/__init__.py:100`），其余工具注册时 `risk` 取默认值空串（`guard.py:130` 签名 `risk: str = ""`）。
- 全仓**不存在** `readOnlyHint` / `read_only` 类字段（零匹配）。

⇒ **要先补工具元数据，否则"按 risk 分级"无从分级。** 这是 P1 的前置项，不是 P1 本身。

### 2.5 关键修正二：`compact_mode` 默认 `shadow`，压缩从未真正执行

`_DEFAULT_COMPACT_MODE = "shadow"`（`context/governor.py:81`）。按 `protocols.py:38` 的定义，shadow 下**照常计算决策但不执行，只写遥测**。也就是说生产环境里长任务完全靠 `react_keep_recent=6` 的硬折叠扛着——这正是"失忆式重复"的根因，也是**不能直接把步数放宽到 50 的硬理由**：窗口先撑不住。

### 2.6 触顶事件确实落库（度量抓手成立）

| 事件 | 方式 | 坐标 | payload 关键字段 |
|---|---|---|---|
| `agent/react/exhausted` | **durable（落 `agent_events`）** | `loop.py:555`（异常/取消）、`loop.py:883`（正常触顶） | `steps`、`reason`；异常支另有 `cancelled` / `abandoned` |
| `agent/react/final` | durable | `loop.py:783` | `steps`、`tokens_in/out` |
| `agent/react/step` | durable | `loop.py:848` | `step`、`budget_used` |
| `agent/react/step/start` / `end` | **emit（live，不落库）** | `loop.py:720` / `852` | — |

注意 `_record()`（`loop.py:1554`）**只写容器级内存字典** `ctx.state[REACT_LAST]`，不落库——`/api/plugins` 看到的状态是它，不能当历史统计用。

`reason` 可区分触顶原因：正常步数触顶写作 `已达步数上限 max_steps=N`；超时、推理失败、连拒各有其文案。

## 3. 业界对照与"意图识别"的结论

### 3.1 Claude Code（官方口径为准）

| 维度 | 机制 |
|---|---|
| 步数 | `--max-turns` 官方原文 **"No limit by default"**；Agent SDK `max_turns` 默认同样无限制。第三方博客流传的"默认 50 turns"与官方文档冲突，**以官方为准** |
| 成本 | `--max-budget-usd` / `maxBudgetUsd`；子 Agent 消耗计入总额，超限后新子 Agent 直接失败 |
| 上下文 | auto-compact：有效窗口 ~93% 触发，三级递进（清旧工具结果 → 会话记忆压缩 → 摘要压缩），**连续失败 3 次熔断** |
| 时间 | 无墙钟上限，靠用量窗口（5 小时滚动）间接约束 |
| 用户 | 随时中断、rewind 回退、continue / resume |
| 并行 | **只读工具并发，写工具串行**（`readOnlyHint` 标注） |
| 规划 | `TodoWrite` 工具（todos 数组：`id/content/status/priority`，整体覆盖式更新，UI 可见）+ plan 流水线（Explore 子代理并行搜索 → 设计方案 → 写计划文件 → `ExitPlanMode` 问人批准） |

### 3.2 Codex

`/plan` → **先提澄清问题（≤4 轮）** → 产出结构化计划（步骤 / 涉及文件 / **验收标准**）→ 人批准或编辑。长任务四文件范式：`spec.md`（目标 + 非目标 + "done when"）、`Plan.md`（里程碑 + 验收 + stop-and-fix 规则）、`Implement.md`、`Documentation.md`。另有 `plan_mode_reasoning_effort`：**规划阶段单独用更高推理强度，执行阶段用便宜档**。

### 3.3 反直觉结论：不要做"意图识别模块"

Claude Code 与 Codex **都没有独立的意图分类器**。是否规划由**模型自己决定**——Claude Code 的做法是给模型一个 `EnterPlanMode` 工具，模型觉得需要就自己调；Codex 靠用户 `/plan` 或提示词规则。

⇒ **建议：不做意图分类器**，那会引入一层僵硬规则（"命中关键词 ⇒ 强制规划"），既误判又不随模型能力演进。正确姿势是**"工具 + 提示词引导"**：给模型能力与纪律，让它自己判断。

### 3.4 本项目的实测缺口

| 项 | 现状 | 缺口等级 |
|---|---|---|
| `REACT_SYSTEM`（`prompt.py:21-30`） | 只有 ReAct 纪律（"够不够回答？够就答，不够就调工具"），**零规划引导** | **高** |
| 待办 / TodoWrite 类工具 | 全仓无 | **高** |
| 模型主动进入 plan 的能力 | 无。plan 模式**只能由人**经 `/api/approval/mode` 设置 | 中高 |
| `approval.submit_plan` | 已有（提交计划问人），但仅 plan 模式可见 | 已有，可复用 |
| 澄清提问 | 无 | 中 |
| 计划持久化 | 无 | 中（长任务才需要） |
| 子 Agent 委派 | **已就位**（`agent.delegate`，含并行 `tasks`、异步 `wait=false`、角色文件） | 已有，是本方案的现成杠杆 |

## 5. 度量：改动前必须先把基线取出来

`agent/react/exhausted` 与 `agent/react/final` **都落 `agent_events`**，故触顶率无需新埋点即可统计：

```sql
-- 触顶率与原因分布（近 N 天）
SELECT
  CASE WHEN event = 'agent/react/exhausted' THEN 'exhausted'
       WHEN event = 'agent/react/final'     THEN 'converged' END AS kind,
  COUNT(*) AS n
FROM agent_events
WHERE event IN ('agent/react/exhausted','agent/react/final')
GROUP BY kind;

-- 触顶原因细分（区分「步数不够」与「超时/异常/连拒」）
SELECT
  CASE WHEN json_extract(payload,'$.reason') LIKE '已达步数上限%' THEN 'step_limit'
       WHEN json_extract(payload,'$.reason') LIKE '%推理失败%'     THEN 'infer_error'
       WHEN json_extract(payload,'$.reason') LIKE '%模型调用被拒%' THEN 'guard_budget'
       WHEN json_extract(payload,'$.cancelled') = 1                THEN 'cancelled'
       ELSE 'timeout_or_other' END AS cause,
  COUNT(*) AS n
FROM agent_events WHERE event = 'agent/react/exhausted'
GROUP BY cause;
```

**必须记录的四个基线数字**：① 触顶率；② 平均/中位步数；③ 触顶原因分布（步数 vs 超时 vs 其它——这条决定该做 P1-3 还是 P1-4）；④ 委派触发率。

⚠ `agent/react/step/start` 与 `/end` 是 `emit`，**不落库**，只能看实时流；历史统计请用 `agent/react/step`。`_record()` 只写内存 `REACT_LAST`，不可当历史用。

## 7. 风险与明确不做

| 项 | 说明 |
|---|---|
| **不做意图分类器** | 业界（Claude Code / Codex）均无独立意图识别模块；规则层僵硬且误判，应走"工具 + 提示词" |
| **不盲目抄 50 turns** | 有效窗口 24K vs 业界 200K~1M，差 1~2 个数量级；且 compact 当前是 shadow ⇒ 松步数必先解决窗口 |
| **并发化的副作用** | 有写副作用的调用不可无脑并发；`agent.delegate` 自身带预算/句柄护栏（24/run、重派 ≤3、pending ≤8），并发下仍需观察真实 token 成本（护栏是**上界不是期望值**） |
| **自动续接的死循环风险** | 必须配总步数账本，否则把"触顶"改造成"死循环" |
| **未经真模型验证** | 本方案中的所有子 Agent 相关结论，其测试（77 例 + 36 处破坏实验）**全部跑在 `agent/fixtures/llm.py` 离线 fixture 下**；真模型下"模型是否主动委派""子 6 步能否收敛"**尚未验证过一次**。P0-4 就是为此设的 |
