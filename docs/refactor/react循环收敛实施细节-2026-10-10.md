### 2.4 架构决策：规划纪律暂不抽成独立插件（2026-10-10）

- **用户判定**：规划属"通用部分"，认同其应独立于部署身份叙事。
- **但本仓接线决定"现在抽 = 搬运式重构"**：`system_memory` 是**单 `SYSTEM_MEMORY` 服务键 + 自目录聚合**（`loader.py:22-38` 只 glob 自己目录、`__init__.py:39` 一次性 `ctx.provide`）；消费点 `build_system(catalog, system_memory)`（`prompt.py:120`）为单参数，`loop.py:606` / `chat.py:653,740` 三处写死 `ctx.get(Services.SYSTEM_MEMORY) or ""`。抽插件不能让 planning 也 `provide(SYSTEM_MEMORY)`（同键冲突/覆盖），必须新增 `PLANNING_PROMPT` 服务键 + 改 4 处消费点 + 新建插件目录与启用登记——为"还是纯文本"多一层插件 machinery。
- **结论**：维持 `system_memory/02-planning.md` 片段不动；**推迟到主方案 P2 阶段**再抽。届时规划会升级为**真实机制**（待办工具 + plan 持久化 + `EnterPlan` 工具 + planner 角色，见主方案 §P2-2/P2-3），纯 md 文件承载不了、必然要走 `provide` 服务 + `ctx.tasks.register` 工具，插件化顺理成章。

### 3.1 设计意图

**(e) 新增方法（放 `ReactLoop` 类内，与 `_act_with_budget` 同级）：**

```python
@staticmethod
def _arg_fp(args) -> str:
    """工具调用参数的稳定指纹（无序、可 JSON 序列化）。"""
    try:
        return json.dumps(args, sort_keys=True, ensure_ascii=False)
    except TypeError:
        return repr(args)

@staticmethod
def _detect_no_progress(call_sigs: list[tuple[str, str]],
                       observed: list[dict], cfg: "ReactConfig") -> str | None:
    """同 (工具, 参数) 在窗口内反复出现 ⇒ 视为无进展。
    泛化 ``run`` 内连拒护栏（``rejected[r.name] > max_rejects``）：那只对「被拒」
    触发，本方法对「反复用同一参数调用同一工具」（含被放行但原地打转）也触发。
    命中返回原因串（走既有 ``stop_reason → break → REACT_EXHAUSTED`` 诚实收尾）；
    返回 ``None`` 表示正常。"""
    if len(call_sigs) < cfg.no_progress_repeat:      # 实施修正：原稿用 steps<window，
        return None                                  #   会延后到窗口满才判，已收紧
    recent = call_sigs[-cfg.no_progress_window:]
    counts: dict[tuple[str, str], int] = {}
    for sig in recent:
        counts[sig] = counts.get(sig, 0) + 1
    for sig, n in counts.items():
        if n >= cfg.no_progress_repeat:
            return (f"无进展检测触发：最近 {cfg.no_progress_window} 步内重复调用 "
                    f"{sig[0]!r}（同参数）{n} 次")
    # 启发式2：最近 N 条观察结果文本完全相同（反复读回同一结果，未产生新信息）
    if len(observed) >= cfg.no_progress_repeat:
        tail = observed[-cfg.no_progress_repeat:]
        hashes = {hash(str(o.get("content", ""))) for o in tail}
        if len(hashes) == 1:
            return (f"无进展检测触发：最近 {cfg.no_progress_repeat} 步观察结果"
                    f"高度重复（未产生新信息）")
    return None
```

> **实施修正**：① 签名去掉未用的 `steps`；② 早退判定由 `steps < no_progress_window` 改为 `len(call_sigs) < no_progress_repeat`——前者会让"第 3 步即同参重复 3 次"也要等到窗口满（5 步）才判，收紧后第 3 步即触发（更早省 token）；③ 启发式2 字段由 `result`（不存在）改为真实字段 `content`（经 `ToolResult.as_dict` 核实）。

### 3.4 防误伤

- **只对"同参数"严格重复触发**（`sig = (name, 参数指纹)`）。合法的"读→改→再读验证"参数不同，指纹不同，**不误伤**。
- 阈值保守：窗口 5 步、重复 3 次才触发；可用配置调松/调紧。
- 检测器本身**不新增收尾分支**，命中后复用现有 `REACT_EXHAUSTED` + `finalize` 诚实收尾（主方案证明该路径已能把"做了什么/卡在哪"交还用户）。

- **用例 B（检测器关闭，断言退化到旧行为）**：同一 fixture 脚本，仅把 `cfg.no_progress_repeat=999`，断言 `result.steps == cfg.max_steps` 且 `reason` 以 `"已达步数上限"` 开头。


- **用例 C（无误伤）**：fixture "两步链路"（参数不同、且正常收敛）断言 `exhausted=False`、`reason is None`、`steps < 8`。

**破坏实验判据（检测器型测试纪律）**：A 与 B 共用同一刺激、唯一变量是阈值——A 提前终止、B 烧满。这正是「删掉检测器 ⇒ A 的提前终止断言失败」的可执行证明（B 即"检测器关闭"的等价态）。初版曾尝试 monkeypatch `_detect_no_progress` 直接置空，但本机 sqlite 连接时序偶发 `_conn=None` 而弃用，改由阈值开关隔离，更稳且同样严谨。

### 3.6 回滚

- 纯新增方法 + 一个 `if` 分支；把 `no_progress_repeat` 设 999 即等效关闭，无需回滚代码。
- 拟议代码不改动 `REACT_SYSTEM`、不动触顶收尾、不碰 `short_term`/`context` 等其他插件。
