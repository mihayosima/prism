## 0. 背景与目标

主 Agent 当前在 `ReactLoop`（`agent/plugins/react/loop.py`）里单实例跑「Think→Act+Observe→收敛」。随着任务复杂度上升，存在两类痛点（业界与本项目共识）：

1. **上下文污染/腐烂**：工具重输出的中间结果（日志、检索、探索笔记）灌进父链，挤压有效上下文。
2. **串行延迟**：相互独立的子任务被迫排队。

**目标**：新增一个 `subagent` 插件，注册一个 `agent.delegate` 工具；主 Agent 在循环内调用它即 spawn 一个**受限子循环**（复用 `ReactLoop`），携带裁剪后的工具集与独立 `run_id`，跑完返回**结构化结果 `{status, answer, evidence, request_id}`**（`answer`=子的 `final_answer`、`evidence`=蒸馏摘要、`request_id`=子独立请求 ID）。所有 LLM/工具调用仍走 `ctx.llm` / `ctx.tasks`，**零特权、护栏全继承**。

| **通用模式（2025）** | 三属性判断是否值得：独立子任务 + 上下文重 + 适合专家；三种委派：① 并行研究 ② 专家角色 ③ 上下文防火墙；反模式：琐碎工作不值得、子需父全量上下文（双向付费+失隔离）、无界并行（≤5 合适）；架构：Hierarchical / Swarm / Supervisor；**上下文隔离是核心设计原则**（instruction passing 默认，file-system memory 升级，full delegation 谨慎） | 价值判定三属性；输出 schema 约束（只返回蒸馏摘要）；并行上限；隔离分级 |

**共识结论**：
- 子 Agent 必须是**受限、独立上下文、返回摘要**的 worker；
- 角色配置化（name/工具白名单/model/sandbox/超时）；
- 三重护栏：嵌套深度、并发上限、超时；
- 权限最小继承；
- 避免无界并行与「子需要父全量上下文」。

### 2.2 关键代码点（实施时务必对照）

- `ReactLoop._run_impl`（`loop.py:457`）：`tools = visible_tools(ctx)`（**总是全量**，需新增可选 `tools_override` 接缝）；`identity` **必须显式传入**（注释明确：ctx.state 被并发请求共享，H5/H6）。
- `visible_tools`（`loop.py:223`）：返回 `ctx.tasks.catalog()` 经权限模式裁剪 + 描述瘦身。
- `ReactResult.as_evidence()`（`loop.py:193-199`）：返回蒸馏摘要（steps/tools/observations/summary），**注意它不含 `self.text`（最终答复）**。子 Agent 必须把 `child_run.text`（finalizer 产出）作为 `answer` 回传，`as_evidence()` 仅作 `evidence` 佐证 —— 直接 `return as_evidence()` 会让父链拿不到任务答案（审查意见 #1）。
- 四组件（`reasoner/actor/observer/finalizer`）在 `react/__init__.py:62` 的 `apply` 内构造；主循环通过 `ctx.get("react.<x>") or Default<X>()` 注入（`:82-85`，故主循环**已 consult 此 key**，可作为未来 per-role 组件的既有读取点）。子 Agent 工厂 `REACT_FACTORY` 闭包捕获的是 `apply` 内本地构造那套组件（**未做 per-role 查找**）。`ReactLoop` 是纯类，subagent 单测可直接用 mock 组件构造 `ReactLoop(...)`（审查意见 #14a 严重度降级）。

## 3. 推荐方案

### 3.1 总体架构

```
主 ReactLoop（plugins.react）
   └─ LLM 返回 tool_call: agent.delegate(task, role?, tools?)
        └─ actor 经 ctx.tasks.invoke("agent.delegate")  ← 全链路护栏照生效
             └─ 子 Agent 工具 handler:
                  • 取父 identity → 构造子 identity（同 tenant/user/session，新 run_id = uuid4().hex）
                  • 经 Services.REACT_FACTORY 构造受限 ReactLoop（tools_override = 角色白名单 ∩ visible_tools(ctx)，max_steps/deadline 缩短，depth+1）
                  • asyncio.create_task / 受 TaskTimeout 约束运行 子Loop.run(ctx, prompt=子prompt, identity=子)
                  • 返回结构化 {status, answer=child.text, evidence=child.as_evidence(), request_id=child_rid}
```

**零特权原则天然满足**：子 Loop 内 LLM 走 `ctx.llm`、工具走 `ctx.tasks.invoke`，guard/budget/owner/审计/S4 全部照常生效，不新建任何特权通道（对齐 `react/__init__.py` 设计要点）。

### 3.1a 子 Agent 的 prompt 形态（instruction passing，审查意见 #7）

上下文隔离的核心接口，单列明确默认模板：

```
子 prompt = task
         + （可选）父维护的 "shared_brief"（非全量历史：关键事实 / 已确认决策 / 用户偏好）
         + （可选）期望输出 schema（由 role 定义或 tool 参数给出 expect_schema）
```

- **父全量 history 永不下传**（上下文防火墙，通用模式③）。
- `prior` 字段在 MVP 默认**空**（原方案 `prior=裁剪摘要?` 未定，现明确默认不下传摘要，避免双向付费与失隔离）。
- 角色可声明 `expect_schema`，让子的 `answer` 结构可控，便于父解析。
- **evidence 透传机制（评审 R1，防止「父中转」污染父上下文）**：父调 `delegate(A)` 拿到的 `tool_result` 只放 `answer`(短结论) + evidence 引用，**不放完整大证据**；完整 evidence 由 subagent 插件按 `run_id` 暂存。`父` 调 `delegate(B, shared_brief=<A 的证据引用>)` 时，handler 从暂存取出 A 的 evidence，**直接作为 B 的 `shared_brief` 入参塞进 B 的 prompt**——进的是 B 的上下文、**不进父的**。这样父上下文始终只持「结论」，证据在子之间经 handler 直达，上下文防火墙不被「父中转」破坏（典型场景：A 产出 2 万字检索证据，父不必消化它即可转发给 B）。

### 3.2 新增接缝（最小侵入、符合本仓库「接缝」哲学）

1. **`core/services_catalog.py`** 新增 `REACT_FACTORY = "react.factory"`（可选 provide；缺省 None ⇒ `agent.delegate` 优雅降级为不可用并提示）。
2. **`plugins/react/__init__.py`** 的 `apply` 内，除 provide `Services.REACT`，再 provide `Services.REACT_FACTORY`。**工厂契约（引擎无关，R6/Q5）**：
   ```python
   # REACT_FACTORY 契约（公开、稳定）：
   #   (tools_override, cfg_overrides, components_override, governance_override, depth)
   #     -> Loop；Loop.run(ctx, prompt, identity) -> Result
   # 不承诺具体引擎；主循环换 LangGraph / 子引擎换 LangGraph，**装配调用点只在 _make_loop 一行**，
   # 但行为等价的引擎实现属实质性重写（四组件→node、guard/ContextVar 挂载点逐一对齐），非一句之事。
   def _make_loop(tools_override=None, cfg_overrides=None,
                 components_override=None, governance_override=None, depth=0):
       rcfg = merge_react_config(_REACT_DEFAULTS, cfg_overrides or {})  # 只覆盖给出的字段, 其余继承父
       comps = _resolve_components(components_override)                # None => 闭包捕获的四组件
       loop = ReactLoop(reasoner, actor, observer, finalizer, rcfg,
                        tools_override=tools_override, depth=depth,
                        governance_override=governance_override)        # 默认 None => 沿用 ctx.get(Services.CONTEXT)
       return loop
   ctx.provide(Services.REACT_FACTORY, _make_loop)
   ```
   - **`merge_react_config(base, overrides)`**：`ReactConfig` 实测共 **10 字段**（`loop.py:76-100`：`max_steps`/`deadline_s`/`history_keep`/`max_rejects`/`finalize_on_exceed`/`react_keep_recent`/`act_fold_tokens`/`lazy_tools`/`lazy_tools_max`/`alignment_enabled`，`@dataclass(slots=True)`）。合并 = 用 overrides 给出的任意字段覆盖 base，**未给出的字段一律继承父**。当前仅 role 用到 `max_steps`/`deadline_s`，但签名已容纳全部 10 字段——未来按 role 配上下文参数（`history_keep`/`react_keep_recent`/`act_fold_tokens`）**无需改签名/调用点**。
   - **`components_override` / `governance_override` 当前恒为 `None`**（沿用闭包默认组件、沿用 `ctx.get(Services.CONTEXT)` 共享治理），但参数已就位；未来按 role 换组件/独立治理时只改工厂内部 + 一个**向后兼容的** `ReactLoop` 可选 kwarg，**派遣契约/handler/工具 schema 一行不改**（见 §3.2a）。
3. **`ReactLoop.__init__` 新增向后兼容可选 kwarg**（当前 `def __init__(self, reasoner, actor, observer, finalizer, cfg)`，`loop.py:382`）：新增 `tools_override`、`depth`、`governance_override`（均默认 `None` = 现状）。`_run_impl` 内 `tools = intersect(visible_tools(ctx), tools_override)`（`tools_override=None` 时等价于 `visible_tools(ctx)`）⇒ **白名单只能收窄、不能放宽**（审查意见 #2 / 最新评审 R3）；`depth` 超 `max_depth` 拒绝（默认 1）；`governance_override` 非 None 时替代循环内 `ctx.get(Services.CONTEXT)` 的治理读取（当前 4 处：`loop.py:1002/1113/1144/1179`）。

### 3.2a 未来增强的预留接缝（零返工约束 —— 据 2026-10-09 范围裁定）

**范围裁定**：当前版本**不做**子 Agent 独立上下文治理（Q4）、**不做**组件全解耦（Q6）；但二者必须「以后能做且不返工」。**零返工的判据**：公开派遣契约 `REACT_FACTORY(...)` 已一次性预留全部未来旋钮；未来能力 = 填参数 + 工厂内合并/查找 + 一个向后兼容的 `ReactLoop` kwarg；**任何调用点、handler、工具 schema 不变**。

- **Q4（独立上下文治理）的预留点**：
  1. 工厂 `cfg_overrides` 已容纳 `ReactConfig` 全部 10 字段（含 `history_keep`/`react_keep_recent`/`act_fold_tokens` 等循环内裁剪参数）——按 role 配「子循环上下文窗口」只需在角色定义加 `config:` 块，`merge_react_config` 直接吸收，无需改签名。
  2. 工厂 `governance_override` 参数 + `ReactLoop` 待加的 `governance_override` 向后兼容 kwarg（默认 None = 沿用 `ctx.get(Services.CONTEXT)` 现状）。子与父**共用同一 `ctx`**，故治理现被共享；将来按 role 注入独立治理器 = 角色定义加 `context:` 块 + 工厂构造 `governance_override` 喂给 `ReactLoop`，派遣契约/handler/schema 一行不改。
  - 注：`plugins.context` 的折叠/水位策略（`clip_*`/`working_window_tokens`）是**会话级、跨所有 loop 共享**，本方案不改它；独立治理属「角色级覆盖」，是上述预留点的消费者，非新机制。
- **Q6（组件全解耦）的预留点**：
  1. 工厂 `components_override` 参数（`dict[str, Component] | None`）。当前 None ⇒ 用闭包捕获的四组件；将来按 role 换组件 = 工厂内按 role 查 `ctx.get("react.<x>")`（主循环已 consult 此 key，`react/__init__.py:82-85`，非新接缝）填入 `components_override`，`ReactLoop` 用覆盖项构造。
  2. 因 `REACT_FACTORY` 公开签名已含 `components_override`，**handler 调用 `REACT_FACTORY(...)` 的写法永不变**；变化只发生在工厂体内与角色定义，不波及派遣契约。
- **零返工判据小结**：公开契约五参数（`tools_override`/`cfg_overrides`/`components_override`/`governance_override`/`depth`）已一次性预留；未来 Q4/Q6 落地 = （a）角色定义增字段、（b）工厂内填参数 + 合并/查找、（c）`ReactLoop` 加一个默认 None 的 kwarg。调用点、handler、`agent.delegate` 工具 schema、任何上游代码零改动。

### 3.3 插件结构（一个业务 = 一个插件）

```
agent/plugins/subagent/
  __init__.py    # @plugin 类 SubAgent：apply 时注册 agent.delegate 工具，注入 REACT_FACTORY
  roles.py       # 角色定义加载（从 config `agent.react.subagents`；内置 default/explorer/worker）
  runner.py      # 受限 Loop 装配 + 运行 + 返回证据 + 超时/深度护栏
```

`agent.delegate` 工具注册（`sys/tasks.py::register`，owner=`plugins.subagent`，**risk=`read`** —— 否则在 plan/只读会话会被 `visible_tools` 直接隐藏，父根本看不到委派入口；委派本身的特权边界交给「子工具 ∩ visible_tools」裁剪，见 §3.2）：
- `schema`：`task`(str, required)、`role`(str, default="default")、`tools`(array, 可选白名单)。
  - **`tools` 参数语义写死为「交集」（最新评审 R3，安全收口）**：最终工具集 = `intersect(visible_tools(ctx), role.tools, param.tools)`。`role.tools` 是安全下界（如只读 explorer 只能给只读工具），`param.tools` 只能在其上**再收窄**、绝不可放宽——否则父能在 delegate 时把只读 explorer 放宽成可写，角色约束破产。
  - **已砍掉 `wait` 参数**（审查意见 #5）：MVP 仅同步委派；`wait=false` 的异步委派属阶段 3，且实现为「父持有 `asyncio.Task/Future` handle，完成时注入下一轮 react 的 `tool_result`」（R2：**非轮询 poll**，方案里无查询句柄机制）。
- **工具描述（tool description）写入适用/不适用场景引导**（审查意见 #9，最低成本引导主 Agent 判断是否委派）：
  > 适用：独立、上下文重、适合专家的子任务（如只读探索、专项研究、代码审查）。
  > 不适用：琐碎一步操作、子必须拥有父全量对话历史才能完成的任务、无界 fan-out。
- **返回契约（结构化，审查意见 #10）**：`{status, answer, evidence, request_id}`
  - `ok`：正常收敛，`answer=子 final_answer`；
  - `incomplete`：`max_steps` 耗尽未收敛，附 `partial=已得结论`；
  - `error`：`str(exc)` **绝不裸回**，回 `{code, request_id=child_rid, 人类可读摘要}`（对齐 H 系列 `run/chat.py:869-988`；child_rid 由 handler 在 spawn 时显式 mint，子 `durable` 事件写入，使其 `agent_events` 可独立关联；并 `durable(SUBAGENT_SPAWN {parent_run_id, child_run_id, role})` 关联父子）。
- `handler` 内：`REACT_FACTORY` 在 `apply` 阶段已确认可用才注册该工具（审查意见 #11）；若 react 插件未启用（opt-in），**不注册 `agent.delegate`**（避免污染工具列表误导 LLM），而非注册后永远抛 `CapabilityNotImplemented`。

### 3.4 子 Agent 角色定义（对齐 Codex TOML）

配置落 `agent.react.subagents`（与现有 `agent.react` 同节）：

```yaml
agent:
  react:
    subagents:
      - name: default        # 通用子 Agent，继承父全量工具
        description: 通用受限子 Agent
        tools: ["*"]
        max_steps: 6
        deadline_s: 90
      - name: explorer       # 只读探索（对齐 Codex explorer）
        description: 只读代码/文件探索，收集证据，不修改
        tools: [agent.read, agent.grep, agent.glob, web.search]   # 白名单
        max_steps: 8
        deadline_s: 120
      - name: worker         # 执行/写（对齐 Codex worker）；审查是其特化：返回 accept 或 reject(理由)，由父层决定是否重派（审查意见 #8）
        description: 执行类子 Agent（含代码审查特化）；可做写操作，但写工具仍过 guard
        tools: [agent.read, agent.grep, agent.write]
        max_steps: 8
        deadline_s: 120
```

白名单解析：`tools` 命中具体工具名 ⇒ 在 `ctx.tasks.catalog()` 里按名过滤；命中 domain（如 `web.*`）⇒ 复用 `_clip_with_fallback`；`"*"` ⇒ 不额外收窄（仍受 `visible_tools` 权限裁剪）。最终工具集 = `intersect(visible_tools(ctx), role.tools, param.tools)`（审查意见 #2 / 最新评审 R3：**三层任意一层都可收窄，但任何一层都不能放宽**——`role.tools` 是安全下界，`param.tools` 只能在其上再收窄）。

> ★ **实测发现并已修复：「安全下界」原本只是提示层软约束**（2026-10-09 实施期破坏实验）。
> `resolve_tools` 把白名单作用于**喂给模型的 tools 数组**（目录裁剪），执行路径 `_act_with_budget`
> → `tasks.invoke` **不做白名单校验**。用离线 fixture LLM 实测：子循环被明确告知
> `tools=["agent.ping"]`，仍成功执行了 `test.echo`（`evidence.tools` 含该工具、无拒绝观察）。
> ⇒ 结论：`sys.guard` 的 `task_allow`/`task_deny` 是**配置驱动的全局策略**，无法表达
> 「仅本子循环内生效」的动态白名单（那必须按 asyncio task 隔离），故不能替代。
> **修复**：`ReactLoop._split_whitelist_denied()` 在**执行前**按同一标识符语义（工具名或
> `owner` 域命中即放行）二次校验，越界 ⇒ 返回 `denied_by="whitelist"` 的拒绝观察（**不执行**），
> 让模型自纠。因口径与 `_apply_whitelist` 一致，不会出现「提示说不能用、实际却调得动」的裂缝。
> `tools_override` 为 None/含 `"*"` ⇒ 直接返回，**父循环与不委派主路径零行为变化**。
> 该拦截是「白名单=安全下界」这一措辞的兑现，缺此则角色约束形同自述。
> 检测器见 `test_delegate_narrows_child_tools_below_parent`（拦截摘除即红）、
> `test_delegate_allows_whitelisted_tool`（域匹配被摘除即红，防误杀正常路径）、
> `test_whitelist_none_path_unchanged`（防拦截误伤默认路径）；破坏实验
> `.workbuddy/verify_subagent_tests_are_detectors.py`（9/9 全部检测到）。

> **「打回」归属澄清（审查意见 #8）**：worker（审查特化）在 `max_depth=1` 下不能 spawn 子，所谓「打回」= 返回结构化 `reject + 理由`，由**父循环编排**收到后重新 `delegate`。该编排逻辑写在 §3.1 主循环描述里，不塞进角色配置。

> **角色文件机制与目录安全边界（评审 R4/Q3）**：优先采用**目录式角色文件**（对齐 Codex `~/.codex/agents/*`），而非插件页 CRUD。规则：
> - **重载触发**：选 (a) **每次 `delegate` 调用时扫目录**（读取几个小 YAML 的 IO 成本相对「起一个 LLM 子循环」可忽略）；不引入文件监视器（`agent/` 源码无任何 inotify/watch 机制，评审核实）。
> - **路径**：固定 `<data_dir>/agent_roles/`，**非 Web 可写目录**。
> - **可写主体**：仅管理员/宿主；终端用户经设置页走校验落盘，**不直接写文件**，避免运行时注入角色（含工具白名单）这一共享部署提权面。
> - **校验**：角色名、工具名必须校验**在 `ctx.tasks.catalog()` 内**（拒绝未知角色/未知工具）；角色文件过 schema 校验。
> - 该能力**提前到阶段 1/2**（否则「加个子 Agent 要改代码」，能力形同虚设）。

## 4. 关键设计决策（对齐业界最佳实践）

1. **返回 `{answer, evidence}` 而非裸 `as_evidence()`**：子 run 收敛时由 finalizer 产出 `final_answer`（`child_run.text`）作为 `answer`；`as_evidence()` 仅作 `evidence` 佐证（审查意见 #1：前者是「答复」，后者是「trace 蒸馏」，语义不同）。
2. **工具白名单取交集**：`tools = intersect(visible_tools(ctx), 白名单)`，`"*"` 表示不额外收窄；**白名单只能收窄、不能放宽**，永不绕过 `visible_tools` 的 `permission_mode` 裁剪（审查意见 #2）。
3. **三重护栏**：嵌套 `max_depth`（默认 1，防无限递归）、并发 `max_threads`（**作用域=每父 run 的在飞子 Agent 数 ≤ N，用挂在父 run 上下文的 `asyncio.Semaphore(N)` 实现**，非全局/非每会话 —— 审查意见 #4）、超时 `deadline_s` + `TaskTimeout`。
4. **权限/审计最小继承**：子继承父会话 `permission_mode` 与 tenant/user/session；子 run 的 LLM/工具调用经 `ctx.llm`/`ctx.tasks` ⇒ 护栏全继承；父子关联经 `durable(SUBAGENT_SPAWN {parent_run_id, child_run_id, role})` 事件，子 run_id 为 `uuid4().hex`（审查意见 #3）。
5. **上下文隔离分级**（对齐通用模式）：默认 **instruction passing**（只把 `task` 描述 + 可选 shared_brief + 可选 expect_schema 传给子，永不下传父全量历史，见 §3.1a）；进阶可选 file-system memory（共享状态落盘）。

`subagent` 是 `agent/plugins/` 下的目录插件，与 memory/context/sandbox 同为 opt-in：必须经 `PluginManager.load()` 加载，而 `load()` 只加载 `data/agent_plugin_state.json` 的 `enabled` 列表中的插件。故**部署时必须把 `plugins.subagent` 加入 enabled**（该状态文件是 gitignored 的每台机器独立运行时状态，不随仓库走）；`react` 须保持启用（factory 缺席则不注册工具）。验证：本机已在状态文件加入 `plugins.subagent` 并重启服务，`/api/tools` 确认 `agent.delegate` 已注册（`owner=plugins.subagent`、`risk=read`、`required=[task]`）。

**真 uvicorn 复验（端口 8720，fixture 模式 + 临时库）**
服务干净启动、无新增报错；`/api/tools` 返回 48 个工具且含 `agent.delegate`（元数据与注册一致）。功能逻辑另由 `test_subagent_plugin.py` 经真容器 + 假工厂端到端覆盖（含父 `REACT_RUN_ID` 复原、`SUBAGENT_SPAWN` 审计落盘）。**真 LLM 驱动的委派端到端建议由你在 Swagger（8720）上验证**：重启你自己的服务（读取已更新的状态文件）后，让主 Agent 调用 `agent.delegate` 观察子答复 + 证据。

## 6. Prism 特有风险与对策

### 6.1 H2 并发会话锁旁路
`sys/chat.py::_acquire_session_run` + `_RUN_LOCK` 是 **HTTP 入口**的会话级 busy 锁（防同会话并发共享 `react_chain`）。子 Agent 是**进程内嵌套调用，不走 HTTP 入口**，若误走该锁会触发同会话 `409`。
**对策**：子 run 的 `run_id` 用**全新 `uuid4().hex`**（天然过 `_SEG_RE` 字符集校验，且 `build_task_id` 明确拒绝含 `:` 的 run_id 并抛 `SessionIdError`，审查意见 #3 原方案 `f"{parent}:child{n}"` 会启动即崩）；**不**经 `_acquire_session_run`；由 `SubAgent` 工具直接构造身份并调用子 Loop。父子关联**不靠字符串拼接**，改由 handler 发 `durable(SUBAGENT_SPAWN {parent_run_id, child_run_id, role})` 事件承载。子 Loop 的 `REACT_START` 事件仍带父 `session_key/tenant/user` 以便关联审计。

### 6.2 ContextVar 隔离（账单/审计归属）
`react/loop.py:501` 在 `_run_impl` 内 `set_current_run_id(task_id)` / `set_current_session_key(session_key)`，按 asyncio task 隔离。
**坑**：若子 Loop 被父循环**直接 await（同 task）**，子会覆盖父的 ContextVar，父后续 step 的 `agent_budget_log`/`agent_events` 会记到子 run。
**对策（二选一，推荐前者）**：
- （a）子 Agent 经 `asyncio.create_task` 跑子 Loop ⇒ 天然新 task，ContextVar 隔离；父 `await` 该 task；
- （b）在 handler 内 save/restore：`old=current_run_id(); try: ... finally: set_current_run_id(old)`。
并行（阶段 2）必须用（a）。

### 6.3 全量工具泄漏
`ReactLoop._run_impl` 固定 `tools = visible_tools(ctx)`（全量）。**必须**加 `tools_override` 接缝（§3.2），否则专家角色失去隔离，与「窄工具集」目标相悖。

### 6.4 identity 显式传参
`_run_impl` 注释明确：`identity` 必须显式线程化传入（ctx.state 被并发请求共享，H5/H6）。子 Agent handler 必须从 `coerce_identity` / `current_session_key` 取父身份，构造子 `SessionIdentity`（同 tenant/user/session，新 run_id）后**显式**传给子 Loop。

### 6.5 覆盖率说明（澄清，审查意见 #14c）
`run/chat.py` 42% 覆盖是**全局**头号待办，但**本方案不改 `run/chat.py`**（改动落在 `react/loop.py` 接缝 + 新增 `subagent` 插件），二者无依赖关系；此处仅说明「勿误以为本方案需顺手补 `run/chat.py` 覆盖」。本方案带来的覆盖增量在 `react/loop.py`（`tools_override`/`depth` 分支）与 `subagent/`（新增）上，由 `test_subagent.py`（检测器型 + 破坏实验）兜底。

## 7. 验证策略（对齐项目验证纪律）

- **接缝破坏性验证（阶段 0）**：破坏实验确认「不传 `tools_override` 时 `ReactLoop` 的**可见工具集相等 + 决策路径等价**」（mock 断言走了 `tools_override` 分支 vs `visible_tools` 分支；LLM 非确定性无法逐字节比，审查意见 #13）。
- **检测器型测试（`test_subagent.py`）**：
  - 子 Agent 返回结构化 `{status, answer, evidence, request_id}`，其中 `answer == 子 final_answer`、`evidence == as_evidence()`（断言穿过 `agent.delegate` 真实返回值，审查意见 #1/#10）；
  - 角色白名单取交集生效（explorer 调 `agent.write` 应被 hidden / guard 拒，经 `ctx.tasks.invoke` 真实读取点断言；且白名单不能比父会话权限更宽，审查意见 #2）；
  - 嵌套超 `max_depth` 被拒（破坏实验：临时把 `max_depth=0` 应失败）；
  - 超时触发 `TaskTimeout`（破坏实验：子任务 sleep > deadline）；
  - 并行 `max_threads` 上限（破坏实验：发 N+1 个子 Agent 应受 `Semaphore` 控）；
  - **隔离性断言（审查意见 #12，§6.2 风险的对偶验证）**：父 run 内 delegate 一个子 run，子 run 结束后断言 `current_run_id() == 父 run_id`；并行场景下断言父的 `agent_budget_log` 记录**不串**到子 `run_id`。
- **真 uvicorn 复验**：接缝/HTTP 层改动必须跑真实 uvicorn（`:8799` 同进程跨文件会串，逐文件独立进程）；`in-process TestClient` 不跑 lifespan ⇒ 容器未 assemble ⇒ 依赖容器端点全 500（夹具局限非缺陷）。
- **全量 pytest 必设 `CODEBUDDY_SAFE_DELETE_SANDBOX=0`**，basetemp 放工作区外（`%TEMP%/pbt_x`）且写 Windows 路径 `C:/…`，否则假红/ERROR。
