## 1. 结论先行

**能接，且不必引入第三方 wrapper——用飞书官方 `@larksuiteoapi/lark-mcp` 的 stdio 模式即可**，理由是它自带工具裁剪（`-t preset.light`），反而比第三方方案更可控。

但有三条硬约束必须先说清楚，它们决定了方案形态：

1. **本仓 MCP 客户端只有 stdio**（`core/mcp_client.py` 仅有 `McpStdioClient`，无 HTTP/SSE/Streamable HTTP 实现）⇒ 飞书官方「远程 MCP」（Streamable HTTP）**接不进来**，除非先给内核补 HTTP 传输（本方案不做）。
2. **本仓客户端不支持 MCP Auth（OAuth 授权流）** ⇒ `--oauth` 首版**必须禁用**，否则 token 过期时子进程等待登录、桥卡死到超时。改用「外部预登录 + token 注入」。
3. **容器沙箱默认镜像 `python:3.12-alpine` 没有 node** ⇒ 本桥首版可移植性只能声明 `("off", "wsl2")`；要支持容器档位必须换 node 镜像（阶段 2）。

---

## 2. 目标与非目标

### 目标
- 新增 `agent/plugins/feishu_mcp`：起一个 stdio 子进程（官方 `lark-mcp`），把飞书工具注册进 agent 工具目录，让 Agent 在推理循环里自主调用飞书（发消息、读文档、查多维表格、建日程等）。
- 与既有三个 MCP 桥（skills / playwright / windows）**完全同形态**，复用同一套契约与自愈机制。
- 工具集**默认裁剪**、风险**逐工具标注**、凭据**不落盘不入命令行**。

### 非目标（明确不做）
- 不做内核 HTTP 传输客户端（Streamable HTTP 支持）——那是独立的内核能力变更。
- 不做「语音输入 → 飞书工作流」的业务编排（阶段 4，与本桥零耦合，另立方案）。
- 不改既有三个桥的 risk 标注（那是独立欠账，本方案只**不重蹈**其覆辙）。
- 不做飞书事件回调（Webhook）/ 长连接机器人——本桥是**主动调用**方向，不是接收方向。

## 3. 现状勘察（本仓真实约束，逐条对齐代码）

### 3.1 传输能力：只有 stdio
`agent/core/mcp_client.py` 顶层只有 `McpStdioClient` 一个类；协议交互仅 `initialize` → `notifications/initialized` → `list_tools` → `call_tool`，**没有 MCP Auth / OAuth 相关处理**。
⇒ 选型必须落在 stdio server 上；且要求 server **不在协议层向客户端索要授权**。

### 3.2 桥样板契约（以 `plugins/skills_mcp` 为蓝本）
- `@plugin` 类：`name="plugins.<x>"`、`layer="business"`、`provides=[Services.<X>]`、`inject=[Services.TASKS]`。
- `_section(ctx)`：`agent.<x>`（覆盖通道）优先，回退顶层 `<x>` —— 两条通路并存是有意为之。
- `resolve(cfg, environ)` 纯函数：`config > env > 默认`，返回 `(command, args, timeout)`，便于离线测试。
- `apply`：启动失败**诚实报**（写 `StateKeys.MCP_ERROR`）而不拖垮装配；成功后逐个 `ctx.tasks.register`，写 `StateKeys.MCP_TOOLS`，`ctx.provide(自身)`，`ctx.effect(close)`。
- **自愈**：`_ensure_client()` 探活（`client.is_alive`）+ 加锁就地重启（免重启整个后端）。
- **沙箱接缝**：`call_spawn_provider(fn, current_session_key(ctx), _BRIDGE)` 取 `{cwd, env, wrap}`，`wrap` 传给 `McpStdioClient` 实现跨边界命令包装。
- 分层：桥只 import `agent.api`，**不 import 其它插件**（`test_plugin_decoupling` AST 守卫）。

### 3.3 工具注册与 risk
`agent/sys/tasks.py::register(ctx, name, *, schema, handler, owner, description, risk="write", timeout_s)`，且 `risk not in RISKS` 直接抛错，`RISKS=("read","write","danger")`。
- **默认 `write`** —— 这正是既有 playwright / windows 两桥的欠账（注册时不传 risk ⇒ 连只读工具也是 write 级 ⇒ `risk.ask` 下"读个东西也要问人"、plan 模式被裁）。
- `skills_mcp` 已修正为按集合标注（`_READ_ONLY_TOOLS` / `_DANGER_TOOLS`，未命中一律保守 `write`）。
- guard（`sys/guard.py`）的 risk 策略可配 `risk: {read|write|danger: deny|ask|allow}`，**默认 open 放行**。

### 3.4 配置登记
`agent/core/config_schema.py` 的 `agent` 节是**严格校验节**：新节不登记 ⇒ 用户一写配置就在装配期 `ConfigError`。
现有 MCP 桥均登记为 `"_any"`（宽松），且**同时登记两处**：`agent.<x>`（第 82–100 行区）与顶层 `<x>`（第 119–124 行区）。

### 3.5 可移植性与沙箱
`core/sandbox_backend.py::BRIDGE_PORTABILITY` 键为**桥 id**（如 `windows_mcp`），`runnable_in()` 同时接受桥 id 与工具域（`feishu` ⇒ 查 `feishu_mcp`）；未登记按"可移植"处理。
- 沙箱后端：`off` / `wsl2`（bwrap 进程级）/ `container`（docker，默认镜像 **`python:3.12-alpine`**）。

### 3.6 插件启用
`run/chat.py:469` `PluginManager(plugin_dir="agent/plugins", state_file="data/agent_plugin_state.json")` ⇒ 目录插件自动发现、**opt-in 启用**（写 state 文件 `enabled`）。
既有先例不一：`skills_mcp` 配置 `enabled` 默认真；`playwright_mcp` 默认未启用。

### 3.7 工具命名前缀
`mcp.playwright.<tool>` / `mcp.windows.<tool>` / `mcp.skills.<tool>` —— 用**短域名**而非桥 id。飞书桥应统一为 `mcp.feishu.<tool>`（与 `runnable_in("feishu")` 的映射一致）。

## 4. 选型：三条路对比

| 方案 | 传输 | 覆盖 | 本仓可接性 | 结论 |
|---|---|---|---|---|
| A. 飞书官方远程 MCP（`open.feishu.cn`） | Streamable HTTP | 仅云文档场景 | ❌ 内核无 HTTP 客户端 | 否决；且个人链路逐步下线、MCP Token 仅 7 天有效 |
| B. `lark-cli` + 第三方 wrapper | stdio | CLI 200+ 命令 | ✅ | 备选：多一层第三方依赖，且要另装 CLI |
| **C. 官方 `@larksuiteoapi/lark-mcp`（stdio）** | **stdio（默认）** | OpenAPI 映射 + preset 裁剪 | ✅ | **推荐** |

**选 C 的决定性理由**：官方包自带 `-t/--tools` 裁剪（`preset.light` 为轻量集，另有 `im.default` / `base.default` / `doc.default` / `task.default` / `calendar.default` 等），**"工具数量撑爆上下文"这个最大担忧在官方包内就能解决**，无需为裁剪引入第三方 wrapper。

### 官方包关键参数（已核实，v0.5.1）
```
lark-mcp mcp -a <app_id> -s <app_secret> [-m stdio] [-t preset.light] \
             [--token-mode auto|tenant_access_token|user_access_token] \
             [--oauth] [--scope ...] [-c snake] [-l en] [--config ./config.json]
```
- **环境变量等价**（官方明确支持，启动可免 `-a/-s`）：`APP_ID`、`APP_SECRET`、`USER_ACCESS_TOKEN`、`LARK_TOOLS`、`LARK_DOMAIN`、`LARK_TOKEN_MODE`。
- `--mode` 默认 `stdio`；`sse` 已废弃；`streamable` 为 HTTP。
- `--token-mode` 默认 `auto`（由 LLM 调用时决定用哪种 token）。
- `--oauth` 为 **Beta**，作用是"启用 MCP Auth Server 自动取 user token，过期自动请求登录"。
- OAuth 回调地址默认 `http://localhost:3000/callback`（以开放平台实际配置为准；社区资料里出现的 3333 为旧/第三方默认值）。
- user token **通常 2 小时**有效；Linux 下 token 存储依赖 keytar/libsecret。

## 5. 关键风险与对策（本方案的核心）

### ★ R1：`--oauth` 会卡死（客户端不支持 MCP Auth）
**现象**：token 过期时 server 走 MCP Auth 向客户端索要授权；本仓 `McpStdioClient` 不处理该流程 ⇒ 请求悬挂，直到 `timeout_s` 超时，期间工具不可用。
**对策**：首版**禁用 `--oauth`**，改走 §6.7 的 token 注入；把 `oauth` 列为一个**显式配置开关且默认 false**，代码注释写明"启用前须先给内核补 MCP Auth 支持"。

### ★ R2：user token 只有 2 小时
- 首版用 **`--token-mode tenant_access_token`**（应用身份）：token 由 server 用 app secret 自行换取与续期，**无交互、无过期中断**。
  - 代价：只能操作应用有权限的资源（应用需被加为群成员 / 文档协作者）。
- 需要读个人日程、个人文档、代用户身份发消息时，再上 user token（阶段 2）：外部执行 `npx -y @larksuiteoapi/lark-mcp login -a ... -s ... --scope offline_access` 完成一次浏览器授权，之后以 `USER_ACCESS_TOKEN` 注入；expiry 前由外部刷新，桥内**不做自动续期**（诚实降级：过期即报明确错误，不静默）。

### ★ R3：容器沙箱镜像无 node
`DEFAULT_CONTAINER_IMAGE = "python:3.12-alpine"`（**沙箱策略级全局配置**，见 `sandbox_backend.py:427`，由 `policy.image` 读取，**不是 per-bridge**）⇒ 容器内没有 `npx`，本桥必崩。
**对策**：`BRIDGE_PORTABILITY["feishu_mcp"] = ("off", "wsl2")`（**不声明 container**）。选中 container 档位时按既有机制**单独降级 off + 计数 + 进 `unportable_targets`**（诚实暴露，不静默）。

⚠ 阶段 2 若要支持容器，**不是"给桥加个 image 配置"就能解决**：镜像是全局策略，换成 `node:22-alpine` 会让 `skills_mcp`（走 `python -m`）反过来崩。真正的解法是给沙箱后端加 **per-bridge image**（新能力，需另立方案）——本方案不做，仅如实记下这条路径依赖。

### ★ R4：凭据泄漏（三条通路都要堵）
1. **不入命令行**：Windows 下命令行可被其他进程读到 ⇒ `-a/-s` 一律改用 env（`APP_ID` / `APP_SECRET`）注入。`child_env()` 是 `os.environ` 叠加式合并，env 注入可行。
2. **不入仓**：`data/` 整目录 gitignore，但 `agent_plugin_config.json` 落在该目录且易被手工编辑 ⇒ 方案约定**配置文件只写非敏感项**（tools / token_mode / timeout），Secret 从**宿主进程环境**取；插件取不到就**早退并报明确错误**，绝不静默降级。
3. 现有 `local_secrets.json` 是明文（既有问题，建议另行轮换，不在本方案范围）。

### ★ R5：工具数量与上下文
`-t preset.light` 起步（默认）；需要某域时按 preset 叠加，例如：
`-t preset.light,preset.calendar.default,preset.base.default`。
非 preset 的单 API 也可用 `-t im.v1.message.create`，但官方明确提示**非 preset API 未做兼容性测试**，故首版只用 preset。

### ★ R6：risk 默认 write 的覆辙
新桥**必须逐工具标注**，规则见 §6.5；未命中规则的工具一律保守 `write`。

### ★ R7：npx 首次下载 + 自愈重启放大延迟
`_ensure_client()` 会在子进程挂掉时就地重启；若每次都走 `npx -y` 且缓存失效，重启会慢甚至失败。
**对策**：默认命令固定版本 `npx`，args 为 `["-y", "@larksuiteoapi/lark-mcp@0.5.1", "mcp"]`；文档建议生产用 `npm install -g @larksuiteoapi/lark-mcp` 后把 `command` 配成 `lark-mcp`（`resolve` 走 `config > env > 默认` 天然支持）。

## 6. 设计

### 6.1 插件结构
新增目录 `agent/plugins/feishu_mcp/`，**单文件** `__init__.py` 即可（比照 `skills_mcp` 体量，约 250 行）：
- `_BRIDGE = "feishu_mcp"`，工具名前缀 `mcp.feishu.`
- `resolve(cfg, environ)` 纯函数（可离线单测）
- `_section(ctx)`：`agent.feishu_mcp` 优先，回退顶层 `feishu_mcp`
- `_spawn()`：拼 env + 接沙箱接缝（cwd/env/wrap）
- `apply()` / `_ensure_client()` / `_close()` / `status()`
- 只 import `agent.api`

### 6.2 配置节（两处均登记 `_any`）
```json
{
  "agent": {
    "feishu_mcp": {
      "enabled": true,
      "tools": "preset.light",
      "token_mode": "tenant_access_token",
      "domain": "https://open.feishu.cn",
      "timeout_s": 60,
      "oauth": false,
      "command": "npx",
      "args": ["-y", "@larksuiteoapi/lark-mcp@0.5.1", "mcp"]
    }
  }
}
```
**默认 `enabled: false`**（与 `playwright_mcp` 同纪律）：飞书是外网写能力（会真发消息、真改文档），**开箱即启风险过高**，且缺凭据时本来也起不来。

### 6.3 启动命令解析
```python
def resolve(cfg, environ=None):
    environ = environ or {}
    command = cfg.get("command") or environ.get("FEISHU_MCP_COMMAND") or "npx"
    args = list(cfg.get("args") or ["-y", "@larksuiteoapi/lark-mcp@0.5.1", "mcp"])
    return command, args, float(cfg.get("timeout_s", 60.0))
```
`-a/-s` **不进 args**；`--token-mode` / `-t` / `-d` 也不进 args（全部走 env：`APP_ID`/`APP_SECRET`/`LARK_TOKEN_MODE`/`LARK_TOOLS`/`LARK_DOMAIN`），避免任何凭据落到命令行。

### 6.4 工具集裁剪
`tools` 配置 → env `LARK_TOOLS`；默认 `preset.light`。

### 6.5 risk 标注规则（★ 不重蹈覆辙）
采用**「读前缀规则 + 显式例外」**，而不是硬编码工具名全集（工具名随上游版本变，硬编码会失效并静默退化成全 write）：

```python
# 命中任一读后缀 ⇒ read（这些是查询类，无副作用）
_READ_SUFFIXES = (".search", ".list", ".get", ".rawContent", ".getNode",
                  ".primary", ".batchGetId", ".freebusy")
# 显式危险：批量写 / 权限授予（影响面大且难撤销）
_DANGER_SUFFIXES = (".batchCreate", ".batchUpdate", ".permissionMember.create")
# 其余一律 write（保守）
```
> 与 `skills_mcp` 的"未命中一律保守 write"同一纪律：宁可多问一次，不因猜错而放行。

### 6.6 状态与自愈
完全照抄 `skills_mcp`：
- 启动失败 → `MCP_ERROR` + `provide(自身)` + 早退（不拖垮装配）；
- `MCP_TOOLS` 记录工具名清单；`status()` 返回 `{enabled, tools, error, alive}`；
- `_ensure_client()` 探活 + 加锁就地重启；
- stderr → `warning`（死因唯一通路，绝不降级丢弃）。

### 6.7 凭据注入
- 从宿主 `os.environ` 取 `FEISHU_APP_ID` / `FEISHU_APP_SECRET`（**配置节不存明文**），映射为子进程 env `APP_ID` / `APP_SECRET`；
- 取不到 ⇒ `apply` 早退，`MCP_ERROR` 写明"缺少 FEISHU_APP_ID/FEISHU_APP_SECRET（请在宿主环境设置，勿写入配置文件）"；
- user token（阶段 2）：`FEISHU_USER_ACCESS_TOKEN` → `USER_ACCESS_TOKEN`。

## 8. 分阶段计划

**阶段 0（前置，须你先做，我代劳不了）**
1. 飞书开放平台创建**企业自建应用** → 取得 App ID / App Secret；
2. 开通权限（按需）：`im:message`、`im:chat`、`docx:document`、`drive:drive`、`bitable:app`、`calendar:calendar`、`task:task`、`contact:user.base` 等；
3. 把应用加进目标群 / 授权目标文档（tenant 身份的必要条件）；
4. 在本机环境设置 `FEISHU_APP_ID` / `FEISHU_APP_SECRET`（不落任何文件）。

**阶段 1（本方案交付范围）**
- 按 §7 落地插件 + 登记 + 可移植性声明 + 单测；
- 默认 `enabled: false`、`token_mode: tenant_access_token`、`tools: preset.light`、`oauth: false`；
- 真连验收：列工具 → 调一个**只读**工具（如群列表/文档搜索）→ 再调一个**写**工具（给自己发一条测试消息）。

**阶段 2（本次不做，待阶段 1 验证后再定）**
- user token 通路（外部 `login` + token 注入 + 过期诚实报错）；
- 容器档位支持（**先决**：沙箱后端支持 per-bridge image，见 R3）；
- MCP Auth / `--oauth` 支持（**须先给内核补能力**）。

> ⚠ **阶段 1 的未知前置（需在实测时确认）**：`wsl2` 档位能否跑本桥，取决于 **WSL2 发行版内是否装有 node/npx**（已核实 WSL2 内有 python3 / bwrap / unshare，但 node 未核实）。若没有，阶段 1 实际只能在 `off` 档位运行——不影响首版交付，但要在验收时如实记录。
