# token 口径对账 — 问题记录

- **状态**：已记录 · **待定方向**（本文只记录问题与收口提案，**未改动任何代码**）
- **日期**：2026-09-27
- **触发**：会话 `ea3563de`「桌面写 3 万字小说」被拒（`预算超限 spent=198087 + est=19524 > 200000`）
- **关联**：`docs/governance/上下文治理-设计方案.md`（G0~G3）、`docs/governance/S3-循环内上下文-设计方案.md`、`docs/governance/S4-MCP源头护栏-设计方案.md`
- **一句话**：两套 token 指标本身正交（合法），但**同一批 token 被三把尺子各量一遍、且互不对账**——这才是坏味道，也是「毫无征兆撞顶」的直接成因之一。

## 一、背景与触发

一次「让 agent 在桌面写 3 万字小说」的任务失败，报错为：

```
已达执行上限：模型调用被拒：能力未就绪: agent.llm.complete
（预算超限 spent=198087+est=19524>200000）；已执行 4 轮工具调用，未能形成最终答复
```

账单已精确复现（`data/agent_chat.db` · `agent_budget_log`）：

| 运行 | 结果 | 累计消耗 |
|---|---|---|
| 1 · 23:34 | 1 步收敛 | +9,172 |
| 2 · 23:38 | **8 步被截断**（`react.max_steps=8`） | +124,561 |
| 3 · 23:40 | **第 5 步被拒**（累计额度闸） | +64,354 |
| **合计** | — | **198,087**（与报错 `spent` 分毫不差） |

该错误**来自 `agent.budget`（成本护栏），不是上下文压缩**。压缩管的是"单次发出去多大"，**无法退回已花的额度**——两者不是一回事。这引出了本文要记录的核心问题。

---

## 二、问题的两层

### 2.1 第一层：两套 token 指标并存 —— 这是**正交且合理**的

| | 窗口预算 | 累计额度 |
|---|---|---|
| 变量 | `max_context_tokens` 24000 / `input_budget()` 20000 | `max_tokens_per_run` 200000 |
| 问的问题 | 一次调用**能装多少** | 一场会话**一共能花多少** |
| 性质 | 模型容量约束（物理） | 成本约束（钱包） |
| 记账周期 | **每次调用**重算 | **容器生命周期累加**，仅「新会话」重置 |
| 归属 | `plugins.context`（S3 红线：token 语义唯一归属） | `agent.budget`（`sys/budget.py`） |
| 超限后果 | 裁内容（折叠 / 丢弃 / 降级） | **拒绝调用**（`denied`） |

- `input_budget()` = `max_context_tokens − reserve_output_tokens` = 24000 − 4000 = **20000**（`governor.py`）。
- `max_tokens_per_run` = **200000**，定义在 `agent/profiles.py:36`，语义见 `sys/budget.py` 头部：「**容器生命周期累计**额度」；`reset_on_new_session=True` → 网页「新会话」时经 `agent/chat/reset` 重置。

**结论**：像「油箱容量」与「油卡余额」——都以"升"计，但一个决定**这次能装多少**，一个决定**总共能加多少次**。只有窗口预算则"跑一整天"无人拦；只有累计额度则"单次撑爆窗口"无人管。**两套都需要，本身不冗余。**

### 2.2 第二层：同一批 token 被**三把尺子**各量一遍 —— 真正的坏味道

这是"两套指标"令人别扭的根源 —— **不是数量问题，是对账问题**：

| 视角 | 口径 | 实测（同一次调用） |
|---|---|---|
| 窗口预算 | `input_budget()` = 20000，**只算 messages** | messages 被钳在 ~20k |
| 预算 est（**放行判据**） | `estimate_tokens(messages)` + `estimate_tokens(工具**名**列表)` + schema | **18,865** |
| 真实账单（**扣款依据**） | 服务端 `prompt_tokens`：messages + **完整 tools JSON 数组** | **25,513** |

同一个调用：est **18,865** → 真实 **25,513**，**低估约 26%**。三个原因叠加：

1. **工具只按名字估**。`sys/llm.py:85` 传给预算的 `tools` 是
   `[str(t.get("name", "")) for t in (tools or [])]` —— **只有名字**；而线上真发的是
   `_wire_tools` 生成的**完整数组**（`description` ≤200 字 + `parameters` JSON schema）。
2. **窗口预算压根不认 tools**。`input_budget()` 只扣 `reserve_output_tokens`，
   没给 tools / schema 留任何位置。
3. **两把尺子本身不同**。`estimate_tokens` 是**启发式**
   （`core/tokens.py`：ASCII 约 4 字符/token、CJK 约 0.75 token/字）；
   `tokens_in` 是 **DeepSeek 服务端真实 usage**（本机 provider 已是 deepseek）。

## 三、证据

### 3.1 尺子实测（同一次调用）

- 放行判据 est：**18,865**
- 服务端真实 prompt_tokens：**25,513**
- 偏差：**≈ +26%**（真实高于估算）

### 3.2 工具目录被线上发送**两遍**（与对账无关的独立浪费）

- `plugins/react/prompt.py::build_system()` 把 `render_tools(catalog)` 写进 **system 文本**；
- `sys/llm.py::_wire_tools()` 又把同一份目录发成 **native tools 数组**。

同一份目录，**文本 + native 各一份**，每次请求都白付一遍。

### 3.3 压缩在本次路径上**不存在作用点**

- `agent_session_summaries` 表 **0 行** → 压缩自历史以来**一次都没触发过**。
- `short_term.compactor` 只扫 **`agent_messages`（跨轮会话历史）**；而本会话历史仅 **6 条消息 / 1.8k 字符**，
  远低于 `compact_trigger_tokens=12000` —— 无从下手。
- 那 19.8 万 token 全烧在 **react 循环内的 chain**；按 S3 明确设计，Think/Act/Observe 是
  "循环内草稿纸"，**绝不写入 `agent_messages`** → 压缩器**根本看不到它**。
- 消耗构成：**输入 180,272 vs 输出 17,815** —— 约 **90% 额度用于"每步把已有正文重发一遍"**
  （循环内输入 7.7k → 16.7k → 25.5k 一路膨胀）。

## 四、影响

1. **额度"提前且突然"撞顶**：护栏按**低估的 est** 放行，post-call 又按**真实值**补记
   （`spent = spent − est + actual`）→ 账面在无察觉时跳变，**这正是本次"毫无征兆被拒"的直接成因之一**。
2. **窗口侧同理**：messages 虽被钳住，真实请求仍可能因 tools 未计入而超出预算。
3. **"压缩救不了"**：累计额度属成本墙，压缩属窗口墙，**方向不同不能互救**。

---

## 五、收口方向（提案，**未实施**）

按预计收益排序：

1. **`input_budget()` 显式预留 tools / schema** —— 即"请求预算 = 窗口 − 输出余量 − 请求附加项"。
2. **预算 est 改用与线上同构的 payload 估**（"发什么就算什么"，别用名字）。
3. **最彻底：只留一个「请求成本估算器」** —— 治理器与预算护栏都调它，谁也别自己算。
   这样"两套指标"就退化为"两种**用途**、一份**账本**"。
4. **单独决策**：工具目录是否真需要"文本 + native"各来一份（消除重复发送）。

## 六、相关但不属本文范围的问题（一并记录）

1. **`ok` 上浮不一致**：预算被拒时 `ReactResult.ok = not hard`，而预算拒绝**不算 `hard`**
   → `CHAT_DONE` 记 `ok=true`。运行 2、3 都"已达执行上限"却对外报成功——文本诚实，但**错误面未上浮**。
2. **写长文的自产出累积无针对性治理**：S3 的 `_prepare_chain` 只折叠"**老的、未 pinned 的 observe**"，
   **不折叠 agent 自己写出的正文**；而"写长文"恰是**自产出累积**场景 → 可作为 **S5** 候选。
3. **两道闸未开放到设置页**：`react.max_steps`(8) 与 `max_tokens_per_run`(200000) 均未登记进
   `_SETTING_SCHEMA`，只能改配置/画像。
