## 一、结论（TL;DR）

**不需要重制。建议「2.0 演进式重构」——保留骨架与契约兼容面，按职责分层扩建。**

三句话说明理由：

1. **骨架是对的**：`assemble()` 的「注册制过滤 → 刚性先扣 → water-filling 回吐 → 块内裁剪 → 互斥输出」管线、零状态纪律、纯度纪律（唯一持有 token 语义）、零特权（只走 `core.tokens`）——这四条是全仓解耦纪律的承重墙，且有 36 项测试 + 逐字节等价对拍在护航。推倒重写等于把已验证资产归零。
2. **缺陷是「职责面缺位」，不是「数据结构错」**：缺的是记账、水位、压缩调度、清除、完整性校验、全景视图——**六项都是「加动词」，不是「改骨架」**。`BlockSpec` 是纯数据 dataclass（扩字段缺省即等价）、`assemble()` 是纯函数（扩参即兼容）、消费方**根本不 import 治理器类型**（鸭子契约），三点合起来意味着扩建的兼容成本接近于零。
3. **唯一真正的结构性问题**：契约是**单向 pull**（消费方提交 → 治理器分配），治理器**无法主动声明「应该有哪些块」**，所以漏报永远无人发现——这正是盲点长期隐形的机械成因。修它需要**新增一个方向**（声明式注册），但这依然是「加契约面」，不是「改骨架」。

**重制的唯一合理触发条件**（当前均不满足，见第三章）：跨 provider 差异化管理、多智能体共享窗口、流式增量装配成为硬需求时。

## 二、评估：为什么是「升级」而非「重制」

### 2.1 现有骨架的正确性证据（重写的沉没成本）

| 资产 | 证据 |
|---|---|
| 装配管线正确 | 36 项治理器测试，含 water-filling 回吐、刚性超限双通道、coverage 左开右闭互斥、pinned 先占降级 |
| 与旧实现逐字节等价 | `test_fallback_byte_equal_to_governor_when_budget_ample`、`test_fallback_byte_equal_when_block_absent`——**改骨架即有破坏证据链的风险** |
| 接缝可替换 | `test_governor_seam_injection`：`ctx.get("context.governor")` 可注入替身；插件停用消费方退回现状不劣化 |
| 零反向查询 | `test_governor_receives_covers_as_param_not_reverse_query`——治理器不反向读 chat/short_term，无循环依赖 |
| 配对原子保护 | 9-29 凌晨新增 `_pair_units`，裁剪切点不拆 tool_use/tool_result 配对（实测 400 已修复） |
| 纯度守卫 | `test_governor_has_no_business_wording` + `test_agent_purity` 的 K0 全目录扫描 |

**判读**：这套骨架的核心判断（治理器只回答「怎么裁、占多少」，不感知业务；零状态；零特权）**没有任何一条被本次事故证伪**。事故证明的是「容量与触发器失配」，不是「抽象错了」。

### 2.2 缺陷的精确边界

把 13 项缺口按「性质」而非「模块」重新归类，结论很清晰：

| 性质 | 缺口 | 是否触及骨架 |
|---|---|---|
| **加动词**（结构性扩展，不动骨架） | 无压缩契约、无清除动词、无水位判定、无完整性校验、无全景账本、无分类视图 | 否 |
| **加字段**（纯增量，缺省等价） | `cap_tokens` / `compact_at` / `on_compact` / `layer` / `required` | 否 |
| **加方向**（唯一真结构问题） | 契约单向 pull → 需新增「声明式注册」方向 | **是（但为新增，非修改）** |
| **改数值**（配置层） | 窗口/阈值锚定 1M | 否 |

**13 项缺口里，只有 1 项触及结构性方向，且是「增加一条通道」而非「改变既有通道」。**

### 2.3 三个决定性事实

**事实一：消费方零类型依赖。**
`agent/sys/chat.py` 第 89 行明写：「governor 的 Assembly 亦按同属性面消费，**不 import 其类型**」；`governor._coerce()` 专门兼容 dict 入参。这意味着**契约扩展不会产生跨模块类型迁移**——重写方案最昂贵的部分（消费方全面改造）在这里近乎不存在。这大幅削弱了「重写更干净」的论点。

**事实二：契约面极薄，只有 15 个方法。**
`GovernorLike` 全部内容：`input_budget` / `memory_budget` / `history_budget` / `source_clip_budget` / `react_budget` / `react_keep_recent` / `react_min_chain_tokens` / `clip_max_tokens` / `clip_head_tokens` / `clip_tail_tokens` / `clip_head_tail` / `pick_history` / `assemble`（+ `from_config`）。**薄契约 + 鸭子消费 = 升级路径畅通**。

**事实三：治理器是纯函数式无状态。**
`assemble()` 无 `ctx`、无 `self` 可变状态、水位可现算。这让「状态机」可以以**无状态方式**加入（每次装配现算 load_ratio / level），不会引入生命周期管理复杂度，也不会破坏「零状态」纪律。这是原设计留下的最优伏笔。

## 三、重制判据（什么情况下才该重写）

咖啡猫给出三条**客观触发条件**，并逐条自证当前不满足：

| # | 触发条件 | 现状 | 判定 |
|---|---|---|---|
| T1 | **跨 provider 差异化管理成为硬需求**——不同厂商的上下文原语不同（如 Anthropic 服务端 `clear_tool_uses` vs 客户端重写），需要在装配层分派 provider 策略 | 当前仅单一 provider（deepseek），且服务端清除尚无对应 API 可用 | ✗ 不满足 |
| T2 | **多智能体/多会话共享同一窗口预算**——需要跨会话的全局配额仲裁 | 当前单会话单窗口，无共享需求 | ✗ 不满足 |
| T3 | **流式增量装配成为硬需求**——SSE 边生成边装配，需要完全不同的增量数据结构 | 当前整段装配后一次性发出，工作正常 | ✗ 不满足 |

**结论**：三条均不满足 → **重制的收益（更干净的抽象）低于代价（归零 36 项测试资产 + 6 项守卫纪律 + 逐字节等价证据链）**。

**反向提示**：若 T1 在未来成立（例如接入 Anthropic/Claude 且要用服务端清除），届时**应该**重制 `Compactor` 单元（而非整个治理器）——因为清除原语是 provider 相关的。所以本方案的架构设计已把「可替换的执行器」作为前提（见 4.3）。

## 四、目标架构（Context Governor 2.0）

### 4.1 分层总览

```
┌─ 消费方（不 import 治理器类型，纯属性面 / dict 入参） ──────────────┐
│  chat·plan        chat·prior       chat·narrate      react·loop   │
└──────────────────────────────┬────────────────────────────────────┘
                               │ ① 声明（新增，启动期一次）
                               │ ② 装配（现有，扩参）
                               ▼
┌─ 契约面 protocols.py（三组） ────────────────────────────────────┐
│  A 被动查询组（现有 12 方法，冻结不动）                          │
│  B 装配组（现有 assemble，扩 phase / ledger 参数）               │
│  C 治理组（新增 4 方法）：declare / assess / plan / execute      │
└──────────────────────────────┬────────────────────────────────────┘
                               │
                               ▼
┌─ 门面 ContextGovernor（保持零状态 · 零业务语义 · 零特权） ────────┐
│  ┌───────────┐ ┌───────────┐ ┌───────────┐ ┌───────────┐        │
│  │  Ledger   │ │ Waterline │ │ Compactor │ │ Inspector │        │
│  │  记账     │ │  水位决策 │ │  执行器   │ │  视图与   │        │
│  │  双账本   │ │  三态机   │ │  清除优先 │ │  不变量   │        │
│  └───────────┘ └───────────┘ └───────────┘ └───────────┘        │
└──────────────────────────────┬────────────────────────────────────┘
                               │ 仅只读调用（零特权纪律）
                               ▼
┌─ core.tokens 公共原语（estimate_tokens / clip_text / guard_source）┐
└──────────────────────────────────────────────────────────────────┘
```

**拆分原则**：门面 `ContextGovernor` 仍是**唯一对外实例**（接缝注入不变、`Services.CONTEXT` 不变、36 项测试的接口不变），四个单元是**内部模块**——这样「拆分」对消费方与守卫完全透明。

### 4.2 契约面三分组

**A 组 · 被动查询（现有 12 方法）**——冻结，不改不删。

**B 组 · 装配（现有 `assemble`，向后兼容扩参）**

```python
def assemble(self, blocks, *, reserve_tokens=0, cost_factor=1.0,
             phase: str | None = None,          # 新增：plan/prior/narrate/loop
             ledger: LedgerSink | None = None   # 新增：可选记账出口
             ) -> Assembly: ...
```

- `phase`：让治理器知道**这是哪个装配端点**，从而知道「本阶段该有哪些块」→ 支撑完整性校验；`None` 时完全退回现行为（缺省等价）。
- `ledger`：可选记账出口，`None` 时零开销。

**C 组 · 治理（新增 4 方法）**

```python
def declare(self, blocks: list[BlockDecl]) -> None: ...
    # 启动期声明：本消费方会提交哪些块、哪些必需、分层归属、cap 与压缩策略
def assess(self, used: int, budget: int) -> WaterlineReport: ...
    # 现算水位：load_ratio / level(normal|high|cooling) / 建议动作（无状态）
def plan(self, report: AssemblyReport) -> list[Action]: ...
    # 决策：keep / clear / compact / evict（清除优先于压缩）
def execute(self, actions: list[Action], blocks: list[BlockSpec]) -> ApplyResult: ...
    # 执行：策略分发 → 结果与不变量校验（失败即降级为 keep，绝不半途破坏结构）
```

> **四方法的纯度保证**：`plan` / `execute` 只输出与消费**通用形状**（token 数、层、cap、回调句柄），策略实现由消费方通过 `on_compact` 回调注入——治理器**只调用、不理解**，纯度守卫可继续通过。

### 4.3 内聚单元四件

| 单元 | 职责 | 关键点 |
|---|---|---|
| **Ledger 记账** | 分类账目：块级 used/requested/allocated（现有 `BlockReport` 扩展）+ **对象级**（tools schema / response_format 等 attachments）+ **真实账**（估算 vs 真实 token，接 `cost_factor`） | 输出 `unaccounted_tokens`——**预算黑洞变成显式告警**；轮次级全景账本 `RoundLedger` |
| **Waterline 水位** | `load_ratio = used / working_window`；三态机 `normal → high(≥0.7) → cooling`；压缩回本判定（`4(W−D)/D` 步）+ 冷却期 | **无状态现算**：每次装配根据实际 used 判定，不记忆历史 |
| **Compactor 执行器** | 策略分发，优先级 **clear > dedupe > summarize > clip**；**清除优先于压缩**（因缓存经济学：清除不破坏前缀，重写破坏前缀） | 执行前校验配对/结构不变量，失败降级为 keep；**provider 相关实现可替换**（对应重制判据 T1） |
| **Inspector 视图与不变量** | `/context` 式分类视图（常驻/按需/运行时/记忆/输入各占多少）；三条不变量断言 | 不变量：①tool_use/tool_result 配对完整 ②thinking block 完整 ③压缩后前缀稳定性可测 |

### 4.4 块模型五层（替代 rigid/flex 二分）

现行 `rigid: bool` 只有二分，而真实治理需要五档差异：

| 层 | 归属 | 策略 | 现行 | 新字段 |
|---|---|---|---|---|
| **resident 常驻** | 系统提示 / 输出格式 | 硬 cap（超限显式告警，不静默） | rigid=True | `layer="resident"`, `cap_tokens` |
| **on-demand 按需** | 工具 schema / 记忆召回 | 可 evict（按需加载） | ⚠️ 预算外黑洞 | `layer="on_demand"`, `cap_tokens` |
| **runtime 运行时** | ReAct 轨迹 | 可 compact / clear | flex (weight 1.0) | `layer="runtime"`, `compact_at`, `on_compact` |
| **memory 记忆** | 长期 / 短期摘要 / 工作记忆 | 可 summarize | 部分 flex | `layer="memory"`, `compact_at` |
| **input 输入** | 用户当前输入 / 附件 | cap 但保护首条 + 最近 N 条 | rigid（无 cap） | `layer="input"`, `cap_tokens` |

**兼容性**：`layer` 缺省时由 `rigid` 推导（`rigid=True → resident`、否则 `runtime`）→ **旧消费方零改动，行为逐字节等价**。

### 4.5 生命周期状态机（把「周期涨落」真正接上）

```
        used/budget ≥ high_ratio(0.7)
normal ──────────────────────────────► high
  ▲                                     │ ① 回本判定：预计剩余步数 ≥ 4(W−D)/D
  │                                     │ ② 冷却期已过
  │                                     ▼
  └────────── cooling ◄──────────── compact 执行（clear 优先 → compact → clip）
              used/budget ≤ low_ratio(0.4)
```

**三个防反优化闸**（据 v1.2 实测结论：压缩省 hit 便宜货、制造 miss 贵货，回本恒 2.7 步）：
1. **阈值闸**：`working_window_tokens × 0.7`（`working_window` 为经济基数，与 1M 能力上限解耦）；
2. **回本闸**：预计剩余步数不足回本步数 → 不压（记录「跳过原因」）；
3. **冷却闸**：一次压缩后 N 步内不再压（防反复付前缀罚金）。

## 五、八项关键设计决策

| # | 决策 | 理由 | 业界对标 |
|---|---|---|---|
| D1 | **双窗口解耦**：`max_context_tokens`（1M 能力上限，总闸）vs `working_window_tokens`（经济基数，默认按任务规模） | 一个字段承担两个量纲 → 窗口放大即全阈值失灵（本次事故根因） | Anthropic「context budget」按任务动态设定，不等同模型上限 |
| D2 | **策略由消费方注入**（`on_compact` 回调），治理器只调用不理解 | 守住纯度纪律（唯一持有 token 语义、零业务感知） | Anthropic compaction API 由调用方给 prompt |
| D3 | **清除优先于压缩**（clear > compact） | 清除不破坏缓存前缀；压缩重写历史必致 miss（贵 5 倍） | Anthropic `clear_tool_uses` 服务端清除；Manus 强调 append-only |
| D4 | **压缩三重闸**（阈值 + 回本 + 冷却） | 实测：短 run 压缩净亏；防「为省 token 反而增费」的反优化 | —（源自本项目实测） |
| D5 | **声明式注册 + 完整性校验**（`declare` / `missing_blocks`） | 单向 pull 无漏报发现能力 → 盲点长期隐形 | Claude Code `/context` 显式列出各段占用 |
| D6 | **双账本记账**（估算账 + 真实账） | 三把尺子 1.7x 漂移已证实；`unaccounted_tokens` 让黑洞可量化 | Harness 层「每个 token 有归处」 |
| D7 | **不变量断言化**（配对 / 思考链 / 前缀稳定） | 9-29 两起 400 的修复本就等于业界不变量，但只是补丁 | Claude Code 三级压缩的三条硬性保护 |
| D8 | **阶段化装配**（`phase`） | 治理器需知道「本阶段该有哪些块」才能校验与定策 | OpenAI Agents SDK 按 agent 角色定义上下文清单 |

**三条纪律不变**（守住既有资产）：
- **零状态**：水位现算，无 `assess` 历史；
- **零业务语义**：只认通用形状（token / 层 / 配对结构），纯度守卫继续生效；
- **零特权**：预算与裁剪只走 `core.tokens`，不碰内核内部。

## 七、不变量与风险

### 7.1 必须永远成立的不变量（断言化后不可绕过）

1. **配对完整**：任何裁剪/清除后，`role=tool` 必有前置 `assistant.tool_calls`（9-28 实测 400 的根因）；
2. **思考链完整**：thinking block 不得被截断或剥离（9-29 实测 400 的根因）；
3. **前缀稳定性可测**：任何改变历史字节的动作必须被记录并可审计（缓存经济学的前提）；
4. **预算守恒**：`Σ 块用量 + attachments + unaccounted = 输入预算`（消除黑洞）。

### 7.2 主要风险

| 风险 | 概率 | 缓解 |
|---|---|---|
| 拆分引入回归 | 中 | 门面接口冻结 + 36 项测试 + 逐字节对拍；四单元先做「纯搬迁」（行为零变），再加能力 |
| 策略扩展破坏纯度 | 中 | 回调注入（D2）+ 纯度守卫测试持续拦截（本次已被拦过一次，机制有效） |

## 附录 B：术语

| 术语 | 含义 |
|---|---|
| **能力窗口** | 模型单次请求物理上限（1M） |
| **经济窗口** | 治理器用于判断压缩时机的基数（`working_window_tokens`），与能力窗口解耦 |
| **清除 vs 压缩** | 清除 = 客户端/服务端移除历史条目（不改写其余字节）；压缩 = 重写历史为摘要（必然破坏前缀缓存） |
| **回本步数** | 压缩付出的 miss 罚金，需后续多少步的 hit 节省才能补回（实测恒 2.7 步） |
| **unaccounted** | 扣了预算但未登记为块的部分（现行：tools schema），记账盲区 |
