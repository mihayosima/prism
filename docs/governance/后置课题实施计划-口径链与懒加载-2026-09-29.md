## 1. 背景与目标

一期/二期解决了「单次窗口多大」（治理器）、「总量超限怎么办」（预留+预警+收尾）、「参数为什么丢」（截断防护）三个问题。本计划处理剩余的结构性欠账：

1. **估算与真实计费存在 ~30% 口径差**（当晚估算封顶 2 万 vs 真实 prompt 2.6 万）——治理器按估算裁，账单按真实记，灰色地带无人管辖；
2. **react 链随 run 死亡**——「继续」只能靠重读文件或烧 token 重推（当晚第 10-12 章蒸发的放大器）；
3. **工具定义全量灌输**——每次请求携带全部工具完整 schema（统一账本只把它「计入」预算，没「减掉」它）；
4. **MCP 工具返回/参数无设计约束**——「不要把完整内容放进上下文」目前只靠护栏兜底，没有源头规约。

**总目标**：把「隐形 token」的三类来源（口径差、链重推、schema 开销）从无人管辖纳入可计量、可调度、可约束的轨道。

## 2. 四个课题的设计

### 课题一 F：真实计费口径闭环（小 · ~60 行 + 6 测试）

#### F1 校准因子（核心）

**现状**：`sys/llm.py` post-call 已捕获真实 usage（一期 S6），budget 对账已用真实值；但**治理器装配**与**budget 预借**仍用 `estimate_tokens` 裸估算——2 万估算窗口真实可到 2.6 万。

**设计**：
- `sys/llm.py` post-call 维护**按模型分桶的校准系数 EWMA**：`ratio = Σ真实tokens_in / Σ估算tokens_in`（指数滑动平均，α≈0.2），写入状态键 `StateKeys.LLM_COST_RATIO`（dict[model, ratio]，新常量，SSOT 登记）；
- 消费方两处，均只**读状态键**（零内核改动、零直连）：
  - `sys/budget.py` `_pre`：`est *= ratio` 后再判断/预借（预借口径贴近真实，超限判定提前且准确）；
  - `plugins/context`（治理器）：装配预算 `input_budget` 换算时乘 ratio——**折衷方案**：不改 core/contract，由治理器在 `react_budget` 查询接缝处读取（若治理器不可达则因子退 1.0，行为不劣化）；
- 因子夹紧 `[0.5, 3.0]`，样本 < 5 次时不启用（防冷启动抖动）；`agent.budget.cost_calibration`（bool，默认 **on**）总开关。

#### F2 账单 run_id 落库（顺手，~15 行）

**现状**：`agent_budget_log.run_id` 全为 NULL，账单无法按运行归组（当晚只能靠时间戳切分）。

**设计**：`agent_budget_log` 缺列自动迁移（`ALTER TABLE ADD COLUMN`，budget 自管表）；`ctx.llm.complete` 增可选 `run_id` kwarg，react 循环与 chat 委托路径传入；post-call 入账时落列。历史 NULL 数据不回填（如实留白）。

#### F3 口径差遥测（~10 行）

post-call 估算与真实差值超 25% 时发 `agent/llm/cost-drift` 事件（durable，目录注册）——口径漂移可被事后回放，不再靠对账发现。

### 课题二 P：链持久化与「继续」低成本续接（中 · ~120 行 + 8 测试）

#### P1 run 收尾链存档（产物外置的延伸）

**设计**：run 结束（正常/触顶均含）时，把**已治理的折叠链**（`_prepare_chain` 产物，天然有界）存入工作记忆 checkpoint（键 `react_chain:{session_id}`，保留最近 1 份）+ durable `agent/react/archived` 事件（带条目数/token 量）。与一期 C 的 `progress` 摘要互补：摘要是给**长期记忆**的结论，链存档是给**工作记忆**的过程。

#### P2 「继续」续接

**设计**：`ReactLoop.run` 增 `resume: bool = False` 参数；`sys/chat.py` 识别「继续/接着写/continue」类续接意图（或用户显式指令）时传 `resume=True`——从工作记忆取回上轮链存档作 `task.chain` 初始（再走 `_prepare_chain` 治理，超限部分正常折叠），prior 照旧。模型直接「知道进度」，不再靠重读文件恢复。

**防串**：存档键带 session_id；`resume=True` 但无存档 → 如实回退现状（不伪造）。

#### P3 前缀稳定与缓存计量（评估性，~20 行）

DeepSeek 有前缀缓存（前缀命中部分计价约 1/10，usage 返回 `prompt_cache_hit_tokens`）。本仓不动发送结构，只做两件事：
- **保前缀**：窗口块顺序已固定（system→prior→prompt→chain），核查治理器装配不做破坏前缀稳定的重排（只验证，不改）；
- **计量**：post-call 把 `prompt_cache_hit_tokens` 一并记入账单明细列（与 F2 同一迁移），为后续「是否值得做真·增量重发」提供数据。

**明确不做**：真·增量重发（客户端侧 delta 发送）依赖服务商 API 形态，风险/收益比差，仅以 P3 数据说话，暂不立项。

### 课题三 L：懒加载元工具（中 · ~100 行 + 8 测试）

#### L1 目录预览 + 元工具（react 私有投影）

**设计**：`agent.react.lazy_tools`（bool，默认 **off** 灰度）。开启后 `visible_tools` 投影变为：
- 常规工具只发**目录卡**：`{name, 一行描述, 参数名列表, risk}`（无完整 JSON Schema，预计省 60-80% schema 开销）；
- 追加两个 react 私有元工具（注册进 `ctx.tasks`，owner=react）：`tool_search(keyword)`（按关键词过滤目录）、`tool_load(names)`（把工具完整 schema 加入本 run 的 `TaskContext.loaded` 集，观察回灌确认）；
- 循环每步按 `loaded` 集组装 native tools：`元工具 + loaded 完整 schema 工具`。

#### L2 约束与联动

- `loaded` 上限（默认 12，配置化 `react.lazy_tools_max`）防膨胀；超限 `tool_load` 如实拒绝并列已加载清单；
- plan 只读模式照常生效：目录卡先按 `risk==read` 裁剪（复用既有 `visible_tools` 逻辑，L1 在其后叠加）；
- approval 零感知：guard/approval 挂在 `TASKS_PRE_EXECUTE`（真实 invoke 闸门），加载只是**可见性**变化，不触碰执行面。

#### L3 风险点（明示）

- fixture provider 需适配元工具路径（离线测试确定性）；
- 模型可能「不加载就幻觉调用」——幻觉调用会得「未知参数/工具目录未加载」错误观察，可自纠（与 B 方案同路）；不设硬拦截（保持失败即观察纪律）。

### 课题四 S：MCP 工具设计规约（小 · 纯文档 + 对照表）

**设计**：新增 `docs/specification/MCP工具设计规约-2026-09-29.md`：
- **write 类**：返回**短确认**（目标路径 + 字节数 + 状态码），禁止返回全文回显；
- **read 类**：必须支持 `maxTokenBudget` 或 `limit/offset`（MCP 游标分页）；大产物返回 ResourceLink/引用，按需拉取；
- **错误**：缺参报错必附必填清单（与一期 B 对齐）；截断类错误附分片指引（与一期 E 对齐）；
- **对照表**：windows_mcp / playwright / 内置工具逐个标记「合规 / 欠账」，欠账项列改造建议但**不强制存量改造**——新工具强约束，存量按改造收益排期；
- 后续可选（不进本计划）：`guard_source` 增 write 返回体积软告警。

## 6. 机制详解（v1.1 应用户要求补）

### 6.1 F1 校准因子：为什么要它，它怎么转

**问题的本质**：全系统有「两把尺子」。治理器裁窗口、budget 预借判定，用的都是 `estimate_tokens`（ASCII÷4、中文×0.75 的**字符启发式**）；而服务商按**真实分词**计费。启发式对代码/JSON/混合文本系统性**低估**——当晚实测：估算封顶 2 万的窗口，真实 prompt_tokens 到 26,127，偏差约 30%。这 30% 意味着：治理器以为「窗口只装了 2 万」，实际每次请求都在按 2.6 万烧钱；预算按估算预借，账面对账时才被真实 usage 拉回——**判定时刻是准头最差的时刻**。

**转法（闭环）**：服务商每次响应都带真实 usage（一期已捕获）。让这个真实值**反过来修正尺子**：

```
每次 LLM 调用完成
   └→ post-call：ratio_本次 = 真实tokens_in ÷ 当次估算tokens_in
        └→ EWMA 平滑：ratio_模型 = 0.8×旧值 + 0.2×ratio_本次   （按模型分桶）
             └→ 写入状态键 LLM_COST_RATIO[model] = ratio_模型
                  └→ 下一次调用的「判定时刻」：
                       budget._pre：est × ratio_模型 后再判断超限/预借
                       治理器装配：input_budget 换算时 × ratio_模型（窗口真实装得更少、更准）
```

- **为何 EWMA 而非即时值**：单次 ratio 抖动大（一条含大 JSON 的消息 vs 一条纯中文），滑动平均稳住长期偏差；α=0.2 约十几收敛到新文本形态。
- **为何夹紧 [0.5, 3.0]**：防异常样本（如一条几乎全转义的参数）把因子打到极端，导致窗口被裁到不可用或彻底放开。
- **为何样本 <5 不启用**：冷启动前几调用因子无统计意义，宁可用裸估算（现状）也不引入抖动。
- **彻底作用的含义**（用户决议）：两个消费点都乘因子。只改 budget 是「账算得准」；改治理器才是「窗口装得准」——后者直接决定真实请求体积，是治本的那个。
- **设置页形态**：`成本护栏` 卡片新增「口径自校准 cost_calibration」开关（默认 **on**）。关闭 = 回到裸估算现状。

### 6.2 P 链持久化：让「继续」不再是重新开始

**当晚发生了什么**：写小说 run 结束后，Think/Act/Observe 链随 TaskContext 丢弃（设计如此，防记忆污染）。用户说「继续」，新 run 对「写到第几章、人物状态、文件在哪」一无所知——只能靠 PowerShell/FileSystem 大量读盘恢复现场，每轮冷启动 8k token 里大半是「重新搞清楚状况」；而第 10-12 章因漏参没落盘，读也读不回来。

**P1 存档**：run 收尾时把**已治理的折叠链**（`_prepare_chain` 产物——注意这天然有界：老观察已折叠、老 act 大参数已折叠）写入工作记忆 checkpoint，键 `react_chain:{session_id}`，只留最近一份。它是**过程**，与一期 C 的 progress 摘要（**结论**，进长期记忆）互补：摘要说「做了 1-9 章」，链存档保「怎么做的」。

**P2 续接**：`run(resume=True)` 时把存档取回作 `task.chain` 初始值（再过一遍 `_prepare_chain` 治理——存档本身也老化，超限部分照常折叠）。模型第 1 步就「看得见」上轮全过程。识别方式（决议暂定轻量）：`agent.react.resume_keywords` 词表（默认「继续/接着/continue/续写」）匹配则传 `resume=True`；无存档如实回退现状，不伪造。

**P3 缓存计量**：DeepSeek 前缀命中部分约 1/10 计价，usage 带 `prompt_cache_hit_tokens`。本仓只把该列记入账单（与 F2 同一迁移）+ 验证装配顺序稳定，**不动发送结构**——是否值得做真·增量重发，让数据说话。

### 6.3 L 懒加载：schema 开销的「按需装载」

**现状**：每次请求携带全部工具完整 JSON Schema（当晚 24 次重发，每次都全量带上 windows_mcp/playwright 全套定义）。统一账本已把这份开销**计入**预算，但没**减掉**它。

**机制**：`lazy_tools` 开启后，请求里的工具分两层——
1. **目录卡**（恒在）：每个工具只有 `{name, 一行描述, 参数名, risk}`，无 JSON Schema——模型靠它知道「世界上有哪些工具」；
2. **完整 schema**（按需）：模型调 `tool_load(names)` 元工具 → 该 run 的 `loaded` 集合增补 → 后续步骤的 native tools 里这些工具带完整参数定义。`loaded` 上限 12 防膨胀。

**关键边界**：加载只改变**可见性**，不触碰**执行面**——真实调用仍走 `ctx.tasks.invoke`，guard/approval 的 `TASKS_PRE_EXECUTE` 闸门、plan 只读裁剪（目录卡先按 risk 裁）全部原样生效。模型不加载就幻觉调用 → 得「目录未加载」错误观察，可自纠（失败即观察纪律，不设硬拦截）。

**设置页形态**：「插件能力」卡片新增「工具懒加载 lazy_tools」开关（默认 **off**——行为变化最大的一项，灰度验证后再议默认值）。

### 6.4 三批次的依赖与顺序

批次一（F+S）先行：校准因子是 P3 缓存计量的口径基础，run_id 落库是 P1/P2 存档事件的归组键；批次二（P）次之；批次三（L）最后（行为变化最大，放末尾灰度）。S 规约文档零风险，随批次一交付。
