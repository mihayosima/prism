## 1. 事故回顾

2026-09-28 21:54–21:59，用户请求「写 3 万字小说，分步完成」。三轮 react 共 27 次 LLM 调用、消耗 435,255 tokens（含被拒的第 28 次预估，合计 ~49.9 万），撞穿 50 万预算闸；第 10-12 章因工具调用参数丢失未落盘；最终以原始报错 `（已达执行上限：模型调用被拒：能力未就绪: agent.llm.complete（预算超限 spent=498748+est=15597>500000））` 收场，无总结、无进度交代。

**账单数据**（agent_budget_log）：三轮 tokens_in 分别 38.6 万级；单笔 tokens_in 峰值 26,127；单笔 tokens_out 峰值 8,244（贴近服务端默认生成上限）。

## 2. 根因分析（四项，均已代码定位）

| # | 根因 | 定位 | 性质 |
|---|------|------|------|
| R1 | **总量维无调度**：治理器管单次窗口（≤2 万估算），预算插件只会耗尽后掐死；「次数 × 窗口」的乘法无人过问，也无 80% 预警 | `sys/budget.py`、`plugins/react/loop.py` | 结构性 |
| R2 | **预算耗尽收尾粗暴**：硬拒绝路径直接输出原始报错；且收尾 finalizer 自身需 LLM 调用、同样会被拒（死结） | `loop.py:314-331` | 缺陷 |
| R3 | **缺参报错弱**：`缺少必填参数 'mode'` 不附必填清单，模型自纠全靠猜 | `sys/tasks.py:90` | 缺陷 |
| R4 | **生成侧截断静默丢参**（本计划核心发现）：请求未设 `max_tokens` → 服务端套用 deepseek-flash 非思考模式 8K 默认生成上限 → 长参数（章节全文）生成被 `finish_reason="length"` 腰斩 → 本仓读到 finish_reason 仅用于 break、不检查 → 残缺 JSON 在 `_wire_call` 被 `except: args = {}` 静默吞掉 → 校验报「缺少 mode」误导表象 | `sys/llm.py:183-187`（未设 max_tokens）、`:275-276`（finish_reason 不检查）、`:136-139`（静默吞） | 缺陷（三层空白叠加） |

**佐证**：当晚 run 2 step 5、run 3 step 1-2 的多次 `is_error: true` 与最终「漏 mode」同构，疑为同一死因反复发作；`finish_reason` 未落库，暂无法逐笔回放确认（本期遥测补齐后可验证）。

## 3. 修复方案

### 3.1 方案 A：预算收尾预留额度（一期）

- **问题**：预算耗尽时 finalizer 也要调 LLM → 同样被拒 → 只能输出原始报错（R2）。
- **设计**：budget 插件新增「收尾预留槽」——总预算的末段（默认 16,000 token，配置化）仅供 finalizer 使用，正常步骤不可侵占；硬拒绝时 finalizer 借预留额度产出体面收尾；预留亦耗尽则退回确定性文案（不调 LLM）。
- **改动**：`sys/budget.py`（预留槽位与设置登记）、`plugins/react/loop.py`（hard 分支改走 finalizer）。
- **规模**：约 25 行 + 3 个测试。

### 3.2 方案 B：缺参报错附必填清单（一期）

- **设计**：`validate_kwargs` 报错改为 `缺少必填参数 'mode'（mcp.windows.FileSystem 必填：mode/path/content，可省：encoding）`；所有工具自动受益。
- **改动**：`sys/tasks.py` 一处。
- **规模**：约 8 行 + 2 个测试。

### 3.3 方案 C：收尾失败摘要 + 进度快照（一期）

- **设计**：
  1. finalizer 输入附带 `tool_trace` 与最后一次 `is_error` 观察摘要；确定性兜底文案列出「已完成 N 步 · 最后失败于 X · tokens 花费 Y」；
  2. run 收尾时把「完成事项 / 未完成事项 / 产物路径」并入 `memory.remember` 载荷沉淀进长期记忆——后续「继续」不再依赖重读文件（当晚三轮冷启动 prior 仅 7-8K，但过程知识全靠烧 token 重推）。
- **改动**：`plugins/react/loop.py`、`sys/chat.py`（remember 载荷）。
- **规模**：约 30 行 + 3 个测试。

### 3.4 方案 E：生成侧截断防护（一期，核心）

- **设计**（全部在 `sys/llm.py`，把三层空白逐一堵上）：
  1. **显式设置 `max_tokens`**：payload 增加配置化上限（默认 8,192，登记 `agent.llm.max_tokens`），把「别人文档里的默认值」变成「自己代码里可查可改的决定」；
  2. **finish_reason 检查**：流式（`:275`）与非流式（`:206`）两路均记录；为 `length` 且带 tool_calls 时在返回结果打 `truncated: true`；
  3. **`_wire_call` 禁止静默吞**：JSON 解析失败保留原始串并标记 `truncated`，下游报错明确写「模型输出被截断」；
  4. **截断报错附自纠指引**：「单次写入过大，请分片（每章拆 2-3 段追加写入）」——与方案 B 配合形成自纠闭环。
- **规模**：约 30 行 + 4 个测试（含流式 fixture 回放 `length` 场景）。

### 3.5 遥测：窗口统计与 finish_reason 落库（一期，顺手）

- `_win_stats` 经既有 `_emit_window` 接缝落 `agent/context/governed` 事件（接缝已在，补调用点）；`finish_reason` 随 LLM 结果记入预算日志事件。
- **规模**：约 8 行 + 1 个测试。**价值**：下次事故可逐笔回放截断与裁剪决策，不再靠 tokens_in 曲线反推。

### 3.6 二期：总量维调度与瘦身

- **D1 预算预警**：budget 在 80%（配置化阈值）时发 `agent/budget/warning` 事件；react 订阅后向后续步骤 prompt 注入「预算紧张，尽快收束并总结」。插件间走事件总线，零直连。约 40 行 + 3 测试。
- **D2 act 大参数折叠 + 产物外置**：`_prepare_chain` 目前只折叠 observe 条目（`loop.py:339`），act 条目里的章节全文参数超 `keep_recent` 后仍全量重发——当晚 24 次重发的最大头。改为：更老 act 条目的大参数折叠为「向 X 写入约 N 字」摘要，完整参数顺手存入工作记忆 checkpoint（`wm.checkpoint` 接缝已在循环内 `loop.py:305`），按引用找回。约 50 行 + 4 测试。
- **D4 工具定义瘦身**：第一步做 description 压缩为单行（纯数据，风险低，约 20 行）；第二步「懒加载元工具」（search_tools/load_tools）涉及插件协议改动，列后置课题。

### 3.7 后置课题（不在两期内，登记备查）

1. D3 增量重发 / react 链持久化（结构级）；
2. 估算 vs 真实计费口径差闭环（当晚实测估算 20K 封顶 vs 真实 26K，偏差约 30%）——需接入真实 usage 反馈校准 `estimate_tokens`；
3. 懒加载元工具（D4 第二步）；
4. 「返回摘要 + 引用」写入 MCP 工具设计规约（新工具强约束：write 类返回短确认、read 类支持 maxTokenBudget/分页）。

## 5. 风险与回滚

- **A 预留额度**：预留段可能被正常步骤抢占的竞态——预留槽在 budget 内独立记账，先于步骤判断；风险低。
- **E 显式 max_tokens**：显式值若低于服务端默认会「提前截断」——默认取 8,192（与服务端非思考默认持平），且配置化可调；thinking 模式口径（64K）后续按 `reasoning_effort` 细化。
- **D2 act 折叠**：折叠过度可能让模型丢失已写内容上下文——仅折叠超 `keep_recent` 的更老条目，且完整参数有 checkpoint 引用可回取；回归用当晚场景回放验证。
- **回滚**：各方案独立开关（配置化），任一异常可单独停用回到现状；不与另一会话未提交的「统一账本」改动耦合，合并前需过一遍冲突检查。
