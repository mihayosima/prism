## 二、验证通过的解耦面（通读实证，非抽样）

### 2.1 分层依赖方向 —— 全绿 ✅

| 规则 | 结果 | 证据 |
|---|---|---|
| core 不反向依赖 sys/plugins | ✅ | `test_agent_purity.test_core_never_imports_sys_or_plugins` + 全量 import 扫描 |
| sys 不依赖业务插件 | ✅ | sys 层仅 import `agent.api`（+ 同层/tables/过渡兼容层 `agent.core.audit`，见 P3-4；方向向下不违规） |
| 插件之间零横向 import | ✅ | 8 个插件互相零引用 |
| 插件不依赖 sys 实现 | ✅ | mcp_client 下沉 core 后，plugins→sys 边已不存在 |
| 插件不绕过 api 直连 core | ✅ | 8 个插件全部只 `from agent.api import …` |

### 2.2 装配耦合（opt-in 语义）—— 通过 ✅

- 全部插件 `inject` 只声明内核服务（db / llm / events / tasks），**无任何插件声明由另一插件提供的服务**——任一目录插件停用都不会引发 `MissingDependencyError`（`test_inject_never_couples_two_plugins` 守卫）。
- `profiles.build_agent` 目录插件显式 opt-in（不传 plugin_mgr 即封闭），测试/无头入口不会误拉真实子进程。

### 2.3 跨插件依赖接缝 —— 模式统一、降级完备 ✅

接缝模式高度一致（这是本代码库最值得肯定的设计纪律）：

| 插件 | 接缝 | 契约位置 | 降级路径 |
|---|---|---|---|
| react | `ctx.get("react.reasoner/actor/observer/finalizer")` | 组件 Protocol（components.py） | 内置默认实现 |
| memory | `ctx.get("memory.store/extractor/search")` | MemoryStoreLike 等 Protocol | 内置实现 |
| context | `ctx.get("context.governor")` | GovernorLike（protocols.py） | from_config 构造 |
| short_term | 门面 `ShortTermMemory` 统一出口 | 门面方法签名 | 消费方各自兜底 |
| 消费方（chat/react） | `ctx.has()/ctx.get() or 默认` | — | HISTORY_LIMIT 硬裁 / 空底座 / 单步回退 |

实证亮点：
- `chat.send` 对记忆四层 + react **全部软感知**，每条缺失路径都有显式降级；`reset` 在无短期记忆插件时**事件照发**（预算清零语义不受插件启停影响）。
- `short_term → context` 单向软依赖：compactor 无治理器时 `kept = raw`（不压缩），反向（context→short_term）不成立。
- `work_memory` Redis 不可用自动降级进程内 dict，委托调用全量吞异常，绝不拖累主链路。

### 2.4 契约 SSOT 体系 —— 完整且有守卫 ✅

四类隐式契约全部常量化并配 AST 守卫：

1. **服务键**（`Services`）：`test_services_contract` 三项——provides/inject 字面量 ∈ Services∪ALLOWLIST、ctx.get 裸串禁令、死常量检测；
2. **事件名**（`Events` + `EVENT_MODE` + `REQUIRED_SUBSCRIBER_EVENTS`）：required seam 必为 waterfall 的**导入期自洽断言** + 装配期接线 fail-fast（`_verify_event_wiring`）+ 运行期 waterfall 守卫，三处同源杜绝漂移；
3. **ctx.state 共享键**（`StateKeys`）：字面量只许出现在 state_keys.py（dict 键豁免设计合理）；
4. **提示词标记**（`MARK_*`）：`<!--` 字面量只许出现在 api.py。

### 2.5 容器机制 —— 扎实 ✅

拓扑装配（Kahn）失败回滚、capture/release 区间对称回收、D-3 服务键/插件 id 唯一、`_awaitable` 诚实边界（apply/start 非 async 即拒）、teardown 聚合错误不中断卸载。

### 2.6 数据层归属（chat 收口）—— 修复成果保持 ✅

`agent_messages` / `agent_session_summaries` 读写全部收口在 `plugins/short_term/store.py`（唯一归属者），chat 侧经门面 `ctx.get(Services.SHORT_TERM)` 调用、零 SQL；`reset` 级联清摘要（事务内），"已删历史摘要残留"缺陷已修。

## 三、发现的问题

### P1｜守卫盲区 + 数据层耦合：`run/chat.py` 直连 `agent_memories`

**位置**：`agent/run/chat.py:607-610`（`/api/memory` 端点）

```python
rows = await c.root.db.query(
    c.root, "SELECT id, kind, content, ... FROM agent_memories ..."
```

`agent_memories` 表 owner 是 `plugins.memory`，run 层（UI）绕过插件接口直连读表——与上一轮已修复的"chat 直连 agent_messages"同类问题（本处为只读展示，危害较小，但破坏归属纪律）。

**为什么守卫没拦住（三层失守，这才是重点）**：

| # | 失守点 | 位置 |
|---|---|---|
| 1 | `_py_files()` 只扫 `core/sys/plugins` + api.py，**`run/` 完全不在扫描范围** | `test_plugin_decoupling.py:37` |
| 2 | `TABLE_OWNER` 登记的是**幻影表名 `agent_memory`**，实际表名是 `agent_memories` | `test_plugin_decoupling.py:181` |
| 3 | 存在性断言用**子串匹配** `assert t in tables_py`——"agent_memory" 恰是 "agent_memories" 的子串，守卫空转通过 | `test_plugin_decoupling.py:227` |

**修法建议**（已按核实结论修订）：
1. `TABLE_OWNER` 改为真实表名 `agent_memories`；
2. 存在性断言改为按 DDL 精确提取表名集合比对，杜绝子串假阳性；
3. `_py_files()` 纳入 `run/`；同时 SQL 检测需升级为 **AST 字符串字面量级**提取——行级启发式会被跨行字符串拼接（`SELECT` 与 `FROM agent_memories` 不同物理行）绕过（本报告初版未发现此第四层失守，修复时经实测补上）；
4. `KERNEL_TABLES` 中 **`agent_plugin_state` 亦为幻影**（它是 JSON 状态文件，不是表），与 `agent_runs` 一并清除（用户核实补充）；
5. `/api/memory` 收口：`:605` 已调用 `ctx.memory.stats()`，直连的仅剩 `rows` 查询；memory 插件现无列表接口（recall 需打分且会 touch），故应**为插件新增只读 list 接口**（`list_recent`），而非简单改用 stats（用户核实修订）。

### P3｜结构性接缝：目录插件双命名空间

`PluginManager` 以 `agent_plugins.*` 文件路径加载目录插件（`_load_module`），与 `agent.plugins.*` 常规导入路径下的类**身份不同**——`isinstance` 失效，须用 `type(x).__name__` 比较。此坑已在开发中踩过两次（记录于工作日志）。这是"避免 import 依赖"的有意取舍，但目前只靠踩坑记忆规避。

**建议**（二选一）：① 在 `plugin_manager` 模块 docstring 与架构文档显式声明该语义；② loader 在 `sys.modules` 中同时登记 `agent.plugins.<名>` 别名，使两种路径解析到同一模块对象（需评估与重复加载防护的相互作用）。
