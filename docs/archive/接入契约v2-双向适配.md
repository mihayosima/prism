## 0. 结论先行

1. **两套运行时，双向适配**：引擎与 Agent 是**两个独立的运行时**——各自容器、各自数据库、各自调度器、各自 ai seam。中间隔一层**双向适配器**，适配器在各自侧以**插件**形态存在。
2. **零共享库**：Agent 与引擎不共享任何 Python 库；契约（消息形状）以**本文档 + 双端同一份 JSON 参考夹具**为唯一事实源，各侧独立实现，schema 带版本号协商，**宁可不兼容也不静默错配**。
3. **交换面只有两类原语，且双向**：**数据只读面**（读对方的数据，不碰对方表）+ **任务面**（`run(ctx, **params)` 一个约定两个方向：agent 能调度引擎干活，引擎也能调用 agent）。
4. **独立性的硬证明 = 可自举**：Agent 脱离引擎、只用自己的离线夹具就能把工具循环跑起来、离线确定性测试全绿。接入引擎只是"把夹具实现换成引擎提供的数据/任务提供方"，**配置替换，不是重写**。
5. **引擎机制层已提供全部底牌**：`@plugin` 协议、`TargetRegistry`（`run(ctx,**params)` 约定）、`CommandRegistry`（owner + schema 校验）、`ctx.effect` 对称卸载、引擎=纯机制纯度守卫。**桥只需要"翻译 + 白名单"，不需要新机制。**

> 一句话：**接入 = 两侧各装一个桥插件 + 冻结一小份交换契约；桥是一等公民，停了桥，两侧照跑、只是互相看不见。**

## 1. 总览（两套运行时 + 双向适配）

```
┌─ 引擎运行时（独立 · 自举照旧）────────────┐        ┌─ Agent 运行时（独立 · 可自举）────────────┐
│  Engine + EngineKernel + ME1_PROFILE      │        │  agent 容器                             │
│  + 业务插件 + ConsoleSkin                 │        │  + ToolLoop/Memory/Budget/Guard/Ai      │
│  DB: data/intel.db（引擎侧 namespace）    │        │  + Skills(20 策略) + Selector            │
│  调度: ctx.scheduler / 命令: ctx.commands │        │  DB: agent.db（agent 独立 namespace）    │
│  ai: 引擎侧 seam（仅供引擎侧插件）        │        │  调度/命令/内存: agent 自持              │
│                                           │        │  ai: 大脑自持（AgentProvider 契约）      │
│  ↑ 桥：engine_agent_bridge（@plugin）     │        │  ↑ 桥：agent_engine_bridge（@plugin）    │
└───────────────┬───────────────────────────┘        └────────────────┬────────────────────────┘
                │       双向适配器（冻结契约 · 可插拔传输）            │
                └── 数据只读面(both) · 任务面(both) · 事件面(可选) ─────┘
```

三层语义：

1. **运行时层（各自独立）**：一切大脑、循环、数据、任务号令都在自己侧。引擎对 agent 的认知止于"桥 + 契约我发布的面"；agent 对引擎的认知止于"桥 + 契约它发布的面"。
2. **适配器层（桥 = 一等公民插件）**：两侧各一个 `@plugin`，只翻译、不实现业务；可独立启停。
3. **交换面层（冻结契约）**：数据面只读、任务面双向、事件面纯数据可选。任何一侧不响应，绝不 hold 对方本地稳定性机制。

## 2. 五项已决决策（用户拍板，逐条落地）

| # | 决策 | 落地含义 |
|---|---|---|
| 1 | **不共享库，agent 可独立运行** | 双端零共享 Python 包；agent 有自己的容器/DB/调度/ai/夹具，可自举。契约 = 文档 + 双方各自落地的独立实现 + 同一份 JSON 参考夹具（防漂移，见 §10）。 |
| 2 | **双向适配，适配器以插件接入** | 引擎侧桥是引擎容器里的 `@plugin`，agent 侧桥是 agent 容器的插件。各自只 import `from engine.api import plugin`（引擎侧）/ `from agent.api import plugin`（agent 侧），**不 import 对方实现**。 |
| 3 | **双方互读数据；agent 可调度引擎；引擎可调用 agent** | 数据只读面双向（§5）；任务面双向（§6）——agent→引擎 派活/注册持久任务，引擎→agent 调用其任务，两条路复用 `run(ctx,**params)` 同一约定。 |
| 4 | **ACL 按推荐** | `engine.ping` + 只读命令对 agent 开放；浏览器写/引擎内部命令默认禁止；越权诚实拒绝（§7）。 |
| 5 | **独立** | agent 表独立 DB 文件 + 独立 namespace；agent 生命周期独立；卸载一侧不影响另一侧（§12）。 |

## 3. 装配模型（物理装载：谁住哪、怎么装上）

### 3.1 代码位置

```
RPA/                         ← 引擎仓库：零改动（不新增引擎核心代码）
选品agent/                   ← Agent 工程（本目录）：agent 运行时 + 两侧桥的代码都住这
```

- **agent 内部一切**（容器/ToolLoop/Memory/Budget/Guard/Ai/Skills/Selector/agent.db）：只在 `选品agent/`，永不 import `engine.*`。
- **引擎侧桥 `engine_agent_bridge`**：代码住在 `选品agent/`（随 agent 包交付），但**只 import `from engine.api import plugin`**，且只依赖引擎服务键。它是"引擎容器里的一个插件"，代码却属于 agent 包——**引擎仓库不被污染，桥可随 agent 卸载**。
- **agent 侧桥 `agent_engine_bridge`**：代码住在 `选品agent/`，只 import `from agent.api import plugin`，只依赖 agent 服务键。

### 3.2 装载路径（不进 `PluginManager` 扫描）

引擎的 `PluginManager` 只扫 RPA 仓库内 `plugins/`，且用 `meridian_plugins.<目录名>` 模块名、约定"单文件优先"。agent 是组合体，**不走这条目录发现路**，避免 `sys.modules` 命名/单文件约束两处硬伤。改用**显式装配**：

```
引擎启动入口（run/*.py 或独立 launcher）：
  1) 读配置/flag：--agent <选品agent 路径>   （未给 → 纯引擎照跑）
  2) import agent 包的 engine 侧桥模块 → 得到 engine_agent_bridge（@plugin）
  3) profile_plugins += (engine_agent_bridge,)   → Engine 容器装配
  4) 引擎侧桥 apply 时按契约读取引擎业务数据、注册白名单任务与 ACL
```

agent 自己独立启动走 `python -m run.agent`（选品agent/ 内入口），装配 agent 容器 + agent_engine_bridge。

> ⚠️ 硬约束：agent 包目录**不得被引擎 `PluginManager` 的 `plugins/` 扫描覆盖到**（否则 `meridian_plugins.<名>` 命名冲突）。agent 目录不在 RPA 下，天然满足。

### 3.3 何谓"引擎作为插件接入 Agent"（对本模型的字面兑现）

agent 容器的宿主契约只认**一组键**（自己的 `db/scheduler/tasks/commands/events/ai`）。自举时这些键由 agent 自己的离线夹具填充；与引擎合体时，agent 通过桥把**引擎发布的数据面/任务面映射到自身的键**。**同一个 agent，两种数据来源，只是 provider 不同**——这就是对称：引擎的能力以插件形式进入 agent 的上下文，agent 的能力以插件形式进入引擎的容器。

## 4. 双向适配器（两侧桥插件）

| 项 | 引擎侧桥 `engine_agent_bridge` | agent 侧桥 `agent_engine_bridge` |
|---|---|---|
| 装入容器 | 引擎容器 | agent 容器 |
| 代码位置 / import | 选品agent/ 交付 · `from engine.api import plugin` | 选品agent/ · `from agent.api import plugin` |
| inject | 引擎键（`db · targets · scheduler · commands · events`，闭集） | agent 键（`tasks · events` 等，agent 自定） |
| provides | `peer_engine`（引擎发布给 agent 的把手） | `peer_agent`（agent 发布给引擎的把手） |
| 职责 | 读引擎业务数据→组织成冻结 facet；把白名单任务/命令暴露为任务面；执行 ACL；把 agent 侧 facet/任务"接进来" | 对称：把 agent 的 picks/scores/skills 组织成 facet；暴露 agent 任务；ACL 对称 |
| 生命周期 | `ctx.effect` 对称卸载；请求带超时；**永不阻塞引擎调度/热路径 await 对侧长活** | 对称 |

桥是**纯翻译器**：不含任何选品词、不含任何站点选择器、不含业务判断。含了，就是污染，回退重写。

## 5. 交换面① 数据只读面（双向）

只读、纯数据、**不碰对方表**。发布方在**自己侧**把内部数据组织成**冻结 schema**；消费方只按 schema 读。

### 5.1 查询协议（两向同构）

```
ReadQuery {
  facet: str,          # 面名（见下）
  schema_id: str|None, # 调用方认识的面版本；None = 取发布方当前版
  filter: dict,        # 轻量过滤（facet 各自定义允许的键）
  limit: int
}
ReadResult {
  facet, schema_id,    # 回显：实际交付的面版本（用于版本协商）
  rows: list[dict],    # 行结构＝该 schema_id 冻结的列集
  truncated: bool,     # 达到 limit 截断标注（诚实）
  error: str|None
}
```

### 5.2 版本协商（防漂移的第一道闸）

- 每次响应**回显 `schema_id`**；消费方校验 `schema_id ∈ 它认识的集合`，不认识 → **显式拒绝**（诚实报错，绝不静默错配）。
- 双方各放一份**同一 JSON 参考夹具**（字段名/类型/示例值逐字一致），是跨侧对齐的唯一事实源（见 §10）。

### 5.3 agent 侧发布的 facet（引擎可读）

| facet | 内容 | 冻结列（草案，随 agent 架构定稿） |
|---|---|---|
| `agent/picks` | 当前短名单 | `product_id · rank · total_score · dimensions(json) · decision · notch(json) · skill_ids · picked_at` |
| `agent/scores` | 逐候选逐维评分 | `run_id · product_id · skill_id · dimension · score · result_json · tokens_used · scored_at` |
| `agent/skills` | 策略注册表 | `skill_id · name · summary · readiness(t0/t1/t2) · enabled · rubric(json) · updated_at` |

### 5.4 引擎侧发布的 facet（agent 可读）

| facet | 内容 | 冻结列（草案，待引擎侧桥落定时确认） |
|---|---|---|
| `engine/intel/bestsellers` | 爆款候选档案 | `product_id · title · price · currency · sales_count · sales_unit · rating · review_count · category · captured_at` |
| `engine/intel/ticks` | 销量/价格时间序 | `product_id · tick_at · sales_count · price · rating · review_count · stock_total · note` |
| `engine/intel/categories` | 类目清单 | `category_id · name · product_count · url` |

> 引擎侧桥读引擎业务表（`tt_%/cs_%`）是在**引擎内部完成翻译**，耦合留在引擎侧；agent 永远只见冻结 schema，**不再认任何引擎业务表名或方法形状**（此即取代旧契约 C-7 的 `recent_ticks`）。

## 6. 交换面② 任务面（双向 · 与引擎同约定）

定义对齐引擎现成约定 `TargetRegistry.plugin_run_entry`：`run(ctx, **params)`。**一个约定，两个方向。**

### 6.1 协议

```
RunRequest { target: str, params: dict, caller: str, txn_id: str, mode: "now"|"persist" }
RunAck     { accepted: bool, txn_id, msg }          # 先接单，再异步执行
RunResult  { ok: bool, txn_id, owner, result: Any|null, error: str|null }
```

### 6.2 引擎 → agent（引擎调用 agent）

引擎侧桥收到 RunRequest → 经 agent 侧桥把关 → 在 **agent 容器**解析到目标（agent 的 task 注册表，等价引擎 `TargetRegistry.resolve`）→ 执行 `target.run(ctx, **params)` → 回 RunResult。场景：引擎侧插件主动要一轮评分 / 重排榜单 / 重新索引技能库。

### 6.3 agent → 引擎（agent 调度引擎，本模型的关键能力）

- `mode="now"`：一次 `run` now —— 引擎侧桥经 `TargetRegistry.resolve(ttype, tname)` 一次执行。
- `mode="persist"`：注册**持久任务** —— 引擎侧桥在引擎 `ctx.scheduler` 上登记 interval/daily 任务（**owner = agent 桥**，控制台可见归属），按 agent 给的 `params` 周期执行。**agent 调度引擎干活**落成真能力：例如 agent 派"每天 09:00 跑品类采集/每 3 分钟采一次销量"。
- 持久任务清理：agent 停用时，引擎侧桥 teardown 按 owner 清任务（沿用引擎"停用=自动清任务"机制）。**不做伪热插拔**：装配仍是启动一次性完成，启停重启生效（引擎诚实边界）。

### 6.4 任务目标白名单（录入/目标 各自注册，agent 开发时更新）

| 方向 | 白名单（草案） | 说明 |
|---|---|---|
| agent 侧目标 | `agent.selector.pick`（一轮评分）、`agent.skills.reindex`（重读技能库）、`agent.picks.export`（导出短名单） | agent 架构定稿后再增 |
| 引擎侧目标 | `engine.ping`（存活/时间戳）、引擎业务插件只读 run/命令（`category_sales` 采集、`tiktok_sales` 观测、`...probe`） | 逐条审定后锁定 |

## 7. ACL（决策 4 · 已按推荐落地）

- **开放**：`engine.ping` + 只读命令 + 白名单任务目标（§6.4）。
- **默认禁止**：浏览器写类命令、引擎内部管理命令、白名单之外的任何写。
- **拒绝形态**：越权 → `CapabilityNotImplemented` 式**诚实拒绝**（带原因），不静默降级、不伪装成功。
- **对称**：两个方向同一套策略——引擎能调 agent 的也只是白名单目标，摸不到 agent 内部。
- **执行点**：落各侧桥（side-local 校验）；引擎侧可选在 `CommandRegistry` 加身份校验层（与原计划 B3-1 同思路，但只对桥开口子，引擎内部命令不加身份概念）。

## 8. 事件/观察面（可选 · 延迟到需要时）

- 纯数据 JSON 事件，双向可订阅，**不进运行热路径**。
- 预留 topic 命名：agent 发 `agent/<类别>`（`agent/score/done`、`agent/pick/done`），引擎发 `engine/<类别>`（`engine/intel/updated`、`engine/task/done`）。
- 默认关闭（决策观感 §9 第三条：数据走 pull）；谁想被广播，另开契约补。

## 9. 传输拓扑（可插拔 Provider）

契约定义在**两侧桥的接口层**；传输是可插拔 Provider（两侧各自实现各自那份，不共享库）：

| Provider | 场景 | 要求 |
|---|---|---|
| `local`（进程内直连） | 开发 / 单测 / 未来"一体部署" | 确定性、离线全绿；agent 侧用自己的离线夹具即此形态 |
| `loopback`（独立进程 + IPC/管道通道） | 真实独立部署 | 超时 / 重试 / 对侧失联标记，绝不影响本地稳定性 |

- **开发约定**：agent 全部离线测试跑 `local`，不依赖引擎进程。
- **验收约定**：另设"合体验收窗口"，用统一 JSON 参考夹具做跨侧**互操测试**（引擎侧实装 ↔ agent 侧实装）。

> 一句话：旧契约冻结区是为"agent 是引擎的居民"设计的；新契约只为"两个对等运行时之间的一小份交换面"设计。机制原语（tasks/commands/owner/scheduler）几乎全部复用，**改的是归属**：谁持大脑、谁持循环、谁持数据。

## 12. 生命周期与稳定性约束（硬性）

1. 两侧独立启停；桥随各自配置；**嵌入式部署下引擎先起、桥后起**（桥可延迟加载）。
2. 请求带超时；对侧不响应 → 标记失联并降级为"只跑本地"，**绝不阻塞本地调度/心跳/看门狗**。
3. 桥 teardown：agent 停 → 引擎侧清 owner=agent 的持久任务 + 注销桥提供的面；引擎停 → agent 侧清对侧注册面。**卸载一侧，另一侧照跑**。
4. 引擎 `test_engine_purity`：agent 的所有业务词、站点选择器、20 策略、`select_*`/`ps_*` 表一概不进入 `engine/` 树；引擎侧桥也只有 peer 机制词、零业务词。
5. agent 侧对等伦理：`agent.api` 内部同样零"引擎实现"词，只表达"我需要的数据面/任务面"。

## 13. 实施分区

| 区 | 归属 | 内容 | 依赖 |
|---|---|---|---|
| **A 区（agent 本体）** | 在 `选品agent/` 做 | agent 容器/键、ToolLoop/Memory/Budget/Guard/Ai、Skills、Selector、`run.agent` 自举入口、离线夹具、agent 侧桥 | 只依赖本契约 §10，**不依赖引擎运行** |
| **B 区（引擎接入）** | 随 agent 交付或引擎侧配合 | 引擎侧桥（engine.api 装配）、引擎 facet 提供者（读引擎业务表→冻结 schema）、目标白名单/ACL 落点、`--agent` 装配入口 | NA-3/NA-4/NA-5 冻结后才能动 |
| **C 区（合体验收）** | 共同 | 双端 JSON 参考夹具逐字对齐、互操测试（A↔B local 形态）、持久任务双向演示、卸载一侧再跑另一侧验收 | A+B 各自全绿 |

里程碑建议：A 区先行（agent 用离线夹具自举，全绿即证明独立性成立）→ B 区在 A 定稿后做 → C 区最后合体。任意里程碑可独立回滚。
