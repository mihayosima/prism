# 选品策略技能库 · 设计

> 归属：选品 Agent（Meridian 扩展），承接《选品agent-架构方案.md》（AI 当 Provider 进引擎）。
> 日期：2026-09-21。状态：设计定稿（无代码）。
> 主题：把 20 条选品策略作为**引擎侧 YAML 技能库**——内容层可即插，机制层不动。

---

## 1. 定位：机制与内容再次解耦

沿着 README「无特权内核」哲学：**评分管线是机制，20 条策略是内容**。

- `scoring.py` 与任何一条策略无关——它只做「加载 skill → 按 data_feed 喂数据 → 按 rubric/signals/prompt 打分 → 校验 → 落库 → 排榜」。
- 每条策略是一个**自包含 YAML 定义文件**。加第 21 条策略 = 加一个文件 + `_index.yaml` 注册一行，引擎零改动。
- 策略之间不互斥：同一商品可被多条策略各打一次（互补/替代/场景看同一商品，各自成立）。

## 2. 目录与文件布局

```
plugins/product_selection/
  __init__.py             @plugin ProductSelection → ctx.selection
  migrations.py           ps_candidates / ps_runs / ps_scores / ps_picks
  scoring.py              评分管线（机制，与策略无关）
  ranking.py              排榜 / shortlist / 周报导出
  skills/                 ← 策略技能库（内容层，即插即换）
    _index.yaml           注册表（id → 文件 · 启停 · 就绪度）
    complementary.yaml    互补型
    substitution.yaml     替代型
    upgrade.yaml          升级型
    …（20 条，id 对齐 §6）
```

技能库是**数据目录**而非代码目录（每条 = 声明式定义），保持「内容改动不触发引擎行为变更」。

## 3. 规范 schema（每条 skill 的文件骨架）

```yaml
schema_version: 1
id: complementary              # 蛇形；与文件名/索引一致
name: 互补型选品
summary: |                     # 一句话定位
  给卖得好的产品找配件/延伸品，借爆款流量。

anchor:                        # 需求锚点（决定喂什么数据）
  family: product              # product | context | trend | calendar | behavior
  object: 爆款商品 + 配件关系
  requires:                    # 缺失 → CapabilityNotImplemented，诚实报缺，不虚标
    - bestseller_list

data_feed:                     # 该策略消费的数据源（映射引擎现有/待补表）
  - source: tt_products
    usage: 候选静态档案 / 爆款排序
  - source: tt_ticks
    usage: 销量差分 → 增速/稳定度
  - source: catalog_accessories   # 待补（见 §7 数据缺口）
    usage: 配件关系

signals:                       # 特征化输入（既喂规则，也喂 AI）
  - name: anchor_sales_velocity
    source: tt_ticks
    note: 锚点爆款销量增速

rubric:                        # 四维权重，一条策略一种「口味」（和为 1；启动默认值，随例子调）
  demand: 0.25
  margin: 0.25
  trend: 0.15
  fit: 0.35                    # 互补：与锚点的契合度最重

prompt: |-
  你是互补选品专家。给定锚点爆款与候选配件：
  - 判断「真需求配件 vs 伪需求配件」
  - 输出 JSON: {verdict, reasons[], fit_score, margin_estimate}

filters:                       # 负向过滤（直接排除，不进候选）
  - already_in_catalog
  - price_out_of_band

examples:                      # few-shot 经验沉淀位（随运营积累扩写）
  - anchor: 便携咖啡杯爆款
    pick: 杯盖 / 保温杯套 / 便携提手

risk: 伪需求配件 —— 只因为「锚点卖得好」就硬凑，无真实使用场景。
readiness: t1                  # 引擎数据就绪度（t0/t1/t2，见 §6）
```

## 4. 注册表 `_index.yaml`

```yaml
schema_version: 1
skills:
  - id: substitution
    file: substitution.yaml
    enabled: true
    readiness: t0
  - id: complementary
    file: complementary.yaml
    enabled: true
    readiness: t1
  # …20 条
```

- 控制台「插件 → 技能」页列出/启停（沿用 plugin_state 精神）。
- **新增** = 写 YAML + 索引注册一行；**停用** = 索引 `enabled: false`；**删除** = 移除文件+条目。

## 5. 评分管线消费契约（机制侧，与策略无关）

`ctx.selection.run_skill(skill_id, params) → run`：

1. 加载 skill（索引 → 文件），缺失 → `CapabilityNotImplemented`。
2. **数据就绪检查**：遍历 `data_feed`，缺表/缺源 → 诚实报缺 + 可选降级（t2 策略缺数据不硬跑）。
3. 组装候选：`data_feed` 取数 → `filters` 排除 → 形成候选集。
4. 逐候选喂 LLM：`rubric` + `signals` 特征 + `prompt` → 结构化打分（复用 `analysis.py` 的 schema 校验 + 重试 + token 核算）。
5. 落 `ps_scores`（含 `skill_id` 维度标签）→ 按 `rubric` 权重合成总分 → 排榜落 `ps_picks`。
6. 审计：`ps_runs` 记录本轮 skill 组合与参数，可回溯。

多策略编排由调用侧决定（`params: skills: [a, b, c]`），机制不内置「策略组合逻辑」——组合策略是业务，不进机制。

## 7. 数据缺口清单（诚实标注 → 决定补哪种数据源插件）

| 缺口数据 | 影响的策略 | 形态 |
|---|---|---|
| `bestseller_list` 爆款排序 | 互补/升级/替代 | 现有 `tt_products` 按销量/增速排序即得（t0 可用） |
| `catalog_accessories` 配件关系 | 互补/跨品类 | 标题/类目共现推断，可先规则后 AI |
| `reviews_sentiment` 评论情绪 | 痛点/升级 | 需评论采集（数据源插件） |
| `search_trend` 搜索/趋势热度 | 潮流/科技/健康/情绪/效率/美学 | 需站内搜索或内容信号源 |
| `calendar_events` 节日表 | 季节/节日 | 静态表即可（成本极低） |
| `audience_tags` 人群/场景标签 | 人群/场景/户外 | 需站内标签/内容数据 |
| `content_engagement` 内容互动 | 社交/情绪/美学/DIY | 需短视频内容级信号 |

**不在第一阶段编造信号**——t0/t1 先跑真实口，t2 逐项补源。技能库的 `readiness` 字段让控制台如实标注「可跑/待数据」。

## 8. 新增/停用流程（引擎零改动）

- 新策略：写 `<id>.yaml` → `_index.yaml` 注册 → 控制台即现。
- 停用：索引 `enabled: false`。
- 调参：改 `rubric`/`signals`/`examples`，只影响该策略后续打分，历史分留在 `ps_scores.result_json` 不回算。

---

**实现建议**：先产出 t0/t1 六条（substitution · consumable · seasonal · complementary · upgrade · scenario）的 YAML 初稿并接入 `scoring.py` 跑通（fixture 全绿），再逐批补 t2。每条 YAML 的 `examples` 留空位，随运营积累填充——技能库是**会生长的内容资产**，不是一次性交付。
