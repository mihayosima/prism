# 沙箱 vs 权限管理器 · 功能重叠核定

编制时间：2026-10-03 20:55（GMT+8）
状态：**诊断结论**（本轮未改任何生产代码）
对象：`agent/sys/guard.py`（97 行）vs `agent/plugins/sandbox/__init__.py`（182 行）

---

## 0. 一句话结论

**两者在"策略判定"这一层高度重复（约 80%），而这一层恰好是沙箱目前唯一在做的事。**
沙箱被创建时自带的"进程隔离"能力**至今为零** ⇒ 它现在实际扮演的角色是
**第二个 guard**，不是沙箱。

★ 但这个重叠**不是设计失误，是"沙箱只做了一半"的必然结果**。
按 DSH 的模型，收敛路径清晰（§5）。

**另发现一处文档与实现矛盾**（§4）：装配顺序决定沙箱实际抢在 guard 前面，
但 guard 的 docstring 自称"先裁决"，事件目录也仍声明该 seam "期望 1 方"。

## 2. 沙箱自称的两条"存在理由"，逐条核实

沙箱 docstring（`:5-8`、`:21-23`）给了两条理由。第一条成立，第二条**目前是空的**。

### 2.1 ✅ 理由一：guard 写不出 `mcp.*` 模式 —— 成立

guard 是精确名匹配，MCP 工具名运行时发现 ⇒ 确实挡不住。
**但这不需要一整个插件** —— 它需要的是把 `match()` 这个函数接进 guard。
差别的量级是"一个 13 行函数"，不是"一个 182 行插件 + 一份配置节 + 一个设置页面板"。

### 2.2 ❌ 理由二：为参数改写占位 —— **目前为空**

docstring `:21-23` 写：
> "载荷带 `kwargs` 且 waterfall 支持参数改写（`tasks.invoke` 比较 `decision["kwargs"] != kwargs`）
> ⇒ 将来做路径重定向必须在 guard/approval 看到参数**之前**完成"

实测：**guard 与 sandbox 都不改写 kwargs**（`grep kwargs` 在两个文件里零命中，
只有 approval 在 `:202-204` 改写）。所以这条理由描述的是**未来式**，
用它论证"现在就该独立成插件"是**事后合理化**。

## 3. 现状的净效果：沙箱是一个默认全通的 no-op + 双重审计

把默认值代进去算一遍一个 MCP 调用的完整路径：

```
1. sandbox.in_scope("mcp.playwright.browser_navigate") → True（默认 targets=["mcp.*"]）
2. sandbox.decide：deny=[] → allow=[] → risk={} 未命中 → default="allow" ⇒ 放行
   ⇒ 落一条 agent/sandbox/decision
3. guard._decide：deny 未命中 → risk="write" 未配策略 → default="open" ⇒ 放行
   ⇒ 落一条 agent/permission/decision
4. approval（append，排最后）：默认不触发
```

★ **今天开沙箱插件的全部效果 = 每个外部工具调用多写一条审计行。**
行为零变化（两处都放行），但账本翻倍。

而如果只开 guard 不开沙箱，**效果完全一样**（guard 也放行）。
⇒ **沙箱插件目前的净贡献 = 一份重复的审计**，因为它的差异化能力（进程隔离）还没做。

## 4. ★ 发现：装配顺序与文档矛盾（沙箱实际抢在 guard 前面）

`core/events.py:85-86`：`prepend` 是 `bucket.insert(0, entry)` ⇒ **后注册者排前面**。

装配顺序（`profiles.py:137,145`）：
```python
container.add(*SYS_PLUGINS, *BUSINESS_PLUGINS, *extra_plugins)   # :137  Guard 在此注册
...
container.add(*pm.load())                                          # :145  Sandbox 在此注册
```

**实测结论**：guard 先注册 → 落位 index 0；sandbox 后注册 → `insert(0)` 顶到 index 0，
把 guard 挤到 index 1。**实际执行顺序是 `sandbox → guard → approval`。**

这与三处文档矛盾：

| 文档 | 写法 | 实际 |
|---|---|---|
| `sys/guard.py:5` | "guard 用 prepend 先裁决，budget 后裁决" | ✗ 被 sandbox 顶到后面 |
| `sys/guard.py:89` 注释 | "prepend=True"（隐含先） | ✗ 同上 |
| `plugins/sandbox:19-20` | "沙箱是最先裁决" | ✅ **对**（但它是靠"后注册"赢的，不是靠设计声明） |
| `events_catalog.py:159` | `TASKS_PRE_EXECUTE: ["agent.guard"]` + `:150` "期望 1 方" | ✗ 实际 3 方 |

★ 符合记忆里那条既有模式：**「文档承诺 > 实现」在本项目已证多处。**
这次是"文档承诺的**顺序**错了"，比"承诺了但没做"更隐蔽 ——
因为两处 docstring 都在描述对方把自己顶掉这件事，而**双方都以为自己在最前**。

**实际后果**（不是纯文档问题）：
- 沙箱拒绝 ⇒ guard 审计行不产生（这一点沙箱 docstring `:30` 已自承）
- guard 拒绝 ⇒ 沙箱审计行已先落，看起来像"沙箱放行了但还是被拒"
- ⇒ **同一个 `request_id` 下两条审计的先后顺序，与读者预期相反**

## 5. 按 DSH 模型看收敛路径

DSH 把这两件事明确分成**两个独立旋钮**，而不是两个裁决器：

| DSH | 职责 | 裁决 allow/deny 吗 |
|---|---|---|
| `approval` | 这次操作**要不要做** | ✅ 是（四态，默认拒） |
| `sandbox` | 操作**最多能碰到哪里** | ❌ **否** —— 它只提供 confinement + 自报 `full`/`partial` |
| `permission preset` | 把两个旋钮捆成一档 | — |

**沙箱不判 allow/deny。它提供 confinement。**
⇒ DSH 那里不重复，因为它压根不做策略判定。

**我们的沙箱做的是策略判定（allow/deny/ask + 名单 + risk）** ⇒ 落在 approval 那一格
⇒ **与 guard 重叠是必然的。**

### 5.1 三条可选路径

| 方案 | 做法 | 代价 | 判断 |
|---|---|---|---|
| **A 合并** | 把 `match()`（尾部 `*`）+ 会话级配置 + `in_scope` 搬进 guard，删沙箱插件 | 删 182 行 + 一份配置节 + 一个设置页面板；**丢失审计分流**（用户已裁定的两处分离） | 短期最干净，但把"外部工具"这个域的概念也一起删了 |
| **B 转型** | 沙箱**停止策略判定**，改做 DSH 式 confinement：提供 `mode` + 自报 `enforcement`，不判 allow/deny；准入判定统一回 guard（吸收 `match()` 与会话级） | 中等；**符合 DSH 模型**；沙箱的 `deny/allow/risk` 四个配置键废弃 | ★ **推荐** |
| **C 保持** | 只修 §4 的文档矛盾，其余不动 | 最小 | 重复持续存在，且沙箱仍是 no-op |

### 5.2 推荐 B 的理由

1. **重叠会自动消解** —— 沙箱不再判 allow/deny ⇒ 与 guard 无交集，无需合并插件。
2. **与已批的 DSH 方案天然衔接** —— 前一轮的阶段 1（restricted token）产出的正是
   `mode` + `enforcement`，沙箱从"判 allow/deny 的网关"变成"提供 confinement 的后端"，
   正好是 DSH 的 `ctx.sandbox` 形状。
3. **审计分流不必牺牲** —— `agent/sandbox/decision` 继续存在，只是记录从
   "判了什么" 变成 "以什么档位启动 / enforcement 是什么"。
4. **`ask` 死胡同一并解决** —— 沙箱不再有 `ask` 档；真要问人只有 approval 一处，
   消除"两个都假装能问人"的歧义。

### 5.3 B 方案里 guard 需要吸收的两件事

| 要吸收 | 从哪来 | 理由 |
|---|---|---|
| `match()` 尾部 `*` 匹配 | `sandbox:79-91`（13 行） | MCP 工具名运行时发现，精确名匹配是真实缺口 |
| 会话级配置 | `sandbox:130-138`（`SESSION_CFG_VIEW` 三层合并） | 对齐 G2；guard 目前只有容器级，是真实不对称 |
| `in_scope` 域限定 | `sandbox:114-116` | guard 现在管辖全部工具；是否需要收窄域**待定**，可能不必搬 |
