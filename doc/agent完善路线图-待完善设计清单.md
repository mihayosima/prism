## 0. 诚实现状（一句话）

**骨架（内核/权限/插件哲学/技能即内容）保值且方向对；但核心数据是 fixture 假口、技能只有 1 条、对话是固定三段——目前它是"替一份假数据做漂亮解释"的壳，不是能靠它做决定的 agent。** 下面每一项 = 需要填充的设计，标了优先级。

**安全一条先插队（P0）**：`sk-...` 曾在对话明文出现过 → 建议**尽快轮换 key**；并把它规整成"只服务器侧注入、绝不回显"。

## 2. 分项设计清单

### 2.1 候选真数据 provider（P0）—— "接入真口"
- **现状**：`candidates` 接缝与契约（`CandidatesProvider`）已定，但唯一实装是 `fixture`（硬编码 5 条）。评分/排榜/解说全流程真实，地基是假数据。
- **要设计**：
  1. **数据源形态选型**：A → 引擎 facet 提供者（读引擎业务表翻译成冻结 facet，契约 §5.4）；B → 引擎只读插件跑完采集后经任务面取数；C → 直接用浏览器 seam 自采；D → 先做 CSV/Excel 导入做一个"半真"试跑点。**（OPEN-1）**
  2. **facet 列 schema 与信号**：候选静态字段 + 信号（销量差分增速、价格带、评分/评论量）在哪算、谁算（provider 侧 vs scoring 侧）。
  3. **能力对齐**：provider 能力清单从写死 → 声明式；skill `anchor.requires` ↔ 真实 feed 的映射表。
  4. **质量闸**：缺字段/格式错/去重/离群的处理（跳过 or 拒脏 or 记 note）；`agent_candidates` 已留 signals JSON。
  5. **更新节拍**：一次性 / 每日 / 引擎调度触发（关联 2.6 持久任务）。
- **关键决策**：OPEN-1 数据源形态；缺数据策略；provider 更新何时发生。

### 2.2 数据能力对齐 / readiness 清单（P0）
- **现状**：readiness = `requires ⊆ capabilities` 已实现；但能力词表没维护、provider 元数据写死。
- **要设计**：抽象能力词表（沿用《技能库》§7：best seller / ticks / category / reviews / trend / calendar / audience / engagement 等）的**维护位置**；provider 能力自动发现 vs 声明；技能 data_feed 抽象来源 ↔ 真实源双向映射。

### 2.3 技能库扩充 1→N（P1）
- **现状**：仅 `substitution` 1 条；rubric/prompt 是初始拍板值。
- **要设计**：首批 t0/t1 六条（substitution / consumable / seasonal / complementary / upgrade / scenario）的真口径 rubric、signals、filters、risk、examples 占位；**多技能编排**（一次跑 `skills:[a,b,c]` 的机制与调用侧）；readiness 标注与数据缺口驱动（承《技能库》§6/§7）。

### 2.4 引擎桥（契约 v2 B/C 区，P1）
- **现状**：契约已冻结（数据只读面 / 任务面 / ACL / NA-1..8），但引擎侧桥插件、agent 侧桥、facet 提供者、local/loopback 传输**均未实现**。
- **要设计**：引擎侧桥的装配形态（引擎容器 `@plugin`，代码随 agent 交付）；facet 提供者如何读引擎业务表翻译成冻结列；任务面 `run(ctx,**params)` 双向映射；ACL 执行点与 owner 归属；跨侧互操测试（双端 JSON 夹具逐字对齐）。
- **联动**：若 2.1 选引擎 facet（OPEN-1=A），本项随 1 前置。

### 2.5 工具回环 / 真 tool-loop（P1/P2）
- **现状**：chat 固定 规划→run→解说 三段；不是自主多工具循环。
- **要设计**：能力目录暴露（`ctx.tasks` 名 + schema 转 json-schema 给模型）；循环状态机（turn/step，可套用核心的 AgentDriver 协议再实现一个 ChatDriver）；模型自主调多工具 + 结果回喂 + 停止条件；预算/权限**在工具层照旧生效**（保持不变）；解说改"引用证据段"。
- **决策**：保留"机器权威"红线（模型可调工具但写类仍走 guard）；多工具编排深度 vs MVP 保守度。

### 2.6 持久任务 / 驻场生产者 T2（P1/P2）
- **现状**：只有一次性 `run(ctx)`；agent 侧无 scheduler/持久任务。
- **要设计**：agent 自持调度（复用核心 scheduler 语义：interval/daily、owner、phase、progress、暂停/恢复/取消、重叠 skip）还是全走引擎调度触发（契约 T2 `persist`）；崩溃追赶；控制台可见；`agent_runs` 已能记每轮审计 → 需"任务定义"表。

### 2.7 评分/解说质量回路（P1）
- **现状**：LLM 结构化一次过、失败重试×2 拒脏；解说独立复述无引用。
- **要设计**：同候选多次评分的**一致性方差**检查（漂移告警）；verdict 门槛用真实小样本校准；解说的**证据引用**（引用 evidence 右上具体行/理由）；拒脏/降级在 UI 明确标注。

### 2.8 记忆 / 跨会话（P2）
- **现状**：无持久上下文；每轮会话失忆。
- **要设计**：记什么（历史运行摘要、被否候选与理由、用户偏好）、存哪（agent 表，如 `agent_memory`）、注入方式（上下文节选进 system）、遗忘/容量策略。

### 2.9 真实成本核算 / budget 定价（P2）
- **现状**：tokens 估算（字符÷4）+ pre 预借；无真价格。
- **要设计**：deepseek 单价表（输入/输出每百万 token，缓存命中价入表）；per-run / per-day 预算落到真钱；`agent_budget_log` 加 est_cost 算真价；UI 成本读数 + 超支告警。

### 2.10 报告导出（P2，承接《架构方案》report 面）
- **现状**：`agent_picks` 是最新短名单；无导出。
- **要设计**：周报 xlsx（openpyxl 已就绪于引擎侧）/ markdown 汇总；通过只读面（`top_picks` 等）取数，不裸查表。

## 3. 安全项（P0，横切）

- **现状**：key 在 `local_secrets.json`（gitignored）；但曾在对话明文出现；provider 从 配置→env→本地秘钥 三路读取。
- **要设计/执行**：① 尽快轮换 key；② 明确"凭据只服务器侧注入、不进入任何 /api 回显、不落日志"；③ 为将来多 provider 统一凭据段（延续"凭据不落明文"纪律）。
