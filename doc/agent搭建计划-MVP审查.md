## 0. 总体结论

范围线清楚、阶段依赖自上而下成立、MVP IN/OUT 划得诚实。主要问题集中在**跨文档不一致**（事件键名、表、目录树三处对不齐）和**少数几个可观测性缺失**（guard 默认全开＝验不到行为、fixture 数据来源语言有裂缝），不构成推倒性缺陷。

---

## A. 动手前必须定调的硬伤（跨文档不一致 / 自相矛盾）

### A1. 事件键名两本账，且互相冲突

| 位置 | 表述 |
|---|---|
| 架构 §8（`架构.md:256`） | `agent/tools/pre-execute|post-execute` |
| 计划 §2.3（`计划.md:67`） | `agent/tasks/pre-execute|post-execute` |
| 计划 §2.3（`计划.md:67`） | 新增 `agent/action/precommit`、`agent/assembly/precommit`——**不存在于架构 §8 事件契约表** |

- 这不是文字问题。guard / budget / tasks 都是按**事件名**订阅的，名字不统一就是运行时对不上。
- `agent/action/precommit`、`agent/assembly/precommit` 是两个新守卫点，架构 §8 没登记。

**建议**：以本计划为准统一事件面；并在计划 §5 阶段 3 的回写清单里补一条「同步事件契约表」（现有回写只写了权限设计与 ACL，漏了事件表）。

### A2. `agent_permission_log` 表没进架构建表清单

- 计划 §2.3 / 阶段 3 要求裁决落 `agent_permission_log`（`计划.md:68/103`）。
- 架构 §6 表清单只有 runs / scores / picks / candidates / events / budget_log 六张（`架构.md:227-234`）；`agent_permission_log` 不在其中。
- 架构的「审计即轴心」= `agent_events` 只读落盘。单独的 `agent_permission_log` 是重复表还是物化视图，没说清；阶段 3 也没提要扩 storage 迁移。

**建议**：二选一并写死——① 裁决作为 durable 事件进 `agent_events`，permission 记录从 events 查询；② 正式加表 + 阶段 3 补一条迁移交付。不要两条都不写。

### A3. `sites/plugin_author` 不在任何架构目录树里，占位又被范围线勾掉

- 架构目录树（`架构.md:54-74`、`270-289`）**没有** `sites/` 或 `plugin_author` 模块。
- 计划阶段 3 却要求「此时只建接口占位与哨兵事件」（`计划.md:105`）；§4 MVP OUT 又标 `sites/plugin_author（T4）`（`计划.md:131`）。

也就是「占位」建在 MVP 内、「实装」划在 MVP 外，但占位住哪个包、长什么样没有任何文档承接。

**建议**：阶段 3 的占位要么写进架构 §10 目录树并给一句「占位 = 空 plugin + 哨兵事件 + 不注册」；要么把这两行从阶段 3 删除，留到阶段 6 一次做。

### A4. budget 和 guard 挂同一 seam，优先级未定义

- budget（架构 §4.3）与 guard（计划 §2.3）**都**监听 `agent/llm/pre-call` 做 waterfall。谁先注册、先短路时另一个还看不看得到？
- MVP 默认全开不会显现（guard 永远放行），但这是埋雷——后 MVP 收紧矩阵时行为未定义。

**建议**：§2.3 写一句「同一 seam 多裁决插件的执行序 = 装配注册序；短路即停」（Cordis 该语义本就支持，只差一句明确说明）。

### A5. P6（profile→patch 叠层）在 MVP 里没有交付物，也无法验证

- §1.1 把 P6 列为核心原则（`计划.md:33`），但阶段 0–5 **没有任何交付物是「装配清单 / profile→patch 加载器」**；阶段 5 自检 P6 时，MVP 只有一个自举 profile，验证不了「多层叠层、配置选择而不是改装配代码」。

**建议（顺带解决 B3）**：MVP 就建**两个 profile**——`offline`（默认全开）+ 一个「矩阵收窄」的测试 profile。一个动作同时验证 P6 叠层 / patch，又给阶段 3 guard 制造真实的「非默认全开」场景。

## B. 阶段级风险（按伤最大排序）

### B1. 阶段 1（kernel）是最大工作量与风险项，应作 spike 处理

- 自研 slim Cordis：Ctx 服务仓 + @plugin + 拓扑装配 + 对称 teardown + 五模式 EventBus + errors。代码量不小，**前面所有阶段都骑在它身上**，是 MVP 的承重墙。
- 已做降配是对的（OPEN-4 先落地 emit/waterfall/bail；环检测 / 缺失清单为必须）。建议再补两条：
  1. 明确「够用内核」的验收子集，把镀金项（并行调度、作用域 GC 边界）显式压到阶段 6；
  2. 第一轮迭代先写最薄的可跑 Container + @plugin + event，**用 tests 钉住最小闭环就往下走**，不要求全。

### B2. 阶段 4 的 `data_feed` → fixture provider 是此刻最该拍死的卡点 seam ⭐

- 阶段 4 首条策略 `substitution`，其 `data_feed` 声明消费 `tt_products / tt_ticks`（`技能库.md:124`）——这些是**引擎表**，MVP 里不存在。
- 但管线同时「数据就绪检查（缺 feed→诚实报缺）」（`架构.md:244`）+「候选组装（fixture provider）」（`计划.md:109`）用了**两套数据来源语言**。不澄清会出现二选一矛盾：

  | 场景 | 后果 |
  |---|---|
  | 严格按 data_feed 检查 | 离线下 tt_* 全缺 → t0 策略诚实报缺 → **MVP 闭环跑不起来** |
  | 有 provider 就跳过 readiness | `data_feed` 退化为纯文档，AC-5「诚实报缺」被架空 |

- **建议**：把 readiness 语义定成「**技能声明的 data_feed 是否被候选 provider 的能力清单满足**」——fixture provider 声明「可提供 bestsellers / candidates / ticks 快照」，引擎 provider 声明「可提供 tt_products / tt_ticks」。一条声明式能力表同时补住两个洞，写入阶段 4 交付物。

### B3. 阶段 3 guard 的 MVP 可观测性很弱（默认全开 = 永远放行）

- 矩阵默认 open，MVP 内又没有任何 T2/T3 外部任务可治理，守卫唯一的真实判别动作（拒绝 + 审计）只有靠「人为收窄矩阵」才能触发。机制落地是真的，验收却几乎验不到行为。
- 见 A5：建一个收窄矩阵的测试 profile，让阶段 3 验收有真实场景；再补 C 节两条断言。

## C. 验收/测试缺的断言

现有验收几乎全是「全绿 / 跑通」，少数关键负路径没有对应断言：

1. **阶段 3**：补「收窄矩阵 → 拒绝走 guard 的 capability 事件路径、而非散装 if」的断言（P4 正面证明）；补 `agent_permission_log`／事件**落库**断言。
2. **阶段 4**：补「缺 data feed → 诚实抛 `CapabilityNotImplemented`」的测试——AC-5 的直接证据，现验收只字未提。
3. **阶段 5**：收敛条件的「重叠 skip / deadline 上限」（`架构.md:218-219`）只在验收写「跑通收尾 + 全绿」；补这两个负路径单测；「卸载 loop 无残留」补一条 teardown 断言（P7）。
4. **阶段 2**（可选）：补「换 provider（fixture→占位）业务零改动」冒烟测试——阶段 2 验收有此承诺，但未写进交付物。

## D. 低成本微调（顺手做）

- **guard 的 T3/T4 precommit 监听桩（`计划.md:67` 列出，`105` 行又说只建哨兵）**：要么给一条断言「惰性、不拦默认路径」，要么直接砍掉留到阶段 6。现为悬空占位，测不到也说不清。
- **`analyze_image`（`架构.md:160`）**：MVP 无任何消费方。留在 LlmProvider 接口里却从不在 pipeline 触发，会制造「定义了但没验证」的诚实度噪音——标注「未消费」或挪出 MVP 接口。
- **LLM seam 的 budget/guard 次序**（A4）顺手写进 §2.3。

---

## E. 做得好的（不用动）

- §0.3 把权限定成「**分执行怎么落地 ≠ 分能不能请求**、默认全开」，MVP 只落机制不落配置内容——避免把审批细节拖进第一版，节奏正确。
- §3 每阶段都有目标 / 交付物 / 验收 / 回滚，验收全部是**离线确定性**，执行纪律扎实。
- MVP OUT 的硬排除（引擎桥、T4 实装、memory、交互驱动）与「零引擎依赖」自洽；阶段 5 作「=MVP 达成」单点，定义清楚。
- OPEN-1~8 与正文逐条对得上，没有「正文写了、决策点另说」的分裂。
